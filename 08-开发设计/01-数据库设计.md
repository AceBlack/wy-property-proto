## 零、这份文档解决什么

### 0.1 它不负责什么

`04-契约/openapi.yaml` 里 439 个 schema 定义的是**接口响应长什么样**，不是**数据怎么存**。两者差别很大：

| 契约里的形状 | 落库时的形状 | 为什么不同 |
|---|---|---|
| `bill` 里带 `itemName`、`unit`、`ownerId` | 都存，但它们是**快照**不是外键 | 改一次收费项名称，历史账单不能跟着变 |
| `bill` 里带 `overdueDays`、`unpaid` | **不存**，查询时算 | 落盘跨天就过期 |
| `payment` 里带 `billId` | 拆成 `payment` + `payment_allocation` | 一笔转账付 3 张账单是常态 |
| `deposits` 一张表含收/退/扣 | 拆成 `deposit` + `deposit_txn` | 押金是负债，要有余额和三向流水 |

### 0.2 从 fixture 反推会踩的三个陷阱

现有 60 个 fixture 是**查询结果的快照**，不是表结构。直接映射会得到病态模型：

**陷阱一：把展开字段当列。** `work-orders.json` 里有 `houseName`、`ownerName`、`assignee` 姓名——这些是 join 出来的，存成列会立刻过期。

**陷阱二：把派生字段当状态。** `bills.paidAmount` 和 `payments` 表是同一笔钱的两个记账点，谁是真源？必须是 `payments`。`paidAmount` 只能是物化缓存。

**陷阱三：漏掉"字段里有、表里没有"的实体。** 三个真实缺口：

| 缺口 | 现状 | 为什么必须补 |
|---|---|---|
| **租约（lease）** | `tenants` 上挂 `leaseStart/leaseEnd/rent` | 一套房租过 5 次，历史无处存；退租后再租，旧记录被覆盖 |
| **发票（invoice）** | `bill.invoiceNo`、`payment.invoiceNo` | 一张发票可含多张账单、可红冲、有抬头和税率，字段挂不住 |
| **调账（bill_adjust）** | 减免只有结果值 `waiveAmount` | 谁批的、什么原因、什么时候改的金额，全丢了 |

本文按业务不变量重建，不按 fixture 抄。

## 一、技术选型与全局约定

### 1.1 为什么是 PostgreSQL

| 需求 | Postgres 的能力 |
|---|---|
| 多租户行级隔离 | **RLS 原生支持**，MySQL 只能靠代码纪律 |
| 金额精确计算 | `numeric` 任意精度 + `CHECK` 约束 |
| 复杂报表（三率、账龄、多项目并排） | 窗口函数、CTE、`GROUPING SETS` |
| JSON 字段（表单自定义、附件元数据） | `jsonb` + GIN 索引 |
| 时序日志（访问日志、操作日志） | 原生分区表 |

### 1.2 命名与类型约定

| 项 | 约定 | 理由 |
|---|---|---|
| 表名 | 单数 snake_case：`bill` 不是 `bills` | 一行=一个实体，读起来是 "a bill" |
| 主键 | `id bigserial`，业务单号单独一列并唯一 | 业务单号会变（补号、重排），主键不能变 |
| 外键 | `xxx_id`，类型与被引用主键一致 | — |
| 金额 | `numeric(14,2)` | 最大 9999 亿，够用；**禁止 float/double** |
| 单价/系数 | `numeric(14,4)` | 水电单价 0.5583、公摊系数 0.0125 需要 4 位 |
| 面积 | `numeric(10,2)` | 18.6 万㎡ 级别够用 |
| 账期 | `char(7)`，格式 `YYYY-MM` | 不用 date，避免"8月1日算不算8月"的争论 |
| 日期时间 | `timestamptz` | 存 UTC，展示时转 Asia/Shanghai |
| 枚举 | `varchar(16)` + `CHECK` | 不用 PG enum 类型（加值要 DDL 锁表） |
| 布尔 | `boolean`，默认 `false`，**不用 0/1** | — |
| 审计四件套 | `created_at` / `updated_at` / `created_by` / `version` | 每张业务表都有 |
| 软删 | `deleted_at timestamptz`，NULL 表示存活 | 不用 `is_deleted` 布尔（无法知道何时删的） |

### 1.3 两张"字典"的分工（这条最容易做混）

| 类型 | 载体 | 例子 | 判断标准 |
|---|---|---|---|
| **可配置字典** | `dict_item` 表 | 减免原因、支出分类、资产类别、公告类型 | 客户会自己加词条 |
| **流程枚举** | `CHECK` 约束 | 账单状态、工单状态、押金方向 | 值变了代码就要改，不能让人在后台随便加 |

把账单状态做成字典表是常见错误：客户加一个"部分已缴（预估）"，整个对账逻辑就崩了。

### 1.4 一个必须提前约定的命名冲突：tenant

"租户"这个词在这个系统里有两个意思，**不约定清楚，代码里会长期混用**：

| 中文 | 英文 | 含义 | 本方案用名 |
|---|---|---|---|
| 租户（多租户） | tenant | 物业公司，数据隔离边界 | `tenant` |
| 租户（承租人） | lessee | 租业主房子的那个人 | `lessee` + `lease` |

行业里"租户"多半指承租人，架构里"租户"指 SaaS 租户。原型 fixture 用的是 `tenants.json`（承租人），如果直接照搬，多租户的 `tenant` 就没名字了。

**约定**：`tenant` 永远指物业公司；房屋承租人一律叫 `lessee`（代码、文档、接口字段全部统一）。接口里的 `tenantId` 也别用来传承租人——那是 `lesseeId`。

## 二、多租户：Postgres RLS

### 2.1 租户边界（先分清三层，否则后面全错）

```
tenant（物业公司）  ← 数据隔离边界
  └── community（项目/小区）  ← 业务单元
        └── house / parking   ← 计费对象
```

**不要把 `community_id` 当租户 ID。** 物业公司撤场、接手新项目时，数据要能干净地交接；租户跟着项目走，就永远交接不干净。

### 2.2 租户表与成员关系

```sql
CREATE TABLE tenant (
  id          bigserial PRIMARY KEY,
  code        varchar(32)  NOT NULL UNIQUE,     -- 对外标识，如 YITONG
  name        varchar(80)  NOT NULL,
  -- 部署路由：默认指向主库；大客户要独立库时改这里，不改代码
  datasource_key varchar(32) NOT NULL DEFAULT 'main',
  status      varchar(12)  NOT NULL DEFAULT '启用'
              CHECK (status IN ('启用','停用')),
  created_at  timestamptz  NOT NULL DEFAULT now(),
  updated_at  timestamptz  NOT NULL DEFAULT now()
);
COMMENT ON COLUMN tenant.datasource_key IS '预留：私有化/独立库路由键，单库部署恒为 main';

-- 用户与租户是多对多（一个人可能服务多家物业公司）
CREATE TABLE tenant_user (
  id         bigserial PRIMARY KEY,
  tenant_id  bigint      NOT NULL REFERENCES tenant(id),
  emp_id     varchar(16) NOT NULL,
  status     varchar(12) NOT NULL DEFAULT '在职'
             CHECK (status IN ('在职','离职')),
  UNIQUE (tenant_id, emp_id)
);
```

### 2.3 每张业务表的 RLS 三件套

以 `bill` 为例，**每张业务表都要做这三步**，缺一不可：

```sql
ALTER TABLE bill ENABLE  ROW LEVEL SECURITY;
ALTER TABLE bill FORCE   ROW LEVEL SECURITY;   -- ← 关键：让表 owner 也受约束

CREATE POLICY tenant_isolation ON bill
  USING      (tenant_id = current_setting('app.tenant_id')::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);
```

**`FORCE ROW LEVEL SECURITY` 不能省。** 默认情况下表 owner（通常是应用连接用的账号）**会绕过 RLS**，等于没做隔离。这一行漏掉，所有策略都是装饰。

### 2.4 应用层怎么设租户（这里踩过一次就要停机排查）

```sql
-- 每个事务开头，必须 SET LOCAL，不是 SET
BEGIN;
SET LOCAL app.tenant_id = '1';
-- ... 业务 SQL ...
COMMIT;
```

| 写法 | 后果 |
|---|---|
| `SET LOCAL`（事务级） | ✅ 事务结束自动失效，连接归还池子后干净 |
| `SET`（会话级） | ❌ 连接被池子复用后，下一个请求会带着上一个租户的 ID —— **跨租户数据泄漏** |

**连接池必须开事务**（`autoCommit=false`）。如果用了 `autoCommit=true`，`SET LOCAL` 立即失效，RLS 会拿不到 `app.tenant_id` 而报错——这个报错反而是好事，比静默泄漏强。

### 2.5 唯一约束必须带 tenant_id

```sql
-- ✅ 正确：A 公司的 1-1-101 和 B 公司的 1-1-101 是两个房
UNIQUE (tenant_id, community_id, building_id, unit_id, room)

-- ❌ 错误：第二个租户建同样房号会失败
UNIQUE (community_id, building_id, unit_id, room)
```

### 2.6 对象存储也要分租户

```
/t/{tenantId}/contract/{contractId}/xxx.pdf
/t/{tenantId}/owner/{ownerId}/avatar.jpg
```

路径里带 tenantId，配合签名 URL 的 scope，防止一次配错把 A 的合同照片给 B。

### 2.7 隔离怎么验收（这组用例必须进 CI）

| 用例 | 期望 |
|---|---|
| A 租户 token 查 B 租户的 `houseId` | **404**（不是空集） |
| A 租户 token 调 `?communityId=B的项目` | **403** |
| A 租户 token 导出，入参含 B 的数据 ID | **403**，且导出任务不生成 |
| 不带 `app.tenant_id` 直接查 bill | **报错**，不返回任何行 |
| 一个事务里先设 tenant 1 再设 tenant 2 | 第二次设值**报错或被拒**（防止事务内串租户） |

## 四、收费域完整 DDL

这是全系统的心脏。表结构定错，对账永远差几分钱。

### 4.1 收费项与单价

```sql
CREATE TABLE fee_item (
  id            bigserial PRIMARY KEY,
  tenant_id     bigint       NOT NULL,
  item_code     varchar(16)  NOT NULL,          -- FI01
  name          varchar(40)  NOT NULL,
  category      varchar(16)  NOT NULL,          -- 常规服务费/公摊/代收/能耗/押金/经营性/工本费
  calc_type     varchar(12)  NOT NULL,          -- 按面积/按户/按车位/按用量/一次性
  cycle         varchar(8)   NOT NULL,          -- 月/季/年/一次性
  unit          varchar(16)  NOT NULL,          -- 元/㎡·月
  -- 参考价（真实价在 fee_item_price，这里只是新建项目时的默认值）
  ref_price     numeric(14,4),
  tax_rate      numeric(5,2) NOT NULL DEFAULT 0,
  tax_category  varchar(20),                    -- 增值税税目
  direction     varchar(8)   NOT NULL DEFAULT 'billable',  -- billable/deposit
  meter_type    varchar(8),                     -- elec/water，计量项才有
  status        varchar(12)  NOT NULL DEFAULT '启用'
                CHECK (status IN ('启用','停用')),
  created_at    timestamptz  NOT NULL DEFAULT now(),
  updated_at    timestamptz  NOT NULL DEFAULT now(),
  version       integer      NOT NULL DEFAULT 1,
  deleted_at    timestamptz,
  UNIQUE (tenant_id, item_code)
);

CREATE TABLE fee_item_price (
  id            bigserial PRIMARY KEY,
  tenant_id     bigint       NOT NULL,
  community_id  varchar(16)  NOT NULL,
  item_id       bigint       NOT NULL REFERENCES fee_item(id),
  biz_type      varchar(16)  NOT NULL DEFAULT '住宅',   -- 住宅/商业/公寓，同一项目分业态定价
  price         numeric(14,4) NOT NULL CHECK (price >= 0),
  effective_from date        NOT NULL,
  effective_to   date,                          -- NULL = 当前有效
  created_at    timestamptz  NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, community_id, item_id, biz_type, effective_from)
);
COMMENT ON TABLE fee_item_price IS '价格按生效期分段，改价不覆盖旧价；账单落库时把 price 存快照';
```

**为什么价格要分段而不是直接改？** 客户 3 月调价，1-2 月的账不能跟着变。用 `effective_from` 分段，历史随时可复算。

### 4.2 账单

```sql
CREATE TABLE bill (
  id            bigserial    PRIMARY KEY,
  tenant_id     bigint       NOT NULL,
  bill_no       varchar(20)  NOT NULL,
  community_id  varchar(16)  NOT NULL,
  house_id      varchar(24),                    -- 车位费时为空
  parking_id    varchar(24),                    -- 车位费时必填
  item_id       bigint       NOT NULL REFERENCES fee_item(id),
  period        char(7)      NOT NULL CHECK (period ~ '^\d{4}-(0[1-9]|1[0-2])$'),

  -- ==== 金额（全部是快照，不 join 主表）====
  quantity      numeric(14,4) NOT NULL DEFAULT 0,   -- 面积或用量
  unit          varchar(16)   NOT NULL,
  price         numeric(14,4) NOT NULL,             -- 开账时的单价
  amount        numeric(14,2) NOT NULL,             -- 原价 = round(quantity * price, 2)
  waive_amount  numeric(14,2) NOT NULL DEFAULT 0,   -- 减免（应收不减，单列）
  late_fee      numeric(14,2) NOT NULL DEFAULT 0,   -- 滞纳金
  payable       numeric(14,2) NOT NULL,             -- 应缴 = amount - waive_amount + late_fee
  paid_amount   numeric(14,2) NOT NULL DEFAULT 0,   -- 物化缓存，真源在 payment_allocation

  -- ==== 归属（开账时快照）====
  owner_id      varchar(16),                        -- 开账时的业主，换主不追溯
  item_name     varchar(40)   NOT NULL,             -- 科目名快照
  tax_rate      numeric(5,2)  NOT NULL DEFAULT 0,

  -- ==== 状态与期限 ====
  status        varchar(12)   NOT NULL DEFAULT '待缴'
                CHECK (status IN ('待缴','部分缴','已缴','已减免','已作废')),
  due_date      date          NOT NULL,
  note          varchar(200),

  created_at    timestamptz   NOT NULL DEFAULT now(),
  updated_at    timestamptz   NOT NULL DEFAULT now(),
  created_by    varchar(16),
  version       integer       NOT NULL DEFAULT 1,
  deleted_at    timestamptz,

  CONSTRAINT ck_bill_payable
    CHECK (payable = amount - waive_amount + late_fee),
  CONSTRAINT ck_bill_paid_range
    CHECK (paid_amount >= 0 AND paid_amount <= payable),
  CONSTRAINT ck_bill_subject
    CHECK ( (house_id IS NOT NULL AND parking_id IS NULL)
         OR (house_id IS NULL AND parking_id IS NOT NULL) ),
  CONSTRAINT ck_bill_waive
    CHECK (waive_amount >= 0 AND waive_amount <= amount),
  UNIQUE (tenant_id, bill_no)
);

-- 房屋账单：同一房、同一科目、同一账期，只能有一张有效账单
CREATE UNIQUE INDEX uk_bill_house ON bill (tenant_id, house_id, item_id, period)
  WHERE house_id IS NOT NULL AND status <> '已作废' AND deleted_at IS NULL;

-- 车位账单：同理
CREATE UNIQUE INDEX uk_bill_parking ON bill (tenant_id, parking_id, item_id, period)
  WHERE parking_id IS NOT NULL AND status <> '已作废' AND deleted_at IS NULL;

-- 三率与账龄的主力索引
CREATE INDEX ix_bill_period   ON bill (tenant_id, community_id, period, status)
  WHERE deleted_at IS NULL;
CREATE INDEX ix_bill_aging    ON bill (tenant_id, community_id, status, due_date)
  WHERE status IN ('待缴','部分缴') AND deleted_at IS NULL;
CREATE INDEX ix_bill_house    ON bill (tenant_id, house_id, period)
  WHERE deleted_at IS NULL;
```

三个关键设计说明：

**① `payable` 用生成列还是普通列？** 用普通列 + CHECK。生成列（`GENERATED ALWAYS AS`）不能有非确定性表达式，且未来可能要做"整单调整"，普通列更灵活。

**② 唯一索引为什么带 `status <> '已作废'`？** 作废后要能重开同一账期的账单。如果把作废单也算进唯一性，重开就冲突了。

**③ 为什么 `quantity * price` 不写进 CHECK？** 因为四舍五入规则由代码控制（`round(x,2)`），DB 的 numeric 舍入模式和业务可能不一致。用 `amount` 独立存，并在应用层保证。

### 4.4 收款流水

```sql
CREATE TABLE payment (
  id            bigserial    PRIMARY KEY,
  tenant_id     bigint       NOT NULL,
  pay_no        varchar(24)  NOT NULL,          -- 收款单号
  community_id  varchar(16)  NOT NULL,          -- 收款归属项目（收款点所在项目）

  -- 付款人（可能是业主、租户、或散客）
  payer_type    varchar(8)   NOT NULL DEFAULT 'owner'
                CHECK (payer_type IN ('owner','tenant','other')),
  payer_id      varchar(16),
  payer_name    varchar(40),

  amount        numeric(14,2) NOT NULL CHECK (amount > 0),

  -- ==== 钱怎么走：渠道 ≠ 收款点 ====
  method        varchar(16)  NOT NULL,          -- 现金/POS刷卡/转账/微信/支付宝/车辆云平台
  channel       varchar(16),                    -- 线下/微信/支付宝/银联
  pay_point     varchar(16),                    -- 前台/南门/车辆云平台（谁在收、跟谁交班）
  channel_txn_no varchar(64),                   -- 支付平台流水号，幂等键

  -- ==== 两个时间，两个口径 ====
  paid_at       timestamptz  NOT NULL,          -- 钱到账（现金收入、日结口径）
  period        char(7),                        -- 归属账期（三率口径；跨期时以 allocation 为准）

  operator_id   varchar(16),
  operator_name varchar(40),

  status        varchar(12)  NOT NULL DEFAULT '正常'
                CHECK (status IN ('正常','已冲红')),
  reversed_by   bigint,                          -- 被哪张红字单冲掉
  remark        varchar(200),

  created_at    timestamptz  NOT NULL DEFAULT now(),
  updated_at    timestamptz  NOT NULL DEFAULT now(),
  version       integer      NOT NULL DEFAULT 1,
  UNIQUE (tenant_id, pay_no)
);

-- 幂等：同一支付平台的同一笔交易，只能入账一次
CREATE UNIQUE INDEX uk_payment_idem ON payment (tenant_id, channel, channel_txn_no)
  WHERE channel_txn_no IS NOT NULL AND channel_txn_no <> '';

-- 日结与现金收入的主力索引
CREATE INDEX ix_payment_paid_at ON payment (tenant_id, community_id, paid_at)
  WHERE status = '正常';
CREATE INDEX ix_payment_point   ON payment (tenant_id, community_id, pay_point, paid_at)
  WHERE status = '正常';

-- 流水只增不改：用触发器禁止 UPDATE 金额与时间
CREATE OR REPLACE FUNCTION deny_payment_mutation() RETURNS trigger AS $$
BEGIN
  IF NEW.amount <> OLD.amount OR NEW.paid_at <> OLD.paid_at
     OR NEW.channel_txn_no IS DISTINCT FROM OLD.channel_txn_no THEN
    RAISE EXCEPTION '收款流水不可修改，请用红字单冲回（30101）';
  END IF;
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_payment_immutable
  BEFORE UPDATE ON payment FOR EACH ROW EXECUTE FUNCTION deny_payment_mutation();
```

**幂等索引的重要性**：微信/支付宝的回调会重发（超时重试、网络抖动）。没有这个唯一索引，一次支付会记三笔钱，日结差额再也对不上。

### 4.5 收款分摊（原型缺这张表）

```sql
CREATE TABLE payment_allocation (
  id          bigserial   PRIMARY KEY,
  tenant_id   bigint      NOT NULL,
  payment_id  bigint      NOT NULL REFERENCES payment(id),
  bill_id     bigint      NOT NULL REFERENCES bill(id),
  period      char(7)     NOT NULL,             -- 冗余账单账期，三率查询免 join
  amount      numeric(14,2) NOT NULL CHECK (amount > 0),
  item_id     bigint      NOT NULL,             -- 冗余科目，收支分项免 join
  created_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, payment_id, bill_id)
);
CREATE INDEX ix_alloc_bill    ON payment_allocation (tenant_id, bill_id);
CREATE INDEX ix_alloc_period  ON payment_allocation (tenant_id, period, item_id);
```

**分摊的平衡约束**（应用层事务保证，也可加延迟约束触发器）：

```sql
-- 每个事务结束前自检：Σ 分摊 = 收款金额
SELECT p.id, p.amount, COALESCE(SUM(a.amount),0) AS alloc
FROM payment p LEFT JOIN payment_allocation a ON a.payment_id = p.id
WHERE p.id = $1 GROUP BY p.id
HAVING p.amount <> COALESCE(SUM(a.amount),0);
-- 有行返回就是不平，必须回滚
```

**预收怎么处理？** 当收款金额 > 账单总额时，差额进 `prepay_account`，不进 `payment_allocation`。恒等式：

```
payment.amount = Σ payment_allocation.amount + prepay_account.入账部分
```

### 4.7 押金（负债，三向流水）

```sql
CREATE TABLE deposit (
  id             bigserial   PRIMARY KEY,
  tenant_id      bigint      NOT NULL,
  deposit_no     varchar(24) NOT NULL,
  type_id        bigint      NOT NULL,          -- 装修/门禁卡/租金…（dict_item）
  community_id   varchar(16) NOT NULL,
  house_id       varchar(24),
  owner_id       varchar(16),
  amount         numeric(14,2) NOT NULL CHECK (amount > 0),  -- 应收押金
  balance        numeric(14,2) NOT NULL DEFAULT 0,           -- 物化：收−退−扣
  status         varchar(12) NOT NULL DEFAULT '在账'
                 CHECK (status IN ('待收','在账','部分退还','已结清','已没收')),
  start_date     date        NOT NULL,
  plan_end_date  date,
  closed_at      timestamptz,
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now(),
  version        integer     NOT NULL DEFAULT 1,
  UNIQUE (tenant_id, deposit_no)
);

CREATE TABLE deposit_txn (
  id          bigserial   PRIMARY KEY,
  tenant_id   bigint      NOT NULL,
  deposit_id  bigint      NOT NULL REFERENCES deposit(id),
  direction   char(1)     NOT NULL CHECK (direction IN ('I','O','D')),
              -- I 收（负债增加）/ O 退（负债减少）/ D 扣（负债转收入）
  amount      numeric(14,2) NOT NULL CHECK (amount > 0),
  method      varchar(16),
  pay_point   varchar(16),
  occurred_at timestamptz NOT NULL,             -- 影响日结的现金流
  reason      varchar(200),                     -- 扣款原因必填（D 向）
  ref_no      varchar(24),
  operator_id varchar(16),
  created_at  timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT ck_deposit_deduct_reason
    CHECK (direction <> 'D' OR (reason IS NOT NULL AND length(reason) >= 4))
);
CREATE INDEX ix_deposit_txn_time ON deposit_txn (tenant_id, occurred_at);
```

**恒等式（必须进日结自检）**：

```
每个 deposit：balance = Σ(I) − Σ(O) − Σ(D)
全租户：Σ(I) − Σ(O) − Σ(D) = Σ(balance)      ← 押金在账总额
```

**为什么押金不能进 payment 表？** 收了 2000 元押金，钱是真的，但不是收入。混进 payment 会让"本月收入"虚增，而且退押金时要冲收入——税务上完全错。押金是负债，必须走独立三向流水。

## 六、七条铁律的落地检查（可直接跑）

```sql
-- ① 有没有用浮点存金额（应该返回 0 行）
SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE table_schema='public'
  AND data_type IN ('real','double precision')
  AND (column_name LIKE '%amount%' OR column_name LIKE '%price%' OR column_name LIKE '%fee%');

-- ② 有没有表缺 tenant_id（应该返回 0 行）
SELECT c.relname
FROM pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE n.nspname='public' AND c.relkind='r'
  AND NOT EXISTS (SELECT 1 FROM information_schema.columns col
                  WHERE col.table_name=c.relname AND col.column_name='tenant_id');

-- ③ 有没有开了 RLS 但没 FORCE（应该返回 0 行）
SELECT relname FROM pg_class
WHERE relrowsecurity = true AND relforcerowsecurity = false;

-- ④ 有没有唯一索引漏了 tenant_id（人工审：打印所有唯一索引）
SELECT indexname, indexdef FROM pg_indexes
WHERE schemaname='public' AND indexdef LIKE 'CREATE UNIQUE INDEX%';

-- ⑤ 账单平衡：payable ≠ amount − waive + late（应该返回 0 行）
SELECT id FROM bill WHERE payable <> amount - waive_amount + late_fee;

-- ⑥ 账单已收超过应缴（应该返回 0 行）
SELECT id FROM bill WHERE paid_amount > payable;

-- ⑦ 押金恒等式（应该返回 0 行）
SELECT d.id, d.balance,
       COALESCE(SUM(CASE t.direction WHEN 'I' THEN t.amount
                                     WHEN 'O' THEN -t.amount
                                     WHEN 'D' THEN -t.amount END),0) AS calc
FROM deposit d LEFT JOIN deposit_txn t ON t.deposit_id=d.id
GROUP BY d.id, d.balance HAVING d.balance <> COALESCE(SUM(CASE t.direction
       WHEN 'I' THEN t.amount WHEN 'O' THEN -t.amount WHEN 'D' THEN -t.amount END),0);

-- ⑧ 收款分摊平衡（应该返回 0 行）
SELECT p.id FROM payment p
LEFT JOIN payment_allocation a ON a.payment_id=p.id
GROUP BY p.id, p.amount HAVING p.amount <> COALESCE(SUM(a.amount),0);
```

**这 8 条要挂进每日巡检**，不只是上线前跑一次。数据一旦脏，越早发现越便宜。

## 八、分区与索引

### 8.1 什么时候分区（现在只分日志）

| `bill` | `(tenant_id, house_id, period)` | 业主端账单列表、收银台 |

## 十、给前端的三个提醒

1. **`unpaid`、`overdueDays`、`paidAmount` 以后端返回为准**，前端不要再算一遍。现在原型里这两个是前端算的，接了真接口如果还留着，会出现"列表显示欠 300、详情显示欠 320"。
2. **金额是字符串**。后端 `numeric` 出 JSON 时用字符串（`"322.39"`），前端 `Number()` 转换后只用于展示，不用于累加。累加由后端做。
3. **`pay_point` 和 `method` 是两个字段**，别合并。渠道是钱怎么走，收款点是谁在收——日报表的差额行靠这两个字段才能对上。
