> 2026-11-18 · 后端线提出

> 前置：`05-后端交接单.md`、`01-数据库设计.md` §4.7

## 零、结论

三条口径确认后，结论比初版更干净：**日结不需要并入押金。**

| # | 决定 | 依据 |
|---|---|---|
| 1 | **禁止收现金押金** | 现金押金无法原路退回，且会让收银抽屉与日结对不上 |
| 2 | **退款必须原路 + 退给原付款人** | 押金是"替业主保管的钱"，退错人就是资金风险 |
| 3 | **押金不开票；增值税由会计线下处理、事后手工补录** | 押金扣除不是经营收入开票场景，税额不系统自动分离 |

由此推出：**押金的现金流 100% 是非现金**（银行代扣/转账/微信/支付宝），它根本不经过收银抽屉。
所以日结（现金账）保持现有 `payment` 口径不变，押金只需两条守卫 + 一张独立的资金台账。

### 四条已验证的事实

1. **押金与收款零交叉**：`payment` 含"押金"字样 0 笔；`bill` 押金科目（FI08）0 张；`deposit_txn` 孤儿流水 0 条。
2. **退款方式全部原路**：352 笔押金，退款方式集合 ⊆ 收款方式集合，**0 笔不一致**。
3. **每笔押金只有一次收款**：352 笔全部单次收款，没有分期收押金，退款校验因此可以做到严格相等。
4. **押金流水体量是营业收入的 84%**（100.5 万 vs 119.2 万）——分开记的价值就在这个数字上：混进去就是营收翻倍。

## 二、三条口径对应到系统里是什么

### ① 禁止现金押金

```java
DepositPolicy.assertCollectMethod("现金");    // 抛 DepositPolicyViolationException
DepositPolicy.assertCollectMethod("银行代扣");  // 通过
```

允许集合：`银行代扣 / 银行转账 / 微信 / 支付宝 / POS`。刻意不含现金。

**为什么不做成"警告"**：现金押金一旦收进来，退款时要么给现金（违反原路），要么转银行（违反原路），两条路都走不通。只能事前拒绝。

### ② 退款原路 + 退给原付款人

```java
DepositPolicy.assertRefundMethod(List.of("银行代扣"), "银行代扣"); // 通过
DepositPolicy.assertRefundMethod(List.of("银行代扣"), "微信");     // 拒绝：必须原路
DepositPolicy.assertRefundPayer("OW0001", "OW0002");              // 拒绝：只退原付款人
```

**这里有一个必须先补的结构缺口**：现在 `deposit` 只有 `owner_id` / `house_id`，`deposit_txn` 没有付款人字段、也没有退款账户字段。
所以"原路"目前**只能校验方式，校验不了账户**。过渡期靠流程兜（退款审批单必须带原收款凭证号），中期建议补：

| 字段 | 表 | 用途 |
|---|---|---|
| `payer_id` / `payer_name` | `deposit` | 记录实际付款人（可能不是业主，如租户交装修押金） |
| `account_ref` | `deposit_txn` | 银行流水号 / 账户尾号，退款时按此原路退回 |

DDL 已冻结，这两列走变更流程，本次只提不改。

### ③ 不开票 + 税额线下补录

系统侧只做三件事：

| 事项 | 做法 |
|---|---|
| 不生成发票 | `invoice` 表在押金扣除时**不产生任何记录**（现在也是 0，保持不变） |
| 收入记含税额 | D 向（扣除/没收）进"其他业务收入"，报表标注**含税、税额未分离** |
| 留补录口 | 建议 `deposit_txn` 增 `tax_amount numeric(14,2)` + `tax_status`（待补录/已补录/免税），DDL 解冻后加 |

**DDL 冻结期的过渡办法**：报表侧出"待补录税额清单"（D 向 57 笔 / 76,473 元全量，2026 年 14 笔 / 19,073 元），
会计每月出凭证后回填台账；`deposit_txn.reason` 统一以 `[税待补]` 前缀标记，便于批量捞。

**必须写进报表脚注的一句话**：其他业务收入为**含税金额**，增值税由会计线下补录，系统未做价税分离。
不写这句，财务会拿含税额去做不含税收入，利润表直接错。

## 三、日结怎么改：**不改**

| 方案 | 做法 | 结论 |
|---|---|---|
| **不并入（采用）** | 日结保持 `payment` 口径；押金走独立资金台账；加两条守卫 | ✅ 政策上押金零现金，抽屉里不该出现押金 |
| 并入现金合计（初版方案 A） | 日结加"押金收取/退还现金"两列 | ❌ 政策确认后无必要，加了反而给"收现金押金"留了口子 |
| 押金塞进 payment（方案 C） | 负数/新状态 | ❌ 营收虚增 84%，破坏触发器与分摊恒等式 |

日结现在的差额自检（Σ收款 vs Σ各收款点 = 0）**保持不动**，它仍然是有效的现金对账。

押金现金流改由 `DepositCashFlowRepository` 单独出（按营业日 × 收款点 × 方式），
定位从"日结的一列"变成**资金台账 + 异常监控**：查历史那 2,390 元、查未来有没有人偷偷收现金。

> **口径已定（2026-11-18）：差额对"收款点全方式"。**
>
> 契约的 `/reports/daily-revenue` 是**经营日报**：三段（收入 / 押金往来 / 押金退款），
> `合计 = 收入 + 往来 − 退款`，差额 = 合计 − 收款点，**含押金收退**。
> 交班表（`SettlementRepository`）仍然是"现金口径"，只回答"抽屉里该有多少钱"。
>
> 两张表并存、各有用途：
> - 经营日报对"前台经手的账" → 差额必须 0，用来发现"某笔收款漏录收款点"；
> - 现金交班对"抽屉里的钱" → 用来点钞，看"现金 / 车辆现金"两格。
>
> 已实现：`/reports/daily-revenue` 七个固定收款点 + 预存抵扣单列；
> 2026-08 实测差额 0。

## 四、建议加进 daily-check 的两条守卫

`sql/daily-check.sql` 现在 12 段。这两段是**新约束**，不是现存问题：

```sql
-- 13. 押金走了现金（应为 0 行；政策禁止收/退现金押金）
SELECT t.id, d.deposit_no, t.direction, t.amount, t.method
FROM deposit_txn t JOIN deposit d ON d.id = t.deposit_id
WHERE t.method = '现金' AND t.direction IN ('I','O');

-- 14. 退款没原路（应为 0 行）
WITH m AS (
  SELECT deposit_id,
         string_agg(DISTINCT method, ',') FILTER (WHERE direction='I' AND method IS NOT NULL) im,
         string_agg(DISTINCT method, ',') FILTER (WHERE direction='O' AND method IS NOT NULL) om
  FROM deposit_txn GROUP BY 1
)
SELECT m.deposit_id, d.deposit_no, m.im, m.om
FROM m JOIN deposit d ON d.id = m.deposit_id
WHERE m.om IS NOT NULL AND m.im IS NOT NULL
  AND NOT (string_to_array(m.om, ',') <@ string_to_array(m.im, ','));
```

**第 13 段现在会返回 31 行**——这是政策前的历史，属预期。建议上线时把时间条件加成
`AND t.occurred_at >= '2026-11-18'`，让历史与新增分开看，别把历史数据当事故报。

按边界本次没改 `sql/`，等表结构负责人确认后加。

## 七、押金状态与退款流程（2026-11-18 定稿）

### 7.1 状态语义：状态只表达"钱在哪"

| 库里的态 | 含义 | 契约态 | 是否在账 |
|---|---|---|---|
| 待收 | 应收未收，属收费流程，不进押金台账 | ——（契约缺） | 否 |
| 在押 | 钱在公司账上，业主还没退 | 在押 | 是 |
| 装修中 | 同上，装修期押金 | 装修中 | 是 |
| 已逾期 | 超过约定期限未退，该催办 | 已逾期 | 是 |
| **待退款** | 已审批、等打款 | 待退款 | 是 |
| **部分扣除** | **扣了一部分、还能再退** → 余额必须 > 0 | 部分扣除 | 是 |
| **部分退还** | 退了一部分、余额仍 > 0 | ——（契约缺） | 是 |
| 已退还 | 钱已全部或部分退回、余额 0 且退过钱 | 已退还 | 否 |
| 已没收 | 全额扣除、余额 0 且没退过钱 | 已没收 | 否 |
| 已结清 | 扣完 + 退完的了结态 | 派生为 已退还 / 已没收 | 否 |

映射实现集中在 `DepositStatus.contractLabel()`，前端/报表/接口都取这一处，不各写一份。

### 7.2 已修正的数据：45 笔"部分扣除"→"已退还"

原数据里 45 笔 `部分扣除` 余额全是 0，流水是 `I = O + D`（扣一部分、余款已退），
按"部分扣除 = 还能再退"的定义，这些应是 `已退还`。

- 修正后：已退还 226（= 退款流水 226 笔，对得上）、在押 31、装修中 50、已逾期 33、已没收 12
- 在账余额不变：665,637.00
- 备份：`backend/verify/out/deposit-partial-deduct-backup.csv`
- 脚本：`backend/verify/fix-deposit-status-partial-deduct.sql`（三重判据，可重跑）

**教训**：状态和金额是两件事。状态写错一位，报表上这笔负债就消失了，但实际还欠业主钱。

### 7.3 退款流程：审批 → 待打款 → 已打款

```
在押 / 装修中 / 已逾期 / 部分扣除 / 部分退还（余额 > 0）
   └─ 提交退款申请            → 待退款（写申请单，不动余额）
        └─ 审批通过（审批人 ≠ 提交人）
             └─ 打款            → 写 O 向流水、减余额
                  ├─ 余额 = 0 → 已退还
                  └─ 余额 > 0 → 部分退还
```

状态机已实现为纯逻辑 `DepositRefundFlow`（含 8 条单测）：金额校验、重复申请拦截、
没审批不能打款、提交人不能审批自己。

### 7.4 为什么还没写接口：缺一张表

当前 DDL 撑不住两步流程：

1. `deposit.status` 的 CHECK **不包含 `待退款`**，改状态会直接约束失败；
2. 没有地方存"申请了多少、谁批的、批到哪一步"。库里也没有通用审批表（查过，0 张）。

**建议的最小 DDL**（等表结构解冻后走变更评审）：

```sql
-- 押金退款申请单：一张单对应一次退款动作，状态推进都记在这
CREATE TABLE deposit_refund (
  id            bigserial PRIMARY KEY,
  tenant_id     bigint        NOT NULL,
  deposit_no    varchar(24)   NOT NULL,
  amount        numeric(14,2) NOT NULL CHECK (amount > 0),
  method        varchar(16)   NOT NULL,          -- 必须等于收款方式（原路）
  payer_id      varchar(16)   NOT NULL,          -- 必须等于原付款人
  status        varchar(12)   NOT NULL DEFAULT '待审批'
                CHECK (status IN ('待审批','待打款','已打款','已驳回')),
  apply_by      varchar(16)   NOT NULL,
  apply_at      timestamptz   NOT NULL DEFAULT now(),
  approve_by    varchar(16),
  approve_at    timestamptz,
  paid_at       timestamptz,
  pay_ref       varchar(64),                     -- 银行流水号
  reason        varchar(200),
  version       integer       NOT NULL DEFAULT 1,
  UNIQUE (tenant_id, deposit_no, apply_at)
);

-- 状态约束补一个值
ALTER TABLE deposit DROP CONSTRAINT deposit_status_check;
ALTER TABLE deposit ADD CONSTRAINT deposit_status_check
  CHECK (status IN ('待收','在押','装修中','已逾期','待退款','部分扣除',
                    '部分退还','已退还','已结清','已没收'));
```

`deposit_refund` 要做 RLS 三件套（ENABLE + FORCE + POLICY），与其它业务表一致。

**在 DDL 落地前，不做"一步退款"的简化版**——那等于把审批与打款合并，事后无法追责，
也解释不了"谁批的"。

## 八、一句话

**押金是"替业主保管的钱"，不走现金，自然也不进日结。**
收入只认账单，现金只认抽屉，押金只认台账——三本账各管一件事，账目能对上，收入也不会虚增。
