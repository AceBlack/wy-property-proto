## 七个数据问题（迁移时逐个修掉）

这些问题在 fixture 里看不出来，只有落到有约束的库里才会暴露。**每一条都可能让后端算法算出错误结果**。

### ① 两个表结构合不住数据

| 原型 | 问题 | 处理 |
|---|---|---|
| `tenants.json` 把租约挂在承租人上 | 一套房租过 5 次，历史无处存 | 拆 `lessee`（80）+ `lease`（80） |
| `deposits.json` 一张表含收/退/扣 | 押金是负债，要有余额和三向流水 | 拆 `deposit`（352）+ `deposit_txn`（635：收 352 / 退 212 / 扣 71） |

### ② 减免账单的 `payable` 口径不是净额

89 张有减免的账单：`payable = amount`（未减减免），`paidAmount = payable − discount`。

原 DDL 写的是 `payable = amount − waive + late`，**全部违反**。

处理：改成 `payable = amount + late`（应缴**原价**），减免单独存 `waive_amount`，净应缴 = `payable − waive_amount`。

这个口径其实更清晰——每个字段只有一种含义。原设计的 payable 同时承担"应缴"和"净应缴"两个角色，容易混。

### ③ 车位费账单用了 448 个车位，台账只有 45 个

缺 403 个，`bill.parking_id` 外键挂不上。

处理：按账单里出现的 `parkId` 补建最小档案（`remark` 标记"由车位费账单补建"），台账里已有的保留原信息。

**这是原型的债**：第 88 批说"车位按车位出账"，但车位台账没跟着补。

### ④ 11 张已作废账单还挂着已收金额

作废即退款，钱不该留。但原型的收款流水还在。

处理：作废单 `paid_amount` 清零；对应收款标为 `已冲红`；不生成 `payment_allocation`。

不这么做的话，「账单已收 = Σ分摊」这条不变式有 451 张账单不平（8 万）。

### ⑤ 28 张「待缴」账单已有回款

有回款就该是部分缴或已缴。处理：按金额重算状态。

**这里踩了一个浮点坑**：`210.64 >= 300.92 - 90.28` 在 JS 的 double 下是 `false`（`210.6400000000000005 < 210.640000000000015`），15 张账单因此被误判成部分缴。改用**整数分**比较后归零。

### ⑥ 84 张账单有已收金额，但没有收款流水

`payments` 只有 3986 条，账单里 `paidAmount > 0` 的有 4070 条。

处理：补造 84 条收款（编号从 `PM900001` 起，避开真实号段；经办人写「历史补录」）。

不补的话，报表的"实收"会少 1.5 万，「账单已收 = Σ分摊」也永远不平。

### ⑦ 165 条"读数"其实没抄

`meter-readings` 里有 165 条 `currentReading = 0`、`readDate` 为空——那是待抄任务，不是读数。

处理：保留但 `read_date` 用当月 15 日兜底。真正的空白读数在原型里没有，所以没丢数据。

## 三个设计要点（给接手的人）

**① 金额一律 `toFixed(2)` 后拼 SQL，比较一律转整数分。**
JSON 里的 `322.39` 是 double，直接参与比较会出错。

**② 主键显式指定，不用自增。**
`bill.id ← BL003536 的数字部分`，这样 `payment_allocation` 能直接引用，不用先查出 id 再插。
迁完必须 `setval` 修正序列（见 `out/99-setval.sql`），否则新插入会撞号。

**③ 顺序按外键依赖排。**
`community → building → unit → house → parking → owner → lessee → lease → fee_item → bill → payment → allocation`。
`run-migrate.sh` 里按文件名排序，所以文件编号就是这个顺序。
