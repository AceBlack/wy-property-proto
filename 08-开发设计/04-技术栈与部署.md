## 一、为什么仍然是 Java + Spring Boot

先看这个项目的三个事实，它们决定了选型：

| 事实 | 数据 | 含义 |
|---|---|---|
| 业务重心是账务 | 三率、账龄、日结、押金恒等式、公摊、分摊 | 事务边界和 SQL 可控性优先 |
| 数据量很小 | 十年 75 万账单，三个项目 | 分库分表、MQ、微服务全是负收益 |
| 并发很低 | 几千户，峰值在收银台（几十 QPS） | 性能不是瓶颈 |
| 团队很小 | 1~2 后端 | 运维复杂度必须压到最低 |

### 三条支撑理由

**① 财务要"可解释"，不是"快"。**
对账时能定位"这条 SQL 为什么多算 3 分钱"，比省 200ms 重要一百倍。Java 的强类型 + 显式事务 + MyBatis 手写 SQL，是"每一步都能看到"的路子。

**② 私有化交付时最好解释。**
客户 IT 看到 `java -jar` + `psql`，知道怎么运维；看到 Node 的 `node_modules` 依赖树，第一反应通常是"这能装在内网吗"。物业公司私有化是常见要求。

**③ 招人与交接。**
物业/ERP 领域 Java 人才池最大。这套系统要维护 5~10 年，交接成本必须算进去。

### 但有三条必须做对，否则 Java 会变成负担

**① 核心账务不要用 JPA / Hibernate。**

用 MyBatis（或 JOOQ）手写 SQL。理由很具体：

- Hibernate 的脏检查在并发下会出现**更新丢失**——两人同时改一张账单，后提交的静默覆盖，而你要的恰恰是 409
- `merge` 时先 `select` 再 `update`，事务窗口被拉长
- 对账排查时日志里是 HQL，看不出实际执行的 SQL

**边界**：字典、配置、组织这类单表增删改可以用 JPA 省事。**凡是金额相关的表，一律手写 SQL。**

**② 不做微服务，做一个单体。**

Spring Boot 单体 + 按域分包（包结构或 Spring Modulith）。注册中心、配置中心、链路追踪、跨服务事务的运维成本，是收益的 10 倍。等真的到 10 家物业公司再谈。

**③ 不用 Spring Security 的默认 Session。**

要同时支持后台（浏览器）、小程序（微信登录）、App（token）三端。用 JWT + Redis 黑名单，`SecurityFilterChain` 里按端分认证方式。默认 session 在移动端会撞墙。

### 两个 Java 特有的坑

**金额序列化**：`BigDecimal` 出 JSON 可能变成 `3.2239E+2`。

```java
objectMapper.enable(JsonWriteFeature.WRITE_BIGDECIMAL_AS_PLAIN);
// 或字段级：@JsonFormat(shape = JsonFormat.Shape.STRING)
```

**逻辑删除与 RLS 是两层过滤，别混用**：

| 表类型 | 删除策略 | 理由 |
|---|---|---|
| 账务（bill / payment / deposit） | **物理不删**，用状态（已作废） | 对账要看到作废记录 |
| 主数据（house / owner / employee） | 软删 `deleted_at` | 历史关联要留 |
| 日志（access_log / operation_log） | 只增不删，按月分区 | 审计要求 |

三层混用没问题，但要在团队里写清"哪张表用哪种"，否则半年后没人记得。

## 二、为什么是 PostgreSQL，不是 MySQL

你已经确认多租户按 RLS 做，这一条基本终结对比：

| 能力 | PostgreSQL | MySQL 8 |
|---|---|---|
| **行级安全 RLS** | ✅ 原生 `CREATE POLICY` | ❌ 无等价物 |
| 时间区间排他约束（租约防重叠） | ✅ `EXCLUDE USING gist` | ❌ 只能应用层校验 |
| 报表（账龄/三率/同比） | ✅ 窗口函数 + CTE 优化成熟 | 🟡 有窗口函数，CTE 优化弱 |
| 部分索引 / 表达式索引 | ✅ | ❌ 不支持部分索引 |
| `jsonb` + GIN | ✅ | 🟡 JSON 较弱 |
| 运维人才 / 云厂商成熟度 | 🟡 比 MySQL 少 | ✅ 更多 |

**MySQL 唯一的实质优势是"运维人多、客户认"。** 如果客户 IT 明确要求 MySQL，多租户就退回"代码拦截器"，也就是 `01` 文档里明确要避免的那条路。

**结论：PG，只为 RLS 这一条。** 其他差异都能接受，这一条不能。

如果被迫用 MySQL，替代方案是**每租户一个 database** + 动态数据源路由。运维成本随租户数线性增长，租户一多就崩——这个代价要提前写进合同。

## 三、阿里云 ECS 架构

单机起步，**不上 K8s**。

```
阿里云 VPC
├── ECS 4C8G
│     ├── Nginx（443，反代 + 静态资源）
│     ├── Spring Boot（8080，单实例）
│     └── Redis（6379，会话 + 字典缓存）
├── RDS PostgreSQL 16（2C4G，ESSD PL1）
├── OSS（合同 / 照片 / 导出文件，按 /t/{tenantId}/ 分目录）
└── 备份：RDS 自动 7 天 + 每周 pg_dump 到 OSS
```

### 三个配置建议

| 项 | 建议 | 理由 |
|---|---|---|
| 磁盘 | **ESSD PL1 起**，不要高效云盘 | IOPS 差一个数量级，账单查询会明显卡 |
| RDS 规格 | 2C4G 起步，够撑到 5000 户 | PG 在小数据量下性能很好 |
| 备份 | RDS 自动备份 + 每周 `pg_dump` | PITR 救急，dump 救"误删库" |

### 为什么应用和数据库分开

数据库要独立备份、独立扩容。混在一台 ECS 上，一次磁盘 IO 打满会拖垮应用。RDS 的自动备份和 PITR 省掉的运维时间，远比省下的钱值。

### ECS 上的应用进程怎么管

```bash
# systemd 托管，不自建 supervisor
/etc/systemd/system/wy-app.service
```

```ini
[Unit]
Description=Wy Property App
After=network.target

[Service]
User=wy
ExecStart=/usr/bin/java -Xms1g -Xmx2g -jar /opt/wy/app.jar
Restart=always
RestartSec=5
Environment="SPRING_PROFILES_ACTIVE=prod"

[Install]
WantedBy=multi-user.target
```

**JVM 参数**：`-Xms1g -Xmx2g` 起步，别把堆开太大（4C8G 机器给 4G 堆会导致 GC 停顿变长）。PG 那边压力不大，内存留给它更值。

## 四、依赖与版本锁定

```xml
<!-- 关键版本，别用 latest -->
<properties>
  <java.version>17</java.version>
  <spring-boot.version>3.2.x</spring-boot.version>
  <mybatis-plus.version>3.5.x</mybatis-plus.version>
  <flyway.version>10.x</flyway.version>
  <postgresql.version>42.7.x</postgresql.version>
  <poi.version>5.2.x</poi.version>
</properties>
```

| 依赖 | 用途 | 注意 |
|---|---|---|
| spring-boot-starter-web | API | — |
| mybatis-plus-boot-starter | 数据访问 | 账务手写 SQL，不用它的自动 CRUD |
| flyway-core + flyway-database-postgresql | 迁移 | PG 16 需要单独的方言包 |
| postgresql | JDBC | — |
| spring-boot-starter-data-redis | 缓存 | — |
| spring-boot-starter-validation | 参数校验 | 契约里的 422 靠它 |
| easyexcel 或 poi | 导出 | 5 万行上限（原型已定的口径） |

**刻意不引入**：

| 不引入 | 理由 |
|---|---|
| Spring Cloud / Nacos | 单体不需要注册中心 |
| RabbitMQ / RocketMQ | 阶段 1 用 Outbox 表 |
| ShardingSphere | 数据量远未到分表线 |
| XXL-Job | `@Scheduled` + 数据库锁足够 |
| Lombok | 争议项：如果团队都接受可以用，但它会让断点调试看不到值 |

## 五、异步：为什么阶段 1 不上 MQ

需要异步的场景有三个：支付回调、消息通知、报表跑批。

**用 Outbox 表解决**：

```sql
CREATE TABLE outbox (
  id           bigserial PRIMARY KEY,
  tenant_id    bigint NOT NULL,
  topic        varchar(40) NOT NULL,        -- payment.paid / notice.send / report.gen
  payload      jsonb NOT NULL,
  status       varchar(12) NOT NULL DEFAULT '待处理'
               CHECK (status IN ('待处理','处理中','已完成','失败')),
  retry_count  smallint NOT NULL DEFAULT 0,
  next_retry_at timestamptz,
  created_at   timestamptz NOT NULL DEFAULT now(),
  processed_at timestamptz
);
CREATE INDEX ix_outbox_pending ON outbox (status, next_retry_at) WHERE status IN ('待处理','失败');
```

业务事务里同时写业务表 + outbox，定时任务每 5 秒扫一次。**不丢、不重、可追溯**——比 MQ 少了"消息丢失怎么排查""重复消费怎么办"两类问题。

**什么时候该上 MQ**：出现真正的削峰需求（比如批量导入 10 万行），或者要跨系统解耦（对接第三方停车平台）。到那时再加，不影响现在的结构。

## 六、私有化打包

物业公司常要求内网部署。与云版共用同一套代码，只改配置。

```
私有化包/
├── docker-compose.yml      # PG + 应用 + Nginx
├── app.jar
├── initdb/                 # 建库脚本（08-开发设计/sql/*.sql）
├── fonts/                  # 中文字体（内网无 CDN）
├── license                 # 离线授权：租户 ID + 到期日
└── backup.sh / restore.sh
```

**四条硬要求**：

| 要求 | 为什么 |
|---|---|
| `docker compose up` 能起来 | 客户 IT 只会这一条命令 |
| **无外网依赖** | 内网白屏的头号原因是字体、地图瓦片、二维码库走 CDN |
| 离线授权 | license 文件签名校验，含租户 ID 和到期日 |
| 备份恢复脚本 + 演练过 | 没演练过的恢复脚本等于没有 |

**最容易漏的是"无外网依赖"**：中文字体、地图、天气预报、二维码生成，任何一个外链都会变成白屏。打包前在断网环境完整走一遍。

## 七、环境就绪后的 PoC（半天，别跳过）

阿里云 RDS 目前不可用，这一节等环境到位后执行。**在写任何业务代码之前做**，半天能挡掉后面所有"选型后发现不支持"的风险。

```sql
-- ① 扩展能不能装（租约排他约束依赖它）
CREATE EXTENSION IF NOT EXISTS btree_gist;

-- ② RLS 能不能建，且 FORCE 生效
CREATE TABLE poc_t (id bigserial primary key, tenant_id bigint not null, v text);
ALTER TABLE poc_t ENABLE ROW LEVEL SECURITY;
ALTER TABLE poc_t FORCE  ROW LEVEL SECURITY;
CREATE POLICY p ON poc_t USING (tenant_id = current_setting('app.tenant_id')::bigint);

BEGIN;
SET LOCAL app.tenant_id = '1';
INSERT INTO poc_t (tenant_id, v) VALUES (1, 'a'), (2, 'b');   -- 第二条应被 WITH CHECK 拒绝
COMMIT;

-- ③ 部分唯一索引
CREATE UNIQUE INDEX ON poc_t (tenant_id, v) WHERE v <> 'x';

-- ④ 排他约束
ALTER TABLE poc_t ADD CONSTRAINT ex_t
  EXCLUDE USING gist (tenant_id WITH =, v WITH =);

-- ⑤ 时区
SHOW timezone;   -- 应为 Asia/Shanghai 或 UTC（应用层显式转换）
```

**五项全过才能开工。** 任何一项不过，回来改方案——改方案比改数据便宜。

本地没有 PG 时，可以用 `08-开发设计/docker-compose.yml` 起一个等价的 PG 16 做同样的验证（托管版差异主要在扩展权限，本地能过不代表云端能过，所以云端还要再验一次）。

## 八、什么情况下我会改主意

| 情况 | 改选 | 代价 |
|---|---|---|
| 客户 IT 明确指定 MySQL | 只能 MySQL | 多租户退回代码隔离，要书面告知客户 |
| 后端只有一个人，且更熟 Node | NestJS + Prisma | 财务 decimal 精度要自己保证；私有化交付解释成本高 |
| 要在 3 个月内上线 | **仍选 Java，砍域** | 别为赶时间换栈，换栈隐性成本比砍功能大 |
| 客户要求信创（国产化） | 人大金仓 / 达梦 | **RLS 和 EXCLUDE 的兼容性要提前 PoC**，不能等上线 |

## 九、三条给团队的话

**① 别为了"以后可能要"提前上复杂度。**
微服务、MQ、分库分表，都是"以后"的问题。现在的瓶颈是功能没开发完，不是架构不够先进。

**② 版本锁定比追新重要。**
物业系统一次部署要跑五年。`latest` 是运维事故的头号来源。
