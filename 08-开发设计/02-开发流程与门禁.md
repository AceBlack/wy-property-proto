# 开发流程与门禁

> 版本：v1.0 · 2026-11-17
> 适用：智慧物业 V2 从原型转真实开发
> 前置：`01-数据库设计.md`（表结构）、`03-UI基线规范.md`（视觉标准）
> 读者：所有参与开发的人，包括 AI 任务

---

## 零、这套流程要防什么

三条真实风险，按发生概率排序：

| 风险 | 后果 | 本文的防线 |
|---|---|---|
| **口径漂移**：前后端对同一字段理解不同 | 联调期天天对字段，报表数字永远对不上 | 契约先行 + 契约测试当验收 |
| **并行撞车**：两条任务改同一文件 | 冲突无法合并，返工比重写贵 | 并行准入检查 + 按域拆文件 |
| **地基返工**：表结构或 UI 标准边做边改 | 改一次牵动全部 | 阶段 0 设门禁，不通过不许往下走 |

原型阶段靠"一个人想清楚"就够了，真实开发必须靠机制。

## 一、四阶段与三道门禁

```
┌─ 阶段 0 · 准备 ─────────────────────────── 1~2 周 ─┐
│  ① 数据库建模（08-开发设计/01）                       │
│  ② 视觉基线（08-开发设计/03）                         │
│  ③ 口径确认单 8 份（客户签字）                         │
│  ④ 非功能定档（部署形态 / 性能 / 合规）                │
└──────────────── 门禁 ① ────────────────────────────┘
                      ↓
┌─ 阶段 1 · 纵切 ─────────────────────────── 4~6 周 ─┐
│  收费主线：账单 → 收银台 → 收款 → 日结 → 三率         │
│  后端真实实现 + 前端 1 条链 + 支付沙箱                 │
└──────────────── 门禁 ② ────────────────────────────┘
                      ↓
┌─ 阶段 2 · 全量 ─────────────────────────── 8~12 周 ─┐
│  按域并行：资产 / 工单 / 巡检 / 品质 / 人事 / 报表     │
│  移动端：uni-app 转真机（独立线）                     │
└──────────────── 门禁 ③ ────────────────────────────┘
                      ↓
┌─ 阶段 3 · 上线 ─────────────────────────── 4 周 ───┐
│  数据迁移 / 压测 / 安全加固 / 培训 / 灰度             │
└──────────────────────────────────────────────────┘
```

### 门禁 ① 定义（准备阶段结束）

全部满足才能进阶段 1，**任何一条不满足就往下走，返工成本翻倍**：

- [ ] 60 张表建完（`sql/run-all.sh` 跑通），§九 验收清单全绿
- [ ] 8 条自检 SQL 全绿（金额精度、tenant_id、RLS FORCE、账单平衡、押金恒等式、收款分摊）
- [ ] 跨租户越权测试 5 条全过（403/404，不是空集）
- [ ] `03-UI基线规范.md` 的 3 个样板页产出，并排对照图已确认
- [ ] 口径确认单至少 4 份有客户签字（优先：分摊、三率、减免、收款归月）
- [ ] 部署形态已定（私有化 / 云）
- [ ] `openapi.yaml` 已按域拆分（见 §3.2）

### 门禁 ② 定义（纵切结束）

- [ ] 收费主线端到端跑通：开账 → 收银 → 收款 → 日结 → 三率报表
- [ ] **契约测试 302 条在真实服务上全绿**（把 `mock-server` 的 base 换成真服务）
- [ ] 日结差额 = 0（现金收入 = 收款点合计，与原型同一口径）
- [ ] 支付沙箱联调通过：回调幂等（同一 `channel_txn_no` 重发 3 次只入账 1 笔）
- [ ] 押金"收−退−扣 = 在账"恒等式成立
- [ ] 前端至少 1 个页面完整走完 mock → http（不是"能跑"，是"删掉 mock 也能跑"）
- [ ] 性能基线：三率报表 3 个项目 12 个月 < 2 秒

### 门禁 ③ 定义（每域上线前）

每个域单独过，不用等全部：

- [ ] 越权测试：跨项目 / 跨角色 / 跨租户三种都返回 403/404
- [ ] 敏感字段：列表只回掩码，揭示走独立接口 + 留痕 + 原因必填
- [ ] 并发：同一资源两人同时改，后提交者拿到 409，不是静默覆盖
- [ ] 该域的契约测试全绿
- [ ] 该域的派生字段全部由后端返回，前端无重算

## 二、日常开发流程（契约优先）

### 2.1 一个功能从想法到上线

```
① 改契约        改 openapi/{域}.yaml
                 ↓
② 跑契约测试    npm test —— 先红，因为后端还没实现
                 ↓
③ 写后端        按契约实现，直到契约测试变绿
                 ↓
④ 写前端        对着真接口调，删掉 mock 分支
                 ↓
⑤ 联调          E2E 走一遍关键路径
                 ↓
⑥ 合并          门禁③ 五项检查
```

**关键在 ②**：契约测试先红后绿，等于给这个功能写了一份可执行的验收标准。后端不用猜，前端不用等。

### 2.2 为什么必须契约先行

原型阶段的教训很具体：`部分缴 / 部分缴费`、`入场 / 进场` 这两组词在不同文件里分叉过两次，靠 `npm run check` 才拦住。那是**同一个人的前后两批代码**。

多人并行时，分叉是必然的，除非契约是唯一来源。

### 2.3 契约变更规则

| 变更类型 | 例子 | 处理 |
|---|---|---|
| **加字段** | 响应加 `payPoint` | 直接加，前端不用改 |
| **加可选参数** | 查询加 `?payPoint=` | 直接加，老调用不受影响 |
| **改字段语义** | `amount` 从"应收"改成"实收" | **禁止**。加新字段 `receivable`，旧字段保留一版 |
| **改字段名** | `payTime` → `paidAt` | 破坏性。新旧同时返回，标记旧字段 `deprecated`，下一个大版本删 |
| **删字段** | 删掉 `invoiceNo` | 破坏性。先 deprecated，观察一个版本，再删 |
| **改枚举值** | `部分缴` → `部分已缴` | 破坏性，且会脏数据。**永远不改，只能加** |

**枚举值只增不改**这条要写进团队规范：数据库里有历史数据，改了就对不上。

### 2.4 分支与提交

```
main                      ← 只有通过 PR 的代码，永远可发布
├── feature/billing-core    ← 收费域
├── feature/wo-sla          ← 工单 SLA
└── release/0.1             ← 发布分支，只修 bug
```

**提交格式**（沿用原型已有的钩子，规则不变）：

```
feat(收费): 收款分摊支持一笔付多单

正文写「为什么这么定」，不写文件清单。

批次: 1
影响: 04-契约, 05-后端
验证: 契约 302/302 · 日结差额 0 · 押金恒等式 0 行
BREAKING: 无
```

这条钩子在真实开发里更有价值：`验证` 那一行强制你写"跑了什么"，写不出来说明没验证。

**PR 要求**：

- 一个 PR 只做一件事（一个域、一个功能链）
- PR 描述里贴契约测试的输出，不是截图
- 涉及表结构变更的 PR 必须附迁移脚本，且脚本可重跑
- 至少一人 review（自己写自己审等于没审）

## 三、多任务并行：什么时候可以开第二条

这是你最关心的部分。直接给规则。

### 3.1 并行度公式

> **并行度 = 无共享写入的模块数**

判断两条任务能不能同时开，只有三个检查项，**任何一项不过就串行**：

| 检查项 | 问题 | 不过的后果 |
|---|---|---|
| 文件 | 两条任务会改同一个文件吗？ | git 冲突，且大文件冲突无法手工解 |
| 表 | 两条任务会写同一张表吗？ | 约束冲突、事务死锁、口径分叉 |
| 口径 | 两条任务对同一个字段有不同理解吗？ | 联调期返工，最难查 |

### 3.2 这个项目有两个"必炸"的共享文件

我在这 93 批原型里实际踩过，值得你先处理掉再并行：

| 文件 | 体积 | 问题 | 必须先做 |
|---|---|---|---|
| `openapi.yaml` | 877 KB 单文件 | 两条任务同时改，冲突率 100%，yaml 冲突几乎无法手工合并 | **按域拆目录** |
| `mock-server.mjs` | 649 KB 单文件 | 同上 | **按域拆模块** |

**拆分方案**（阶段 0 做，约 1 天）：

```
04-契约/
├── openapi/
│   ├── _index.yaml        # 只做 $ref 汇总，不写内容
│   ├── billing.yaml       # 收费域
│   ├── asset.yaml         # 资产域
│   ├── workorder.yaml     # 工单域
│   ├── hr.yaml            # 人资域
│   └── ...
└── mocks/
    ├── index.mjs          # 路由装配
    ├── billing.mjs
    ├── asset.mjs
    └── ...
```

拆完之后，**一个域一个文件，两条任务改不同域就永不冲突**。这一步现在做成本极低，等并行开工再做就要停工返工。

### 3.3 可以开第二条任务的信号

我会在下面这些情况主动提醒你"可以开新任务"，或者"再等等"：

**✅ 可以开**：

- 阶段 0 已过门禁 ①（表结构 + UI 基线 + 契约已拆域）
- 两条任务负责的域不同，且表之间无外键依赖
- 共享文件（`enums.json`、契约主文件）已经拆开或被其中一条独占
- 每条任务启动时会写"边界声明"（见 §3.5）

**⏸ 必须等**：

- 表结构还在改（阶段 0 未完）—— 表一动，所有下游任务都要跟
- 两条任务都要改同一份契约文件
- 前一条任务的输出是后一条的输入（如后端接口 → 前端联调）
- 涉及支付通道、消息通道这类外部依赖，等到有沙箱再说

### 3.4 按阶段的具体建议

| 阶段 | 并行度 | 具体怎么开 |
|---|---|---|
| 0 准备 | **1 条** | 串行做：数据库 → 契约拆域 → UI 基线 |
| 1 纵切 | **2 条** | ① 后端收费域 ② 前端收费链路。两条每天对一次接口 |
| 2 全量 | **4~6 条** | 按域：资产 / 工单 / 巡检品质 / 人事 / 报表，各一条 |
| 2 移动端 | **+1 条** | uni-app 转真机，独立仓库或独立目录，和后台无文件交集 |
| 3 上线 | **1~2 条** | 迁移、压测串行；安全加固可并行 |

**移动端为什么必须等**：卡在外部依赖——小程序 AppID、微信支付资质、商户号、真机调试权限。这些不是写代码能解决的，早开也是空转。等阶段 2 主体跑通再启动，那时后台接口已稳定，移动端只需要对接。

### 3.5 每条任务启动时必写的边界声明

无论人还是 AI 任务，开工前先填这五行，贴在任务开头：

```markdown
【边界声明】
- 我负责的表：bill / bill_adjust / payment / payment_allocation
- 我负责的接口：openapi/billing.yaml
- 我读但不改：enums.json、openapi/_index.yaml
- 我不碰：任何其他域的 yaml、mock 主文件、tokens.css
- 我的产出验收：契约测试 billing 段全绿 + 日结差额 0
```

这五行能挡掉 80% 的并行事故。**没有边界声明就不许开工**——这条对 AI 任务同样适用。

### 3.6 我会怎么提醒你

在后续任务里，我会按这个格式给你判断：

> **并行判断**：可以开第 2 条 / 建议等
> **理由**：两条任务的表无交集，但都要改 `enums.json`，需先把它锁定给其中一条
> **建议边界**：任务 A 独占 `enums.json`，任务 B 只读

不会只说"可以并行"，一定会说清"哪条界线不能碰"。

## 四、测试分层

不做金字塔面子工程，只做四层，每层都有明确目的：

| 层 | 测什么 | 数量目标 | 谁写 |
|---|---|---|---|
| **单元测试** | 纯算法：三率、账龄分档、公摊分摊、押金恒等式、金额舍入 | 核心 20 个函数全覆盖 | 后端 |
| **契约测试** | 334 条接口的行为与错误码 | 已有 302 条，逐步补齐 | 谁改契约谁补 |
| **集成测试** | 事务边界：退款四步、收款分摊平衡、日结锁定 | 每个跨表事务一条 | 后端 |
| **E2E** | 用户关键路径 | **只测 10 条**，多一条都是负担 | 前端 |

**E2E 只测 10 条**：登录、开账、收银、收款、退款、日结、工单派单、工单完成、业主缴费、报表导出。再多的 E2E 会因为选择器变动而长期飘红，最后没人看。

### 4.1 必须写的五条不变式测试

这五条是财务系统的命门，写成测试而不是靠人检查：

```
① 应收 = 已收 + 未收 + 减免          （每张账单）
② 现金收入 = Σ 各收款点金额           （每日）
③ 押金：收 − 退 − 扣 = 在账余额      （每个押金单）
④ 收款金额 = Σ 分摊 + 预收入账        （每笔收款）
⑤ 分摊总额 = 公司级费用总额           （若做分摊）
```

这五条对应 `01-数据库设计.md` §六 的 SQL 自检，**测试里要断言"返回 0 行"**。

### 4.2 测试跑在哪

| 时机 | 跑什么 | 时间预算 |
|---|---|---|
| 提交前 | 单元 + 契约（本地） | < 60 秒 |
| PR | 单元 + 契约 + 集成（CI） | < 5 分钟 |
| 每日 | 全量 + 8 条数据自检（CI 定时） | 不限 |
| 发布前 | 全量 + E2E + 压测 | 不限 |

`npm run check` 那种静态自检要保留并扩展——它在原型阶段抓到过至少两次真实缺陷（`updateBillField` 不存在、枚举分叉）。

## 五、环境与发布

### 5.1 三套环境

| 环境 | 用途 | 数据 | 谁能写 |
|---|---|---|---|
| `dev` | 日常开发 | 造数脚本，可随时重置 | 所有人 |
| `staging` | 验收、客户演示 | 脱敏的准生产数据 | 只允许通过迁移脚本改 |
| `prod` | 生产 | 真实数据 | 只允许通过迁移脚本改 |

**staging 和 prod 禁止手工改数据。** 一次手工改数，后面所有问题都查不清。要改就写迁移脚本，走 PR。

### 5.2 发布流程

```
release/0.x 分支 → 打 tag v0.x.y → CI 构建镜像 → staging 部署
  → 冒烟（10 条 E2E）→ 客户验收 → prod 部署（灰度 10% → 全量）
```

**发布前检查**（写在 PR 模板里）：

- [ ] 本次涉及的表结构变更已备份
- [ ] 迁移脚本可重跑（幂等）
- [ ] 回滚方案写清楚了（数据回滚不了就要说"不可回滚"）
- [ ] 8 条数据自检在 staging 全绿

### 5.3 私有化交付的额外要求

如果客户要私有化部署（物业公司常见）：

- 一键安装包（`docker compose up` 能起来）
- 无外网依赖（镜像、字体、地图瓦片全部本地化）
- 离线授权（license 文件，含租户 ID 和到期日）
- 数据备份与恢复脚本 + 演练过至少一次

**"无外网依赖"最容易漏**：地图、天气预报、二维码生成、字体 CDN，任何一个外链在客户内网都会变成白屏。

## 六、角色与节奏

### 6.1 最小团队配置

| 角色 | 职责 | 人数 |
|---|---|---|
| 后端 | 表结构、接口、算法 | 1~2 |
| 前端 | 后台 + 移动端 | 1~2 |
| 设计 | UI 基线、样板页 | 0.5（可兼） |
| 测试/交付 | 契约测试、E2E、验收 | 0.5~1 |

**不建议一个人同时写前后端**：契约的约束力来自"两边是不同的人"。自己写自己调，契约会退化成注释。

### 6.2 节奏

| 频率 | 做什么 | 产出 |
|---|---|---|
| 每日 | 15 分钟站会：昨天做了什么、今天做什么、卡在哪 | 无 |
| 每周 | 周五验收：本周完成的域跑一次契约测试 + 8 条自检 | 一页验收记录 |
| 每阶段末 | 门禁检查 | 门禁清单签字 |

**每周验收必须有可执行的证据**，不接受"我觉得差不多了"。证据 = 契约测试输出 + 自检 SQL 结果。

| 天 | 内容 | 产出 | 依赖 |
|---|---|---|---|
| D1 | 建库（`sql/run-all.sh`）+ 复核 | 60 张表 + 冒烟 13 条全过 | 无 |
