# UI 基线规范

> 版本：v1.0 · 2026-11-17
> 适用：`03-原型` 存量工程 + 真实前端开发（同一套标准）
> 前提：**不换组件库**。Element Plus 已用透，迁移成本远大于视觉收益。
> 与 `视觉改造执行计划.md` 的关系：那份说"改什么"，这份说"改成什么值、怎么验"。

---

## 零、这份规范只管三件事

| 管 | 不管 |
|---|---|
| 一套可判定的数值（间距、行高、圆角、字号） | 具体某个页面怎么布局 |
| 6 个 EP 组件的结构样式（覆盖集中在**一个文件**） | 业务组件的交互逻辑 |
| 3 个样板页的验收标准 | 全站 103 页逐页精修 |

**核心判断：不做全站原型精修。** 原型的历史价值在流程和口径，像素会在真实开发时重做一遍。所以这份规范的落地范围是：`element-vision.css` + 3 个样板页，其余 100 页在真实前开发时按规范实现。

---

## 一、诊断：问题不在颜色

实测现状：

| 层 | 现状 | 判断 |
|---|---|---|
| Token | `tokens.css` 25KB，主色/辅色/侧栏/圆角 4 档/阴影 6 档/字号 6 档 | **已经够用**，不缺 |
| EP 覆盖 | `app.css` 18KB，但只覆盖 5 类选择器 `.el-button` `.el-table` `.el-form-item` `.el-dropdown-menu` `.el-icon`，共 12 处 | **最大缺口** |
| 自研组件 | 18 个（KpiCard / StatusTag / EmptyState / DetailDrawer / AsyncBlock / ScopeFilter …） | 有基础 |

结论说清楚：**"看起来像通用 SaaS 模板"，不是因为配色不对，是因为 Element Plus 的骨架从没被改过。**

Token 决定了"用什么色、多大圆角"，但 `el-table` 的行高密度、`el-card` 的分块方式、`el-tag` 的形态、`el-form` 的节奏、`el-menu` 的层级，全是 EP 出厂默认结构。所以页面感觉是"配色是我们的，骨架是别人的"。

### 分工：自研容器类不在这份规范里

原型里有两类样式，问题不同、解法也不同：

| 类别 | 例子 | 问题 | 谁管 |
|---|---|---|---|
| **Element Plus 组件** | `el-table` / `el-card` / `el-tag` / `el-form` / `el-menu` | 出厂骨架没改过 | **本规范** |
| **自研容器类** | `.panel`（507 处复用）/ `.dstat` / `.qvwrap` | 所有区块视觉权重相同，页面"平" | 单独处理：投影=主体、描边=次级 |

`.panel` 那条线已经在动（容器层级 + 页面底色），与本规范的 EP 组件改造**不重叠**，可以并行。但两边都要遵守同一条纪律：**覆盖集中在样式文件里，页面里不写 `:deep()`**。

### 一个建议：不换主色，但把它的使用面积降到 1/3

主色 `#5b6cff`（靛紫）本身不难看，问题在于**每一页都在大面积用它**：主按钮、链接、选中态、图表、标签、进度条、KPI 数字。一个颜色出现 20 次，就没有重点了。

真实开发阶段建议：

- 主色只用于：**主按钮、当前选中项、关键数字**
- 其余场景用中性色（石板灰阶）+ 语义色（成功绿 / 警告橙 / 危险红）
- `--biz-gradient`（紫绿渐变）**限用于品牌区**（登录页、首页欢迎块），不进表格和卡片

如果确实要换主色，token 层改 7 行（`--el-color-primary` + 6 个衍生色），但要重算图表配色和所有 `*-light-9` 底色，约 1 天。**建议先按"降面积"做一版看效果，再决定要不要换色**——大多数情况下，降面积就够了。

## 二、Token 基线

### 2.1 现有值（不改，作为基线）

| 类别 | Token | 值 |
|---|---|---|
| 主色 | `--el-color-primary` | `#5b6cff` |
| 主色 hover / active | `--biz-primary-hover` / `-active` | `#4d5ef7` / `#3f4ee0` |
| 辅色 | `--biz-accent` | `#2ed9a3` |
| 侧栏底 | `--biz-sidebar-bg` / `-deep` | `#101f42` / `#0b1730` |
| 圆角 | 控件 / 按钮 | `6px` |
| 圆角 | 卡片 / 面板 / 胶囊 | `10px` / `12px` / `999px` |
| 阴影 | 卡片 / 悬浮 / 浮层 | `0 2px 8px rgba(31,37,64,.05)` / `0 6px 18px rgba(63,76,158,.10)` / `0 8px 28px rgba(31,37,64,.14)` |
| 字号 | 基准 / 小 / 更小 | `14px` / `13px` / `12px` |
| 侧栏宽 | `--biz-sidebar-w` | `220px`（折叠 64px） |

### 2.2 要补的：密度 token（现有最大缺口）

```css
/* 追加到 tokens.css */
--biz-row-compact: 40px;   /* 数据密集页：账单、流水、抄表明细 */
--biz-row-default: 48px;   /* 默认：绝大多数列表 */
--biz-row-loose:   56px;   /* 卡片式列表、详情内嵌表 */

--biz-gap-module:  24px;   /* 模块（卡片）之间的间距，全局统一 */
--biz-gap-inner:   16px;   /* 卡片内元素间距 */
--biz-pad-card:    20px;   /* 卡片内边距 */
--biz-pad-page:    24px;   /* 页面内容区外边距 */
--biz-content-max: 1440px; /* 内容区最大宽度，超宽屏居中不拉伸 */

--biz-line-subtle: #f2f4f8; /* 表格分隔线，比 EP 默认更淡 */
--biz-line-base:   #e6eaf0;
```

**为什么密度是第一优先级**：后台"高级感"的 80% 来自密度控制，不是颜色。同样一份数据，行高 56 显空、40 显挤、48 正好；间距 16 显乱、24 显稳。

## 三、六个组件的改法（全部集中在一个文件）

新建 `styles/element-vision.css`，在 `main.js` 里**排在 EP 样式之后**引入：

```js
import 'element-plus/dist/index.css'
import './styles/tokens.css'
import './styles/element-vision.css'   // ← 新增，最后引入
import './styles/app.css'
```

**纪律：页面里不许再写 `:deep(.el-table__row)` 这类样式覆盖。** 全部集中在这一个文件。理由：EP 升级时覆盖会失效，集中一份只需查一个地方；散在 100 个页面里，升级等于重做。

### 3.1 el-table（性价比最高，先改这个）

```css
/* 行高与密度 */
.el-table {
  --el-table-border-color: var(--biz-line-subtle);
  --el-table-header-bg-color: transparent;
  --el-table-row-hover-bg-color: #f7f9fc;
  --el-table-fixed-box-shadow: 6px 0 8px -6px rgba(31, 37, 64, .10);
  font-size: 13px;
}

.el-table th.el-table__cell {
  background: transparent;
  font-weight: 600;
  color: var(--el-text-color-regular);
  border-bottom: 1px solid var(--biz-line-base);   /* 只留一条底线，去掉整块底色 */
}

.el-table td.el-table__cell {
  border-bottom: 1px solid var(--biz-line-subtle);
  padding: 0 12px;
}

/* 三档密度由行 class 决定，不写死数值 */
.el-table--row-default .el-table__row td { height: var(--biz-row-default); }
.el-table--row-compact  .el-table__row td { height: var(--biz-row-compact); }
.el-table--row-loose    .el-table__row td { height: var(--biz-row-loose); }

/* 数字列等宽，避免小数点错位 */
.el-table .cell-num {
  font-variant-numeric: tabular-nums;
  text-align: right;
}
```

**验收**：1440×900 视口下，账单列表首屏可见 ≥ 12 行；金额列小数点纵向对齐。

### 3.2 el-card / 页面区块

```css
.el-card {
  border: 1px solid var(--biz-line-subtle);
  border-radius: var(--biz-radius-card);
  box-shadow: var(--biz-shadow-card);
}
.el-card__header {
  padding: 14px var(--biz-pad-card);
  border-bottom: 1px solid var(--biz-line-subtle);
  font-weight: 600;
  font-size: 14px;
}
.el-card__body { padding: var(--biz-pad-card); }
```

**关键改动是 `__header` 和 `__body` 分离**。EP 默认两者内边距相同，看起来是一坨；分开之后卡片才有"头部 → 内容"的层级。

### 3.3 el-tag → 胶囊 + 语义收口

```css
.el-tag {
  border-radius: var(--biz-radius-pill);
  border: none;
  padding: 0 10px;
  height: 22px;
  line-height: 22px;
  font-size: 12px;
  font-weight: 500;
}
```

**更重要的一条不是样式，是纪律**：页面里禁止直接用 `el-tag` 表达业务状态，一律用已有的 `StatusTag` 组件。`StatusTag` 里有统一的状态→颜色映射；散用 `el-tag` 会出现"同一个'已缴'在 A 页是绿的、B 页是蓝的"。

### 3.4 el-form-item

```css
.el-form-item { margin-bottom: 20px; }
.el-form-item__label {
  width: 96px;                    /* 定值，不随内容抖动 */
  justify-content: flex-end;
  color: var(--el-text-color-regular);
  font-weight: 400;
}
.el-form-item__error {
  position: absolute;             /* 错误提示不撑开行高，避免下方元素跳动 */
  padding-top: 2px;
}
.el-form--label-top .el-form-item__label { width: auto; }
```

**标签宽度定值**是表单最重要的细节。不定值的话，每换一个字段名，整列标签宽度就在抖，看起来永远"没对齐"。

### 3.5 el-menu（侧栏）

```css
.el-menu {
  border-right: none;
  background: transparent;
}
.el-menu-item, .el-sub-menu__title {
  height: 42px;
  line-height: 42px;
  margin: 2px 10px;
  border-radius: var(--el-border-radius-base);
  color: rgba(255, 255, 255, .72);
  transition: background-color .15s, color .15s;
}
.el-menu-item:hover, .el-sub-menu__title:hover {
  background: rgba(255, 255, 255, .06);
  color: #fff;
}
/* 激活态：浅底 + 左侧指示条，不再用整块高亮 */
.el-menu-item.is-active {
  background: rgba(91, 108, 255, .16);
  color: #fff;
  position: relative;
}
.el-menu-item.is-active::before {
  content: '';
  position: absolute;
  left: -10px; top: 50%;
  transform: translateY(-50%);
  width: 3px; height: 18px;
  border-radius: 0 2px 2px 0;
  background: var(--el-color-primary);
}
```

**为什么加左侧指示条**：EP 默认激活态是整块背景色，二级菜单展开后会有一大片同色块，层级全糊。指示条把"我在哪"从"颜色"变成"位置"，一眼能认。

### 3.6 el-empty / el-skeleton → 收口到自研组件

不做样式覆盖，做**替换**：

| 禁用 | 改用 | 原因 |
|---|---|---|
| `<el-empty>` | `<EmptyState>` | 统一插画尺寸、文案槽、可带主操作按钮 |
| `<el-skeleton>` | `<AsyncBlock>` | 统一 loading / error / empty 三态，含重试 |
| `<el-loading>` 遮罩整块 | `<AsyncBlock>` 局部 | 全屏遮罩会闪，局部骨架不闪 |

**这条是硬要求**：三态（loading / empty / error）不统一，是后台"廉价感"的第二大来源。

## 四、三个样板页（验收基准）

不逐页改，只做这三页。它们覆盖了全站 90% 的页面类型，改完之后其余页面照抄结构。

| # | 页面 | 类型 | 为什么选它 | 验收要点 |
|---|---|---|---|---|
| 1 | **账单查询** | 列表页 | 全站最复杂：12+ 列、有固定列、有筛选区、有批量操作 | 首屏 ≥ 12 行；金额右对齐；固定列阴影不明显；筛选区高度 ≤ 88px |
| 2 | **房屋编辑** | 表单页 | 字段最多（20+），有分组、有联动、有只读态 | 标签列宽 96px 固定；分组间距 24px；错误提示不撑高 |
| 3 | **房屋详情** | 详情页 | 聚合多块（档案 / 业主 / 账单 / 工单），是"信息密度"的极限 | 卡片间距 24px；同一行内信息对齐；长文本折行不撑破 |

### 4.1 交付形式

每个样板页出**并排对照**：左"改造前"、右"改造后"，同一份数据、同一个视口（1440×900）。

确认方式：你说"要右边这个，但圆角再小 2px"，比形容词高效十倍。这个对照页同时当团队验收标准。

### 4.2 验收的可判定标准（不靠感觉）

| 项 | 判定方法 | 通过线 |
|---|---|---|
| 密度 | 1440×900 下首屏可见行数 | 列表页 ≥ 12 行 |
| 对齐 | 金额列小数点是否在同一条竖线 | 逐列目视，无错位 |
| 间距 | 卡片之间距离是否一致 | 实测 24px，误差 ≤ 2px |
| 点击区 | 最小可点区域 | ≥ 32×32px |
| 三态 | 每页都有 loading / empty / error | 三个状态都能触发 |
| 字号 | 全文使用的字号种类 | ≤ 4 种（20/14/13/12） |

**六个可判定项，全部能机器测或目视一秒判断**，不需要争论"够不够高级"。

## 五、禁则（比"要什么"更重要）

| 禁止 | 为什么 |
|---|---|
| ❌ 页面里写 `:deep(.el-*)` 覆盖 | 升级即失效；100 个页面改不动 |
| ❌ 用 `el-tag` 表达业务状态 | 状态色会分叉，必须走 `StatusTag` |
| ❌ 硬编码颜色 / 间距数值 | 一律走 token；硬编码的第二次改不动 |
| ❌ 用渐变做卡片背景、表头、按钮 | 渐变只允许在品牌区，否则一眼是模板 |
| ❌ 一屏出现 3 个以上主色块 | 没有重点。主色只给关键动作 |
| ❌ 全屏 loading 遮罩 | 闪白。要局部骨架 |
| ❌ 表格里出现两行文字换行 | 说明列太多或内容太长，改列宽或加省略 + tooltip |
| ❌ 图标 + 文字按钮混排在同一组操作里 | 操作区视觉噪音，选一种 |

## 六、给真实开发的衔接

这份规范不是"原型打磨方案"，是**真实前端的实现标准**。落地顺序：

| 阶段 | 做什么 | 说明 |
|---|---|---|
| 阶段 0（现在） | 出 `element-vision.css` + 3 个样板页 | 只做这 4 件事，其余不动 |
| 阶段 1（纵切） | 收费链路 5 个页面按规范实现 | 用真接口，不用 mock |
| 阶段 2（全量） | 每域页面按规范实现 | 不回头改原型 |

**原型不再精修。** 阶段 2 的页面直接从规范实现，原型只作为"字段和流程"的参考，不作为"像素"的参考。

### 一条建议：把样板页留在原型里，作为长期对照

`/shell/vision` 这样的对照页（同组件改造前/后并排）建议保留。它的作用是：

1. 新加入的人一眼看懂标准
2. 视觉走样时，拿它当基准比对
3. 组件升级后，跑一次截图就知道哪里坏了

成本半小时，价值很长。

## 八、和"降面积"配套的一页检查表

改完之后，随便打开三页，按下面五个问题自查：

- [ ] 这一页的**主色**出现在几处？超过 3 处就是没重点
- [ ] 表格行高和旁边卡片的间距**是同一套数值**吗？
- [ ] 有没有哪个数字**小数点没对齐**？
- [ ] 空态 / 加载态 / 报错态**三个都在**吗？
- [ ] 把这一页截图给没看过的人，他第一眼看到的是**数据**还是**装饰**？

第五条是终极判断：后台的第一眼应该是数据。
