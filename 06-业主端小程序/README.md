## 二、v0.3 做了什么

### 2.1 邻里：从「物业发帖 + 评论」改为**四频道**

原因是类目红线，不是产品取舍：一旦有业主对业主的公开回帖，就往微信【社交-社区/论坛】类目靠，
需要常态化内容审核，物业没有这个编制。所以「话题广场 / 跟帖 / 公开评论墙」**整条下线**。

| 频道 | 业主端能做什么 | 关键口径 |
|---|---|---|
| **公告** | 列表（按类型筛、分页）、详情、**签收**、附件、阅读数 | 与 PC 同一张 `notices` 表，只同步「已发布」；阅读数/对象户数直接用公告自带的 |
| **投票** | 单选 / **多选（最多 N 项）**、截止倒计时、**投完才看结果**、我参与过 | 只做意见征询，结果里没有「通过 / 未通过」；参与率按**户**算，租户不计 |
| **活动** | 5 个阶段、收费活动报名（出行人 / 投保 / 条款）、取消并按分档退款 | **「待成行」不能报名**（已截止但没到成团下限）；证件号只在投保时收 |
| **闲置** | 浏览、想要、**站内私信**、发布（先审后发）、我发布的 | 展示只到**楼栋**，不显示门牌；手机号默认不公开 |

配套页面：`notice.vue`、`vote.vue`、`activity.vue` + `activity-enroll.vue`、`secondhand.vue`、
`item-publish.vue`、`my.vue`（我发布的 / 我报名的 / 我投的）。原 `post.vue`、`survey.vue` 已删除。

### 2.2 租售信息：五屏，前三个**不挂门禁**

业主把房子挂出来，责任楼管审一道；想租的人**留下自己的电话**等楼管联系。
物业不展示任何员工手机号 —— 电话从访客流向楼管，不反向流出。

| 页面 | 门禁 | 要点 |
|---|---|---|
| 房源频道 `house-sale/list` | **无** | 游客可看；小区 / 户型 / 租金区间 / 排序 |
| 房源详情 `house-sale/detail` | **无** | 无房号、无业主信息、无楼管手机号 |
| 我要看房 `house-sale/viewing` | **无** | 同号同房 24h 一次；「楼管会在 24 小时内联系你」；90 天自动删除告知 |
| 发布租售 `house-sale/publish` | `gateOwner` + **身份必须业主** | 只填 5 项；面积/户型/朝向/楼层从档案带出且只读；首屏放照片正误对照 |
| 我的挂牌 `house-sale/mine` | `gateOwner` | 状态、**驳回理由原样展示**、下架、一键续挂、浏览 / 看房数 |

入口：首页服务区「租售信息」（第 5 格）、我的房屋页「发布租售 / 我的挂牌」、我的页九宫格与列表。

## 四、六条硬口径（都写死在代码里）

### 4.1 登录 ≠ 认证（动作级门禁）

```
L0 游客   session=null            公告 / 邻里 / 生活 / 公共报修 / 房源频道 都能用
L1 登录   手机号                   活动报名、闲置想要 / 私信
L2 认证   手机号+姓名+证件后四位    缴费、个人报修、门禁、房屋、发布
          · 业主 → 全部
          · 家属 → 缴费/报修/开门；看不到租约金额、不能发布租售
          · 租客 → 报修/开门；看不到业主账单；**不参与投票**
          对不上 → 人工审核（必须上传购房合同 / 房产证）
```

门禁是**动作级**的（`utils/guard.js`）：`gateLogin / gateOwner / gatePerm / gateVoter`。
房源列表与详情**一个 guard 都不调** —— 那批客源基本不是业主。

### 4.2 家庭账单：多房合并，但合并的是"付款动作"

合计 = 已绑全部房产 + 本人名下**不挂房的车位费**（`bills` 里 1,344 张 `houseId` 为空）；
页面先给总账、再按房分组小计；一次支付可覆盖多房多张账单，但订单 `lines` 逐条带 `houseId`。

### 4.3 增项：合并进本单，只补差额

`dueFee = totalFee - paidAmount`。只改总额不改支付状态，那 80 块永远收不上来。

### 4.4 支付只到「模拟成功」

账单 / 报修 / **活动报名费**（`type='activity'`）共用一个支付入口；
真接入替换点写在 `api/mp.js` 的 `simulatePay()` 注释里。

### 4.5 邻里五条（§12.3）

1. 公告 = 同一张表，只同步已发布；
2. 投票只做意见征询，**不出现「通过 / 未通过」**，参与率按户算；
3. 收费活动三约束：成团下限、退款分档、投保开关（证件只投保时收）；
4. 闲置先审后发，驳回必带理由，展示只到楼栋，手机号不公开；
5. 不做话题广场 / 跟帖 / 公开评论墙。

**退款分档**由 `src/api/refund-rule.mjs` 实现，与后台 `refundRatioOf` 同一口径：
按提前天数**从高到低**命中即止。升序会退化成"永远退最低档"（后台踩过），
`check:data` 有一条单调性守卫钉住它。

### 4.6 租售四条（§13）

1. 只做信息发布：不代收、不抽佣、不做带看排期；
2. **楼管手机号不进任何对外返回**，只给姓名 / 微信 / 二维码；
3. **房号与单元连登录也不给**，字段白名单在 `api/listing-view.mjs`，加字段会被 `check:data` 拦住；
4. 面积 / 户型 / 朝向 / 楼层从档案派生，业主改不了。

## 五、数据：读同一份，不另造一份

| 来源 | 用途 |
|---|---|
| `03-原型/src/mock`（`@pc` 只读） | 房屋 / 账单 / 工单 / 公告 / 员工 / 水电表 / 投票（`surveys`） |
| `04-契约/fixtures`（`@contract` 只读） | 邻里活动 17 / 报名 268 / 闲置 34 / 挂牌 14 / 看房 10 |
| 本机 `localStorage` | 登录、认证、缴费、报修、报名、投票、发布、看房请求 |

用来演多选投票。**不新增模板行** —— 多一行会消耗随机流，后面 30 多张表会整体漂移。
权限表 `permissions.json / roles.json` 里补了 `a.listings.view / audit / viewing` 三个码（`03 check` 要求）。

### 演示态（界面有 `演示` / `占位` 角标）

| 项 | 现状 | 真接入要换什么 |

| 房源图片 | 占位色块 | 实拍图 + 去门牌水印 + 审核必看清单 |
| 生活 tab | 只有卡片，无下单无支付 | 商户资质、库存、分账、售后、结算（独立项目） |

### 缺口（本轮明确不做）

1. **话题广场 / 跟帖 / 公开评论墙** —— 类目红线，不是排期问题。
2. **法定业主表决** —— 投票只是意见征询；法定表决要面积+人数双过半、实名留痕、可公证。
3. **在线过户 / 产权变更** —— 涉及原业主确认，P2。
4. **出售房源** —— 一期只做出租，字段留着、入口不开。
5. **经纪类能力**（佣金 / 成交价 / 带看排期 / 在线议价）—— 做了就变成房地产经纪，要备案。
6. **门禁 / 停车 / 访客完整闭环** —— 需硬件与后台。
7. **员工端与本工程不共享运行时** —— 一致性体现在契约与状态机；员工端仍未把增项写回
   `workOrders[].addons`，所以报修详情保留「模拟加项」入口。
8. **业主端发布的内容不会出现在 PC/员工端队列** —— 两端各自内存，审核用「模拟通过 / 驳回」代替。

### 7·补二 · 批 A：认证链路已切到接口（2026-11-08）

前 38 屏全是本地数据，一个网络请求都没有。切接口是**分四批**做的，批 A 只切认证：

| 已切（`VITE_USE_API=true` 时走接口） | 仍本地 |
|---|---|
| 登录 `/mp/auth/wechat-login`、实名 `realname`、候选 `bindings/candidates`、绑定 `bindings` | 选社区 / 楼栋 / 房间、房屋详情、在住人 |
| `/mp/me`（已就绪，首页角标批 B 才接） | 账单、报修、支付、评价、内容侧 |

**怎么开**：复制 `.env.example` → `.env.local`，把 `VITE_USE_API=true` 打开，
另开一个终端在 `04-契约` 下 `npm run mock`。关掉就删这一行，代码不用动。

**为什么这么切**：一次全切的话，出问题分不清是接口错还是本地逻辑错。现在两种模式共用
同一套页面与规则，差别只在"判定发生在哪一层"—— 回退成本是 0。

**验收**（puppeteer 实跑，截图 `screenshots/api-*.png`）：

- 业主（张建国）：登录 → 选 0501 → 实名 → 提交 → `auth=approved`、`identity=业主`、
  绑定 `[H010110501]`、token 已存；四个请求都打在假服务上，零 console 错误；
- 家属（陈静）：同一条路径，`identity=家属` —— 身份以档案为准，不看用户选的"业主"；
- 证件不符：服务端返回 `level=none` + `mismatch.cert=true`（契约测试覆盖，UI 侧未单独截图）。

### 7·补三 · 批 B：房屋 / 住户 / 账单 / 价目（2026-11-08）

| 已切（`VITE_USE_API=true` 时走接口） | 仍本地 |
|---|---|
| 房屋详情 `/mp/houses/{id}`、住户 `/residents`、租客登记、账单 `/mp/bills`、价目 `/mp/pricing` | 选社区 / 楼栋 / 房间、报修下单、支付、评价、内容侧、租售 |

**没有把 38 个页面改成 async。** 页面的数据都是 `computed(() => myBills())` 这种同步选择器，
逐个改成 `onLoad` 里 await 等于重写全部生命周期，而且以后每加一页都要记得"这里也要 await"。

走的**缓存水合**：`src/api/remote.js` 的 `hydrate()` 在登录后 / 启动时 / 绑定成功后

1. **60 秒 TTL + `force`**：`onShow` 会频繁触发，每次都打四个请求没必要；

2. **拉失败不抛**：`hydrate()` 内部 catch 打 warn，继续用本地数据。
   演示现场网络抖一下，不该看到白屏或"数据加载失败"。
3. **登出要清快照**：`logout()` / `resetAll()` 都清 `app.remote`。
   不清的话换个人登录，页面会先渲染上一个人的账单 —— 这种"上一个人的数据"是最吓人的 bug。

**一个真 bug，两条纪律**：

`remoteMyListings()` 一开始写成 `app.remote?.myListings || null`。默认值是空数组，

- 停在同一个 hash 上 `page.goto` 是**空操作**，`onShow` 不触发 —— 页面会停在刚才的空态。

`api/park.js` 取数、`api/park-rule.mjs` 放纯规则（到期分档、预缴顺延、车牌格式、额度计数），
`check:data` 直接跑后者 —— 规则只有一份，页面与自检不会对不上。

四条前置**全部明写在换绑页上**（不满足就写为什么不满足），而不是点了按钮才报错：
业主身份 / 已实名 / 车位管理费未到期 / 本月次数还有。

三条刻意的口径：

1. **额度按车位 + 自然月，不按业主**。按业主算会误伤真有两个车位的人 ——
   他换两个车位是两件事，不是刷次数。阈值将来由后台 `/e/config` 下发（任务清单 H1），
   这一版是常量 `PLATE_LIMIT = 1`，不是"忘了做"。
2. **换绑留痕但不伪造回执**。车牌识别系统还没对接，`vendorStatus` 一律「待同步」。
   写一个"已同步"只会在联调时多一轮排查。
3. **预缴只写流水 + 顺延到期日，不并入家庭账单**。并入要改 `api/mp.js` 的账单层，
   而那个文件此刻正被员工端窗口改；预缴的是未来账期，本来不在当期欠费里，
   所以待缴合计不受影响，**不构成第二份金额真相**。并入在批次 82。

管理费账单是**按 `parkId` 精确归集**的（03 的 `bills` 1344 条车位账单全带 `parkId`，
王浩然两个车位各 3 期不串账）；`04/fixtures` 的投影白名单把 `parkId` 裁掉了，
那种情况下自动退回"按业主归集"——补齐 fixtures 是批次 82 的事。

#### 刷脸通行（80）

首页原来的「手机开门」是个占位二维码 —— 小区没有二维码闸机，实际是人脸识别通行。
这个入口留着比没有更糟：业主会以为能远程开门。现在改成「刷脸通行」，点开是**人脸状态页**，
页面上**没有开门按钮**（门是刷开的，不是点开的）。

五态：未采集 → 待核验 → 已生效，另有已驳回（带原因）与已冻结（租约结束 / 撤回）。
业主端**不允许自助生效** —— 生效只能由物业核验动作触发（后台 H4），否则谁都能给自己开门。

谁能录，按"谁对谁负责"分：

| 身份 | 能做什么 |
|---|---|
| 业主 | 本人 + 本房**已核验**成员（老人孩子的主要场景） |
| 家属（扫码绑定） | **只能录本人**。走 me 语义，不下发也不需要 `memberId` |
| 租客 | 只读 —— 人脸在租约核验时由物业录 |

三条限制写在 `access-rule.mjs` 里：待核验期间不许重复提交（审核人正在看那张照片）、
24 小时最多 3 次、**没核验的成员不能代录**（没核验就录脸，等于填个名字就能给别人开门）。

合规四条摆在页面底部（用途 / 核验 / 存储 / 撤回），不是注释：人脸属于敏感个人信息。

#### 验证

`check:data` 新增 32 条（车位 21 + 人脸 11）全过 · `build:h5` 通过 ·
puppeteer 两轮走查 21/21 + 25/25（截图 `api-g-05` ~ `api-g-14`）：车位列表/详情/换绑成功/
次数用尽，人脸已生效→重新采集→待核验→撤回，成员页代录，家属只见本人，租客只读。

**还没做的**：首页信息流合并（批次 81）、车位与人脸的契约化（82 / 83，等员工端窗口收工）。

### 7·补十 · 批次 81：首页社区合成一条流（2026-11-09）

原来的首页是「社区活动横滑 4 张 + 社区公告 3 张」两块。活动多时好看，
**活动少时那块就是一条空轨道** —— 而真实小区的活动密度本来就是波动的。
这一批把四个频道合成一条流：`api/home-feed-rule.mjs`（纯规则）+ `api/home-feed.js`（取数）。

排序按"要不要我动手"，不按时间：待签收公告 → 未投投票 → 报名中活动 → 置顶公告 → 其余公告 → 在售闲置。

**一个必须设的配额**：不设上限时，样例里 P01 有 10 条没签收的停水/安全公告，
它们会把 5 个位置全占满，首页变成一面"催签墙" —— 那正是这一批要解决的问题，只是换了个方向复发。
所以 `KIND_CAP = { notice: 2, vote: 1, activity: 1, item: 1 }`，**先按配额混排、空位再回填**。
实测：游客态只有投票与活动时，回填会给出 4 条投票（没有别的可给，这是对的）；
有 10 条待签收时，流里仍然是 4 个频道各占其位。

两个坑，都写在代码注释里：

1. **签收判定不能读 `signRequired`**：列表接口不返回这个字段（只有详情有），
   拿它过滤的结果是一条"待签收"都出不来 —— 首页第一条会一直是投票。
   按类型判（停水停电 / 安全提示）与服务端同一口径。
2. **改完不 build 等于没改**：本机 5170 上跑的是 `dist/build/h5` 的静态服务，
   不是 vite dev。上一版 bundle 里还是旧规则，看起来像"改了没生效"。
   先 `npm run build:h5` 再验收，这条比任何断言都容易踩。

周边服务：只做入口（`lifeHome().hot` 前 4 条 + 「进入生活」），**不放商品卡、不带购买**，
并写明"本轮只展示，不下单、不支付"。推荐位不参与排序、不做竞价。

验证：`check:data` 新增 11 条（配额 / 优先级 / 回填 / 空态）· puppeteer 13/13
（截图 `api-g-15` / `api-g-16`）· `smoke` dev + dist 全绿。

### 7·补十一 · 批次 82–83：车位 + 刷脸切服务端（2026-11-10）

`@pc/mock` 到此**不再出现在任何一条正常链路上**。之前剩下的两处
（车位三页、刷脸页）现在都走 `/mp/parkings*` 与 `/mp/access/*`。

**这一层不做缓存水合**，理由与选房三级一样：车位最多三五个、人脸只有本人加几个成员，
提前拉没有收益；而换绑成功后必须立刻看到新记录 —— 缓存等于让业主"明明换了，
退出来再进去还是老车牌"。所以是「进页面拉一次」，`remote` 只做一次请求内的中转。

#### 三个真坑（都写在代码注释里）

1. **`remote` 是普通对象，computed 追踪不到它。**
   `const cars = computed(() => vehiclesOf(parkId))` 在接口模式下永远是首次渲染的空数组：
   `park` 的引用没变，computed 不重算，页面就一直显示"0 辆 · 还没有换绑记录"。
   修法是这些 computed 显式读一次 `ver.value`（列表页早就是这么写的，详情页漏了）。
2. **`remote.js` 原来只 `import { get }`。** 新加的四个写接口用了 `post`，
   点击没有任何反应、也不报错到页面 —— 只在 console 里一句 `post is not defined`，
   被 `catch` 吃掉变成 toast。这类错在"只测 GET"的验收里永远发现不了。
3. **页面读 `v.cardNo`，服务端只给 `cardNoTail`。** 结果是 `IC 卡 ****` 后面空空。
   现在 `vehiclesOf()` 两种模式都只给 `cardNoTail`，本地那段也不再保留完整卡号 ——
   页面只认一个字段，才不会一边显示 `****2192`、一边显示 `****`。

#### 接口模式下续费不可用（有意）

车位续费的本质是「按车位出账 → 支付 → 账期顺延」，而批次 82 只落了车位四件套，
没有"按车位出账"的接口。所以在 `IS_API` 下 `renew()` 直接抛
「请在家庭账单里缴纳，缴完后账期自动顺延」，**不写本地流水**：
写了就变成页面显示已续到 12 月、后台显示 10 月到期，两边各说各话。

本地模式保留原演示（写 `parkPays` + 顺延 `parkExpire`），因为它要在没有服务端时把流程演完。
按车位出账归到下一批。

#### 验收

接口模式 puppeteer **31/31**（截图 `api-g-20` ~ `api-g-26`）：车位列表 / 详情（车辆、记录、
按 parkId 的三期账单）/ 换绑成功（服务端生成 PL00003）/ 额度用尽拦截 / 刷脸已生效 /
重新采集进待核验 / 撤回变已冻结；全程零 console 错误、无 4xx。
本地模式 `check:data` 全过、`build:h5` 通过、`smoke` dev + dist 全绿。

### 7·补十二 · 2026-11-11：报修两条线分家 · 预存余额口径修正

这一轮都不是新功能，是**把已经存在的错误口径改对**。

#### 一、公共报修不再要求选项目

原来两条线共用一个表单：位置 → **报修项目（价目表）** → 描述 → 照片。
公共区域维修是物业出人出料、免费处理，让业主先挑一个"角阀/软管更换 ¥125"再免费修，
既荒谬又容易让人以为要收钱。

改完的公共表单：**位置（10 个高频快捷项 + 「其它位置」手填）→ 部位 → 描述 → 照片**。

为什么还留"部位"：它决定派给哪个工种，也是工时积分的权重来源（电梯 1.5 / 配电 1.3）。
一行 7 个 chip，页面上写明"不影响收费"。

契约同期放宽（见 04 README §11.16）：公共单不再要 `priceCode` / 预约时段，
`place` 支持自由文本（≤40 字）—— 小区总有列表没覆盖的角落（消防通道、屋面、架空层）。

两处容易漏的服务端细节：公共单标题原来拼了 `price.name`，不传项目会变成
`1栋大堂 · undefined`；价目四个字段也要置空，否则后台列表会出现空壳项目。

#### 二、个人报修项目：分类折叠 + 搜索

现在只有 10 项（10 个分类各 1 项），但项目是会加的 —— 一次摊开几十项就没法选。
改法不是加层级（报修是"边说边选"，层级越深越难），而是：

- 每类一个标题行，右侧「收起 / 展开」，显示条数；
- 默认展开前 3 类（水管 / 下水道 / 电路，最常见的三种）；
- 顶部搜索框，**搜索时无视折叠状态全部展开** —— 搜到了还要再点一次展开，等于没搜；
- 项目行改成紧凑样式（`opt--dense`），一屏能看 7-8 项。

#### 三、预存余额：一个数字被算了两遍

`utility.js` 把 `prepayAccounts`（业主预存账户）挂在**每个户号**上，
页面顶部再写"本房水费 + 电费余额 = 各户号余额之和"：

```
水表.balance = 预存账户余额 4809
电表.balance = 预存账户余额 4809   ← 同一个账户
顶部            = 4809 + 4809 = 9618
```

而 `prepayAccounts` 是**按房一个账户**（后台 `/b/prepay` 用它抵扣各项账单：
物业费 2213 + 水费 687 + 电费 640 + 车位费 1344 全都走 `bills`）。

改法：

- `accountsOf()` 只回答"哪个户号、本期用多少、应缴多少"，**不再带余额**；
- 新增 `prepayOf(houseId)`，余额只有这一个来源，页面上只展示一次；
- 户号卡的标签从"余额充足 / 待充值"改成"本期待缴 / 本期已结清"；
- **充值改成充进预存账户**，不再按户号充 —— 按户号充会让"水表充 100、电表充 100"
  变成"账户只多 100"，账面与流水对不上。

`check:data` 加了 4 条守卫：一房最多一个有效账户、账户必须挂房、表具必须挂房、
账户数不超过有表具的房数。样例里 249 个有表具的房只有 126 个开了账户，
所以没账户按 0 处理并提示"未开通预存"，不是错误。

#### 验收

折页/搜索/其它位置/提交 共 **18/18**（本地模式，截图 `api-g-30` ~ `api-g-34`）；
`check:data` 全过（新增 4 条）· `build:h5` · `smoke` dev + dist 全绿 · 04 test 283/283。

### 7·补十三 · 2026-11-11：账户入口（预存 + 商业）

「我的」页头部下方多了一条账户条，**两块并排、各有各的名字与出口**：

```
物业预存 ¥917.14          商业积分 1280 分
可抵 ¥1,179.78 待缴        2 张券可领
```

合成一个"总余额"是错的：物业预存是预付账款（能抵物业费），
商业平台的是储值与积分（只能去平台花）。放一起，业主第一个问题就是"能不能交物业费"，
而答案是不能 —— 所以干脆不给他这个机会。

#### 一、预存账户（`pages/prepay/index`）

一个页面做完三件事：看余额、充值、抵扣，外加流水。

- **首次充值即开户**：没账户时返回「未开通」而不是 404，充一笔就开了。
  做成"先去后台开户"会把业主挡在门外。
- **抵扣允许部分**：余额只够一张的一部分时，账单变「部分缴」、差额留在账上。
  这是真实情况，"装成结清"比不给功能更糟。
- **流水是余额的解释**：最后一条的余额必须等于账户余额，页面上两处都显示，对不上就是 bug。
- 营销位（充值赠送 / 积分 / 礼包）在页面上写明"规则确定后再上线，本期不产生任何赠送" ——
  接口已经预留 `campaignCode` 与 `gift`，服务端恒返回 null。

本地模式与接口模式差一处：**本地没有历史预存**（`@pc/mock` 的 prepayAccounts 里没有张建国），
余额从本地充值累计；接口模式才有 917.14 的历史。这是数据差异，不是逻辑差异。

#### 二、商业账户（`pages/commerce/index`）

只读镜像：积分、等级进度、优惠券。**没有余额**（见上）。

券按"可领取 → 已领取 → 已过期"排序，一进来先看到能拿的。
「去领取」不写任何状态 —— 弹一句"领取与使用都在商业平台"，原型不打开外部链接。

#### 三、账单一侧的连带改动

`markBillDeducted()` 新增，`rehydrate()` 也改了：原来刷新页面会把 `billPays` 里的账单
**一律还原成「已缴」**，部分抵扣剩下的差额会被抹成 0 —— 等于把欠的钱藏起来。
现在按"实际付了多少"还原 `paidAmount` / `unpaid` / `部分缴`。

#### 验收

账户走查 **24/24**（截图 `api-g-40` ~ `api-g-46`）：未认证时账户条给空壳、
未开通 → 充值 500 → 抵扣 → 流水两条 → 账单同步变「部分缴」、商业页积分/券/领取引导；
零 console 错误。`check:data` 全过 · `build:h5` · `smoke` dev + dist 全绿 · 04 test 287/287。

## 八、这一轮踩到的坑（都在代码注释里）

1. **楼栋名不能从 `fullName` 切**：`翡翠城 1栋2单元1102` 取空格后一段，会把单元与门牌一起带出去，
   闲置列表直接泄露房号。必须取 `buildings.name`。`check:data` 有一条守卫盯着。
2. **三类人都带 `ownerId`**：家属挂在业主上、租客也记着业主，靠 `ownerId` 判身份会把租客当业主。
3. **演示身份别用文字点**：陈静的描述写着「张建国的配偶」，按文字匹配会点到她 → 身份行加 `id`。
4. **`Bar` 的 `#right` slot 会吃掉默认主按钮**；次要动作放 `#left` 或正文。
5. **只清 localStorage 不整页重载**：store 在模块初始化读缓存，换身份必须 reload。
6. **`<text>` 默认 inline**：同容器两个 text 会粘成一行，两行结构要显式 `display:block`。
7. **删代码块要顺手搜引用**：重构 `listing.js` 时把 `allRaw / viewingsOf` 一起删了，
   dev 有 HMR 缓存看着正常，`build` 后才炸 `ReferenceError`。
8. **加种子行会漂移随机流**：给问卷加一条模板，后面 30 多张表内容全变 —— 改为生成后定点改字段。
