# 员工端 APP 原型

uni-app（Vue 3 + Vite，JS 模板）实现，跑 H5 演示，**不接后端**。
本 README 是工程与后续任务之间的交接物，配合 `02-原型设计/交接单-员工端APP.md` 一起看。

## 一、现在有什么（34 屏 / 4 个身份 / 5 个 Tab）

```
工作台(Tab)  任务(Tab)  工单(Tab)  消息(Tab)  我的(Tab)
    │            │         │
    ├─ 审批列表 → 审批详情（通过 / 驳回 / 转办）
    │            └→ 发起申请（6 类单据，字段与审批流来自后台配置）
    ├─ 整改列表 → 整改详情（提交 / 整改复核 / 改派）
    ├─ 我的楼栋（欠费户 → 催收跟进 → 业主与房屋：标签 / 租户档案 / 批量催缴）
    ├─ 邻里待办（待审闲置 / 待处理举报）→ 邻里活动（卡片上直接代报名）→ 详情 · 代报名 / 签到
    ├─ 通讯录（部门 + 明文手机）
    ├─ 我的考勤（月度确认 / 申诉）
    ├─ 我的工资条（本人规则，含应发 / 代扣明细）
    ├─ 我的提成（按人工费计提，已结 / 在途，独立结算单）
    └─ 费用看板（只读）
任务 Tab → 任务详情 → 开工打卡 → 逐项执行 →（异常项）转工单 → 提交结果
工单 Tab → 工单详情 → 抢单 / 到场 → 完工（含现场增项）→ 收款码 → 业主配合度回评
```

外加一页 **多屏画廊**（`/static/preview.html`）：34 屏 iframe 并排，切身份全部一起换视角，评审时一屏一屏过。

## 二、工单：抢单是给「付费入户单」用的，不是所有单

这一版把工单从「接单」改成了**有动机的抢单**，口径由业主方在 2026-11-01 确认：

| 规则 | 说明 |
|---|---|
| 谁能抢 | 维修岗（维修工 / 工程主管），且在项目参数里 `enabled` |
| 什么单进池 | **只有付费入户维修**（`feeType=收费`）。公区维修没有提成 → 一律后台指派，不进池 |
| 并发 | 两人同时点只能一人抢到；失败文案是「手慢了，已被 X 抢走」（后台条件更新 + 409） |
| 到场 | 抢到后 `grabArriveMinutes`（P01 = 15 分钟）内必须到场打卡，超时记迟到 |
| 刹车 | 不去要按「放弃」，累计弃单；超过 `abandonLimit`（P01 = 3）当天不能再抢 |
| 派单 | 三档：客服（本项目受理单）/ 班组长（本班组公区单）/ 项目经理（跨班组、特急升级、业主点名的付费单）。**付费单只有项目经理能派** —— 随手一派就吃掉师傅提成 |

**提成口径**（`repairPrices.json` 按项目配置，不写死在代码）：

- 基数只算**人工费**（材料费是成本；数据里材料占收费单 54%，按总额提成等于把成本分给个人）；
- 比例 `commissionRate`（P01 35% / P02 32% / P03 30%）+ 保底 `minCommission`；
- **已收款才结**：已付 → 已结，完工未收 → 在途。列表页顶部直接给「本月抢单提成 ¥X · 在途 ¥Y」。

**取价读下单时的快照，不反查字典**（2026-11-04 · 后台第 47 批）：工单行自带 `priceCode / serviceName / serviceCost`，
详情页展示这一份；字典（`repairPrices.items`）只用于「下单与加项取价」和「当前价对比」。
反查字典的后果很具体：运营把角阀更换从 ¥125 调到 ¥135，**所有历史单详情立刻变 135**，而实际收款是 125，
同一屏上"标准人工"与"提成"按两个价算，师傅一定会来问。字典价与快照价不一致时，页面明确写"按下单时价格结算"。

**工单类型分流**：`商业服务`（付费入户，可抢单）／`公共区域维修`（公区设施，免费、无提成）——
抢单池只收前者；公区单详情不显示费用与提成，改为一句"不向业主收费，也不计提成"。

**提成为什么不直接写进工资条**（Q9 的落地方式）：工资表是**期间锁定**的核算快照，10 月表发出去以后，
10 月才收到的钱没处记。所以提成先出**独立结算单**（`TC202610-01`，按完工月归集，只算已收款），
次月随工资并入为工资条里的一行 `commission`。移动端：
工单列表顶部卡片 →「我的提成」→ 结算单（已结 / 在途 / 明细 / 口径），工资条页也留了入口并写明「不在这张表里」。

**入户单没有报价环节**：业主下单时已看到价目并预付，所以详情页给的是「价目编码 + 标准材料/人工」，
不是"师傅现场报价"。现场多出来的活走**增项**：

```
加增项（改价不算数）→ 待业主确认 → 业主确认（业主端上线前用「当面确认」桥接）→ 合并进本单 → 后付
```

有未确认增项时**不许完工** —— 否则会出现"单子结了、钱多了一截没人认"。
收款只出**收款码**（钱进项目账户），员工不经手现金：现金要配交班、日结、实点与差异说明，
等于把收银台搬上手机，风险全压一线。

## 三、楼管：住在里面的人 + 批量催缴

- **租户**（160 条）：姓名、租期、在住人数、认证状态（57 户「信息不全」/ 55 户「待核验」）、人脸是否已录；
- **共住成员**（169 条）：关系、手机（脱敏）、认证与人脸标记、是否绑小程序；
- **不给的**：租户**租金**（合同价属财务/项目经理）、**身份证号**（要核对走 PC 档案并留痕）。

**批量催缴**照 PC 催缴工作台的口径，不另立一套：按**房屋**聚合（一户挂三个月账只出现一行）→
账龄 / 费项筛选 → 勾选 → 生成一个批次（`CJ20261020-01`）→ 可按批次追溯。两条现场规则：

1. 同一户 **7 天内催过默认不打勾**（服务端也要拦），否则一天三条短信；
2. **只催不收** —— 谈成了引导到小程序缴费或收银台。

## 三之二、OA：一线也能发起，不只是"待我审批"

后台第 50 批给了 6 类单据（用车 / 报销 / 请假 / 加班 / 用印 / 采购），字段是**描述驱动**的。
员工端原来只有审批、没有发起 —— 一线要请假只能回办公室。

现在：审批列表顶部「发起申请」→ 选类型 → 表单由 `OA_FORM_DEFS` 生成（text / textarea / number / money /
date / datetime / select / file）→ 底部实时显示**审批路径**（节点 + 审批人 + 时限，金额变化会改级数）→ 提交。

三个细节值得说：

- **日期给「今天 / 明天」**：现场两下点完，不用在日历里翻（园区巡检场景，手机常在手套里）。
- **预览与结果必须一致**：`oaPreviewFlow` 内部按 `currentOperator()` 解析审批人，所以预览要**临时切到本人角色**再算，
  否则会出现"预览写周建国、提交后变陈瑞"。切角色放在 `watch` 里做，不能放 computed —— 求值中改响应式状态会重入，实测把页面卡死。
- **没审批权也能进 OA**：原来整页被 `f.approval.handle` 挡住，现在权限门只挡「待我处理 / 我办过」两个页签，
  「我发起」对全员开放。

## 三之三、业主标签与租户管理（楼管的两个高频动作）

**业主标签**（`ownerTags` 12 个 / 启用 11 个 / 350 位业主已打标）：房屋页业主卡直接显示标签，
点「调整」按「关怀 / 风险 / 价值 / 行为」分组多选，**点一下即生效**（失败如实报错，例如标签已停用）。
字典的增删改留在 PC（要 `e.ownerTags.edit`，楼管没有）。

**租户档案**（`pages/building/tenant`）：楼管本来就有 `a.tenants.edit`，但之前只能看。现在能：
看 5 项核验门槛（姓名 / 手机 / 证件 / 与业主关系 / 居住人数）→ 补资料 → 核验通过或退回 →
录人脸（前置：已核验 + 已实名）→ 标记搬离（释放房屋在住关系、停用人脸、记录保留）。
租金仍然不展示（合同信息属财务 / 项目经理）。

## 三之四、通讯录：同事之间不脱敏

一线最常问的是"这事找谁"。入口两处（工作台宫格 + 我的 → 工具），**不占 tab**。

- 搜索支持姓名 / 岗位 / 部门 / **手机后 4 位**（前台记不住完整号码，但记得尾巴）；
- 部门 chips 只铺**一级 + 二级**，三级班组不铺 —— 手机上展开三层树就没地方看人了；
- 手机号**明文**，与「员工档案」刻意相反：档案里看手机是查隐私，通讯录里看手机就是它的用途；
- 只取在职、只回 7 个字段（不含薪资/证件/银行卡/紧急联系人），15 个角色都有 `c.contacts.view`。

## 三之五、邻里：只接「离开手机做不了」的四件事

**待审闲置 3 条 / 待处理举报 2 条**（本项目口径；PC 全公司是 8 + 4，差的是数据范围）。

- **两个队列不合并**：待审核是「能不能发」，待处理是「发了之后怎么办」，判断依据与留痕要求都不同；
- **审核只到楼栋**：卡片显示「012 栋」，不显示门牌 —— 判断内容是否合规不需要知道具体住哪户；
- **驳回必填理由**：业主会拿着驳回通知来问「为什么」；
- **举报四动作**（忽略 / 仅警告 / 下架并警告 / 封禁 7 天），说明必填；封禁只记处置状态，原型不做登录拦截；
- **活动三态**：报名中 / 待成行 / 已成行都列出来。待成行**不能报名也不能签到**（人可能根本不成行），
  卡片显示「还差 7 人成团」；
- **代报名两处入口、一份表单**：列表卡片在「报名中」状态下多一行「＋ 代报名」（`@tap.stop`，不进详情），
  活动详情底部也有；两者都渲染 `components/EnrollSheet.vue`，校验规则只有一处。
  满员显示灰色「名额已满」；名额不够本次人数在提交前用红字拦；
- **代报名规则**：人数受每户上限、要投保的活动每位出行人都要姓名 + 证件号、同手机号重复报名会被拦；
  现场可勾「已收款」并选现金/扫码 —— 记 `operator` + `paymentMethod`，回 PC 能对上日结；
- **退款金额由分档算**（提前 7 天 100% / 3 天 50% / 当天 0%），页面只展示、不可手改；签到记经办人。

**不做**：邻里任何发布（公告/投票/活动新建）、确认流团（批量退款）、名单导出。

## 三之六、租售：审房源、回电话、留联系方式

**只做三件事**：审挂牌、回看房电话、维护自己的联系方式。发布 / 下架 / 改派 / 导出全部在 PC ——
连函数都没 import，免得有人顺手加个「下架」按钮。

- **审核并入邻里「待审核」队列**，不新增入口；队列**按权限收条目**：客服只看到闲置（无 `a.listings.audit`）、
  楼管只看到房源（无 `n.items.audit`）、项目经理两类都有。工作台的待办数也只数"能办的"；
- **审核页只给四样**：图、价格与描述、房号与楼栋、产权人已核验 ✓。面积户型楼层**连行都不出现** ——
  档案派生的，业主改不了，让楼管在手机上再核一次等于把已做对的校验重做一遍；
- 判断标准一句话：**这张图能不能让陌生人找到这户人家**。驳回给 6 条预设理由 + 补充说明（业主看得到）；
- **看房请求**：卡片带「已等 N 小时」+ 左侧红条；48 小时内一律按小时说（"已等 1 天"读起来像"还好"）；
  一键拨号取详情里的全号（列表脱敏）；拨完就地写结果 —— 只能从「待联系」转出，结果必填；
- **我的联系方式**：微信号 + 二维码，本人自助**无权限码**；不设「是否公开」开关（填了就是愿意展示）；
  手机号不在这里，它只在内部通讯录里。

**取数口径**（`src/api/listing.js` 文件头有完整说明）：读切「全部项目」取全量、再按
`communityId` + `stewardEmpId` 自己收（PC 的 `_lvScopedListings()` 对本部门 / 责任范围会因
`communities` / `houseIds` 为空直接返回空列表）；写切登录人角色，否则经办人记错人。

## 三之七、消息：待办提醒在前，公告按类型分类

一屏公告列表既没有分类也没有"要我干什么"，和公告栏没区别。现在第一个页签是**待办**（有活时也是默认落点），
后面才是公告的类型页签。

### 待办：五个来源，不重写判断

聚合在 `src/api/inbox.js`，**只做索引**——"什么算待办"的规则仍在各域。复述一遍的后果是
"消息里 3 条、进工单页 5 条"，用户不知道信哪个。

| 来源 | 取什么 | 权限 |
|---|---|---|
| 工单 | 抢单池（可抢的付费单）+ 我处理中**已超时**的 | `f.workorders.view` |
| 巡检 | 待执行 + 逾期（`listForTab(name,'todo')` 的 pinned 与 groups 两段都要） | `f.inspect.view` |
| 审批 | 待我处理（`oa.listFor(persona,'todo')`） | `f.approval.handle` |
| 邻里 | 闲置待审 + 举报待处理 | `n.items.audit` / `n.reports.handle` |
| 租售 | 房源待审（逐条）+ 看房待回（**汇总一条**） | `a.listings.audit` / `a.listings.viewing` |

四条关键决策：

- **必须五个来源**。只做工单/巡检/审批的话，楼管登录后待办是 **0** —— 他的活（房源审核、看房回电）
  一条都不在里面，等于这功能对一半身份无效。第一版就是这样，实测才发现。
- **待办不进「未读数」**：顶部两个数字分开（待办 N / 公告未读 M）。要处理的与要阅知的混成一个数会被忽略。
- **待办不做已读**：处理掉就消失。套用公告那套已读逻辑会造出"读了但没办"的僵尸提醒。
- **看房请求汇总一条**，其他逐条：看房的处置是在列表页逐条做的、没有单条详情，
  列 5 个相同入口只会把别的待办挤下去。

每组封顶 5 条 +「还有 N 条」跳到该域列表页，不把消息页拉成一条无限长列表。

### 公告：按类型分类

| 决策 | 依据 |
|---|---|
| 页签 = 全部公告 + 6 类，**只列有内容的类型** | 本项目没有「收费通知」时还摆一个 0 的页签，点进去是空态，纯属让人多点一次 |
| 类型顺序按「影响当下」排 | 停水停电 / 维修施工在前，政策公示在后；PC 的 `NOTICE_TYPES` 是同一组值，只是这里多定了顺序与配色 |
| chips 横向滚动，**不复用 Segmented** | 页签会随身份变成 7～8 项，平分每项约 50rpx，"停水停电"四个字放不下 |
| 未读 = 本地已读集合的补集 | P0 没有已读回执接口，`readNotices` 存本机；**展开即已读**（这个 App 里「看」的唯一动作就是展开） |
| 未读用「左侧竖条 + 圆点」，不只靠加粗 | 一条一条扫过去时，竖条是最容易看到的信号 |

顺带修掉两处口径错误（都是"给员工看了不该看的"）：
- 原来**不过滤 `status`**，草稿 4 条 / 待审核 9 条 / 已撤回 2 条会被下发 —— 这是越权，不是显示问题；
- 原来 `communityId === 本项目` 把 **10 条集团公告**（`communityId` 为空）全过滤掉了，员工永远收不到集团通知；
- `noticeTotal` 数的 `notices.length` = 106 条含草稿，头部「全公司公告总数」这个数字本身就是错的。

现在 P01 员工可见 **28 条**（本项目已发布 21 + 集团 7），6 个类型都有内容。


## 四、这台手机上「权限」是怎么表达的

移动端不是把 PC 菜单缩小，而是**按能力装配**：没权限的模块不出现，直接进 URL 会被权限门挡住并说明原因（`NoPerm` 组件）。

**新增能力位**（PC 的 72 个权限码里没有，已写进契约 `mobile` 标签）：
`c.notices.read` · `c.attendance.self` · `c.payroll.self` · `f.approval.handle` · `f.wo.dispatch` · `f.rectify.recheck`。

**审批「谁能审」**（`src/api/oa.js`，2026-11-04 重写）：**读部门负责人关系表**，不再按岗位名猜。
节点名 → 组织（`客服主管*` → `O-{项目}-T1`，`工程主管验收` → `T2`，`项目经理/部门负责人` → 项目组织）→
`activeLeadersOf(orgId)` 取在期正职；正职空缺落到在期代理；**副职不参与单签**。再叠两条纪律：只看本项目、申请人不能审自己那一单。

**会签**：节点带 `approvers[] + signMode`（单人/会签/或签），详情页显示「会签 1/2 · 全部同意才通过」与名单（姓名·职务·状态）；
一人驳回即整单驳回，其余未签的标「已跳过」。会签节点不给"转办"（会把名单里某个人换掉，语义混乱）。
**移动端不办的节点**（如合同初审）显示"在 PC 端办理"，而不是做成点了没反应。

**整改的三条边界**：责任人本人提交；本部门**组长**可代提交（记录提交人，不冒名）；复核归项目经理 / 品质督导，
且提交人不能自己复核。项目经理**不能**替全项目代提交。

## 七、技术决定（会踩坑的地方）

### 1. `@pc` 只读引用：用 transform 改写，不跟 uni 抢 alias

uni-app 自己注册了 `@/` → 本项目 `src` 的别名，且 Vite 的 alias **先于用户插件执行**，
PC 源码里的 `@/mock` 一定被解析到 `05/src/mock`（不存在）。
做法：PC 的 `.js` 载入后、import 分析前把 `'@/x'` 改写成 `'@pc/x'`；并关掉依赖预扫描
（`optimizeDeps.noDiscovery`，它不走 transform，会在 dev 启动刷红屏）。

### 2. 写操作是「内存态 + 本地缓存」，但钱的口径不靠缓存

- 复用 PC：`submitInspectResult`、`approvalAction`、`submitRectify` / `recheckRectify` / `reassignRectify`、
  `createWorkOrder`、`updateOwnerField` / `updateHouseField`、`feeSummary` / `payrollDetailOf`；
- 移动端新增（PC 没入口，已进契约）：`checkIn`、`claim` / `arrive` / `abandon` / `dispatchTo`、
  `addAddonItem` / `ownerConfirmAddons`、`payByQr` / `hangUp`、`commissionSummary`、批量催缴、`residentsOf`；
- **金额一律由数据层算**：提成用 `labor × rate`，增项按价目 `code` 取值，页面不自己乘一遍。

### 3. `@pc` 字段契约自检（2026-11-04 新增）

`@pc` 是活引用：PC 改字段名/结构时员工端**不会编译报错**，只会在运行时变 `undefined`。
本轮吃到两次（审批从 87 涨到 96、工单类型「入户维修」改名「商业服务」），所以把依赖清单写死：
`src/config/pcSchema.js` 列了 20 条"员工端离不开的字段"，启动时对一遍并在控制台报错；
`npm run check:schema` 走同一套规则，`build:h5` 前自动执行，缺字段直接退出码 1。
清单不 import `@pc`（数据由调用方传入），所以 node 与运行时用的是同一份规则。

### 4. 演示时钟固定 2026-10-20 10:00

mock 的日期都在 9–10 月，用系统当天「今日」「剩余时间」全错。写操作时间戳也落在这天，
避免「11-01 提交、10-20 计划」的怪记录；7 天去重也以它为准。

## 十、移动端的边界（刻意不做）

- **不碰钱**：没有现金收款、日结月结、导出；项目经理/财务只有只读看板；楼管只催不收。
- **不代他人操作**：没有代打卡、代接单、代确认增项、代提交；组长代提交整改会记录提交人。
- **不做配置**：价目、提成比例、模板、计划、报表、组织权限全留在 PC 后台。
- **不做真互评**：员工侧只记「业主配合度」，内部参考、不进业主考核。
- **不展示业主画像**：职业、政治面貌、经济等级、爱好、宠物、负面记录这些字段后台有，移动端一律不读 ——
  现场用不上，且多一个入口就多一处泄露面（2026-11-05 已确认）。
- **不做租户换承租主体 / 批量核验**：换主体要传营业执照影像件，批量核验会变成"点一下核验一整层"；
  移动端一次一户，做的是"核实这套房住的是谁"。
- **邻里不做发布**：公告、投票、活动新建/编辑、确认流团、名单导出全在 PC。移动端只做"看一眼、点一下"。
- **不建标签**：打 / 去标签可以（`a.owners.edit`），建与停用留在 PC（`e.ownerTags.edit`）。
  读启用的标签列表走 `a.owners.view`，**不是** `e.ownerTags.view`（那个码楼管没有，契约里已写死）。
