## 二、三条通用约定

1. **统一信封**：`{ code, message, data }`，`code=0` 成功；失败给五位业务码 + 对应 HTTP 状态。
2. **分页**：`pageNo`（从 1 开始）+ `size`（1..100，越界 400）；响应 `data = { rows, total, pageNo, size }`。
3. **金额**：`number`，单位元，两位小数。不用字符串、不用分。

## 四、假服务不是"随机造数"

常见做法（Prism / MSW 随机响应）只能验证"字段形状"，验证不了业务；这个假服务实现的是**真语义**，因此能提前暴露四类问题：

| 行为 | 为什么重要 |
|---|---|
| 业主列表脱敏、详情明文 | 前端如果拿列表的掩码值去编辑，会把 `138****8001` 存回去——原型里踩过 |
| 越权返回 **403**（不是空列表） | 空列表会让前端以为"没数据"，403 才会暴露隔离逻辑 |
| 退款**冲回账单** | 只给流水打标记的话，欠费报表会少一笔；联调时这是最容易漏的 |
| 批量操作**部分成功** | 一张已缴单让整批失败，业务上不可接受，必须按条回报原因 |
| 核验门槛只有 5 项 | 实名 / 人脸属核验**结果**，若当门槛会让"永远验不过"（原型踩过） |
| 监督任务 NG 必须指定责任员工 | 不指定就归不到人，考核等于白查 |
| 复核退回要把整改项**归零** | 只改状态的话，部门再点一次"提交"就能过，闭环形同虚设 |
| 搬离要**释放房屋的在住关系** | 不释放，那套房永远显示有人住 |

### 第三批（报表快照）· 为什么不是实时算（2026-10-30 拍板）

欠费账龄 / 收缴率 / 部门达标率 **不做实时查询**，一律走跑批快照。三条理由：

1. 账龄 = 统计日 − 到期日，实时算会让同一张表每刷新一次变一个数；
2. 审计要能回答「上个月报表当时长什么样」，实时算答不了；
3. 部门达标率要扫全量巡检明细，实时算会把列表拖到秒级。

契约形态：

```
GET  /reports/snapshots          批次列表（哪天跑过哪张表、失败原因）
GET  /reports/arrears            读快照：楼栋 × 账龄
GET  /reports/collection-rate    读快照：账期 × 科目（分母剔除作废与减免）
GET  /reports/dept-target        读快照：部门 × 周期
POST /reports/recalc             → 202 + taskId（同参数运行中 → 200 + reused=true，幂等）
GET  /reports/recalc/{taskId}    轮询进度；成功后才产出 batchNo
```

每条响应都带 `meta`：`statDate / batchNo / calcAt / dataCutoff / formulaVersion / rowCount / partial / stale`。
没有 meta 的报表接口不算交付——出了数说不清来源等于没数。

### 期次：月报 / 年报（2026-10-30 拍板）

报表先分两类，只有第二类才有「期次」概念：

| 类型 | 报表 | 月报 | 年报 | 能否由日快照累加 |
|---|---|---|---|---|
| 时点型 | `arrears` | 月末那天 24:00 的余额 | 年末那天的余额 | 可以（取那一天） |
| 期间型 | `collection-rate` / `dept-target` | 整月重算 | 整年重算 | **不能**（补录、退款会让日累加 ≠ 整期） |

参数也分两套，别混：

```
时点型：?statDate=2026-10-21 | ?month=2026-09 | ?year=2026     （三选一，给两个 400）
期间型：?periodType=月&period=2026-10  /  ?periodType=年&period=2026
行级过滤用 billPeriod，不要和报表期次 period 撞名
```

年报**拆两张表**：余额走 `arrears` 年视图（时点），发生额走 `collection-rate` 年视图（区间）。
部门年报按全年任务累加后重算比率，**不是 12 个月达标率取平均**。

未月结的期次照样能出数，但 `provisional=true`、`statDate` 落在今天：
**月报＝月结后一次算，当月给试算值**；日快照不标试算（它本身就是那天当时的数）。

批次号：日 `RPT-20261021-01` / 月 `RPT-202610-M01` / 年 `RPT-2026-Y01`。
`meta` 还带 `periodValue`（本期主指标）与 `compare{prevPeriod,prevValue,yoyPeriod,yoyValue}`，
没有上一期时给 `null`——**不要给 0**，0 会被当成"上期是 0 收缴率"。

### 期间关账（月结）· 三条口径先定，接口才有意义

月结不是"点个按钮锁数据"，它背后有三个必须回答的问题。这一版按下面的答案落：

| 问题 | 答案 | 为什么 |
|---|---|---|
| 谁有权结 | `b.monthClose.edit`（财务）。**项目经理没有** | 封账是财务动作。让项目经理封自己项目的账，等于让他自己掩盖欠费 |
| 能不能反结 | 能，走 `e.monthReopen.edit`（更高一级；**刻意在 e 域**，否则财务的 `b.*` 通配会自动授予）+ 必填 ≥10 字原因 | 不允许反结的结果是有人去数据库改数——那才是真正的失控。允许，但要留痕 |
| 结完能改什么 | 该期间流水 / 退款一律 **409 / 40903** | 退款会改上月已封存的收款与欠费，必须「反结 → 改 → 重结」 |

```
GET  /month-closes                  记录列表（含已反结，按期间倒序）
GET  /month-closes/preview?period=  预览：能不能结、欠什么、上月净额
POST /month-closes                  提交 → 201；已结 → 409 / 40904
POST /month-closes/{id}/reopen      反结 → 记录留痕 + 批次作废 + 期间解封
```

反结做四件事，**一件都不能省**：记录置「已反结」并留 `reopenReason` / `reopenCount` / `reversalNo`；
该期间报表批次标 `voided=true`（保留可查，不删除）；期间恢复可写；报表实时回到 `provisional=true`。

两个容易做错的地方：

- `provisional` **必须实时按"该期是否已月结"算**，不能用建批次时存下的值——反结后旧批次仍是那份冻结的数，
  但它已经不是定稿了。状态属于**期间**，不属于批次。
- 反结**不写进退款流水**。反结不是退款，混进去会让「退款金额」统计失真；它有自己的红冲凭证号。

### 批次保留与清理

日快照一天 3 张表，一年 1000+ 批次，不设保留策略下拉框和索引都会被拖垮。但也不能随便删：

| 粒度 | 默认保留 | 理由 |
|---|---|---|
| 日 | 90 天 | 日常核对用 |
| 月 | 24 期（2 年） | 年度审计要看前两年月报 |
| 年 | **永久** | 年报是最小粒度的历史凭证，删了等于抹账 |

**已月结期间的批次一律受保护**——审计要能回答「那个月报表当时长什么样」，而月结正是"当时"被确认的时间点。
受保护数量单独计（`protectedClosed`），不混进 `expired`：混进去会表现成"怎么清都清不干净"。

`POST /reports/purge` 带 `dryRun`（首次上线前先看会删什么）且**幂等**（第二次 `removed=0`）。
清理任务必须能无条件重试，否则失败一次就没人敢再跑。

**实测（假服务）**

```

dryRun      removed=6（7-15 / 7-16 各 3 张表），跑完老批次仍可读
真清理      removed=6 → 7-15 批次 404/40402；10-19 仍在；再跑 removed=0
收紧参数    keepDays=1 / keepMonths=1 → keptProtected=12；
            9、10 月（已月结）仍在，8 月（已反结）可清
```

### 合同与公告 · 两条状态机口径

**合同：变更是独立单据。** 改金额、改期限、提前终止都不直接改合同，而是生成 `ContractChange`
（`before` / `after` 快照）进审批，通过才回写。直接改合同的话——谁在什么时候把 30 万改成 50 万，永远查不出来。

```
GET  /contracts                列表（vf 服务端算：pending/expiring/expired/big/group/changePending）
GET  /contracts/summary        KPI，与列表同一套谓词
GET  /contracts/{id}           详情（ref 按 refType 带出；断链给 null，不让详情页 500）
POST /contracts                新建（单号服务端生成，前端传了也忽略）
POST /contracts/{id}/changes   发起变更 → 201；已到期/终止 422；已有变更在审批 409/40906
```

两条容易做错的：

- **`expiring` 用状态不用天数**。样例里「即将到期」是按 90 天标的（62 天的也在里面），
  前端如果按 30 天重算，会和服务端差 6 条，而没人说得清谁对。
- **`phone` 列表与详情都掩码**。合同相对方是个人时就是个人信息。

**公告：状态机单向。** 草稿 → 待审核 → 已发布 → 已过期；已发布可撤回，撤回后要重新提交审核。

```
GET   /notices                 列表（vf：pending/published/expired/top/lowRead）
GET   /notices/summary         avgReadRate 只统计已发布
POST  /notices                 新建 → 只能是「草稿」，发布是独立动作
PATCH /notices/{id}            已发布不能改内容（409/40907）——业主看过了，改了等于篡改留痕
POST  /notices/{id}/publish    已发布/已过期不能再发（409/40908）——重复点，业主收两条一样推送
POST  /notices/{id}/repush     补推未读（只推没看过的人）；没有未读 → 422，不静默成功
POST  /notices/{id}/withdraw   要原因；**已读不清零**——业主确实看过，抹掉就是伪造
```

**实测（假服务）**

```
合同   85 条 · 总额 15,671,445.18 · 履行中 35 / 即将到期 7 / 已到期 28 / 待审批+待生效 9
       电话 175****1790 · 详情 ref 断链给 null · 变更 201 后合同金额不变（changePending=true）
       重复变更 409/40906 · 已终止 422 · 前端传的单号被忽略

## 六、后端（Java / Spring Boot）接入提示

1. **枚举直接映射中文值**：`@JsonValue` 返回中文，`@JsonCreator` 按中文反序列化；不要另造英文 code
   （否则前后端各存一套，必然分叉——原型里 `部分缴 / 部分缴费`、`入场 / 进场` 已经分叉过两次）。
2. **数据范围在 Repository 层强制**：不要在 Controller 里判断，也不要依赖前端传；越权返回 403，不是空集。
3. **敏感字段在序列化层统一脱敏**：列表接口只回掩码，别指望每个接口自己记得脱敏。
4. **退款是一个事务**：退款单 + 流水累计 + 账单回落 + 发票红冲，四步要么全成要么全不成。
5. **SLA 由服务端算**：工作日历（9–18 点、跳周末与节假日）、「待确认」停表，前端只展示
   （前端也有实现，但只用于原型；上线后以服务端字段为准，避免两套算法）。
6. **乐观锁**：行上带 `_ver`，`PATCH` 回传，冲突 409/40901。
7. **验收就用 `npm test`**：把 `04-契约` 挂进 CI，指向你的服务地址即可（把 `mock-server` 的 `startServer` 换成外部 base）。
8. **核验 / 复核这类"责任动作"要和编辑分开授权**：`a.tenants.verify`、`f.rectify.edit` 不应和改备注同级。
9. **整改复核要记复核人**：提交人与复核人相同必须拒绝（原型里已有这条守卫，别在后端丢掉）。

## 七、已知限制（别指望这一版覆盖全部）

- 覆盖 **12 个域 64 个接口**（新增合同台账与公告通知）；品质**评价录入**、组织与权限（含**权限变更日志**）、
  员工与工资、其余报表仍是原型 mock——这几块牵涉企业自定义流程，等实际客户口径定了再进契约。
- 报表只进契约了 3 张（欠费账龄 / 收缴率 / 部门达标率）；费用明细、押金、报修、巡检、主管发现数仍是「实时查明细」，
  要不要也改成跑批，等后台给出跑批窗口与存储成本再定。
- 报表快照按**天**粒度；月报/年报需要再定 `statPeriod`，当前契约没有。
- 假服务把状态存在**内存**，重启即还原（这是刻意的：它是规格，不是数据库）。
- 契约里的枚举值是**中文**；若后端强要求英文常量，用 `enums.json` 生成映射层，前端不用改。
- 没有分页游标、没有幂等键、没有限流；这些属于第二批（契约里已留了错误码位置）。
- `contract-test.mjs` 是**黑盒**测试（打 HTTP），不含单元测试；后端自己的单测仍需写。

### 员工域（人事口径，不含薪资）· 三条刻意为之的取舍

**① 薪资不在这里。** `baseSalary / monthlySalary / bankCard` 属工资域（`c.payroll.view`）。
混进人事档案的结果是：能看到员工列表的人，就能看到全公司工资。详情里 `related.payrollRecords`
给 `null` 不给 `0`——0 会被读成「有工资条但一条都没生成」，与「本域不管这事」是两码事。

**② 角色不存员工表。** 由岗位反推（`roles.positions`），人工调整写一层覆盖
（`roleSource: position | override`）。角色存进员工表的结果是：改一次岗位要手工改一遍权限，
两边还会长期不一致。**调岗必须清掉覆盖**——人已经去工程组了，系统还让他批客服的假，就是这条没做。

**③ 离职即收权。** 离职员工 `roleId` 为空、`assignable=false`、不能调角色（409/40910）。
人走了权限还在，是最常见的一类越权。

组织归属拆两个字段：`homeOrgId`（人事档案上存的项目部）+ `orgId`（岗位反推出的班组 / 职能部门）。
合成一个字段的话，班组调整会顺手改掉档案归属，人力对不上花名册。

**实测（假服务 + 页面）**

```

否则这个隔离永远没有反例可验。

### 工资域 · 状态机比字段重要

**工资条是核算快照，不是查询结果。** 每月生成一批、核算后冻结金额。实时算的结果是同一个人
今天看 11,058.98、明天补录一条加班就变 11,120.31，员工截图来问"为什么少了 62 块"时，
谁也说不清哪个对。

```
草稿 →（核算锁定）已核算 →（提交发放）待发放审批 →（审批通过）已发放 →（冲正）已冲正
                        └──（驳回）已核算
```

三条硬规矩：

| 规矩 | 不这么做会怎样 |
|---|---|
| **金额只由服务端算**（`grossPay` / `deductionTotal` / `netPay`） | 页面各加一遍 → 列表一个数、工资条一个数、汇总又一个数 |
| **已核算后金额不可变**（409/40913） | 发一次钱、记两本账 |
| **提交人不能审批自己的发放单**（409/40915） | 一个人既能核算又能批准，"谁批的"永远写的是同一个人 |

另外两处：

- **`dataScope=仅本人` 只回自己那一条**（不是下发全表让前端藏）。工资表最容易被做错的就是这一步：
  列表给全量、前端按权限隐藏——等于没做。样例里专门加了 `staff` 账号（EM0020 / 仅本人）来守这条。
- **已冲正的行不进 `netTotal`**，单列 `reversedCount` / `reversedAmount`。冲正的钱已经退回去了，
  还算在实发里就是账上凭空多一笔。

**实测（假服务 + 页面）**

```

            行里没有 bankCard / phone / idCard —— 工资域不是员工档案的后门
汇总        应发 836,324.18 − 代扣 81,817.35 = 实发 754,506.83（与行加总一致）

> **实测踩到的两个坑**：
> ① 页面 mock 是内存态，**切角色必须在同一个页面内切**（顶栏下拉）。新开页面 = 刷新 = 状态回到种子，
> 我第一版测试用 `page.goto` 换角色，看到的是"审批通过后又是草稿"。

### 组织与权限（纯 RBAC）· 提权要批、降权即时

**权限只挂角色，人只挂角色**——没有"给某人加一个权限码"这种接口。逐人授权的系统最后
没人说得清"谁到底能干什么"。员工那侧通过"岗位 → 角色"反推，人工调整写覆盖。

保存矩阵的三条分支（服务端自己算 diff，前端只提交保存后的完整集合）：

| 情况 | 结果 |
|---|---|
| 与保存前完全一致 | 200 `noChange=true`，**不写日志**（原样保存也记一条 → 日志里全是噪声） |
| 新增命中高敏白名单 | **202，不生效**，生成 `PermRequest` 等审批 |
| 纯降权 / 普通新增 | **200，立即生效**并记 diff |

高敏五类：`a.sensitive.view`（看证件明文）/ `e.monthReopen.edit`（推翻封账）/
`e.org.edit`（改权限本身）/ `c.payroll.edit`（改工资表）/ `a.stewards.edit`（改责任范围）。
共同点是「拿到就等于能自己扩权或掩盖问题」。

**双人原则**：提交人不能审批自己提交的申请（409/40917）。自己提自己批，等于没有审批，
而且日志里还会留下一次"审批通过"的假象。

**日志是追加写 + 哈希链**：访问/导出日志每条带 `hash` / `prevHash`，任何一条被改动，
链上后面全对不上。没有这个，「谁在什么时候看了谁的证件号」这条记录本身就可以被删掉。

**实测（假服务）**

```

角色详情    matrix 3 层（域→功能→操作）· GM 持有全部 5 类高敏 · 楼管也持有 a.sensitive.view

> **反向发现的一处授权基线问题**（没改 seed，记录在案）：14 个角色里有 **10 个**都持有
> `a.sensitive.view`，包括客服专员、收银员、楼栋管家——只有工程维修、品质督导、环境保洁、
> 秩序维护员、只读观察员没有。也就是说"敏感字段明文"这个权限位在样例里基本是默认发出去的。
> 契约把提权路径收紧了，但**基线本身太宽**：真接后台要按最小权限重排一遍，
> 否则审批流拦的只是"从一个已经很宽的口子再加一点"。

### 10.3 两处脱敏口径相反，别统一

- `ownerPhone`：列表脱敏、**详情给全号**（审核要打给业主）；
- `phone`（看房请求）：列表脱敏、**详情给全号**（楼管要打这个电话）。

一句话：会被投屏的页面不摆全号，需要操作的场景才给。

`POST .../viewings/{id}/contact` 是这套设计的落点：**只能从「待联系」转出**（重复标记 409/40942），
**结果必填**（422）。不写结果的话，同一个访客会被三个人各打一遍电话，
而访客记住的是"物业老打电话"。手机端是唯一入口 —— PC 那页只做"谁超时了"的监控。

1. **投票不给结论。** 没有 `passed`，连 `conclusion: ''` 这种空壳也删掉了

   《民法典》278 条决议来主张的成本，比少一个字段大得多。
2. **参与率分母取 `max(应投户数, 票数)`。** 种子票数是独立随机的，出现过 310 票 / 189 户。

3. **流团只发生在收费活动。** 公益没有成团下限（`minCapacity = 0`），报名截止后

（敬老 / 亲子 / 文体 / 出游）。两套含义挤在一个字段里，所以列表上会同时出现

| 字段 | 值域 | 来源 |

| `feeType` | **免费 / 收费** | 由 `fee > 0` 派生，不落库 |

两个维度同词必然有人填错。这也让语义变成正交 —— 公益类别的活动完全可以是收费的

### 11.15 刷脸通行四件套（批次 83 · 2026-11-10）

| 接口 | 用途 |
|---|---|
| `GET /mp/access/faces` | 本人 + 本房成员的人脸状态 |
| `POST /mp/access/faces` | 提交本人（进待核验） |
| `POST /mp/access/faces/members/{memberId}` | 帮已核验的家庭成员提交 |
| `POST /mp/access/faces/{faceId}/withdraw` | 撤回（置为已冻结，保留记录） |

**模型：申请单是唯一真相，`members.faceStatus` 是它的投影。**
五态里「未采集」**不落记录** —— 没有申请单就是没采集。为"字段齐全"造一条空记录，
后面每个查询都要额外判断"这条算不算数"，迟早有人判错。

三条边界，都是"责任"而不是"权限"：

- **家属只能录本人**：走 me 语义，不下发也不需要 `memberId`。家属之间是平级关系，
  让他替配偶录脸，等于给了他一把能开门、也能给别人开门的钥匙。
- **未核验成员不能代录**（40934）：没核验就录脸，等于填个名字就能给别人开门。
  成员登记页那个"待核验"就是为了卡这一步。
- **业主端不能自助生效**：接口里**没有任何**"直接置为生效"的参数，包括看起来
  人畜无害的 `autoApprove`。生效只能由物业核验触发（后台 H4 的面核工作台）。

三条限次：待核验期间不能重复提交（40932，审核人正在看那张照片）、
24 小时最多 3 次（40933）、撤回后置「已冻结」且不能重复撤回（40935）。

**重新采集时旧人脸继续有效**，这句话由服务端写进 `note` ——
不写，业主会以为"我现在刷不了门了"，而他要赶着上班。

合规口径写在 description 里并落到页面上：单独同意、用途、存储期、可撤回。
原型不存真图，`images` 只记张数。撤回的表述是「门禁停用、影像件 30 天内删除」，
**不承诺"立刻"** —— 闸机同步有时间差。

### 11.16 公共报修：不是"少选一项"，是两条线本来就不同（2026-11-11）

`POST /mp/orders` 原来把 `priceCode` / `appointDate` / `appointSlot` 全列为 required，
两条线一个标准。看似严谨，实际逼着业主给"电梯异响"先挑一个**收费项目**再免费处理。

翻数据才发现契约比数据模型收得更紧：

| 后台 75 张公共单 | 事实 |
|---|---|
| `priceCode` / `serviceName` | **75 张全是空** |
| `appointAt` / `appointSlot` | **0 张有值** |
| `category` | 部位（电梯 18 / 给排水 16 / 门窗五金 12 / 土建 11…），不是价目分类 |

所以这次是**把契约放宽到与数据一致**：

- `priceCode`、`appointDate`、`appointSlot` → 只在 `scope=personal` 时要求；
- public 改要求 `place`（必填、≤40 字、**允许自由文本**）+ `description`；
- public 新增可选 `category`，不传按「公共设备」处理。

**`category` 的语义在 2026-11-12 又改了一次：从「部位枚举」改成「业主写的原文」。**

改了两轮才定下来：

1. 先要求业主端给一行 7 个「部位」chip —— 太硬，业主不会把"电梯运行到 6 层会顿一下"
   翻译成「电梯」；
2. 再改成让业主自由输入 —— 位置对了，但**类型让业主白写等于放弃派单口径**；
3. **最终：端上做下拉（7 个固定项 + 「其他」手写），服务端仍按自由文本收。**

固定项与 `LABOR_POINT_RULE.weights` 的键一一对应（电梯 1.5 / 公共设备 1.4 / 配电 1.3 /
给排水与道闸门禁 1.2 / 土建 1.1 / 公区照明与门窗五金 1.0），点一下就是标准值；
列不进去的用「其他」写原文，前台受理时归类。

服务端为什么**不跟着做白名单**：后台代下单、老版本客户端都可能传别的值，
拒掉只会让一笔真实报修进不来。代价是 `laborPointWeight()` 取不到就落默认 **1.0** ——
这是可接受的，比丢掉一张单好。

校验只有三条：长度 ≤20、空值落「公共设备」、**不做白名单**。

服务端同步改了两处容易漏的：

1. **标题**：原来是 `${位置} · ${price.name}`，不给项目就变成 `1栋大堂 · undefined`。
   现在公共单是 `${位置} · 公共区域报修`。
2. **价目字段**：`serviceItemCode / serviceName / priceCode / priceName` 公共单一律空串，
   `priceQty = 0` —— 与后台公共单的既有形态一致，05 与 03 不用为它加特例。

用例 `公共报修：只给位置与描述就能下单` 钉住九件事：不传价目能下单、价目字段为空、
免费、不生成支付单、类型原文落库、标题不含项目名、位置必填且限长、
**以及个人单缺价目仍然 422**（放宽 public ≠ 两条线都不校验）。
2026-11-12 又补三条：不填类型落「公共设备」、类型超 20 字 422、传标准部位原样保留。

### 11.17 预存账户与商业账户：两笔钱，两个入口（2026-11-11）

> ⚠️ **这一节整体已过期，留作决策记录**：物业预存账户体系在 2026-11-13 下线
> （`/mp/prepay`、`/mp/prepay/recharge`、`/mp/prepay/deduct` 三条一并删除），
> 原因见 §11.18。现在只有「商业平台账户」还活着，且仍是只读镜像。
> 下面关于预存的描述只说明**当初为什么这么设计**，不要照着实现。

业主端一直缺"我账户里有多少钱"。补的时候才发现系统里有**两种**账户，
而它们不是一件事 —— 混成一个"余额"，业主第一个问题就是"能不能交物业费"。

| | 物业预存（`/mp/prepay`） | 商业平台账户（`/mp/commerce/account`） |
|---|---|---|
| 钱是谁的 | 物业的预收账款 | 商业平台的储值 |
| 能干什么 | 抵**本房**账单（物业费 / 水费 / 电费 / 车位费） | 积分、优惠券（领了去平台花） |
| 能不能抵物业费 | 能 —— 它就是干这个的 | **不能**，接口连 `balance` 都不给 |
| 谁在写 | 业主端可充值、可抵扣；后台可代充与人工抵扣 | 只读镜像，物业侧一个字都不写 |

`GET /mp/prepay` 的三个刻意设计：

1. **按房取，不汇总**。账户挂在 `houseId` 上，多房业主有两个账户、两个余额。
   汇总等于把 A 房的钱算到 B 房头上，抵扣时必错。
2. **没开户不是 404，是「未开通」**。样例里 249 个有表具的房只有 126 个开户，
   这是常态。返回 404 会逼客户端为一个正常场景写特例。
3. **待抵账单按账期升序**。业主说的"欠了三个月"是三张账单，
   先还早的，逾期天数才降得下来。

`POST /mp/prepay/deduct` 的两种语义：

- 不传 `billIds` → 用余额**尽量抵**，抵到用完为止（最后一张可只抵一部分，账单变「部分缴」）；
- 传 `billIds` → 只抵这几张，余额不够直接 422/42213，**不做半途而废**。

抵扣与销账在同一个函数里完成（写流水 → 改 `unpaid` / `status` / `payMethod=预存抵扣`）。
拆开就会出现"扣了余额但账单还欠着"。

**营销位先留、规则不做**：充值请求可带 `campaignCode`，响应有 `gift` 字段，
但服务端**恒返回 null**。写一个假的"充 500 送 20 元券"只会在对接运营系统时多一轮排查；
字段先占住，将来后台配好活动、`gift` 一填，客户端不用改。

`/mp/commerce/account` 是**镜像**：带 `syncedAt`、不带 `balance`、券带 `claimUrl`。
领取与核销都在商业平台 —— 物业端替它记账就是越界，而且明天一定对不上。

fixtures 用 `scripts/gen-account-fixtures.mjs`：16 个预存账户（15 个投影 + 1 个演示种子）、
5 条流水、1 份商业镜像。脚本会校验「流水最后一行余额 = 账户余额」——
这也是页面唯一能自洽的凭据。

### 11.18 水电改账单缴费，预存账户下线（2026-11-13 · 批 3 端上侧）

客户的原话是「预存的钱算公司收入不合理」。这不是文案问题 —— 三笔账混在一起了：

| 混在一起的三笔 | 实际是什么 | 现在 |
|---|---|---|
| 业主交的钱先进"余额" | 预收款 = **负债**，不是收入 | 取消，交多少记多少，钱与账期一一对应 |
| 水费电费按"充值买量"收 | 计量收费：用量 × 单价 = 应收 | 抄表出账 → 待缴账单 → 缴费 |
| 余额抵扣物业费 | 一笔钱抵两笔应收，账龄就乱了 | 取消，物业费按账期收、水电按账单收 |

**`/mp/prepay`、`/mp/prepay/recharge`、`/mp/prepay/deduct` 三条一并删除**
（配 10 个 `MpPrepay*` schema）。留着"只是不用"比删掉更危险 —— 下一个人会以为它还能用。
fixtures 里的 `prepay-accounts` / `prepay-flows` **保留**：后台「预存清退」要看历史流水。

新增 `GET /mp/utility`，返回本房水、电两块表。**能不能缴由项目模式决定，不由有没有账单**：

| mode | 端上 | `canPay` |
|---|---|---|
| `meter` | 用量 / 单价 / 应缴 / 账期 / 账单号 + 去缴费 | `true`（有未缴账单时） |
| `card` | 「插卡表 · 到物业服务中心买量」 | `false` |
| `none` | 「由国家电网 / 自来水公司直接收取」 | `false` |

P03（星光天地）就有一张**电费逾期单**，而它的电是 `card` —— 这正是那条规则的试金石：
只看"有没有账单"会给插卡表一个支付按钮，等于替它代收。用例把这条钉住了。

三个实现细节，都是踩过的：

1. **账单字段"缺省"而不是 `null`。** 没有账单时不返回 `price/usage/amount/period/billId`，
   不是给个 `null`：契约校验器不认 nullable，直接判 schema 失败；而且"系统里没有这个数"
   本来就该用缺省表达。
2. **金额以账单为准，端上不自己乘。** 水电 fixtures 里
   `用量 × 单价 ≠ 金额` 的单子有一大批（1327 张里 903 张不吻合，滞纳金与阶梯价）。
   端上自己乘一遍，就会和账单对不上 —— 用量与单价只用来解释"这个数怎么来的"。
3. **项目从房屋取，不从表具反推。** 插卡表（`card`）压根没有远传表记录，
   按 `meter.communityId` 反推会拿到空串、模式落 `none` —— P02 的水会被当成"业主自缴"。
   这条在 04 的实现和 06 的 `check:data` 里各修了一次。

fixtures 用 `scripts/gen-utility-fixtures.mjs`（幂等，带闭合自检）：
`community-utility` 3 条（项目模式）、`meters` 406 条（都是 03 里有、且房屋都在 fixtures 里的）；
另外给 P03 唯一有业主的 H030110205 **取回** 5 张被 `gen-fixtures` 切掉的真实账单
（原样照抄，不造数），否则那一套房在 04 里是空壳，端上三态演示不全。

**业务码清理**：`40936` 原本被"预存账户状态"占用，但它同时是"抢单池只收商业服务单"的码 ——
预存下线后这个冲突自然解开，码表里改成抢单池的含义。

### 11.7 业主认证落地（批 A · 2026-11-08）

`/mp/*` 之前是"设计态"（契约写了、服务没实现），业主端直读 fixture 能跑，但**实名比对在前端**：
等于把整份业主档案发给每个客户端。批 A 把这条链路搬到了服务端。

| 接口 | 现在做什么 |
|---|---|
| `POST /mp/auth/wechat-login` | 按手机号在 **owners / members / tenants** 三张表里找，返回身份与可绑房产；**不返回姓名与证件** |
| `POST /mp/auth/realname` | 只收姓名 + 后四位，存进会话，不落库完整证件号 |
| `GET /mp/auth/bindings/candidates` | 三项比对（手机号 / 姓名 / 证件后四位）+ **房归属**，四态 `mismatch` 逐位给 |
| `POST /mp/auth/bindings` | **重算一遍**候选再校验，不在名下的房 403（不能"绑上了再看"） |
| `GET /mp/me` | 身份 + 已绑房产 + 首页三个数（待缴含"本人名下不挂房的车位费"） |

三处口径写死在代码里：

1. **身份以档案为准**，不取用户自选的那个 —— 家属选了「业主」也按家属生效，业主端要把这句提示出来。
2. **三类人都有 `ownerId`**（家属挂在业主上、租客也记着业主），所以不能用 `ownerId` 区分身份，
   必须看各自的专属字段（业主 = houseIds、家属 = memberId、租客 = tenantId + houseId）。
3. **`mismatch.house` 单独一位**：三项全对但房不在名下（买了没过户、档案漏录），
   和"名字填错"要给完全不同的提示 —— 这是人工审核里最常见的一类。

新增 fixture：`members.json`（13 条，从 02 的 169 条里裁到已导出的 60 位业主名下）。
生成器：`node scripts/gen-members-fixture.mjs`。

**已知限制**：`work-orders.json` 里没有 `addons` 字段，所以 `/mp/me` 的 `pendingAddons` 恒 0，
业主端首页"待确认 0 项"在接口模式下是**真实但空**的数（本地模式有演示数据）。
批 C 补增项数据时要把这条测试从 `eq(..., 0)` 改成 `> 0`。

（houses **220** 套、业主带 `tagIds`、房屋带 `orientation`），而 `gen-fixtures.mjs` 现在的切片是
`houses.slice(0, 160)`。整目录重跑的后果是 bills / tenants 里指向 161~220 的房屋全变孤儿，
"张建国的两套房"直接查不到。缺字段写增量脚本（先例：`gen-members-fixture.mjs`、
`gen-tenant-rent.mjs`、`gen-pricing-fixture.mjs`），这条已写进脚本头部。

**一条种子数据问题**（不修，先记）：`BL000130` 状态=`已减免` 但 `unpaid` 仍是 263.12
（`02/seed_dataset.py:439` 随机挑状态，但金额没跟着清零）。接口按**状态**判欠费，
所以它不进欠费合计；但账单明细里仍挂着未收金额。真实环境不会有这种数据，
样例里留着是为了让"按状态判还是按金额判"这条守卫有东西可钉。

## 十一、后台侧收尾接口（2026-11-11）

> 起因：H1/H2/H4/H5 四个功能在 03 都做完了，**契约里一条都没有**。
> 而业主端早就能提交人脸（`/mp/access/faces`）、能自助换绑（`/mp/parkings/{id}/plate`）——
> 提交了没有接口受理，正是 H4 当初要解决的那个毛病。这组补的是**受理侧**。

### 11.1 三组接口

| 组 | 路径 | 权限 |
|---|---|---|
| 系统参数 | `GET /system/params`、`PATCH /system/params/{key}` | 仅登录 |
| 车位换绑 | `GET/POST /parkings/{parkId}/changes`、`POST .../changes/reset` | `a.vehicles.view` / `.edit` |
| 人脸核验 | `GET /access/faces`、`GET /access/faces/stats`、`POST /access/faces/{faceId}/audit` | `a.owners.view` / `.edit` |

系统参数**故意不设权限码**：03 的 `/e/config` 本来就没有页面级权限，为两个接口去编
`e.config.*` 要同步 03/02 的 permissions、roles、seed 四处，不值当。要拆时再加。

### 11.2 三处口径

**① 日志是唯一真源。** `POST /parkings/{id}/changes` 写日志的同时改 `parkings.plateNo` 与
`vehicles`。只写日志不改车位，详情页就会出现"记录写着换成 A、车辆还是 B"。

**② 人脸申请单是唯一真相。** `owners.faceRegistered` / `members.faceStatus` /
`tenants.faceRegistered` 都是它的投影，由 `audit` 写。驳回**不动**已有的人脸 ——
重新采集期间原人脸继续有效，否则业主会以为自己这会儿刷不了门。

**③ 驳回必填原因。** 三条写入接口（换绑、重置、驳回人脸）都强制 422 ——
原因会原样展示给业主，只写"不合格"等于让他猜。

### 11.3 两次踩到的坑

**时间戳要精确到秒。** 客服同一分钟内连办两笔换绑，分钟粒度的时间戳相同，
排序就退回成"谁先插入谁在前"，看上去像记录乱序 —— 契约测试也偶发失败。
现在 `at` 到秒，且排序用 `logId` 兜底。

### 11.7 押金 fixture：12 条合成 → 352 条真实台账投影（2026-11-14）

`/deposits` 原来在 `mock-server.mjs` 里**现场造** 12 条：取前 12 套房、类型轮换、退款按下标取模。
接口能跑通，但三件事说不清 ——

1. 报表「押金在账」算出来的余额和 03 的真实台账没关系，数字对不上；
2. 分页（`size` 上限 100）与按类型 / 状态筛选只有 12 条可玩，翻不出边界；
3. 恒等式 `收 = 退 + 扣 + 在账` 成立，但成立得很假（金额全是标准额）。

改为投影 `03-原型/src/mock/decorationDeposits.json`（352 条），生成脚本
`scripts/gen-deposit-fixtures.mjs`，按 `Deposit` schema 做字段白名单：

- 多出来的 `houseName` / `ownerName` / `phone` / `overdueDays` 是页面展示用的，契约里没有，**不传**；
- `quantity` 03 没有，补 1；
- 日期 null 只允许 `checkDate` / `refundDate`（其余统一 `''` —— schema 不认 nullable）。

**落盘前两道自检，不通过就非零退出**（宁可没数据，不留脏数据）：逐条恒等式、
`houseId` / `ownerId` 对 houses / owners fixture 查孤儿。

结果与 03 逐字段相同：352 条，收 ¥1,619,548 / 退 ¥877,438 / 扣 ¥76,473 / 在账 ¥665,637。

`DP_SEQ` 一并改：原来接 `DEPOSITS.length` 发新编号，而 fixture 的 DP 号是打散的（1..352 不连续），
