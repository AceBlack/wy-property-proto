## 二、三条通用约定

1. **统一信封**：`{ code, message, data }`，`code=0` 成功；失败给五位业务码 + 对应 HTTP 状态。
2. **分页**：`pageNo`（从 1 开始）+ `size`（1..100，越界 400）；响应 `data = { rows, total, pageNo, size }`。
3. **金额**：`number`，单位元，两位小数。不用字符串、不用分。

错误码：

| code | HTTP | 含义 |
|---|---|---|
| 40001 | 400 | 参数错误（分页越界、枚举非法、必填缺失） |
| 40101 | 401 | 未登录 / 令牌过期 |
| 40301 | 403 | 超出数据范围 |
| 40400 | 404 | 接口不存在 |
| 40401 | 404 | 资源不存在 |
| 40402 | 404 | 该期次没有成功批次（报表专用；空表与「没跑过」必须能区分） |
| 40903 | 409 | 该期间已月结，数据只读（退款 / 补录一律拒） |
| 40904 | 409 | 该期间已月结，不能重复提交 |
| 40905 | 409 | 该记录已反结，不能重复反结 |
| 40901 | 409 | 版本冲突（乐观锁） |
| 40902 | 409 | 唯一约束冲突 |
| 40906 | 409 | 该合同已有变更在审批中（先处理那一单） |
| 40907 | 409 | 已发布的公告不能修改（先撤回） |
| 40908 | 409 | 当前状态不允许发布 |
| 40909 | 409 | 当前状态不允许撤回 |
| 40910 | 409 | 离职员工不能调整角色（先恢复在职） |
| 40911 | 409 | 该员工已是这个角色（无需处理） |
| 40912 | 409 | 该期工资表已存在（重算需 overwrite=true） |
| 40913 | 409 | 工资已锁定（已核算 / 已发放），不能重算（先冲正） |
| 40914 | 409 | 当前状态不允许该动作（看状态机） |
| 40915 | 409 | 提交人不能审批自己提交的发放单（换人审批） |
| 40916 | 409 | 同一角色已有相同内容的提权申请在审批中（等那条） |
| 40917 | 409 | 提交人不能审批自己提交的权限申请（换人审批） |
| 40918 | 409 | 申请状态不允许该动作（看状态） |
| 42201 | 422 | 业务校验失败（原因必填、金额超限、状态不允许） |
| 50000 | 500 | 服务异常 |

## 四、假服务不是"随机造数"

常见做法（Prism / MSW 随机响应）只能验证"字段形状"，验证不了业务；这个假服务实现的是**真语义**，因此能提前暴露四类问题：

| 行为 | 为什么重要 |
|---|---|
| 业主列表脱敏、详情明文 | 前端如果拿列表的掩码值去编辑，会把 `138****8001` 存回去——原型里踩过 |
| 越权返回 **403**（不是空列表） | 空列表会让前端以为"没数据"，403 才会暴露隔离逻辑 |
| 退款**冲回账单** | 只给流水打标记的话，欠费报表会少一笔；联调时这是最容易漏的 |
| 批量操作**部分成功** | 一张已缴单让整批失败，业务上不可接受，必须按条回报原因 |
| 核验门槛只有 5 项 | 实名 / 人脸属核验**结果**，若当门槛会让"永远验不过"（原型踩过） |
| 监督任务 NG 必须指定责任员工 | 不指定就归不到人，考核等于白查 |
| 复核退回要把整改项**归零** | 只改状态的话，部门再点一次"提交"就能过，闭环形同虚设 |
| 搬离要**释放房屋的在住关系** | 不释放，那套房永远显示有人住 |

## 五、和前端适配层怎么配合（已端到端跑通）

前端已经有 `03-原型/src/api/`（与 `utils/api.js` 同签名的适配层）：

```bash
cd 03-原型
VITE_API_MODE=http VITE_API_BASE=http://127.0.0.1:4010 npx vite --port 5175
```

此时 `src/api/*` 里的调用会走真 HTTP（页面仍然 import `utils/api` 的域不受影响，可**按域灰度**）。

令牌处理在 `src/api/client.js` 里：`login()` 拿到 tokens 后写入 `localStorage.wy_api_token`，
后续请求自动带 `Authorization: Bearer`；401 会**清令牌**（否则页面会拿过期令牌反复重试，看起来像"没数据"）。
不做自动刷新——刷新涉及并发与竞态，留给真实登录流程，避免"看起来能用、实际会串号"。

### 第三批（报表快照）· 为什么不是实时算（2026-10-30 拍板）

欠费账龄 / 收缴率 / 部门达标率 **不做实时查询**，一律走跑批快照。三条理由：

1. 账龄 = 统计日 − 到期日，实时算会让同一张表每刷新一次变一个数；
2. 审计要能回答「上个月报表当时长什么样」，实时算答不了；
3. 部门达标率要扫全量巡检明细，实时算会把列表拖到秒级。

契约形态：

```
GET  /reports/snapshots          批次列表（哪天跑过哪张表、失败原因）
GET  /reports/arrears            读快照：楼栋 × 账龄
GET  /reports/collection-rate    读快照：账期 × 科目（分母剔除作废与减免）
GET  /reports/dept-target        读快照：部门 × 周期
POST /reports/recalc             → 202 + taskId（同参数运行中 → 200 + reused=true，幂等）
GET  /reports/recalc/{taskId}    轮询进度；成功后才产出 batchNo
```

每条响应都带 `meta`：`statDate / batchNo / calcAt / dataCutoff / formulaVersion / rowCount / partial / stale`。
没有 meta 的报表接口不算交付——出了数说不清来源等于没数。

**实测（假服务）**

```

### 期次：月报 / 年报（2026-10-30 拍板）

报表先分两类，只有第二类才有「期次」概念：

| 类型 | 报表 | 月报 | 年报 | 能否由日快照累加 |
|---|---|---|---|---|
| 时点型 | `arrears` | 月末那天 24:00 的余额 | 年末那天的余额 | 可以（取那一天） |
| 期间型 | `collection-rate` / `dept-target` | 整月重算 | 整年重算 | **不能**（补录、退款会让日累加 ≠ 整期） |

参数也分两套，别混：

```
时点型：?statDate=2026-10-21 | ?month=2026-09 | ?year=2026     （三选一，给两个 400）
期间型：?periodType=月&period=2026-10  /  ?periodType=年&period=2026
行级过滤用 billPeriod，不要和报表期次 period 撞名
```

年报**拆两张表**：余额走 `arrears` 年视图（时点），发生额走 `collection-rate` 年视图（区间）。
部门年报按全年任务累加后重算比率，**不是 12 个月达标率取平均**。

未月结的期次照样能出数，但 `provisional=true`、`statDate` 落在今天：
**月报＝月结后一次算，当月给试算值**；日快照不标试算（它本身就是那天当时的数）。

批次号：日 `RPT-20261021-01` / 月 `RPT-202610-M01` / 年 `RPT-2026-Y01`。
`meta` 还带 `periodValue`（本期主指标）与 `compare{prevPeriod,prevValue,yoyPeriod,yoyValue}`，
没有上一期时给 `null`——**不要给 0**，0 会被当成"上期是 0 收缴率"。

### 期间关账（月结）· 三条口径先定，接口才有意义

月结不是"点个按钮锁数据"，它背后有三个必须回答的问题。这一版按下面的答案落：

| 问题 | 答案 | 为什么 |
|---|---|---|
| 谁有权结 | `b.monthClose.edit`（财务）。**项目经理没有** | 封账是财务动作。让项目经理封自己项目的账，等于让他自己掩盖欠费 |
| 能不能反结 | 能，走 `e.monthReopen.edit`（更高一级；**刻意在 e 域**，否则财务的 `b.*` 通配会自动授予）+ 必填 ≥10 字原因 | 不允许反结的结果是有人去数据库改数——那才是真正的失控。允许，但要留痕 |
| 结完能改什么 | 该期间流水 / 退款一律 **409 / 40903** | 退款会改上月已封存的收款与欠费，必须「反结 → 改 → 重结」 |

```
GET  /month-closes                  记录列表（含已反结，按期间倒序）
GET  /month-closes/preview?period=  预览：能不能结、欠什么、上月净额
POST /month-closes                  提交 → 201；已结 → 409 / 40904
POST /month-closes/{id}/reopen      反结 → 记录留痕 + 批次作废 + 期间解封
```

反结做四件事，**一件都不能省**：记录置「已反结」并留 `reopenReason` / `reopenCount` / `reversalNo`；
该期间报表批次标 `voided=true`（保留可查，不删除）；期间恢复可写；报表实时回到 `provisional=true`。

两个容易做错的地方：

- `provisional` **必须实时按"该期是否已月结"算**，不能用建批次时存下的值——反结后旧批次仍是那份冻结的数，
  但它已经不是定稿了。状态属于**期间**，不属于批次。
- 反结**不写进退款流水**。反结不是退款，混进去会让「退款金额」统计失真；它有自己的红冲凭证号。

### 批次保留与清理

日快照一天 3 张表，一年 1000+ 批次，不设保留策略下拉框和索引都会被拖垮。但也不能随便删：

| 粒度 | 默认保留 | 理由 |
|---|---|---|
| 日 | 90 天 | 日常核对用 |
| 月 | 24 期（2 年） | 年度审计要看前两年月报 |
| 年 | **永久** | 年报是最小粒度的历史凭证，删了等于抹账 |

**已月结期间的批次一律受保护**——审计要能回答「那个月报表当时长什么样」，而月结正是"当时"被确认的时间点。
受保护数量单独计（`protectedClosed`），不混进 `expired`：混进去会表现成"怎么清都清不干净"。

`POST /reports/purge` 带 `dryRun`（首次上线前先看会删什么）且**幂等**（第二次 `removed=0`）。
清理任务必须能无条件重试，否则失败一次就没人敢再跑。

**实测（假服务）**

```
retention   日 15 批 / 过期 6；月 9 批 / 过期 0；年 3 批 / 永久
dryRun      removed=6（7-15 / 7-16 各 3 张表），跑完老批次仍可读
真清理      removed=6 → 7-15 批次 404/40402；10-19 仍在；再跑 removed=0
收紧参数    keepDays=1 / keepMonths=1 → keptProtected=12；
            9、10 月（已月结）仍在，8 月（已反结）可清
```

### 合同与公告 · 两条状态机口径

**合同：变更是独立单据。** 改金额、改期限、提前终止都不直接改合同，而是生成 `ContractChange`
（`before` / `after` 快照）进审批，通过才回写。直接改合同的话——谁在什么时候把 30 万改成 50 万，永远查不出来。

```
GET  /contracts                列表（vf 服务端算：pending/expiring/expired/big/group/changePending）
GET  /contracts/summary        KPI，与列表同一套谓词
GET  /contracts/{id}           详情（ref 按 refType 带出；断链给 null，不让详情页 500）
POST /contracts                新建（单号服务端生成，前端传了也忽略）
POST /contracts/{id}/changes   发起变更 → 201；已到期/终止 422；已有变更在审批 409/40906
```

两条容易做错的：

- **`expiring` 用状态不用天数**。样例里「即将到期」是按 90 天标的（62 天的也在里面），
  前端如果按 30 天重算，会和服务端差 6 条，而没人说得清谁对。
- **`phone` 列表与详情都掩码**。合同相对方是个人时就是个人信息。

**公告：状态机单向。** 草稿 → 待审核 → 已发布 → 已过期；已发布可撤回，撤回后要重新提交审核。

```
GET   /notices                 列表（vf：pending/published/expired/top/lowRead）
GET   /notices/summary         avgReadRate 只统计已发布
POST  /notices                 新建 → 只能是「草稿」，发布是独立动作
PATCH /notices/{id}            已发布不能改内容（409/40907）——业主看过了，改了等于篡改留痕
POST  /notices/{id}/publish    已发布/已过期不能再发（409/40908）——重复点，业主收两条一样推送
POST  /notices/{id}/repush     补推未读（只推没看过的人）；没有未读 → 422，不静默成功
POST  /notices/{id}/withdraw   要原因；**已读不清零**——业主确实看过，抹掉就是伪造
```

**实测（假服务）**

```
合同   85 条 · 总额 15,671,445.18 · 履行中 35 / 即将到期 7 / 已到期 28 / 待审批+待生效 9
       电话 175****1790 · 详情 ref 断链给 null · 变更 201 后合同金额不变（changePending=true）
       重复变更 409/40906 · 已终止 422 · 前端传的单号被忽略
公告   106 条 · 已发布 68 · 平均阅读率 76.1% · 草稿 4 / 待审核 9 / 已撤回 2
       已发布改内容 409/40907 · 重复发布 409/40908 · 撤回后 readCount 不变 · 无渠道 422
```

## 六、后端（Java / Spring Boot）接入提示

1. **枚举直接映射中文值**：`@JsonValue` 返回中文，`@JsonCreator` 按中文反序列化；不要另造英文 code
   （否则前后端各存一套，必然分叉——原型里 `部分缴 / 部分缴费`、`入场 / 进场` 已经分叉过两次）。
2. **数据范围在 Repository 层强制**：不要在 Controller 里判断，也不要依赖前端传；越权返回 403，不是空集。
3. **敏感字段在序列化层统一脱敏**：列表接口只回掩码，别指望每个接口自己记得脱敏。
4. **退款是一个事务**：退款单 + 流水累计 + 账单回落 + 发票红冲，四步要么全成要么全不成。
5. **SLA 由服务端算**：工作日历（9–18 点、跳周末与节假日）、「待确认」停表，前端只展示
   （前端也有实现，但只用于原型；上线后以服务端字段为准，避免两套算法）。
6. **乐观锁**：行上带 `_ver`，`PATCH` 回传，冲突 409/40901。
7. **验收就用 `npm test`**：把 `04-契约` 挂进 CI，指向你的服务地址即可（把 `mock-server` 的 `startServer` 换成外部 base）。
8. **核验 / 复核这类"责任动作"要和编辑分开授权**：`a.tenants.verify`、`f.rectify.edit` 不应和改备注同级。
9. **整改复核要记复核人**：提交人与复核人相同必须拒绝（原型里已有这条守卫，别在后端丢掉）。

## 七、已知限制（别指望这一版覆盖全部）

- 覆盖 **12 个域 64 个接口**（新增合同台账与公告通知）；品质**评价录入**、组织与权限（含**权限变更日志**）、
  员工与工资、其余报表仍是原型 mock——这几块牵涉企业自定义流程，等实际客户口径定了再进契约。
- 报表只进契约了 3 张（欠费账龄 / 收缴率 / 部门达标率）；费用明细、押金、报修、巡检、主管发现数仍是「实时查明细」，
  要不要也改成跑批，等后台给出跑批窗口与存储成本再定。
- 报表快照按**天**粒度；月报/年报需要再定 `statPeriod`，当前契约没有。
- 假服务把状态存在**内存**，重启即还原（这是刻意的：它是规格，不是数据库）。
- 契约里的枚举值是**中文**；若后端强要求英文常量，用 `enums.json` 生成映射层，前端不用改。
- 没有分页游标、没有幂等键、没有限流；这些属于第二批（契约里已留了错误码位置）。
- `contract-test.mjs` 是**黑盒**测试（打 HTTP），不含单元测试；后端自己的单测仍需写。

### 员工域（人事口径，不含薪资）· 三条刻意为之的取舍

**① 薪资不在这里。** `baseSalary / monthlySalary / bankCard` 属工资域（`c.payroll.view`）。
混进人事档案的结果是：能看到员工列表的人，就能看到全公司工资。详情里 `related.payrollRecords`
给 `null` 不给 `0`——0 会被读成「有工资条但一条都没生成」，与「本域不管这事」是两码事。

**② 角色不存员工表。** 由岗位反推（`roles.positions`），人工调整写一层覆盖
（`roleSource: position | override`）。角色存进员工表的结果是：改一次岗位要手工改一遍权限，
两边还会长期不一致。**调岗必须清掉覆盖**——人已经去工程组了，系统还让他批客服的假，就是这条没做。

**③ 离职即收权。** 离职员工 `roleId` 为空、`assignable=false`、不能调角色（409/40910）。
人走了权限还在，是最常见的一类越权。

组织归属拆两个字段：`homeOrgId`（人事档案上存的项目部）+ `orgId`（岗位反推出的班组 / 职能部门）。
合成一个字段的话，班组调整会顺手改掉档案归属，人力对不上花名册。

否则这个隔离永远没有反例可验。

### 工资域 · 状态机比字段重要

**工资条是核算快照，不是查询结果。** 每月生成一批、核算后冻结金额。实时算的结果是同一个人
今天看 11,058.98、明天补录一条加班就变 11,120.31，员工截图来问"为什么少了 62 块"时，
谁也说不清哪个对。

```
草稿 →（核算锁定）已核算 →（提交发放）待发放审批 →（审批通过）已发放 →（冲正）已冲正
                        └──（驳回）已核算
```

三条硬规矩：

| 规矩 | 不这么做会怎样 |
|---|---|
| **金额只由服务端算**（`grossPay` / `deductionTotal` / `netPay`） | 页面各加一遍 → 列表一个数、工资条一个数、汇总又一个数 |
| **已核算后金额不可变**（409/40913） | 发一次钱、记两本账 |
| **提交人不能审批自己的发放单**（409/40915） | 一个人既能核算又能批准，"谁批的"永远写的是同一个人 |

另外两处：

- **`dataScope=仅本人` 只回自己那一条**（不是下发全表让前端藏）。工资表最容易被做错的就是这一步：
  列表给全量、前端按权限隐藏——等于没做。样例里专门加了 `staff` 账号（EM0020 / 仅本人）来守这条。
- **已冲正的行不进 `netTotal`**，单列 `reversedCount` / `reversedAmount`。冲正的钱已经退回去了，
  还算在实发里就是账上凭空多一笔。

**实测（假服务 + 页面）**

```

            行里没有 bankCard / phone / idCard —— 工资域不是员工档案的后门
汇总        应发 836,324.18 − 代扣 81,817.35 = 实发 754,506.83（与行加总一致）

> **实测踩到的两个坑**：
> ① 页面 mock 是内存态，**切角色必须在同一个页面内切**（顶栏下拉）。新开页面 = 刷新 = 状态回到种子，
> 我第一版测试用 `page.goto` 换角色，看到的是"审批通过后又是草稿"。

> 断言要直接取 `.el-timeline-item`，不能拿抽屉的 `innerText` 当全文。

### 组织与权限（纯 RBAC）· 提权要批、降权即时

**权限只挂角色，人只挂角色**——没有"给某人加一个权限码"这种接口。逐人授权的系统最后
没人说得清"谁到底能干什么"。员工那侧通过"岗位 → 角色"反推，人工调整写覆盖。

保存矩阵的三条分支（服务端自己算 diff，前端只提交保存后的完整集合）：

| 情况 | 结果 |
|---|---|
| 与保存前完全一致 | 200 `noChange=true`，**不写日志**（原样保存也记一条 → 日志里全是噪声） |
| 新增命中高敏白名单 | **202，不生效**，生成 `PermRequest` 等审批 |
| 纯降权 / 普通新增 | **200，立即生效**并记 diff |

高敏五类：`a.sensitive.view`（看证件明文）/ `e.monthReopen.edit`（推翻封账）/
`e.org.edit`（改权限本身）/ `c.payroll.edit`（改工资表）/ `a.stewards.edit`（改责任范围）。
共同点是「拿到就等于能自己扩权或掩盖问题」。

**双人原则**：提交人不能审批自己提交的申请（409/40917）。自己提自己批，等于没有审批，
而且日志里还会留下一次"审批通过"的假象。

**日志是追加写 + 哈希链**：访问/导出日志每条带 `hash` / `prevHash`，任何一条被改动，
链上后面全对不上。没有这个，「谁在什么时候看了谁的证件号」这条记录本身就可以被删掉。

**实测（假服务）**

```

角色详情    matrix 3 层（域→功能→操作）· GM 持有全部 5 类高敏 · 楼管也持有 a.sensitive.view
降权        R-VIEW 去掉 a.vehicles.view → 200 applied=true · diff.removed=[a.vehicles.view] · 立即生效
提权        R-CLN 加 a.sensitive.view → 202 applied=false · request.status=待审批 · 权限未变

双人        gm 提交后 gm 审批 → 409/40917；换 pm 审批 → 已通过且权限生效；再批 → 409/40918
驳回/撤回   驳回要 ≥4 字原因，权限不生效；撤回只有提交人能操作（staff 撤 → 403）
访问日志    12 条 · 逐条 prevHash === 上一条 hash（链完整）· 成功/脱敏/拦截三态齐全
六档        78（有角色的）+ 2（离职无角色）= 80 人
```

> **反向发现的一处授权基线问题**（没改 seed，记录在案）：14 个角色里有 **10 个**都持有
> `a.sensitive.view`，包括客服专员、收银员、楼栋管家——只有工程维修、品质督导、环境保洁、
> 秩序维护员、只读观察员没有。也就是说"敏感字段明文"这个权限位在样例里基本是默认发出去的。
> 契约把提权路径收紧了，但**基线本身太宽**：真接后台要按最小权限重排一遍，
> 否则审批流拦的只是"从一个已经很宽的口子再加一点"。

## 九、变更流程

1. 改 `openapi.yaml`（加字段可以，改类型/改枚举值必须先通知前端）；
2. `npm run gen:enums` / `npm run gen:fixtures`（数据或枚举有变时）；
3. `npm test` 必须全绿；
4. 在 git commit message 里写 `contract:` 前缀，方便回溯。
