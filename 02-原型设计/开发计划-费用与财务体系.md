# 开发计划 · 费用与财务体系改造（2026-11-12）

> 目标：把「收了多少钱」升级为「哪类收入、花了多少、任意区间都能算清」，
> 为收缴率 / 欠费率 / 预缴率提供统一口径的数据底座。
>
> 状态：**口径已全部确认，待开工**。开工顺序见 §六。

## 一、范围

**做**

- 项目级水电收费模式（A 国网自缴 / B 插卡 / C 抄表），按表计类型分别配置
- 收银台两形态：非计量项按「单价 × 月份」预收并平摊；计量项按金额 ⇄ 用量换算
- 应收矩阵（户 × 账期）：应收、已收、减免三列，支撑任意区间三率
- 抄表推单、小程序缴费
- 取消预存账户体系
- 费用分类字典（收支统一口径的根）
- 合同收支方向 + 类型两级树 + 多种经营拆分
- 支出三类归集 + 手工补录（含税费）
- 三率报表

**不做（留结构或转 backlog）**

- 卡内余额（不在系统范围，只记预充值金额）
- 空置减免默认比例（只留开关，默认 0，比例可配）
- 调价执行（矩阵存 `unitPrice` 快照，先不分段）
- 历史余额迁移（新系统无历史）
- 报表导出模板 → 见 §七第一批增强

## 二、已确认口径（写死在代码里，不留给人工判断）

| # | 口径 | 结论 |
|---|---|---|
| 1 | 水电收费模式 | 允许同一项目电走国网、水走物业；按表计类型分别配置三态 |
| 2 | B 类插卡余额 | 系统不管卡内余额与消耗，只记预充值金额 |
| 3 | 非计量项金额 | `金额 = 收费项单价 × 月份数`，月费 = 面积 × 单价 |
| 4 | 计量项换算 | 金额 ⇄ 用量双向；单价取收费项，**单据存快照** |
| 5 | 减免口径 | **应收不减，`waived` 单列**；收缴率分母 = 应收 − 减免 |
| 6 | 减免原因 | 必选，取字典；报表按原因汇总（原自由文本已无法归类） |
| 7 | 水电单价归属 | 收费项级（不同项目各配一个） |
| 8 | 业主端展示 | **不出现应收/已收/待收**，只给待缴清单 + 缴费记录 |
| 9 | 平摊校验 | 金额 = 月应收 × 月数 才允许平均分摊；否则逐月冲抵，余额作预付 |
| 10 | 收款单时间 | 双维度：`paidAt`（现金收入/开票）+ `period`（归属月/三率） |
| 11 | 应收铺底 | 按房屋建档日往前铺 24 个月，否则清欠无处落格 |
| 12 | 退费 | 费用不可退；**押金可退**；录错走单据作废（红冲），不用负向收款 |
| 13 | 税费 | **单列**，只允许财务手工补录，计入支出 |
| 14 | 公共收益 | 建台账，多种经营收入 = 合同金额 − 公共收益 |

三率公式（区间 `[T1, T2]`）：

```
应收 = Σ 面积 × 单价（按账期）
收缴率 = Σ已收 ÷ (Σ应收 − Σ减免)
欠费率 = 1 − 收缴率
预缴率 = Σ(归属期 > T2 的已收) ÷ Σ(归属期 > T2 的应收)
清欠额 = Σ(归属期 < T1 的已收)        ← 与预缴分开，混算无意义
现金收入 = Σ(paidAt ∈ 区间) 的收款金额  ← 与归属口径并行，可互相勾稽
```

## 十一、收银台重做 · 三栏 POS（2026-11-13）

> 触发点：「页面整体还太像后台管理，不像一个在前端收银的页面」。改之前先出了三套布局稿
> （`03-原型/design/cashier-layouts.html`），确认后按业务规则重做（`design/cashier-final.html`）。

### 11.1 为什么不是"一排卡片"

用户给的三条业务事实推翻了通用卡片方案：

| 业务 | 规则 | 形态 |
|---|---|---|
| 物业服务费 | 账单制、按月、**能欠** | 账期格子（红几格 = 欠几期） |
| 车位管理费 | 周期制、**不欠费**、到期失效 | 有效期 + 续 1/3/6/12 月 |
| 水费 / 电费 | 按量、**按业态计价**、三种模式 | 预充换算 / 抄表待缴 / 自缴灰显 |

车位不存在"欠 3 个月"——过期那天车牌就不是月租了。硬塞进账期格子，前台会去找不存在的"补缴"。
反过来，物业费放进"有效期"里，欠 5 期的户也只显示一个到期日，账龄就没了。

### 11.2 水电价目表（新增一层）

以前单价是 `feeItems.price` 一个数字，备注里拿文字写"阶梯：0-200 度 0.62…"。
这等于没有结构：报表算不出价、调价要改字符串、商业户和住宅户只能共用一个价。

现在独立成表 `utilityPrices.json`，四元组取价：

```
(项目 × 表计 × 业态/房屋类型) → 档位单价，房屋可单独覆盖
```

| | 住宅 / 公寓 | 零售铺 | 餐饮铺 | 办公 |
|---|---|---|---|---|
| 水费 | 3.85 | 5.55 | 5.55 | 5.55 |
| 电费 | 0.568 | 0.80 | 0.90 | 1.00 |

取价顺序：**房屋覆盖 → 房屋类型精确 → 业态 → 通用**。取不到**抛错**，不静默回落 ——
一旦回落成住宅价，商业户每次都被少收，报表上只表现为"电费收入偏低"，没人会发现。

同业态不同价（转供电协议价）用 `houseUtilityBinding.json` 存例外，
单条带原因与操作人，页面上标"单人价"。

`houses.usage`（住宅 592 / 公寓 44 / 商业 120）与 `houseType`（零售铺 / 餐饮铺 / 办公）
**本来就有**，不用改数据模型。

### 11.3 三种水电形态由项目配置驱动

| 项目配置 | 收银台 | 金额可改 |
|---|---|---|
| `card` 插卡预充 | 金额 ⇄ 用量换算框 | 能（钱换量） |
| `meter` 物业抄表 | 待缴单列表（期/用量/金额/状态） | **不能**（改了等于改读数） |
| `none` 国网自缴 | 灰显"不产生应收、不收款、不计收入" | — |

抄表待缴单直接用 `bills` 里 `FI05/FI06` 的未缴记录（现有 687 + 640 笔），不另建订单表。

### 11.4 加收：其他科目 / 押金 / 临时收费

右栏内联展开三个 tab，不弹窗：

- **其他科目**：从收费科目取（门禁卡、临停、垃圾清运），数量 + 金额，**可微调**
- **押金**：装修 3000 / 门禁卡 50 / 非机动车牌 20，金额**不可改**（改了就是议价），
  **只能收不能退**，退还走押金台账并需审批
- **临时收费**：事项 + 金额 + 说明，**说明必填**（日结对不上时要能查）

押金写入 `decorationDeposits`，状态新增 `在押`（门禁卡押金不是"装修中"）。

### 11.5 合计必须拆三行

```
收入类合计        1,065.20
减免                  0.00
押金（负债，不计收入）  50.00
────────────────────────
本次实收         ¥1,115.20
```

押金收进来是钱（进实收），但不是收入（不进收入表）。混在一起当月营收就虚增。
实收 = 收入类 − 减免 + 押金，页面与报表用同一个式子。

### 11.6 六个坑（都不是 build 能发现的）

| 问题 | 现象 | 修法 |
|---|---|---|
| `watch(payableTotal)` 提前注册 | `Cannot access before initialization`，整页白屏 | watch 移到 payableTotal 之后；watch 注册时会立刻跑一次 getter |
| `splitCheck` 条件分支漏依赖 | 加了车位/押金后校验仍用旧总额，点收款被"超出 ¥410"拦住 | 先无条件读 `payableTotal.value` 再判断 |
| 矩阵状态与账单不一致 | 有账单且已计滞纳金的月份显示"未到期"，格子点不动 | 有未缴账单即判欠费，优先级高于矩阵的"当前月"判断 |
| `payBills` 只认账单 | 支付拆分含车位/押金时被判"超出" | 账单那一笔按账单实收单独配平（`fitSplits`），差额由各单据自己落库 |
| 换客户不清清单 | 上一单的车位、押金跟着下一个客户的账一起收 | `watch(ownerId)` 清空 sel / extras |
| `el-select` 点外层不展开 | 测试里下拉 0 项 | 点 `.el-select__wrapper` |

## 十三、收银台第三轮修正（2026-11-13）

### 13.1 账期改成两段：欠费段 + 未来 12 个月

第一版固定铺 6 期（2026-08 ~ 2027-01），从今天算只有 2~3 个未来月份能点，
"预缴一年"这件事在界面上根本做不到。

现在两段，各管一件事：

| 分段 | 范围 | 点一下是什么 |
|---|---|---|
| 欠费与当期 | 回溯 6 期，**有更早的欠费就自动往前扩到那一期** | 有账单 → 销账；没出账单 → 补缴（写矩阵，不补开单） |
| 未来 12 个月 · 可预缴 | 当期后 12 期 | 预缴，收完即记已收，不生成账单 |

回溯不早于**房屋交付月**：不设这个下限，2015 年交付的楼会凭空长出一年的"欠费"。

### 13.2 快捷缴费：3 / 6 / 12 个月，金额写在按钮上

- 从**当期**起连续取 N 期未收清的月份，已收清的自动跳过并顺延
- 不往欠费段里捞 —— 清欠有「全选欠费」和点格子两条路；混进来会让"12 个月"变成
  "12 期（含去年欠的）"，金额与业主预期对不上
- 每个按钮直接写该档金额（`3 个月 ¥1,056.21`），点完块头出现
  `已选 12 期 · ¥4,224.84 · 2026-10 ~ 2027-09`
- 快捷档是**替换**不是叠加；手点任一格子会清掉按钮的选中态

### 13.3 右栏预缴合并成一行

12 期预缴会产生 12 条清单项，一条条列会撑爆 320px 右栏。
现在按房合并：`物业服务费（预缴）· 2026-11 ~ 2027-09 · 共 11 期`，
金额仍是逐期落库（`createPrepayForPeriod` 一期一条），销账不受影响。

### 13.4 口径统一：格子红了 11 期，块头不能写"欠 2 期"

原来 `periodDebtCount` 只数**有账单的**格子，但矩阵里 2025-11 就有应收、账单只开到最近两期，
于是格子红 11 格、块头写"欠 2 期"，前台第一句就被业主问住。

现在：谁还有未收金额就算一期（`segment !== 'future' && unpaid > 0`），
「全选欠费」也按这个口径选——有账单的销账，没出账单的补缴。

### 13.5 散客 / 外来人员：摆摊费这类钱不挂户

摆摊费、场地租用、赔偿款，付款方是门口摆摊的、来租场地的、施工队 ——
既没有业主档案，也没有房屋，挂不到任何应收上。

- 左栏顶部常驻**「散客 / 外来人员」**入口（橙色头像，与业主列表有分隔线）
- 中栏切成散客形态：客户条换成「姓名 / 手机 / 所属项目」三个必填项，
  物业费 / 车位 / 水电三块整体不出现（不挂户就没有账期、没有车位、没有表计）
- 加收只留「临时收费」：其他科目与押金都要挂房屋才落得了库
- 落库为 `partyType: '外部'`，**计入收入、不进收缴率**
- 新增「最近散客收款」区块：同一摊位一天来两趟，"我上午交过了"要能当场翻出来

硬挂一个业主的后果是：这户的收款流水里混进一笔不属于他的钱，业主来查账说不清。

### 13.6 三个真实缺陷（都不是样式问题）

| 临时收费只建单、没收款 | 收款提示成功，台账里停在「待收款」，日结看不到这笔现金 | `saveTempCharge` 之后补 `payTempCharge` |

| 散客模式下 `p` 为空 | 左栏 `quickDebt` 读 `p.value.ownerId` 会抛错，整页白屏 | 全部改成可选链，`quickDebt` 对散客直接返回 0 |

## 十四、批 3 交付记录（2026-11-13）

> 后台侧完成；业主端改造已写进 `交接单-业主端小程序.md` §三十，在另一个任务窗口执行。

### 14.1 抄表推单：把"已计费"这个假状态接上真账单

原来「复核通过」只是把读数状态改成「已计费」—— **没有金额、没有账单、没有应收**。
表抄了一堆，系统里一分钱没收上来，账面上也看不出这个月该收多少水电。
这一批把最后一段接上：

```
读数（待录入 → 待复核）→ 复核通过 → 用量 × 业态单价 → 水电账单 → 业主缴费 → 进收入与日结
```

页面上是「抄表与公摊」的第二个 tab：账期 + 项目 → 预览（每行能不能出账、出多少钱、为什么不能出）→ 生成账单。

### 14.2 三类项目模式必须分开（这是本批最容易做错的地方）

`communityUtility` 里每个项目的水电独立配置，推单只对 `meter` 生效：

| 模式 | 处理 | 对项目推单的后果 |
|---|---|---|
| `meter` 抄表 | 出账单 | — |
| `card` 插卡 | **不出账**（先买量后插表，本来就没有账单） | 凭空给业主开一张不该缴的单 |
| `none` 自缴 | **不出账**（国网/水司直收） | 等于代收国网的钱，还进了自己的收入表 |

现有配置正好三种都有：P01 双抄表、P02 电自缴水插卡、P03 电插卡水抄表，
所以这条不用造数据也能验（`meter-billing.mjs`）。

### 14.3 单价按业态取，不读收费科目上的参考价

`feeItems` 上水费是 4.2 元/吨、电费 0.62 元/度，那是**住宅参考价**，
真正的价在批 2 建的水电价目表里（住宅电 0.568、零售铺 0.80、餐饮铺 0.90、办公 1.00、商业水 5.55）。
推单走 `utilityPriceOf(houseId, meterType)`，取不到价直接列为阻断项 —— 不静默回落成住宅价，
否则商业户每月都被少收，而报表上只表现为"电费收入偏低"，没人查得出来。

### 14.4 阻断 vs 部分推单：两个都要，但必须说清

- 默认**整批拒绝**：有未抄/待复核的表就不出账。只出一半，另一半户这个月没有应收，
  收缴率的分母凭空少一截，而且没人会发现少了哪几户。
- 抄表是分批做的（先抄完的楼栋先出账），所以按钮**不硬拦**：点了会弹确认
  「还有 21 条未抄/待复核，本次只出已抄完的 6 户，被跳过的户这个月不会有账单」。
- 幂等：已推过的读数（`readingId` 已回填 `billId`）不重复生成，重复点只提示"已全部推过单"。

### 14.5 账单能追回读数

推单时把 `readingId` 与 `meterNo` 写进账单。业主问"这个月怎么用了 79 吨"时，
账单 → 读数 → 上期/本期读数一条链走完，不用去翻抄表本。

### 14.6 顺带补的一个真 bug：账单缴费没有落矩阵

`payBills` 销账后**从来没有写过应收矩阵** —— 矩阵的"已收"只有收银台的
`createPrepayCollect` / `createPrepayForPeriod` 在写。结果是：走账单缴费的户，
账单列表显示已缴、收缴率却永远不涨，两个口径各说各话。

现在 `payBills` 销账后对 `isReceivableItem` 的科目补写 `MATRIX_TX`（实收 `source: 'bill'`，
减免 `source: 'waive'`）。水电账单不写矩阵 —— 水电没有月度固定应收，口径见 §六验收点。

### 14.7 取消预存：只停新、不清旧，账上的钱必须能退

137 个账户、几十万在账余额。直接删页面，这笔钱既不是收入、也不在负债里，审计一问就哑。
所以拆成两件事：

| 动作 | 处理 |
|---|---|
| 停止新增 | `PAY_METHODS` 去掉「预存抵扣」；`recharge` / `deductPrepay` / `toggleAutoDeduct` 三个函数直接抛错；`payBills` 显式拒绝 `method='预存抵扣'` |
| 清理存量 | `/b/prepay` 改「预存清退（已停用）」：只剩「退还余额」，整额退 → 写退款流水 → 账户置「已销户」永久留档 |

历史流水里 129 条 `channel='预存抵扣'` 的记录**不动**：`payChannel` 枚举保留该值，
日结的「预存抵扣」筛选也保留 —— 那是历史，改了日报表就查不出来。

### 14.8 一个口径选择：为什么"销户仍有余额"要单列

`prepayClearanceSummary().closedWithBalance` 统计"已销户但余额不为 0"的账户。
正常情况下这两件事互斥，出现就说明当年是人工作废而不是退款 —— 这类账户要单独核对，
混在"已清退"里等于把没退的钱当成退过了。

## 十五、批 4 交付记录（2026-11-13）

### 15.1 方向 ≠ 收入分类（这一批最容易做错的一处）

合同上只有一个 `incomeCategory`（主营业务 / 多种经营 / **不计入**），没有任何方向字段。
直觉做法是「不计入 = 支出」，跑一遍数据就会发现它错了：

| 合同类型 | 份数 | incomeCategory | 真实方向 |
|---|---|---|---|
| 租赁 | 16 | 多种经营 | 收入 |
| 物业服务 | 1 | 主营业务 | 收入 |
| **物业服务** | **6** | **不计入** | **收入**（钱已按物业费账单逐月收过，合同不再重复计） |
| 外包服务 / 采购 / 劳动 | 62 | 不计入 | 支出 |

按「不计入 = 支出」算，这 6 份 322 万的物业服务合同会进成本 ——
成本虚增、利润虚减，而且报表上看不出错在哪，因为两个字段都叫"不计入"。

所以：

- **方向看合同类型**（`contractDirectionOf`）：物业服务 / 租赁 → 收入；外包 / 采购 / 劳动 → 支出
- **是否计入收入看 incomeCategory**（`contractCountsInRevenue`）：收入合同里还有 6 份不重复计

界面上这两个维度同时可见：一行里既有「收入」标签，又有「不计入」标签，不冲突。

### 15.2 类型两级：方向 → 类型 → 子类型

`contractTypeTree(direction)` 返回方向下的一级类型与子类型份数，筛选联动用它：

- 选「支出」→ 类型下拉只剩 外包服务 / 采购 / 劳动（不会出现「广告位租赁」）
- 选「收入」→ 只剩 物业服务 / 租赁
- 换方向时清掉已选的类型与子类型，否则会同时带两个互斥条件，列表一片空白

### 15.3 顶部统计改成收支分列

原来是「合同总数 / 合同总金额 1567 万 / 年化商业合作 / 到期」。1567 万这个数最容易被误读成收入，
但里面 1074 万是支出。现在：

| 卡片 | 内容 | 为什么 |
|---|---|---|
| 合同总数 | 85 份（收入 23 · 支出 62） | 一眼看出结构 |
| 收入合同（期间额） | 492.8 万，其中计入收入 17 份 192 万 | 收入合同 ≠ 计入收入的合同 |
| 支出合同（期间额） | 1074.3 万，只进成本 | 再也不会有"公司收了 1567 万"的误解 |
| 年化商业合作收入 | 77.0 万，16 份经营合同，已扣公共收益 | 真正的收入口径 |
| 到期 / 待审批 | 7 / 28 / 9 | 保留原来的盯到期 |

口径说明里写死了那句话：**方向看合同类型，是否计收入看「收入分类」，两者不是一回事。**

### 15.4 公共收益台账（新页）

`/b/public-revenue`，数据源只有一个：合同表的 `publicRevenue`，**不另造数**。

三个数缺一不可：`合同额 = 归业主 + 归物业`。

- 只给合同额：汇报时会被当成公司收入，而这笔钱大部分不是公司的
- 只给归业主：看不出物业自己的服务费有多少
- 两个都给：公示稿能直接抄，审计也能对上

附带的两个东西：

## 十六、批 5 交付记录（2026-11-13）

### 16.1 支出不是一张表，是四类来源汇过来的

这一批最容易做错的地方，是以为「支出 = 报销」。实际有四类来源，**确认时点各不相同**：

| 来源 | 确认时点 | 为什么不能混 |
|---|---|---|
| 费用报销 | **付款日**（不是审批通过日） | 批了没付，钱还在账上，记成支出就是提前确认成本 |
| 工资 | **当月** | 薪酬是期间费用，发薪日跨月不改变归属月 |
| 合同支出 | **期间摊**（合同额 ÷ 月数） | 3 年的保洁合同一次性记进当月，当月成本会翻三倍 |
| 手工补录 | **补录的账期** | 税费、通道手续费这类没有单据流 |

归集表的每一行都保留「来源」拆分列。合并成一个总数之后，问"这个月运营费用为什么涨了"就答不上来 ——
分不清是报销多了、还是合同摊多了。

### 16.2 两个口径并排，差额必须写出来

页面上有两套视角，数字天然不同，不解释一定被问：

- **按一级分类**（钱花在什么上）：合同支出 ¥179,071.09（2026-09）
- **按来源**（单据从哪来）：合同支出 ¥284,330.70

差 ¥105,259.61 —— 外包人力合同的支出归在「人力成本」、采购合同归在「运营费用」。
两个视角不冲突，但页面必须把差额写出来。

同期还修了一个同类的坑：**指标卡一开始按一级分类算、来源卡按来源算**，并排放着就是 22 万 vs 31.6 万。
现在指标卡统一为来源视角，与「按来源」逐项相等；一级分类只在左侧块里出现。

### 16.3 手工补录：谁能进，由分类字典说了算

不是页面不给选，而是 `allowSources` 里没有 `manual` 的分类根本不出现在下拉里：

| 分类 | allowSources | 能否补录 |
|---|---|---|
| 税金及附加 | manual | **只能补录**（没有别的通道） |
| 差旅费 / 业务招待 | reimburse | **不能**，必须走报销 |
| 办公费用 / 维修材料 | reimburse, manual | 可以，但优先走报销 |
| 通道手续费 | manual | 只能补录 |

配套三条硬规则：

1. 只能挂**二级**分类（一级只是汇总口径，不能直接入账）
2. 方向必须与分类一致（收入分类不能记成支出）
3. **只增不改**：录错要作废重开，作废必须写原因 —— 补录是"没有单据流"的钱，
   删掉就再也查不到它曾经存在过

### 16.4 押金：负债，不是收入

`depositLedger()` 把「收 − 退 − 扣 = 在账」固化成一条口径，并在押金台账页写明：
押金对应分类「押金及保证金」（`LIA_DEPOSIT`），**只有扣款部分（业主违约）才转成收入**。
这和已下线的预存是同一类错：把别人的钱算成营收，报表好看但经不起审计。

## 十七、批 6 交付记录（2026-11-13）

### 17.1 三率不是三个百分比，是同一套数的三种切法

分开算一定会漂移（三个页面各算一遍，谁也不服谁），所以 `threeRateReport` 一次算完：

```
应收   = Σ 面积 × 户级单价 × 期数     （按账期铺，不看有没有开单）
已收   = Σ 矩阵流水（不含减免）
减免   = Σ 矩阵流水 source=waive
未收   = 应收 − 已收 − 减免            ← 不减到 0
收缴率 = 已收 ÷ (应收 − 减免)
预缴率 = Σ(归属期 > T2 的已收) ÷ Σ(归属期 > T2 的应收)
清欠额 = Σ(归属期 < T1 的已收)
现金收入 = Σ(paidAt ∈ 区间)
```

**报表自带自检线**：`已收 + 减免 + 未收 = 应收`。这条线在页面上是绿色/红色横幅，
不做旁注 —— 它不通过时，下面所有百分比都不可用。验收脚本也自己加了一遍，
不只信页面写的"成立"。

### 17.2 抓到一个会让两个指标同时失真的 bug：户级单价

`monthlyFeeOf` 原来统一取 `feeItems.price`（2.8），但数据集里物业服务费有三档：
**住宅 2.8 / 公寓 3.2 / 商业 8.5**（120 户）。后果是：

| | 修之前 | 修之后 |
|---|---|---|
| 应收（2026-08~10） | 77.4 万（少了 40 万） | 118.1 万 |
| 已收 | 97.9 万 | 97.9 万 |
| 收缴率 | **126.39%**（超 100） | 82.86%（合理） |
| 超额收款户 | 276 户（全是假的） | 0 户 |

一个错、两个指标同时失真，而且"收缴率 126%"看起来像"经营特别好"。

修法：`houseUnitPriceOf(houseId, itemId)` 取**该户该科目最近一张账单上的 price 快照**，
没有账单历史才回落收费项单价。用快照而不是按 `usage` 硬编码，是因为快照本身记录了
"这户当时按什么价开的"——调价、一房一价都能自动跟上。

`monthlyFeeOf` 也一并改掉，让收银台、矩阵、报表三处用同一个价：
否则会出现"收银台按 2.8 收、报表按 8.5 算应收"的更坏情况。

### 17.3 收支分项：两侧来源不同，不能套同一套模板

- **收入**：账单实收（按科目）+ 合同收入（按期间摊）+ 临时收费 + 手工补录收入
- **支出**：报销 + 工资 + 合同摊 + 手工补录（复用批 5 的 `expenseCollect` 逐月累加）

结余 = 收入 − 支出，**不含押金**（负债不是收入）。按月趋势给出单月水位，
负结余的月份标红 —— 单月亏损不是问题，连续三个月才是。

### 17.4 演示数据的三个边界（已写进页面页脚）

1. **账单只覆盖 2026-08 之后**：往前看时"没开单的月份"仍按面积计应收，收缴率会明显下降。
   这是数据边界，不是收缴水平 —— 所以默认区间取最近 3 期。
2. **预缴原本为 0**：数据集里只有"已缴账单"，没有一笔提前缴的，预缴率恒为 0，看着像指标没用。
   补了演示种子（80 户 × 3 期，跳过收银台默认客户），预缴率约 1.7%。
3. **薪酬规模与在管规模不匹配**：在管 756 户的物业费月应收约 25.8 万，而数据集里 120 人月薪合计 127 万。
   所以结余为负是**数据问题不是口径问题**。换真实数据后这一项才有解释力。

这三条不藏着：页面上写清楚，比让人误以为系统算错了强。
