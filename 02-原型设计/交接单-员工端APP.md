### 0.3 员工端现在**已经在错**的三个地方

这三处不是"缺功能"，是"现在就是错的"。改之前先复现一遍：

**① 工单取价不读快照**（`05-员工端APP/src/api/wo.js`）
```js
const price = priceOfCategory(w.category)   // 反查字典
```
全文件搜不到 `totalFee` / `serviceName` / `priceCode`。后果：运营在服务项目页把角阀更换 ¥125 改成 ¥135，
**员工端所有历史工单详情立刻显示 ¥135**，而实际收款是按 ¥125 记的。提成走 `w.laborFee`（快照，是对的），
于是同一屏上"标准人工"和"提成"按两个价算 —— 师傅一定会来问。

**② 会签没有界面**（`src/api/oa.js` 直接 `import { approvalAction } from '@pc/utils/api'`）
PC 第 53 批给 `approvalAction` 加了会签分支，员工端**自动继承**了逻辑，但界面还是老样子：
点「同意」只签掉一个人、单据停在原地，用户看不到「会签 1/2」和名单，会以为点坏了。

**③ 审批人判定两套口径**（`src/api/oa.js` 的 `TEAM_OF_LABEL`）
员工端按岗位名推"我是哪个班组的主管"，PC 第 52 批已改成读 `orgLeaders` 关系表。
两边并行会出现"员工端认为我能审、后台认为不能"（或反过来）。

##### 66 批 · 员工端通讯录

**入口**：不占 tab（5 个 tab 已经满了）。放两处：
1. 「工作台」宫格里的快捷入口（和"报修""巡检"并列）；

**页面**：`pages/contacts/index`，一屏搞定，**不做部门树** —— 手机上展开三层树太占地方。

```
[搜索框：姓名 / 岗位 / 部门 / 手机后 4 位]
[全部] [总部职能中心] [翡翠城项目部] [财务管理部] ...   ← 横向滚动 chips
─────────────────────────────
白静   人事专员
翡翠城项目部
17583131790        [复制]
─────────────────────────────
```

- 部门 chips 用 `contactTree()` 拍平后的**一级 + 二级**节点（树上只有 7 个，手机上放得下）；
- 选择部门后调 `queryContacts({ orgId })`，默认含下级；
- 卡片点一下 → 弹「呼叫 / 复制号码」两个动作；直接点号码也行（`uni.makePhoneCall`）；
- **手机号明文**，和 PC 一致 —— 不要"为了安全"在移动端脱敏，那会让这个功能失去意义。

**口径（照做，别重新设计）**：

| 项 | 值 |
|---|---|
| 数据函数 | `queryContacts({ orgId, kw })` / `contactTree()` / `contactStats()` / `contactMe()` |
| 返回字段 | 只有 `empId / name / position / orgId / orgName / phone / gender` —— **薪资、证件、银行卡、紧急联系人不在返回里**，别去 `employees` 表捞 |
| 在职范围 | 只取在职（含试用），离职不出现。函数内部已过滤，**不要**自己再筛 |
| 权限 | `c.contacts.view`，**15 个角色全都有**。仍要 `canViewContacts()` 判断，但正常不会 403 |
| 脱敏 | **不脱敏**。这是与员工档案刻意相反的口径（档案里看手机是查隐私，通讯录里看手机就是它的用途） |
| 座机/分机/邮箱 | 数据模型里没有，**不要造字段** |

**会踩的坑**：
- `contactTree()` 已经 prune 掉 0 人节点，前端**不用再过滤**（但也不要假设层级固定，将来可能加部门）；
- 搜手机号后 4 位是函数内部支持的（`kw.length >= 4` 时 `endsWith`），前端只要把 `kw` 传进去；
- `tel:` 链接在 uni-app 里没意义，用 `uni.makePhoneCall({ phoneNumber })`；
- 复制用 `uni.setClipboardData`，成功回调里 `uni.showToast` —— 它自己会弹一个"内容已复制"，要 `showToast` 前先 `uni.hideToast()` 或者干脆不弹，否则两个提示叠一起。

### 0.9 追加（2026-11-06 · 列表内代客报名）

#### 修掉一个真 bug：退款分档一直命中最低档

`refundRatioOf` 把分档**升序**排后取第一个 `gap >= days` 的档 —— `days=0` 那档永远最先命中，
于是「提前 38 天取消」也只退 0%。页面只显示「已退款」，金额没人核，一直没暴露。

### 5.4 uni-app 特有注意（这几条不知道会白干半天）

| 坑 | 说明 |
|---|---|
| 没有 vue-router | 路由是 `pages.json` + `uni.navigateTo/redirectTo/switchTab`，页面栈语义不同，别照搬 PC 的 router 结构 |
| 尺寸用 rpx | 750 设计稿基准；`1rpx = 屏宽/750`。设计稿按 375 宽画时，数值 ×2 写 rpx |
| tabBar 在 `pages.json` 里 | 不是组件；图标要先备好（可用纯色 PNG 或字体图标，原型阶段可先只写文字） |

### 11.1 一句话

PC 已经做完了「发布 + 配置」；移动端只承接**离开手机就做不了的四个动作**：

### 11.2 三条划分原则（先立规矩，再列页面）

1. **产生 vs 消费**：产生内容（建投票 / 建活动 / 发公告）→ PC；消费内容（看一眼、点一下）→ 移动。
2. **一对多 vs 一对一**：要对着整屏表格做判断、要导出、要批量 → PC；对着**一条内容或一个人** → 移动。
3. **可撤销 vs 不可撤销**：批量退款、确认流团、改价格 → PC，且要更高权限 + 二次确认。

补一条：移动端**不做「缩小版后台」**。投票结果这种纯阅读内容不上移动端 ——
上去就是一个没人点的入口，还会被误认为"手机也能发布"。

### 11.4 两类事项的定义（最容易混的地方）

**待审核 = 事前把关。** 内容还没给业主看过，等你决定「能不能发」。

| | |
|---|---|
| 范围 | 只有一类：闲置，`status = 待审核` |
| 动作 | 通过 / 驳回（**驳回必填理由**） |
| 特征 | 单向判断，没有"被投诉方" |
| 权限 | `n.items.audit` |
| 演示数据 | 全公司 8 条；翡翠城(P01) **3 条** |

**待处理 = 事后处置。** 内容已经上线，有人投诉，等你决定「怎么办」。

| | |
|---|---|
| 范围 | 只有一类：举报，`status = 待处理` |
| 动作 | 忽略 / 仅警告 / 下架并警告 / 封禁 7 天（**说明必填**） |
| 特征 | 有投诉方与被投诉方，处理说明要能对外解释 |
| 权限 | `n.reports.handle` |
| 演示数据 | 全公司 4 条；翡翠城(P01) **2 条** |

**为什么必须是两个入口**：混在一起的后果是"审核的人顺手把举报也点通过了" ——
一个是"能不能发"，一个是"发了之后怎么办"，判断依据和留痕要求都不同。

⚠️ 数字对不上是正常的：手机上是 3 + 2，PC 后台是 8 + 4，差的是**数据范围**（员工登录人只属于一个项目）。

## 十二、租售信息（2026-11-06 · PC 第 69 批 · 移动端范围）

### 12.1 一句话

移动端只做三件事：**审房源的挂牌、接看房请求回电话、维护自己的联系方式**。

### 12.2 三块范围

| 块 | 内容 | 权限 |
|---|---|---|
| 房源审核 | 通过 / 驳回（必填理由） | `a.listings.audit` |
| 看房请求 | 看谁想看、一键回电、标记已联系 + 写结果 | `a.listings.viewing` |
| 我的 → 联系方式 | 微信号、二维码上传 | 本人，无码 |

### 12.3 审核：并入邻里的「待审核」队列

**不新增入口。** 沿用 §11.5 的「邻里待办」，作为第二类内容（闲置 / 房源）。

关键在于**队列按权限过滤条目**，不是按入口过滤：

| 角色 | 进「待审核」看到什么 |
|---|---|
| 客服（R-CS） | 只有闲置（他没有 `a.listings.audit`） |
| 楼管（R-STW） | 只有房源（他没有 `n.items.audit`） |
| 项目经理 / 总经理 | 两类都有 |

这一条比开两个入口干净得多，也不会出现"点进去全是没权限的"。

**审核详情页只显示四样**：图、价格与描述、房号与楼栋、**「产权人已核验 ✓」**一个标记。

产权校验在后台做完了（发布人必须是 `house.ownerId`），手机上不该再判断一次。
这一点很重要：让楼管在手机上核对产权关系，等于把已经做对的校验再做一遍，还容易看错。

**审核只看图。** 面积户型楼层是从档案派生的，业主改不了，不用核对。
必看清单：门牌号、邻居家门、楼道、窗外能定位到哪栋、家庭合照与证件、是不是网图。

话术：**"这张图能不能让陌生人找到这户人家"**——能，就驳回。

### 12.4 看房请求：这是移动端的核心场景

PC 只做监控（谁超时了），**真正回电话的动作在手机上**。

- 一条待办卡片：谁想看、留了什么号码、方便时间、留言、**已等多少小时**
- 一键拨号（`uni.makePhoneCall`），拨完标记「已联系」+ 写一句结果
- **超过 24 小时标红**，48 小时会升到楼管的直属上级

⚠️ 这个模块**不展示楼管手机号**给外部，所以访客留的号码是唯一的联系线索。
**楼管不回，这条线索就死了**，而且访客记住的是"物业发信息没人理"。
回拨时效是这套设计的生命线，移动端必须把"等了多少小时"做得足够刺眼。

### 12.5 我的 → 联系方式

```

contactQrUrl    二维码图片（可空）
```

- **不设「是否公开」开关**：填了就是愿意展示，没填就不显示。
  加开关只会出现"填了但关着"的困惑状态
- 填写页给一句说明："该信息会展示在租售信息页，供看房者联系你"
- 展示侧是条件渲染：有二维码就显示二维码 + "或搜索微信号 xxx"，都没有就只留「我要看房」
- **手机号不参与展示**，只在员工内部通讯录里

## 十七、消息中心承接业务提醒（2026-11-09）

### 17.1 为什么做

上一轮把公告按类型分好了页签，但消息 tab 里**只有公告**：工单派给我、巡检超时、审批等我处理，
一条都看不到，得回工作台挨个翻。评审时一定会被问「为什么派单不进消息」。

### 17.2 五个来源，只做索引

新增 `src/api/inbox.js`。它**不重写任何业务判断**，只把各域已有的待办函数聚成统一卡片形状 +
给出跳转地址：

| 来源 | 复用的函数 | 权限 |
|---|---|---|
| 工单 | `grabPool` / `myOpen`（筛 `slaBreached` 或 `isOverdue`） | `f.workorders.view` |
| 巡检 | `listForTab(name,'todo')` 的 pinned + groups **两段** | `f.inspect.view` |
| 审批 | `oa.listFor(persona,'todo')` | `f.approval.handle` |
| 邻里 | `todoOf({items, reports})` | `n.items.audit` / `n.reports.handle` |
| 租售 | `listingAuditQueueOf` / `viewingsOf` | `a.listings.audit` / `a.listings.viewing` |

**为什么必须五个**（第一版只做了前三个）：楼管登录后待办是 **0**。
他的活是房源审核和看房回电，一条都不在前三个来源里 —— 等于这功能对一半身份无效。
实测：补上后莫瑞有 2 条租售待办、汪磊有巡检 1 + 审批 3 + 邻里 5 + 租售 1。

### 17.3 四条设计决策

| 决策 | 依据 |
|---|---|
| 待办**不进未读数**，顶部两个数字分开（待办 N / 公告未读 M） | 要处理的与要阅知的混成一个数会被忽略（§11 早已定过这条） |
| 待办**不做已读** | 处理掉就消失；套用公告的已读逻辑会造出"读了但没办"的僵尸提醒 |
| 每组封顶 5 条 +「还有 N 条」跳该域列表页 | 周明初始有 21 条待办，全铺开会把公告挤到看不见 |
| 看房请求**汇总一条**，其余逐条 | 看房的处置在列表页逐条做、没有单条详情，列 5 个相同入口只会挤掉别的待办 |

### 17.4 踩到的三个坑

1. **`inited` 在 persona 就绪前被消费**：刷新后 `personaId` 从 storage 异步恢复，
   第一次 `onShow` 时 `persona` 还是 null（待办算出 0），`inited` 却已置 true ——
   于是永远停在公告页。实测徐悦就这样（顶部显示待办 2、列表却是公告）。
   修法：`if (!inited && persona.value)`。
2. **房源没有 `title` 字段**：挂牌数据是「地址 + 价格 + 描述」，不是标题化的内容。
   第一版拿"房源待审"当标题，结果和左边的标签一字不差，扫过去等于没读到信息。
   改成「小区 + 楼栋 + 房号」。
3. **测试断言写死条数**：第一版写「待办 21 条」，实测变 17 —— 前面的段落跑过提交巡检、抢单、
   审核房源，数据已被消费。改成验**内部一致性**：顶部数字 = 各组之和、卡片数 = Σmin(n,5)。
4. **「还有 N 条」点了没反应**：目标是 tabBar 页面（工单 / 任务列表），`navigateTo` 会静默失败，
   必须 `switchTab`。这类 bug 不报错、也不白屏，只能点一下看 URL 变没变 —— 已加断言守住。

### 17.5 验证

`05 npm run smoke` **189 → 197**（新增 8 条待办断言）· `build:h5` 通过 · 零 console 错误。

新增断言里三条值得记：
- 「顶部待办数 = 各组条数之和」—— 防"上面说 21、列表里只有 13"这种糊弄；
- 「卡片数 = Σmin(n,5)」—— 截断逻辑错一张都会红；
- 楼管那两条验的是**权限过滤**而不是"还剩几条"（他的房源已被前面的段落审完，0 才是对的）：
  待办里不该出现巡检与审批组。

### 20.1 为什么这轮只做契约

工单域比巡检大得多：`wo.js` 608 行 / 41 个导出 / 14 处写操作调用。开切之前先量了一下缺口，
发现**契约根本不够支撑**：

| 缺口 | 具体 |
|---|---|
| 详情字段 | `GET /work-orders/{woId}` 只回 `{workOrder, timeline}`，而 `detailOf` 要 20 个（费用构成、增项、提成、收款状态、评价） |
| 移动端接口 | `/mobile/*` 下**一条工单接口都没有**（只有 tasks / collections / commission / pricing / residents） |
| 提成参数 | 契约 `repair-prices.json` 的 `projects[]` **没有 `commissionRate`**，假服务只能硬编码 35% |

所以这轮把契约和服务端补足，05 的切换放下一轮 —— 因为工单的读写**必须一起切**：
只切列表不切写，会出现"抢了单但列表还在"（写操作改的是本地种子，列表读的是接口）。

### 20.2 新增两条接口

| 接口 | 干什么 |
|---|---|
| `GET /mobile/work-orders?tab=` | 页签 + 计数 + 当前 tab 的行，**一次给全** |
| `GET /mobile/work-orders/{woId}` | 详情聚合：费用 / 增项 / 提成 / 评价 / 时间线 |

**为什么页签和行要一次给**：四个 tab 各请求一次，响应之间会互相矛盾 ——
抢单池刚少一张、"我的"还没更新，用户看到"抢了但我的里没有"。

**两条金额口径必须分清**（这是这次最容易被写错的地方）：
- `fee.total` = 单额 + **已确认**的增项。未确认的算进去，师傅会去要一笔业主没认的钱；
- `addonSum.pending` 却要数**全部**未确认的 —— 它回答"还有几笔等业主点头"，不是金额。

`settled` 跟收款状态走：完工未收款是**在途**，不能算进当月收入。

### 20.3 顺手修掉的四个真问题

1. **提成比例硬编码 35%**：契约 fixture 缺 `commissionRate`，服务端写死 35 ——
   而 P02 是 32%、P03 是 30%，那两个项目的提成一直多算。已补齐 fixture（0.35 / 0.32 / 0.30）
   并改成按单取项目比例。P01 的数字不变（¥94.5），所以既有断言没动。
2. **客服主管一条工单权限都没有**：R-SEC 的 `f.*` 里 `workorders.*` 为零。
   但 05 的 `canDispatch` 早就允许客服派**公区单** —— 权限字典跟不上业务规则。
   已补 `f.workorders.view` + `f.workorders.dispatch`（三份 roles 同步），
   并在服务端把客服的待派池**限定为公区单**：付费单指派会直接吃掉师傅的提成，
   不能只靠前端按钮灰着。
3. **`POST /work-orders` 不写 SLA 字段**：新建的工单没有 `slaDueAt` / `slaBreached`，
   列表里「剩余时间」整列为空，而 `WorkOrder` schema 把它们标成 required ——
   测试红在"缺字段"上，看起来像移动端接口写错。已与巡检转单那条路径对齐补上。
4. **契约校验器不支持 `nullable`**：yaml 里从第一批就在用（设备购买日期、价目价格），
   但 `validate()` 只判 `type`，`null` 一律报"类型应为 object"。
   已按 OpenAPI 3.0 语义补上：nullable 只放开 null，enum / required / items 照旧。

## 二十一、工单域 05 侧：读写一起切完（2026-11-09）

### 21.1 补完契约的两处缺口

上一轮只做了契约骨架，这轮补完才开始切：

收款接口在它们之前，原来靠 `const` 提升不到，只是碰巧没被调用过。

## 二十三、smoke 的偶发红：一条真错变八条假错

### 23.1 现象

本轮 smoke 跑了三次：**197 全过 / 8 条红 / 10 条红**，红的位置几乎一样
（[5] 手机号、[11] 断网、[16] 邻里入口、[17] 看房卡）。

一开始以为是"我改坏了审批"，但失败项全在别人的模块里，而且失败信息很怪 ——
「一线（工程维修）看不到邻里入口 — 条件不成立」，意思是一线**看得到**。

### 23.2 根因

```js
async function asPersona(idx, name) {
  await goto('/pages/login/index')
  await tapSel('.pcard', idx, 1300)
  return waitText(name)          // ← 调用方不看返回值
}
```

切换身份**失败时静默继续**：首屏慢（负载高时确实会超过 5 秒）→ `waitText` 返回 false →
函数正常返回 → 后面一整段用**上一个身份**跑 → 断言按错误的前提判断。

于是一条"身份没切过来"的错，摊到后续段落里变成八条互不相关的假错。

### 23.3 修法

1. `asPersona` 重试 3 次（每次加长等待），仍失败就**抛错** —— 让失败点落在"切换本身"；
2. 新增 `waitFor(sel, ms)`：`visible()` 是"此刻在不在"，操作完立刻断言会偶发 false，
   要断言"操作后应该有"就用轮询版；
3. 断网段那三处 `has(...)` 立即断言改成 `waitText` / `waitFor`。

**这不是让测试变松**：抛错会让套件更快地停在一个明确的位置，
而不是拿一堆假错去误导下一轮的人。

## 二十四、楼栋域切到 HTTP（B 档第 4 站）

### 24.1 契约的两处缺口

| 缺口 | 具体 |
|---|---|
| 没有欠费接口 | 只有 `/houses/{id}` 和 `/mobile/houses/{id}/residents`，没有"我负责的楼栋欠了多少钱" |
| 没有催收历史 | `collectionRecords`（186 条）只在 PC 侧，契约里没有 —— 工作集的"距上次催 N 天"会全是空 |

补法：
- `fixtures/collection-records.json`（P01 的 150 条），由 `gen:mobile` 生成；
- `GET /mobile/debts?buildingId=&aging=&item=&skipRecent=`。

### 24.2 一个接口服务两个页面

楼栋首页的「欠费户列表」和催收页的「工作集」是**同一个东西**（欠费户），差别只在筛选。拆两条会出现
"首页显示 12 户、催收页显示 9 户"，用户会怀疑哪边算错了。

三条口径写在接口上：
1. **按房屋聚合，不是按账单**：一户一行。楼管打电话是打给"这户"，不是打过期的水费和物业费各一次。
2. **`skipRecent` 默认 true**，跳过近 7 天已催的户。一屏全是"刚催过"的，等于把今天该打的电话淹掉。
3. **`summary` 永远按全范围算**，不随 `aging` / `item` 筛选变小 —— 否则"欠费合计"会跟着筛选条件跳动。

**两个页面的 `skipRecent` 必须传不同的值**：首页要 `false`（全部欠费户）、工作集要 `true`。
首页也跳的话，用户会以为"这几户已经缴清了"。

### 24.3 05 侧

只留**最近一次拉的结果**（`LAST_DEBT`），不做多份缓存：一个页面同一时刻只有一种筛选，
多份反而要处理"这份是哪个筛选的"。切筛选时页面重新 `loadDebts(...)`，`ver++` 重算。

批量催收走 `/mobile/collections/batch`，写完之后**必须重新拉一次** —— 刚催过的户会从工作集里消失。

### 24.4 三个坑

1. **`allowed` 少了 `ver` 依赖**：楼栋首页有个"只对楼栋管家开放"的锁屏，判定用
   `scopeRowsCount() > 0`。HTTP 模式下这个值来自刚拉回来的数据，第一帧是 0 ——
   不重算的话页面**一直停在锁屏上**，而下面几条 computed 都有 `ver`，看着像"数据到了但门没开"。
2. **逐字段挑字段会漏**：`scopeSummary` 的 HTTP 分支我一开始只挑了 7 个字段，
   漏掉 `rate`（收缴率），页面 `s.rate.toFixed(1)` 直接报 `undefined.toFixed` 白屏。
   改成 `{ ...d.summary, buildings }` 整包透传，以后服务端加字段这里不用再改。
3. **按费项筛要截断 items**：服务端一开始只过滤了行、没截断 `items`，
   于是"选了水费，卡片上显示的却是水费+物业费的合计"——电话打过去报的数和业主查到的不一致。
   已改成：筛费项时 `items` 只留该费项、`debt` 与 `maxOverdue` 也按该费项重算。

### 25.2 但一跑就 403，挖出权限字典漂移

HTTP 模式下汪磊（客服主管）的邻里待办是 **0 条**，控制台一片 403。

查下来：**契约的角色授权里，所有角色一条 `n.*` 都没有**。而 PC seed 里 R-SEC / R-PM 是有完整邻里权限的。

再一比对，问题是**系统性的**：

| | PC seed | 契约 fixture |
|---|---|---|
| 权限码表 | 114 条 | **92 条**（落后 23 条：邻里、多经、开票设置…） |
| 角色授权 | — | 13 个角色合计**少 106 条** |

契约的 roles / permissions 停在 2026-10-30 的快照，之后 PC 陆续加了模块，契约没跟上。

**修的顺序不能反**：先补**码表**（92 → 115），再补角色授权（+106）。
反过来的话，角色会引用一批"码表里不存在"的权限，`/roles` 那条覆盖度断言会直接红
（GM 应拿「全部权限位 - 执行类」，码表没补时算出来是 91，而实际授了 114）。

补完自洽：GM = 115 − 1（`f.inspect.exec` 是执行类，通配 view/edit 覆盖不到）= 114 ✓

> 这是第三次撞到同一类问题：R-SEC 没有工单权限、组织负责人表正职错人，现在又是邻里权限。
> 共同点是**契约在"抄" PC 的时候只抄了当批新增的，没做全量对齐**。
> 下次动 PC 的角色/组织数据，建议顺手跑一次全量 diff，而不是等某次切换才暴露。

## 二十八、补上审批动作的权限校验（B 档遗留第 1 项）

### 28.1 原来是什么样

`POST /oa/requests/{approvalId}/action` **完全不校验"我是不是当前审批人"** ——
只要知道 `approvalId`，任何人（包括一线维修工）都能把别人的单审掉。

这是 B 档六轮里唯一一个**安全问题**，一直单独挂着，因为改它会牵动 4-5 条既有测试的数据设计。

### 28.2 怎么定的

难点在于：不能一刀切卡成"只认名单里的人"。

- **会签名单里常有副职**（副职不参与单签、只参与会签），而他们未必有登录账号；
- **集团总经理**是系统里最高一档，他发的单没有第二个人能批 —— 严格禁止的结果是他的单永远卡在「待审批」；
- 测试里大量用例是 `gm 发起 → gm 审`，切太狠会把它们全打掉。

所以分两层判定（`oaCanAct`）：

| 谁 | 结果 |
|---|---|
| 名单里的人 / 单人节点的 signer | 正常签，但**不能签自己发起的** |
| 集团总经理 | 允许**代签**，且豁免"不能审自己"（他上面没有人） |
| 该项目的项目经理 | 允许**代签**，但不豁免"不能审自己" |
| 其他任何人 | **403**，并告诉他这单卡在谁那里 |

最后的拒绝文案是有意写具体的：

```
这单卡在「部门负责人审批」，由 杜若曦 处理，不是你
```

而不是一句"无权限" —— 现场的人看到前者会知道去找谁，看到后者只会再点一次。

### 28.3 与待办列表的关系

`oaCanHandle`（列表用）和 `oaCanAct`（动作校验）是两件事：

- 前者回答"要不要把它放进我的待办"；
- 后者回答"我点同意会不会被放行"。

**代签规则只放在后者**：如果把"我能代签的"都算进待办，总经理的待办会变成全公司的单。

### 28.4 验证

| 项 | 结果 |
|---|---|
| `04 npm test` | **288/288**（+1 条动作权限断言） |
| `05 npm run verify:oa`（HTTP） | **7/7**（员工端审批链路没被误伤） |
| `05 npm run smoke`（mock） | **197/197** |

新断言守的三件事：

1. 一线员工（周明）点同意 → **403**，且文案说明卡在谁那里；
2. 被拒之后单据状态**没被动过**（时间线上没有任何人签过）；
3. 集团总经理代签**能过**（不豁免的话他的单永远卡住）。

「不能审自己」这一条没有单测：会签名单在生成时就排除了申请人，正常流程构造不出来，
真正触发它的是代签场景，硬造数据要改组织负责人，成本比收益高 —— 代码里保留了判断，注释写清了原因。

### 30.2 为什么这两条不能"照着 mock 抄一遍"

`saveOwnerField` / `saveHouseField` 背后不是简单的"改个字段"，而是一整套规则：

1. **字段白名单**：`OWNER_EDITABLE` / `HOUSE_EDITABLE` 逐字段带 label 与 `check()`；
2. **并发保护**：`checkVersion()` —— 两个人同时改同一条，后提交的拿 **409**，由页面提示刷新，
   **不静默覆盖**；
3. **唯一性**：业主手机号在档案里不允许重复（同号视为同一人，应走合并流程）；
4. **跨字段业务约束**：房屋 `useStatus` 改成"已入住/正在装修"前，要先看 `deliverStatus` ——
   未交房的房子不能被标成已入住，否则它当天就进计费与可出租候选，而钥匙还没交。

把这四条搬到服务端，工作量主要在**确认规则**（哪些字段可改、校验怎么写、409 怎么返回），
不在写 PATCH 本身。这是设计工作，不是移植。

### 30.3 拆分建议

| 步骤 | 内容 | 能否独立交付 |
|---|---|---|
| 3a | 读全切：住户名单 / 房屋详情 / 业主详情 / 租户详情 | ✅ 可以，纯读 |
| 3b | 租户动作切：核验 / 刷脸 / 退租 / 改租户信息（契约已有） | ✅ 可以 |
| 3c | 补 2 条 PATCH + 四条规则搬到服务端 + 字段白名单进契约 | 需要单独设计一轮 |

**不建议只做 3a、3b 就收工**：读切了、写还改本地种子，
结果是"改完手机号，刷新又变回去"——这正是工单那轮反复强调的"读写必须一起切"。
所以这个域要么整块做（3a+3b+3c），要么先不动。

1. **手机上用卡片，不用表格**。9 列在 375px 宽上没法操作；PC 那边是表格，两边布局不同但字段同一份。
2. **报销金额只读**，自动取明细合计。原来是一个手填金额，审批人无法判断"明细 800 / 报销 1000"该信哪个。
3. 明细一变就回写 `amount`：审批路径按金额分级（3000 两级、8000 三级），金额不同步会走错流程。

### 31.2 提交后的链路（跨端，务必知道）

```

```

**审批通过不等于已付款**：批了没付不算成本。这条口径与 PC 完全一致，端上文案也改成了这个说法
（原来写"批准即结束：报销批了不生成付款单"）。

   （PC 假服务已按这条实现：`mock-server.mjs` 的 `POST /oa/requests`）。

### 33.1 采购明细的九列

| 列 | 说明 |
|---|---|
| 物品名称 | 必填 |
| 型号规格 | 选填 |
| 单位 | 个 / 米 / 包 |
