# 租售信息模块 · 方案说明

> **状态**：待确认（2026-11-06 第四版 · 口径收齐）
> **归属**：物业管理系统的 A 域（房产与业主）独立子模块，**不进商业系统**
> **一句话**：业主把房子挂出来，责任楼管审一道；想租的人留下自己的电话，等楼管来联系。

---

## 一、边界：只做信息发布

| 做 | 不做 |
|---|---|
| 业主自助发布（认证 + 名下有房） | 物业代业主发布、代填价格 |
| 责任楼管审核（看人 / 看内容 / 看图） | 代业主议价 |
| 公开列表 + 详情（**游客可见，不需登录**） | 在线聊天、平台排期带看 |
| 访客留联系方式（「我要看房」） | **对外展示楼管手机号** |
| 楼管主动回拨、加微信 | 代收定金 / 租金 / 房款、按成交抽佣 |
| 业主或物业置「已成交 / 已下架」 | 自动生成租约、自动改产权 |

**唯一的分水岭：物业是否参与撮合与成交。**
一旦出现「经纪人」「带看」「佣金」「成交价」，性质就从"信息发布"变成"房地产经纪"，
需要《房地产经纪机构备案表》，微信类目也要换。

## 二、主流程

```
业主（认证 + 名下有房）
   │ 发布：价格 / 装修 / 配套 / 描述 / 图片（面积户型楼层只读，从档案带）
   ▼
系统校验产权 ──不通过──▶ 发布页都进不去（不是审核时才拦）
   │ 通过
   ▼
待审核 ──分派给该房的责任楼管──▶ 已驳回（必填理由，业主改后可重提）
   │ 通过
   ▼
已发布（公开：游客可看列表与详情，无房号、无业主信息、无楼管电话）
   │
   ├──▶ 游客看详情 ─┬─▶「我要看房」→ 留称呼 + 手机号 → 楼管收到待办 → 主动回拨
   │                └─▶「加楼管微信」→ 扫码 / 复制微信号 → 直接聊
   │
   ├──▶ 业主置「已成交 / 已下架」；物业可强制下架（须写原因）
   └──▶ 60 天自动过期 → 业主可续挂（内容未改则免审）
```

**没有"访客账号"这一层。** 游客不注册、不登录。留电话只是留一个号码，
不建账号、不进客户池——它是"这一次联系"的凭据，不是 CRM 线索。

| **楼管微信号 / 二维码**（员工填了才显示） | ✅ | ✅ | ✅ |
| **楼管手机号** | ❌ | ❌ | ✅ |

## 四、联系方式：访客留资为主，微信为辅

### 4.1 主路径：「我要看房」

```
点「我要看房」→ 表单：称呼 / 手机号 / 方便时间 / 留言（选填）
        ↓
生成一条「看房请求」（listing_viewing）
        ↓
进入该房责任楼管的待办 → 楼管回拨 → 标记「已联系」+ 写一句结果
```

- **不建账号**：不校验短信、不留 userId、不进客户池
- 页面上明确承诺：**"楼管会在 24 小时内联系你"**
- 同一手机号同一房源 24 小时内只能提交一次（防刷）
- 24 小时未联系 → 提醒楼管；48 小时仍未联系 → 升到直属上级（同审核超时那套）

**回拨时效是这套设计的生命线。** 不展示电话，访客唯一的出路就是等。
楼管不回，这条线索就死了，而且访客会记住"物业发信息没人理"。

### 4.2 访客的号码要保护，这是本版的新义务

责任方向变了：过去是"员工号码被全网看到"，现在是"访客号码交给物业"。
所以合规重心也要跟着换：

- **用途告知**：提交按钮下写明"该号码仅提供给本房责任楼管，用于本次看房联系"
- **不做营销**：不得进入任何推送、群发、二次营销名单
- **保存期限**：90 天后自动清理（成交或关单的立即清理）
- **可删除**：客服可按访客要求删除

这四条写进隐私政策和接口注释。不写，将来一定有人把这张表导出来做电话营销。

### 4.3 次路径：加楼管微信

员工在**员工端「我的 → 联系方式」**里自己维护：微信号、二维码图片。

- **不设"是否公开"开关**——填了就是愿意展示，没填就不显示。
  加一个开关只会出现"填了但关着"的困惑状态
- 详情页：有二维码就展示二维码 + 一行"或搜索微信号 xxx"；两者都没填就只留「我要看房」
- 填写页给一句说明："该信息会展示在租售信息页，供看房者联系你"

### 4.4 为什么不展示楼管手机号

三个理由，都成立：

1. **安全**：员工手机号一旦上页面，等于挂在公开互联网上，爬走、打包卖、骚扰电话都跟着来。
2. **合规**：对外公开员工手机号属于处理个人信息，需要单独同意；微信/二维码的暴露面小得多。
3. **可换**：手机号是员工私人的，换号就得改所有房源。微信号 / 二维码是工作身份，换人换号都不影响房源页。

### 4.5 二维码的风险

小程序内展示**个人微信二维码**，容易被审核判为「诱导添加好友 / 导流」——
轻则驳回该版本，重则影响类目评估。

降低风险的做法：

- 默认引导上传**企业微信二维码**（员工在企微里自己的活码），个人微信也允许但要弹提示
- 二维码加白底边框 + 一行"物业服务联系"，避免看起来像微商名片
- 一期字段和上传入口都做好，展示走条件判断（有就显示）；**默认只有少数楼管填了，等于灰度**

## 五、数据模型

### 5.1 `listing` 挂牌

```
listingId        LS000001
houseId          外键，唯一真相
ownerId          发布时的产权人（留证）
publisherUserId  发布账号（一期 = ownerId）
stewardEmpId     该房责任楼管快照（分派与审核依据；联系方式不存这里）
type             本期固定「出租」（出售留字段，不开放）
price            元/月
deposit          押金
payTerm          押一付三 / 押二付一 / 半年付
decorate         毛坯 | 简装 | 精装 | 豪装
facilities[]     冰箱 / 洗衣机 / 空调 / 热水器 / 宽带 / 家私
availableFrom    可入住日期
desc             ≤ 300 字
images[]         ≤ 9 张，含 watermark 标记
status           见第六节
contentVersion   内容版本号，任何展示字段变更即 +1
auditedVersion   审核通过时的版本号（判断续挂能否免审）
expireAt         发布后 60 天
auditBy / auditAt / rejectReason
offlineBy / offlineAt / offlineReason
dealAt
viewCount / leadCount
```

**不存** `area / layout / floor / communityId / buildingId` —— 从 `houseId` 派生。
**也不存** 楼管姓名 / 微信 / 二维码 —— 从 `employee` 实时取（换人换号自动生效）。

### 5.2 `listing_viewing` 看房请求

```
viewingId / listingId
name / phone / preferredTime / note
status      待联系 | 已联系 | 已带看 | 已关闭
createdAt / handledBy / handledAt / resultNote
expireAt    90 天后自动清理（合规要求）
```

不关联账号（没有 `visitorUserId`）。查重键：`phone + listingId + 24h`。

### 5.3 `employee` 扩展两个字段

```
wechatId        微信号
contactQrUrl    二维码图片
```

手机号不新增字段（本来就有），但**只用于内部与回拨，不对外展示**。

## 六、审核：归责任楼管，超时上升一级

**不设审核角色，按责任范围分派。**

```
houseId → buildingId → buildingStewards → 责任楼管
```

- 只有该楼栋的责任楼管能审；`assertInScope` 已有这个能力，直接复用
- **24 小时未审 → 升到该楼管的直属上级**，按 `orgLeaders` / 组织负责人解析，
  不写死角色名（当前组织下就是项目经理；将来设了"楼管组"自动变成组长）
- 升级后原楼管仍可审，只是不再是唯一入口；后台标红、看板单列「已升级」

### 状态机

```
草稿 ──提交──▶ 待审核 ──通过──▶ 已发布 ──成交──▶ 已成交
                 │                │
                 └──驳回──▶ 已驳回 │
                              │    ├──业主下架 / 物业强制下架──▶ 已下架
                        改后重提   │                              │
                              └────▶待审核                        └──重新上架──▶ 已发布
                                  │
                                  └──60 天──▶ 已过期 ──续挂──▶ 已发布
```

**审核只针对「内容版本」**：`contentVersion !== auditedVersion` 才需要再审。
业主原样续挂、原样重新上架，直接回到「已发布」——否则每 60 天全量重审一遍，
楼管会被这种重复劳动逼疯。

改变内容版本：改价格 / 改描述 / 换图 / 改装修配套。
不改变：下架、续挂、置成交。

## 七、关键校验

| # | 规则 | 落在哪 |
|---|---|---|
| 1 | 发布人必须是该房产权人 | 入口前置，不在名下进不了发布页 |
| 2 | 租户不能发（只有使用权，无处分权） | 同上 |
| 3 | 家属不能发（显式授权一期不做） | 同上 |
| 4 | 面积 / 户型 / 楼层只读，从档案带 | 表单层，不允许输入 |
| 5 | 审核人必须是该房责任楼管或已升级的上级 | 接口层 |
| 6 | **楼管手机号不入任何对外接口返回** | 接口层字段白名单 |
| 7 | 看房请求 24h 内同号同房只允许一条 | 接口层 |
| 8 | 看房请求 90 天自动清理；成交 / 关单立即清理 | 定时任务 |
| 9 | 楼管离职 / 换片区 → 房源重新分派，微信随之变化 | 定时任务 + 离职流程挂接 |
| 10 | 驳回必须写理由 | 接口层 |
| 11 | 强制下架必须写原因 | 接口层 |
| 12 | 同一 `houseId` 只能有一条在架出租挂牌 | 唯一约束 |
| 13 | 60 天自动过期 | 定时任务 |
| 14 | 单 IP 每日详情浏览上限（建议 60 条） | 风控，防同行批量采集 |

### 照片是唯一必须人眼看的一项（业主自拍，风险更高）

审核必看清单：

- 门牌号、单元号、楼栋号
- 邻居家的门、对门、楼道
- 窗外能看到的具体位置（能定位到哪栋）
- 可识别的个人物品：家庭合照、证件、快递单、工牌
- 是不是网图 / 样板间图（这套房楼管去过，应该认得出来）

话术一句话：**"这张图能不能让陌生人找到这户人家"**——能，就驳回。

价格不做人工干预。物业没有定价权，管了就变成"你凭什么说我的房子不值这个价"。
只在偏离小区均价明显（低于 50% / 高于 200%）时给提示标签，**不拦**。

## 八、类目风险与 Plan B

**风险等级：中偏高。** 详情完全公开、连登录都不要，审核员看到的就是一个对外开放的
租房信息页。按"功能实质"判，完全可能要求补「房地产服务-房产中介/经纪」。

三条降低概率的做法：

1. **措辞干净**：不出现「中介 / 经纪 / 佣金 / 成交价 / 带看 / 委托代理」。
   用「业主发布的租售信息」「我要看房」「楼管会联系你」。
2. **不展示经纪人身份**：没有经纪人头像、从业年限、成交记录卡片。
   楼管就是楼管，"责任楼管：莫瑞"是物业服务标识，不是经纪身份。
3. **提审主动说明**：信息由业主提供并授权发布，物业仅代为展示、由楼管答复咨询，
   不参与交易与议价。

**Plan B**：若被要求补类目而物业无备案，把 `visibility` 从 `公开` 改成 `认证可见`——
退回"只有本小区认证业主能看"。产品不用重做，只是少一批受众。
**所以可见范围必须是配置项，不能写死。**

> 代价要认：一旦退回认证可见，外面的人看不到，这模块价值折掉大半。
> 提审前，文案与界面元素就按最保守的准备一遍。

> 代码在 `03-原型`，方案与实现有三处细微差异，以本节为准。
