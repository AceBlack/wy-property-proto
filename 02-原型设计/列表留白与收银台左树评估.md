# 列表页右侧留白 & 收银台左侧树 · 分析与方案

> 状态：**仅分析，未改代码**　生成时间：2026-10-23
> 结论基于 Element Plus 源码 + 浏览器实测（Chrome headless，视口 1440 / 1600 / 1920）

---

## 〇、结论先行

### 问题一：列表页右侧大面积留白

**根因只有一个**：这些页面的主表格**每一列都写死了 `width`，没有任何 `min-width` 弹性列**。

Element Plus 的列宽算法（`table-layout.mjs`）只有在存在「没有 `width`、只有 `min-width`」的列时，
才会把容器剩余宽度按比例分给这些列；一个弹性列都没有时，它直接把 `bodyWidth` 设为列宽之和，
**容器多宽都留白**，且不会触发横向滚动。

因此这不是「页面宽度异常」，而是「表格宽度正常、列宽分配缺了一个弹性列」。
左侧 248px 的树只是把可用宽度压小了 264px，**不是主因**——同样带树的房屋台账、业主档案留白为 0，区别只在它们首列用了 `min-width`。

### 问题二：PC 收银台是否加左侧树

**结论：不建议加常驻左树。**

- 中栏账单表在 1600px 视口下正好 656px、7 列刚好铺满，**零余量**；再切 248+16px 给树，中栏只剩 392px，必然横向滚动、关键列被推出视口。
- 1440px（笔记本主力分辨率）当前已经是 496px < 602px 需要横向滚动，加树后彻底不可用。
- 数据侧只有 **16 栋 / 30 个单元 / 3 个项目**，树最多 3 层、每个项目 ≤16 个叶子，信息密度撑不起 248px 的常驻栏。
- 收银台的核心动线是「业主报姓名 / 房号 / 手机」→ 搜索命中，按楼栋逐层点选是低频路径；且搜索框已支持房号、手机号、身份证后四位，中间栏还有按房屋切换的 radio。

替代做法见第四节，推荐「左栏顶部楼栋/单元级联」或「按需抽屉树」。

### 1.3 源码依据（`node_modules/element-plus/es/components/table/src/table-layout.mjs`）

```js
const flexColumns = flattenColumns.filter((column) => !isNumber(column.width));  // L98
if (flexColumns.length > 0 && fit) {                                            // L102
  if (bodyMinWidth <= bodyWidth) {
    const totalFlexWidth = bodyWidth - bodyMinWidth;                            // L108
    if (flexColumns.length === 1) flexColumns[0].realWidth = minWidth + totalFlexWidth;
    else { /* 按各弹性列 minWidth 比例分摊 */ }                                  // L111-119
  }
} else {                                                                        // L129
  flattenColumns.forEach(c => c.realWidth = Number(c.width || c.minWidth));     // L130-133
  this.bodyWidth.value = bodyMinWidth;                                          // L136  ← 表格只剩列宽之和
}
```

`table-column/render-helper.mjs:40` 是关键判定：`if (!realWidth && realMinWidth) column.width = undefined`
——**只有「没写 width、只写 min-width」的列才会进入 flexColumns**。写了 `width` 的列永远不参与分配。

## 二、为什么偏偏是这 12 个页面

三个条件叠加，缺一不可：

1. **列配置全固定**：主表每一列都给了 `width`（数值列本就该固定，但文本列也固定了）；
2. **没有兜底弹性列**：没有任何一列用 `min-width`；
3. **外壳变宽**：`.app-body` 随窗口拉满（1920 下内容区 1700px），固定列不跟涨。

左侧 `.ia` 树（248px + 16 gap）只是让「表格容器」变窄 264px，放大观感，不改变机制。
证据：带树的房屋台账/业主档案留白为 0；不带树的考勤/工资表同样留白 392 / 350。

## 三、问题一：修正方案

### 3.1 P0 · 把「文本类列」改成弹性列（唯一必要动作）

原则：

- 每个主表挑 **2–3 个文本类列** 从 `width` 改为 `min-width`（数值、金额、日期、状态、操作列保持固定）；
- 弹性列统一加 `show-overflow-tooltip`，防止长文本撑破；
- 多设几列而不是只设一列——EP 按 `minWidth` 比例分摊，单列会一个人吃掉 400–500px，看起来同样别扭。

逐页建议（列名按当前表头）：

预期效果：1920 下上述页面右侧留白归 0，操作列贴右；1600 下表格填满面板；1440 下仍可横向滚动（列不被压缩截断）。

补充：这些页面的左树本来就有「收起」按钮（`treeCollapsed`），空间紧张时可回收 264px，属于已有能力，无需改动。

**不动**：抽屉内的明细小表（宽度本来够）、`el-table` 的 `height/max-height`、任何数据与业务逻辑。

### 3.2 P1 · 把规则沉淀下来

- 在 `README` 的「工程纪律」里加一条：**主表格至少要 2 个 `min-width` 弹性列，否则宽屏必然留白**；
- 新页面自查：把窗口拉到 1920，看表格右边缘是否与面板内边距齐平。

### 3.3 P2 · 可选：内容区最大宽度

1920 以上屏幕，14 列拉满 1652px 会显得很空。可选：

```css
.page { max-width: 1680px; margin-inline: auto; }
```

- 优点：超宽屏观感稳定，不需要给每列都设弹性；
- 代价：会改变全站（含 KPI 卡片）的观感，右侧出现对称留白，属于设计决策；
- 建议：**先只做 3.1**，看效果再决定是否加。默认不加。

### 3.4 明确不采用的做法

| 做法 | 为什么不行 |
|---|---|
| 表格末尾加一个空 `<el-table-column>` 占位 | 会进入导出列、读屏、列设置，属于「用数据补样式」 |
| `:fit="false"` | 更糟：所有列都按声明宽，留白照旧 |
| `.el-table { width: fit-content }` | 表格比面板窄，右侧露出面板底色，问题更明显 |
| 全局 CSS 覆盖 `colgroup col:last-child { width:auto }` | EP 用 JS 算 `realWidth` 并写进 colgroup，CSS 会被下一次 layout 覆盖 |
| 给「操作」列设 `min-width` | 按钮区被拉宽，视觉更差 |

## 四、问题二：收银台左侧树评估

### 4.1 现状结构

```css
.cashier { display: grid; grid-template-columns: 284px minmax(0, 1fr) 320px; }
```

三栏：左「业主」列表（284）· 中「待收账单」表（自适应）· 右「结算」（320）。

实测（选中一位业主后）：

| 视口 | 内容区 | 三栏实际 | 中栏账单表 | 7 列所需 | 状态 |
|---:|---:|---|---:|---:|---|
| 1440 | 1220 | 284 / 536 / 320 | 496 | 602 | **已横向滚动** |
| 1600 | 1380 | 284 / 696 / 320 | 656 | 656 | 刚好铺满、零余量 |
| 1920 | 1700 | 284 / 1016 / 320 | 976 | 976 | 有余量 |

### 4.2 加 248px 左树后的推演

树列 248 + gap 16 = 264px，从中栏扣除：

| 视口 | 中栏 | 账单表 | 结果 |
|---:|---:|---:|---|
| 1440 | 272 | 232 | 7 列 602px 塞进 232px，**4/5 的列不可见** |
| 1600 | 432 | 392 | 仍差 264px，**必须横向滚动** |
| 1920 | 752 | 712 | 勉强可用（唯一能看的分辨率） |

也就是说：加了树，**只有 1920 及以上能正常用**，而收银台是前台的高频操作页，1440/1600 才是主力。

### 4.3 必要性判断

支持加树的理由（成立但弱）：

- 上门收费/按楼栋扫楼时，需要「项目 → 楼栋 → 单元 → 业主」的浏览路径；
- 只知道房号时，逐层点选比输入更直观。

反对理由（更强）：

1. **数据密度不够**：全库 3 个项目、16 栋、30 个单元，树只有 3 层、单项目最多 16 个叶子——248px 的树大概只有半屏内容，剩下是空白；
2. **主路径已被覆盖**：搜索框支持「姓名 / 房号 / 手机号 / 身份证后四位」，业主列表已按欠费排序，中间栏还有按房屋切换的 radio；
3. **成本直接由中栏承担**：树挤压的是「待收账单」——这是本页唯一不可替代的区域；
4. **与本项目 IA 一致性问题**：其他页的 `.ia` 树是「范围筛选」，收银台加树会变成「导航 + 筛选」双重语义，容易和其他页混淆。

### 4.4 结论

**不做常驻左侧树。** 若确实需要楼栋维度，按性价比排序：

| 方案 | 做法 | 代价 | 推荐度 |
|---|---|---|---|
| **A（推荐）** | 左栏顶部加一行「楼栋 / 单元」两个级联下拉（284px 内），选中后过滤业主列表，并显示「清除」 | 0 额外宽度，只动左栏 | ★★★★ |
| B | 左栏标题右侧加「按楼栋浏览」按钮，点开抽屉树（width 360），选完关闭 | 不改栅格，多点一次 | ★★★ |
| C | 常驻树，但仅在 ≥1800px 展开、<1800 收起（可手动展开） | 需要响应式 + 折叠态，中栏在 1600 下仍会挤 | ★★ |
| D | 常驻树，同时把结算区改成抽屉 | 结算区常驻是这个页面的核心体验，不建议动 | ★ |

如果最终仍要选 C/D，最低边界条件：树 200px、中栏保底 560px、<1800 默认收起、结算区不得窄于 300px。

## 五、验收标准（落地后按此验）

1. 1920 / 1600 两档：目标页面表格右边缘与面板内边距齐平，**留白 ≤ 2px**，操作列贴右；
2. 1440 档：允许横向滚动，但列宽不得被压缩到文字截断（保持声明宽度）；
3. 任一页面不出现「列宽之和 > 容器且无滚动条」的组合；
4. `npm run build` 通过，首屏 chunk 不增长（只改列属性，预计 +0.1KB 以内）；
5. 12 个页面逐页截图对比，无 console 错误；
6. 收银台（若按方案 A）：1600 下中栏仍为 696px，账单表不出现横向滚动。

## 六、影响面与风险

- 只改模板里的列属性（`width` → `min-width`），不动数据层、不动交互逻辑、不影响导出（导出列是独立配置）；
- 风险点：弹性列变宽后长文本撑行 → 统一加 `show-overflow-tooltip`；
- 风险点：`组织与权限` 有 4 张表（成员/角色/数据权限/抽屉），需三张主表都改，避免切 Tab 后仍留白；
- 工作量评估：12 个页面 ≈ 12 处模板改动，0.5 人日内可完成并逐页截图验收。

## 七、落地记录（2026-10-23）

### 7.1 列表留白

**做法微调**：原方案是「每表 2–3 个弹性列」，实测发现宽屏下剩余宽度会被这 2–3 列按比例吞掉
（1920 下「业主」被拉到 299px、「承载对象」463px），观感同样别扭。
最终改为：**主表所有数据列统一用 `min-width`，只保留「选择列 / 操作列 / 固定列」为 `width`**。
剩余宽度按各列 minWidth 比例均匀分摊，相当于整体等比放大，1920 下各列落在 135–190px，视觉自然。

已改 12 个页面 / 14 张表（组织与权限 3 个 Tab 各一张）：

| 账单查询 | 8 | 544 → 0 |

### 7.2 收银台

按 **A 方案** 落地：未新增栅格列，左栏（284px）顶部加「楼栋 / 单元」两级下拉 + 范围提示 + 清除。

- 数据层新增 `cashierBuildingOpts` / `cashierUnitOpts` / `cashierOwnerRoom`，并扩展
  `cashierOwnerList(kw, { buildingId, unitId })`：按「业主名下任一房屋落在范围内」过滤，按房号排序，单栋上限 60 户；
- 左栏业主条目在选中楼栋/单元时显示具体房号（如「1栋1单元0101」），不再只显示「N 套房」；
- 换范围后若当前业主不在结果里，自动落到第一位，避免中栏/右栏停留在范围外的人。

实测（1600px）：三栏仍为 284 / 696 / 320，账单表 656px、无横向滚动；
选「翡翠城 1栋」→ 42 位业主，再选「1单元」→ 22 位，清除后回到默认 8 位（演示 + 欠费 Top）。
