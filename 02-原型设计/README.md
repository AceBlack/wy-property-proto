## 四、三条最容易踩的坑

1. **`tokens.css` 的引入顺序**。Element Plus 的样式是运行时注入的 CSS 变量，`tokens.css` 必须在其后引入才能真正覆盖 `--el-color-primary` 等变量。顺序反了会表现为「改了没生效」。
2. **EP 把组件变量定义在组件作用域**。`--el-table-*`、`--el-pagination-*`、`--el-checkbox-input-*`、`--el-datepicker-*` 写在 `:root` 无效，必须写成 `.el-table {}` / `.el-pagination {}` 这样的组件选择器（见 `tokens.css` §16）。这是「变量改了没反应」的第二大原因。
3. **`bills.json` 有 2.4MB**。原型阶段按需 import 即可，正式开发一律改接口分页，不要把全量账单塞进前端。

**两条工程纪律（踩过坑，务必保持）**：

1. **写操作必须同步派生行**。`api.js` 里 `OWNER_ROWS / HOUSE_ROWS / WO_ROWS / NOTICE_ROWS / PLAN_ROWS / EMP_ROWS / ROLE_ROWS`
   是模块级派生数组，只改原数组会出现「保存成功、列表不变」。写操作统一走 `_syncXxxRow(row, { insert })`。
2. **内联编辑的值由组件自持**。`InlineField` 保存成功后自己显示新值，不等父组件回填
   （详情抽屉里父级数据常被整体替换，回填不一定触发该字段重渲染）。
3. **权限矩阵要读「生效权限」而不是原始字典**。`permissionMatrix()` 走 `rbac.permCodesOfRole()`，
   保存后再 `syncRolePermsRow()` 回写 `ROLE_ROWS`；否则会出现「菜单已收紧、抽屉仍显示 50/50」。
4. **数据范围只在数据层收一次**。列表与汇总统一走 `scopeFilter()`，页面不各写一套；
   新增列表查询时记得挂上，否则会出现「菜单看着对、列表越权」。
5. **表格数据列用 `min-width`，只有「选择 / 操作 / 固定列」用 `width`**。Element Plus 的列宽算法
   （`table-layout.mjs`）只在存在 `min-width` 弹性列时才分摊剩余宽度；全写死 `width` 会在宽屏右侧留白
   （实测 1920 下最多 554px），且「操作」列的 `fixed="right"` 因无横向溢出而不生效。
6. **KPI 汇总也要跟着写操作刷新**。转工单、改状态后若 KPI 是 setup 时算好的普通对象，数字就不动。
   汇总统一做成 `ref(...)`，写成功后 `summary.value = xxxSummary()`；左树计数同理。
7. **写操作前先分清「原数组」与「派生数组」**。`api.js` 里 16 个 `*_ROWS` 都是 `{...}` 浅拷贝：
   列表 / 树 / 汇总读派生数组，`feeSummary` / `debtPoolRows` / `houseRow.debt` 读**原数组**——
   只改一边就出现同会话数字不一致（如「账单列表已缴、催缴台仍显示欠费」）。
   第 9 批逐一对账后补齐 `_syncBillRow` / `_syncHouseRow` / `_syncPayRow`；新增写操作先确认两边都改。
8. **枚举值必须与字典一致，且不要硬编码 ID**。第 9 批抓到两处：`deductPrepay` 写「部分缴费」
   （全站口径「部分缴」）→ 部分缴费账单整笔从欠费统计消失（抵扣 500 元却错降 1,194.08 元）；
   `generateShareBills` 把科目 ID 硬编码成 `FI07`（车位管理服务费）→ 736 笔公摊账全算进车位费、
   FI03 公共能耗分摊为 0。状态与字典 ID 一律按名称反查或引用常量。

## 六·补、巡检体系职责划分（第 10 批 P0，2026-10-29）

原先的巡检模型把「一线作业」和「管理」混在一起：执行页挂在后台菜单、任何能看列表的人
都能代填结果、也没有「谁去核验下属」这一层。按业务口径重构为三级，**配置权与执行权分离**：

```
物业公司 · 品质管理部（品质督导 = 品质经理）
├── 维护【执行模板】→ 告诉一线员工「做什么、什么算合格」
├── 维护【监督模板】→ 告诉部门经理「查下属哪些方面、什么算不合格」
└── 下达【监督计划】→ 指派到具体部门经理
        ↓
各项目 · 各部门（组）· 部门经理 = 组长
└── 只做现场核验：抽查下属责任区实际达标情况 → 发现问题 → 指定责任员工
        ↓
一线员工：按执行模板作业、留证、提交（移动端）
        ↓
品质督导：按部门 × 周期聚合 → 加权达标率 → 生成品质检查记录
```

### 职责边界（后台 vs 移动端）

| 模块 | 后台（PC） | 移动端 |
|---|---|---|
| 任务类型 / 检查模板 | ✅ 品质督导配置，其余角色只读 | 只读（据此渲染表单） |
| 巡检计划 | ✅ 品质督导建计划并指派 | 只读（接收排班） |
| **任务执行** | ❌ **不做**（仅监管视图：完成率 / 异常 / 超时） | ✅ 接单 → 打卡 → 逐项判定 → 拍照 → 异常转单 |
| **监督核验** | 配置规则、查复核记录与统计 | ✅ **部门经理专属**：现场核验 → 标记问题 → 指定责任员工 |
| 品质评价 | ✅ 聚合执行数据 → 加权 → 出记录 | 只读 |
| 报表 | ✅ 全部 | ❌ |

## 六·补2、整改闭环与主管考核（P3，2026-10-29）

评价只解决「打多少分」，还差两件事：**分低之后谁去改、改没改完**，以及**主管到底查不查**。
P3 补的就是这两条，并让它们与评价结果咬合。

### 1. 整改闭环 `/f/rectify`

流程与状态机（四态 + 两个派生标记）：

```
开单 ──▶ 待整改 ──提交整改──▶ 待复核 ──复核通过──▶ 已闭环
              ▲                    │
              └────── 已退回 ◀──────┘（退回后整改项归零，需重做再提交）
派生：overdue（过期限未提交） / recheckOverdue（提交后 >3 天未复核）
```

- **开单来源**：现场抽查记录（76 条有扣分项的记录自动派生整改单，问题项沿用评分卡的问题库）、
  任务评价自动开单、手动开单；整改单是**独立台账**，不塞进品质记录里就地展开。
- **责任归属**：区域 → 责任班组（园区外围/车库→安保、设备房/机房→工程、大堂/公区/绿化→环境），
  责任人取该班组一线岗位，可「改派 / 延期」。
- **与评价联动（三处）**：① 评价不合格（<70 分）自动开单，问题项取该部门本期监督任务查出的问题
  （带责任员工）+ 抽查问题；② 整改项进度实时回写品质记录的 `rectifyCount / rectifyDone`，
  记录状态随「待整改 / 待复核 / 已闭环」变化；③ 删除评价时联动删除其整改单，不留悬空单号。
- **一处克制**：不允许「提交人自己复核」（提交人 = 复核人时直接报错），避免闭环自证。

### 2. 主管发现问题数 `/f/sup-finding`（独立考核报表）

| 指标 | 口径 |
|---|---|
| 统计对象 | 部门经理本人提交的**监督**任务（一线执行任务不计） |
| 发现问题数 | 监督任务 `issueCount` 合计，每项必须指定责任员工 |
| 次均问题 / 检出率 | 发现问题 ÷ 已完成监督任务 / 发现问题 ÷ 检查项总数 |
| 申报冲突 | 下属当日申报「零异常」却被组长查出问题的次数（自动比对，非人工填写） |
| 抽查未发现 | 评价记录录入的 `crossIssues`；未评价时按同项目同月「现场抽查」扣分项依区域折算 |
| 主动发现率 | 自查 ÷（自查 + 抽查未发现） |

- 展示维度：**按主管**（考核明细，可下钻到该主管本期每一条监督任务与问题项）与**按部门**（汇总）双视图，
  右侧配「发现问题排名」条形，报表中心同步注册 `sup-finding`（可导出）。
- 排除项：无监督任务的班组不进表；下钻抽屉只读，写操作仍归移动端作业台。

**实测（2026-10）**：11 名主管 / 监督任务 29-33 / 发现问题 27 项 / 次均 0.93 / 申报冲突 5 次 /
主动发现率 14%（10 月抽查未发现 166 项）——「主管自查覆盖率低」这个结论是数据算出来的，不是写死的。

### 3. 种子扩充（不消耗 PRNG）

监督计划 6 → 11（补齐三个项目的工程 / 客服组），监督任务 12 → 66（每名主管覆盖近 6 周，
问题数按主管做出梯度），任务总量 240 → 306；权限位 55 → 58（`f.rectify` view/edit、
`f.supFinding` view），角色按「品质督导配置+复核 / 部门经理提交+查看 / 项目经理双向」分配。

## 六·补3、租户口径修正（P4，2026-10-29）

### 定性（用户确认）

> 租户是**业主**出租产生的，不是物业出租；租户信息（含新增）**主要由业主在小程序维护**；
> 物业可**代为补充或修正，保存即生效**（不需要业主二次确认），且补充动作要能在
> **「租户到场代缴物业费」的收银台流程里完成**。物业不是出租方 ⇒ **租金不进后台**。

一句话：物业要的是「这套房现在住着谁」，用于门禁人脸、通知触达、上门服务；不是替业主管租约。

### 「租约管理」→「在住人管理」的具体改动

| 处理 | 内容 | 理由 |
|---|---|---|
| 删 | KPI「月租金合计 / 平均月租」、列表「月租」列、详情「年租金」 | 租金是业主与租户的商业条款，物业既不掌握也不该考核 |
| 删 | 主按钮「新增租约」→ 改「代业主登记」；「发起续租」→ 删除 | 物业无权签/续租，只能代录与提醒 |
| 删 | 左树（项目/楼栋/单元） | 租户有唯一检索键（姓名/电话/房号），树只是三次点击换 5 行结果；状态与范围本应可叠加，树让二者互斥 |
| 改 | 状态语义：生效中/即将到期/已到期 → **在住 / 已搬离**（届满只提醒，不自动改状态） | 合同状态 ≠ 在住状态，搬离必须人工确认 |
| 加 | `source`（业主自助 / 物业补录）、`verifyStatus`（待核验 / 已核验 / 信息不全）、`relation`、`residents` | 数据主权在业主，物业侧必须能看出"谁录的、核过没有" |
| 加 | 顶部快捷视图（全部在住 / 待核验 / 信息不全 / 未实名 / 未录人脸 / 90 天内届满 / 已搬离）+ 项目·楼栋·单元·核验·来源筛选 | 状态与范围**可叠加**（例如「翡翠城 + 待核验」26 条） |
| 加 | 信息完整度：8 项口径（姓名·手机·证件·实名·人脸·关系·居住人数·紧急联系人），其中 6 项基础信息是**核验门槛** | 补什么、能不能核验，要有一把尺子 |
| 加 | 操作闭环：补充信息 → 核验通过（=实名成立）→ 录入人脸（门禁授权）→ 标记搬离（停用门禁、释放房屋） | 物业该做的三件事：核验、补全、失效 |

## 六·补4、楼栋责任范围（P5，2026-10-29）

### 需求（用户确认）

### 模型：三级粒度 + 两张数据

| 层级 | 落点 | 说明 |
|---|---|---|

## 六·补5、数据安全：敏感字段与导出留痕（P6，2026-10-29）

### 需求

> 用户信息（业主 / 租户的姓名、手机、证件）比较敏感，需逐级管理并隔离权限。

P5 解决的是「**看不看得到这一行**」（责任范围），P6 解决的是「**看得到这一行，但是不是能看到明文**」——两层叠加：

| 层 | 手段 | 落点 |
|---|---|---|
| 行级 | 数据范围六档，责任范围默认拒绝 | `scopeFilter(..., { house })` |
| 字段级 | 敏感字段默认脱敏 + 揭示留痕 + 导出校验 | `maskSensitive` / `revealSensitive` / `prepareExport` |

### 敏感字段白名单

`phone / mobile / emergencyPhone / idCard / bankAccount` 五个 prop 登记在 `SENSITIVE_FIELDS`，
只有登记过的列才参与脱敏、留痕与导出校验（其他字段一律不动，避免误伤）。

- **展示**：`<SensitiveText>` 统一渲染 → 默认 `138****8001` / `5101**********1231`，点眼睛才出明文；
- **留痕**：每点一次写一条 `查看明文`（操作人 / 角色 / 组织 / 对象 / 字段 / 来源页面 / 时间）；
- **编辑**：`InlineField` 加 `sensitive` 属性 —— 未揭示时不允许直接编辑（否则会把掩码值存回去）；
- **逐级**：`a.sensitive.view` 决定能不能揭示，角色矩阵里取消该位即刻生效。

### 权限位（60 → 62）

| 权限码 | 名称 | 分配 |
|---|---|---|
| `a.sensitive.view` | 敏感字段明文 | 楼管 / 客服 / 收银员 / 项目经理 / 部门经理 / 财务 / 人事（**只读观察员不给**，按外部审计口径只看脱敏） |
| `e.accessLog.view` | 数据访问日志 | 总经理 / 项目经理 / 人事 / 只读观察员 |

`a.sensitive.view` 的 `route` 故意留空：它不是一个页面，而是「在页面上点开脱敏值」的能力，
绑路由会抢掉 `/a/owners` 的页面守卫（`permCodeOfPath` 按 route 精确匹配取第一个 view）。

### 导出校验（`prepareExport`，页面 → 下载中心唯一入口）

| 情形 | 处理 | 日志结果 |
|---|---|---|
| 含敏感列 + 有明文权限 | 明文导出 | 成功（说明里标「含敏感字段 X（明文）」） |
| 含敏感列 + 无明文权限 | **自动改脱敏值导出**（不拦截，避免业务停摆） | 脱敏 |
| 条数 > 200 | 照常导出 | 成功，说明标「大额导出」 |
| 条数 > 系统配置「导出单次上限」 | **直接拦截，不产生下载任务** | 拦截 |

### 页面

| 页面 | 改动 |

| `/e/access-log`（新页） | 4 KPI（查看明文 / 涉及对象 / 导出任务 / 脱敏·拦截）+ 动作·结果·操作人·时间·关键字筛选 + 明细表 + 导出；<b>只增不删，无删除入口</b> |

## 六·补6、列表骨架收敛：A 型保留 4 页，其余全部转 B 型（2026-10-29 夜）

### 决策依据

树承担四类职能：①定位 ②盘点 ③定范围 ④承载虚拟视图。判断公式：

> **目标本身是空间实体、且用户需要「发现未知」→ 树必需；用户带着唯一键来（单号/车牌/人名）→ 树的①③用不上，只剩②④，而②④不需要 248px。**

另加一条实测出来的硬伤：**⑤ 状态维度与空间维度能否叠加**。原实现里 `onPick` 先 `Object.assign(query, BLANK)` 再套节点，
而虚拟视图节点的 `patch` 又把 `communityId/buildingId/unitId` 置空 —— **点「已逾期」就清掉楼栋**，
「1 栋的已逾期账单」这种最常用组合根本筛不出来。

### 最终分档

| 档 | 页面 | 理由 |
|---|---|---|
| **A 型（保留树）** | 房屋台账、业主档案、车位与车辆、组织与权限 | 空间/组织本身是主键，需要「盘点未知」（哪些房空置、哪栋还有闲置车位） |
| **B 型（去树）** | 租户管理、账单查询、缴费流水、工单列表、品质检查记录、通行记录、合同管理、公告通知 | 主键是人/单号/车牌/时间；树只剩「定范围」，而范围用 3 个下拉更快，且能与状态叠加 |

### 新增两个公共组件（避免 8 页各写一遍）

| 组件 | 职责 |
|---|---|
| `QuickViews.vue` | 带计数的单选 chips（`items[{key,label,n}] + v-model`），替代原树的虚拟视图节点；支持 `#after` 插槽放附加开关 |
| `ScopeFilter.vue` | 项目 → 楼栋 → 单元级联（`levels` 可只保留项目），改上级自动清下级；发出 `patch` 事件而不是直接改 prop |

配套 CSS：`.ia.is-flat`（去掉 248px 左列）、`.scopebar__sum`（范围小计）、`.qvwrap`（chips 行与筛选栏的分隔线）。

### 逐页迁移要点

| 页面 | 树原来给什么 | 迁移后 |
|---|---|---|
| 账单查询 | 项目→楼栋→单元 + 4 个状态节点（带应收/欠费金额） | 5 chips + 3 级筛选；**新增「范围小计条」**（张数 / 应收 / 未收 / 有欠费张数）承接树节点金额 |
| 缴费流水 | 同上 + 「车位收费」分支 | 同上；车位收费 → **「只看车位收费」开关**（可与视图叠加）；小计给笔数/金额/现金/未开票 |
| 工单列表 | 项目→楼栋→单元 + 「公共/非入户」分支 | 5 chips + 3 级筛选；无房屋工单 → **开关**；「哪栋报修集中」改由**报表**回答 |
| 品质检查记录 | 项目 → 区域（保洁/安保/工程/客服） | 6 chips + 项目 + **区域下拉**；区域是业务条线不是空间层级 |
| 通行记录 | 项目 → 车库区域 | 5 chips + 项目 + **车库区域下拉**；道闸跨项目复用，只能做筛选 |
| 合同管理 | 类型 → 子类型 | 6 chips + **类型/子类型下拉（联动）** + 状态 + 项目 |
| 公告通知 | 类型 → 项目 | 6 chips + **类型下拉** + 状态 + 项目 |
| 租户管理（P4 已改） | — | 同一套骨架，本次统一到公共组件 |

去树后「哪栋报修集中」不能靠翻树，改由报表回答：`项目 / 楼栋 / 工单数 / 未闭环 / 已超时 / 紧急及以上 / 涉及户数 / 每百户工单 / 主要类型`，
按工单数倒序（实测 14 栋，最高翡翠城 6栋 4 单）。

## 六·补9、派生值怎么算：报表改为跑批快照（2026-10-30 拍板）

**决策**：欠费账龄 / 收缴率 / 部门达标率这类**派生值不做实时查询**，由夜间跑批算好落库，页面读统计批次快照。

三条理由（写在 `api.js` 的注释里，免得以后有人改回实时）：

1. 账龄 = 统计日 − 到期日，实时算会让同一张表每刷新一次变一个数；
2. 审计要能回答「上个月报表当时长什么样」，实时算答不了；
3. 部门达标率要扫全量巡检明细，实时算会把列表拖到秒级。

### 一、原型侧怎么落

| 能力 | 落点 | 口径 |
|---|---|---|
| 快照存储 | `api.js` 的 `REPORT_SNAPSHOTS` | 模块加载即「跑一次夜批」，算完**冻结**；之后改账单不影响已生成批次 |
| 统计批次 | 报表页页头下拉 | 2026-10-19 / 10-20 / 10-21 三批；一天一批，一批里 3 张表（`RPT-20261021-01/02/03`） |
| 批次元信息 | 页头一行 | 生成时间 / 数据截止 / 公式版本 / 行数 / 耗时；落后最新批次给「落后最新批次」标签 |
| 重算 | 「重算」按钮 | 异步任务 → 轮询 → 生成新批次并跳转；同参数运行中不重复建批次（幂等） |
| 范围 | 读取时裁行 | 批次**全局算**，越权在读取时按行过滤（与契约一致，不是两套口径） |
| 失败批次 | 保留 | `dept-target` 10-20 留了一条失败批次：能查失败原因，但不参与「最新成功批次」选取 |

### 二、报表中心变化

- 新增分组 **G 统计（跑批）**：`欠费账龄统计`（楼栋 × 账龄）、`收缴率统计`（账期 × 科目）。
- `部门达标率` 改为快照版（列里补「已完成」，去掉与口径无关的「申报冲突」）。
- 其余明细类报表（费用明细 / 欠费明细 / 未收费房屋 / 缴费明细 / 营业报表 / 押金 / 报修 / 巡检 / 主管发现数 / 工单按楼栋）仍是**实时查询**——
  明细按行查更合适，物化收益不大。卡片上带「跑批」标记，一眼能分清。

### 六、月报 / 年报：期次模型（2026-10-30 拍板）

拍了两条板：**月报＝月结后一次算，当月给试算值**；**年报拆两张表——余额（时点）与发生额（区间）**。

| 类型 | 报表 | 月报 | 年报 | 能否由日快照累加 |

### 九、月结落进契约 + 反结（2026-10-30 夜）

上一批的月结只在原型里跑通，接口没进契约——因为三条口径没定。这一批按行业惯例定了，并写进契约：

| 问题 | 答案 | 理由 |
|---|---|---|
| 谁有权结 | `b.monthClose.submit`（财务），**项目经理没有** | 封账是财务动作。让项目经理封自己项目的账，等于让他自己掩盖欠费 |
| 能不能反结 | 能，`b.monthClose.reopen`（更高一级）+ 必填 ≥10 字原因 | 不允许反结的结果是有人去数据库改数，那才是真正的失控 |
| 结完能改什么 | 该期流水 / 退款一律 409 / 40903 | 退款会改上月已封存的收款与欠费，必须「反结 → 改 → 重结」 |

**反结做四件事，一件都不能省**：记录置「已反结」（留 `reopenReason` / `reopenCount` / `reversalNo`）；
该期报表批次标 `voided`（保留可查，不删除）；期间恢复可写；报表实时回到 `provisional=true`。

两个在实现时才想明白的点：

1. **`provisional` 必须实时算**，不能用建批次时存下的值。反结后旧批次仍是那份冻结的数，但它已经不是定稿了——
   状态属于**期间**，不属于批次。这一条不改，反结后报表会一直显示「定稿」，比不显示更误导。
2. **反结不写进退款流水**。反结不是退款，混进去会让「退款金额」统计失真；它有自己的红冲凭证号。
   （契约里本来写的是"生成一条反结流水"，实现时发现这个坑，已把契约措辞改掉。）

### 十、批次保留与清理

日快照一天 3 张表，一年 1000+ 批次。设了保留策略：**日 90 天 / 月 24 期 / 年永久**，
且**已月结期间的批次一律受保护**——审计要能回答「那个月报表当时长什么样」，而月结正是"当时"被确认的时间点。

`POST /reports/purge` 带 `dryRun`（首次上线先看会删什么）、幂等（第二次 `removed=0`）。
**清理任务必须能无条件重试**，否则失败一次就没人敢再跑。

原型侧只在报表中心加了一句说明——内存态没有清理的意义，硬做会变成假动作。

### 十一、月结两级授权：会结账 ≠ 能反结（2026-10-30 夜）

上一批只做了接口语义约束，页面上人人可见按钮——权限做成了 UI 装饰。这一批补上：

| 权限码 | 守什么 | 谁有 |
|---|---|---|
| `b.monthClose.view` | 页面守卫（能不能进 `/b/month-close`） | 财务、财务主管、总经理、只读观察员 |
| `b.monthClose.edit` | 提交月结 | 财务、财务主管、总经理 |
| `e.monthReopen.edit` | 反结 | 财务主管、总经理（**财务专员没有**） |

**反结权限刻意放在 e 域而不是 b 域**：财务角色对 b 域是通配（`b.*` view/edit），反结是治理动作，
不该被"管收费"这一个事实自动授予——放 b 域的结果是每个财务都**静默**获得推翻封账的能力，
而页面上看不出区别（按钮就在那里）。`/e/audit` 新增两条不变量专门锁这个设计：

- 「会结账 ≠ 能反结」：可结账的角色里，只有显式授权的才能反结；
- 「反结是无路由的按钮级权限」：绑了路由会抢走页面守卫，两级授权塌成一级。

**权限码是服务端校验，不只是隐藏按钮**。`submitMonthClose` / `reopenMonthClose` 开头就
`assertPerm()`，无权限直接 403/40301——只在前端隐藏按钮而接口不校验，改个请求就绕过去了。

新增角色 **R-FINM 财务主管**（14 个角色 / 69 个权限位）：封账归财务专员，推翻封账归财务主管。

### 十三、权限变更留痕：记 diff，不记动作（2026-10-30 夜）

这套 RBAC 之前唯一缺的一环：**改完权限查不到是谁动的**。`/e/org` 能勾选，保存就生效，
没有任何记录——真出事时只有"现在这个样子"，没有"怎么变成这样"。

新页 `/e/perm-log`「权限变更日志」（E 域，`e.permLog.view`）：

| 纪律 | 做法 | 为什么 |
|---|---|---|
| **记 diff，不记动作** | 每条记 `added[]` / `removed[]` + 逐条明细 | 只记「保存了一次角色权限」等于没留痕：查不到动了哪一位 |
| **无变化不记** | `logPermChange` 返回 `null`，提示「权限未发生变化」 | 点开看一眼再保存不是治理事件，记了只是噪音，会把真事件淹掉 |
| **只增不删** | 页面无任何删除入口 | 同数据访问日志的口径 |
| **可解释** | 编辑态多一个「本次变更说明」（选填） | 收回权限时尤其该写：审计要问"为什么收" |

`/e/org` 保存后的提示直接带变更摘要与记录号：
`已保存「集团总经理」70 个权限位（+1，记录 PC001006）`。

**为什么不塞进 `operationLogs`**：那张表记的是"谁做了什么动作"（发布公告 / 提交品质检查），
粒度到"改了权限"就没了。审计真正要问的是——谁在什么时候、给哪个角色、加了哪一个权限。

`/e/audit` 加两条不变量锁这个设计（29 → 31）：

- 变更只记有差异的记录，且 `+N / -N` 与明细条数一致（防止以后改成只记动作）；
- 明细里的权限码都存在于权限表（写错码 = 留了一条**假痕**，比没记更糟）。

**实测**

```

改一次权限  提示「（+1，记录 PC001006）」→ 日志 5 → 6 条，KPI 4 人操作
```

### 十四、高敏权限审批：提权要批，降权即时（2026-10-30 夜）

上一批解决了"改完查不到是谁动的"，这一批解决"**能不能随便改**"。

不是所有权限都送审——普通权限（看报表、执行巡检）每天要调十几次，全要审批的结果是审批人闭眼点"通过"，
**审批变成橡皮章，真正该看的反而没人看**。所以只拦五类（`SENSITIVE_PERM_RULES`）：

| 权限 | 为什么算高敏 |
|---|---|
| `a.sensitive.view` | 能看业主 / 租户的证件号与银行账号明文 |
| `e.monthReopen.edit` | 能推翻已封账的月结结果 |
| `e.org.edit` | 能改角色权限本身——等于能给自己加任何权限 |
| `c.payroll.edit` | 能改工资表 |
| `a.stewards.edit` | 能改楼栋责任范围——等于能自己扩大可见范围 |

### 两条不显然但很关键的口径

**① 提权要审批，降权即时生效。**
判断只看 `added`，不看 `removed`。发现谁多给了权限，第一反应是**马上掐掉**——
卡在审批队列里等一天，等于让漏洞多开一天。收紧方向不需要拦，只需要留痕。
（这条是实测时发现的：第一次测的是"收回敏感权限"，结果被卡进审批，当场改了。）

**② 提交人不能审批自己提交的申请（双人原则）。**
审批权只给总经理与财务主管两个角色，于是形成闭环：

```
人事提交    → 总经理 / 财务主管 都能批
总经理提交  → 只能财务主管批（自己批不了自己）
财务主管提交 → 只能总经理批
```

单人演示时这条很碍事（"我为什么点不了通过"），但它是「不能给自己提权」的唯一技术保障。
页面上对"我提交的"那条直接显示「我提交的 · 撤回」，不给通过按钮——不是灰掉，是根本不给点。

审批通过时**先写权限、再记变更日志**：顺序反了，中途失败会留下一条"批准了但没生效"的假痕。

### 实测（切角色逐个验，零 console 错误）

```

R-HR 提权    勾「敏感字段明文·查看」→「本次新增 1 项高敏权限，已提交审批（REQ0004）」（warning）
             待审批 2 → 3 条，变更日志仍是 5 条（**未生效**，这就是审批的意义）
R-HR 降权    收回同一项 →「已保存 14 个权限位（-1，记录 PC001006）」（success，即时生效）
R-GM 审批    通过 REQ0002 →「已通过，收银员权限已更新（记录 PC001006）」→ 待审批 2 → 1
/e/audit     34 条全过，治理留痕 5 条（新增 3 条：已通过必有记录、不得自批、申请明细可解析）
```

`/e/audit` 新增的三条不变量本质是在防"断链"：**批准了不写权限**（等于没批）、
**写权限不留痕**（等于没批）、**自己批自己**（等于没设审批）。

### 两条状态机口径（这轮最值钱的部分）

**合同：变更是独立单据。** 改金额、改期限、提前终止都**不动合同**，先生成 `ContractChange`
（`before` / `after` 快照）进审批，通过才回写。直接改合同的话——谁在什么时候把 30 万改成 50 万，永远查不出来。

变更单在审批中时：合同金额**不变**，且 `changePending=true` 挡住第二次变更（**409 / 40906**，不是 422——
这不是参数错，是要先去处理那一单）。

**公告：单向状态机。** 草稿 → 待审核 → 已发布 → 已过期；已发布可撤回，撤回后重新提交审核。三条硬约束：

| 约束 | 回应 |
|---|---|
| 已发布不能改内容 | 409 / 40907——业主已经看过了，改了等于篡改留痕，要改先撤回 |
| 已发布/已过期不能再发布 | 409 / 40908——重复点，业主收两条一样的推送，然后打客服问"到底停不停水" |
| 撤回不清零已读 | 业主确实看过，撤个公告就抹数字就是伪造台账（重新发布才归零） |

最后一条顺手把原型里 `withdrawNotice` 的 `readCount = 0` 删了——原来那个写法是错的。

### 联调抓到三处"真接一下"才暴露的问题

### 十七、员工域进契约（人事口径，不含薪资）

| 口径 | 不这么做会怎样 |
|---|---|
| **薪资不进本域**（`baseSalary` / `monthlySalary` / `bankCard` 归工资域） | 能看到员工列表的人，就能看到全公司工资 |

没有则说明仅能看人事档案）。适配层对这一域**统一剥掉薪资字段**——页面拿不到就不会去显示，
显示过一次就再也回不去了。

### 十八、工资域进契约：状态机比字段重要

`04-契约` 新增 `payroll` 域 10 个接口，规模到 **74 路径 / 82 接口 / 147 schema / 91 条测试（91 通过）**。

工资表原来是前端实时算 + `paid` 一个内存 Set，三个按钮（重新核算 / 导出 / 批量发放）里两个是提示框。
这次把它做实，核心不是字段而是**状态机**：

```
草稿 →（核算锁定）已核算 →（提交发放）待发放审批 →（审批通过）已发放 →（冲正）已冲正
                        └──（驳回）已核算
```

三条硬规矩：

| 规矩 | 不这么做会怎样 |
|---|---|
| **金额只由数据层算**（`grossPay` / `deductionTotal` / `netPay`） | 页面各加一遍 → 列表一个数、工资条一个数、汇总又一个数 |
| **已核算后金额不可变**（409/40913） | 发一次钱、记两本账 |
| **提交人不能审批自己的发放单**（409/40915） | 一个人既能核算又能批准，"谁批的"永远写的是同一个人 |

另外两处口径：

- **`dataScope=仅本人` 只回自己那一条**，不是下发全表让前端藏。样例里专门加了 `staff` 账号
  （EM0020 / 仅本人 / 只有 `c.payroll.view`）来守这条——这类账号最容易漏测，因为只有大规模上线后
  才会被发现"能看到别人的工资"。
- **已冲正的行不进 `netTotal`**，单列 `reversedCount` / `reversedAmount`。钱已经退回去了，
  还算在实发里就是账上凭空多一笔。

**页面改造**（`/c/payroll`）：按钮按状态出现/隐藏（草稿才有"重新核算 / 核算锁定"，已核算才有"提交发放"，
待审批才有"审批通过 / 驳回"），行内加「明细」抽屉——应发/代扣分解项与流转时间线**全部由服务端给**
（`calc` + `timeline`），页面不自己拼。

**实测**

```
契约        80 行 · 每行 netPay = grossPay − deductionTotal · 应发 836,324.18 → 实发 754,506.83
            行里没有 bankCard / phone / idCard（工资域不是员工档案的后门）
            草稿直接发放 409/40914 · 已核算重算 409/40913 · 自己审批 409/40915
            staff 列表 total=1 · 冲正后 reversedCount+1、netTotal 减掉该笔
页面        118 人：草稿 → 核算 → 提交 → 自己审批被拦 → 切财务主管审批通过 → 明细(4 条时间线) → 冲正
            零 console 错误
```

> **两个坑**：① 页面 mock 是内存态，**切角色必须在同一页面内切**（顶栏下拉）。新开页面 = 刷新 = 回种子，
> 第一版测试用 `page.goto` 换角色，看到的是"审批通过后又是草稿"。
> ② `el-drawer` 内部是滚动容器，`innerText` 只覆盖首屏——时间线 4 条只读到 1 条，
> 断言要直接取 `.el-timeline-item`。

**仍未做**：个税还是简化的 3% 速算（真接要换成年度累计预扣，税率表不能留代码里）；
批量冲正（现在逐条调）；代发文件导出（银企直连格式）；工资条 PDF；离职当月工资手工补录。

### 十九、组织与权限域进契约（提权要批、降权即时）

`04-契约` 新增 `access` 域 13 个接口，规模到 **86 路径 / 97 接口 / 172 schema / 106 条测试（106 通过）**。
这是最后一个还全在 mock 的业务域。

**权限只挂角色，人只挂角色**——契约里没有"给某人加一个权限码"这种接口。逐人授权的系统最后
没人说得清"谁到底能干什么"。

保存权限矩阵三条分支（**服务端自己算 diff**，前端只提交保存后的完整集合）：

| 情况 | 结果 |
|---|---|
| 与保存前完全一致 | 200 `noChange=true`，不写日志 |
| 新增命中高敏白名单 | **202，不生效**，生成待审批申请 |
| 纯降权 / 普通新增 | **200，立即生效**并记 diff |

高敏五类：看证件明文 / 推翻封账 / 改权限本身 / 改工资表 / 改楼栋责任范围——共同点是
「拿到就等于能自己扩权或掩盖问题」。**降权即时**：收回还要等审批，这段时间里他能做的事一点没少。

双人原则（409/40917）在这条链上是唯一的意义：自己提自己批，等于没有审批，
日志里还会留下一次"审批通过"的假象。

日志是**追加写 + 哈希链**：访问/导出日志每条带 `hash`/`prevHash`，任何一条被改，链上后面全对不上——
否则"谁在什么时候看了谁的证件号"这条记录本身就可以被删掉。

**实测**

```

降权       R-VIEW 去掉 a.vehicles.view → 200 立即生效 · diff 写清是哪个码
提权       R-CLN 加 a.sensitive.view → 202 未生效 · 重复提交 409/40916
原样保存    noChange=true · log=null · 日志条数不变
双人       gm 提交 → gm 审批 409/40917 → pm 审批通过 → 权限此时才生效 → 再批 409/40918
驳回/撤回   驳回要原因且权限不生效；撤回只有提交人能操作
访问日志    12 条逐条 prevHash === 上条 hash · 成功/脱敏/拦截三态齐全
六档        78（有角色）+ 2（离职无角色）= 80 人
```

> **反向发现**：14 个角色里有 **10 个**都持有 `a.sensitive.view`（含客服专员、收银员、楼栋管家）。
> 契约把提权路径收紧了，但**授权基线本身太宽**——真接后台要按最小权限重排一遍，
> 否则审批流拦的只是"从一个已经很宽的口子再加一点"。没改 seed，记录在案。

**未做**：`/e/org`（963 行）与两个日志页仍在用 `utils/api`，还没切到 `@/api`——

### 二十二、组织 CRUD 进契约（原型只有读，没有写）

补 3 个接口，规模到 **88 路径 / 100 接口 / 174 schema / 109 条测试（109 通过）**：

| 接口 | 关键约束 |
|---|---|
| `GET /orgs` | 扁平列表 + `parentId` + `sort` + 人数。返回树的话，"按部门下所有班组筛人"还得先摊平一次 |
| `POST /orgs` | 只能建**部门 / 班组**（集团与项目要伴随立项一整套动作）；`orgId` 服务端生成；同级重名 409 |
| `PATCH /orgs/{orgId}` | 不能改 `type`；改上级**防环**（422） |

两条值得单独说的：

- **为什么不做 DELETE**：删组织要么带着人一起删（等于离职），要么先把人挪走——两种都是组织调整单据，
  一个 `DELETE` 表达不了；硬做的结果是库里留下一批 `orgId` 指向不存在组织的员工。
- **为什么改 `type` 也要拦**：把「班组」改成「部门」，挂在它下面的人从"走排班"变成"走职能"，
  等于重挂一批人。这该是组织调整，不是一个字段。

防环的后果很具体：把「工程组」的上级设成它自己的下级，这棵子树在组织树上就点不到了，
但列表里人还在——最后没人解释得清"为什么这个人不在组织架构里"。

**实测**：列表 20+ 节点、`headcount ≥ selfHeadcount`、组织树根节点人数之和 = 员工总数；
新增班组 ID 形如 `O-P01-T5`、同级重名 409/40902、建"项目"422、上级不存在 404；
改名/负责人/排序生效、改 type 422、挂到自己下面 422、集团改上级 422。

**`/e/audit` 34 条自检没有接口化**，这是有意的：它检查的是**库里的数据**，不是一个业务资源。
做成 REST 接口后后台要维护 34 条 SQL 断言，收益低于成本；更合适的形态是运维健康检查端点
（`/health/checks`）或定时任务，不该进业务契约。

### 二十三、清掉五处遗留补口（收尾批）

契约到 **91 路径 / 104 接口 / 178 schema / 112 条测试（112 通过）**。这一批全是"接一个口子"的活：

| # | 补口 | 关键点 |
|---|---|---|
| 1 | 公告**提审 / 发布拆开** | 两个动作两个角色。草稿直接发布 → 409/40914；提审不清已读，发布才归零 |
| 2 | 合同**附件下载** | 列表只回元数据，下载**签发临时链接**（20 分钟）并写导出日志 |
| 3 | **`dataScope` 变更纳入审批** | 变宽 → 202；变窄 → 200 立即生效；同档换项目也算变宽 |
| 4 | **审批超时提醒** | 申请带 `ageHours` / `overdue`，`vf=overdue` 只挑挂满 24h 的 |
| 5 | **月结按项目分别结账** | 全公司结账要求"有业务的项目"先结；反结**级联**项目级 |

四处的判断值得记下来：

- **公告拆开**的理由不是"REST 更纯粹"，而是**提审与发布不是同一个人**。合成一个接口的结果是
  只要点了发布就自动跳过审核，"谁审的"那栏永远是空的。
- **附件不发下载地址**：给地址的接口一旦被复制，链接就永远有效。所以列表只回元数据，
  下载单独签发临时链接并留痕——合同是"谁拿走了扫描件"最该查得到的一类文件。
- **`dataScope` 也是扩权**：改「全部项目」扩的是"能看多少行"，不是"能点哪个按钮"。
  档位取 `仅本人 < 本部门 < 责任范围 < 本项目 < 指定项目 < 全部项目`；
  「指定项目」排在「本项目」之上是保守取法——指定 3 个项目的人通常比只看 1 个项目部的人看得多。
- **月结前置 + 级联反结**：全公司结账要求有业务的项目先结（汇总前明细没清，等于用总数掩盖问题）；
  但**当期一笔账都没有的项目不参与**，否则空项目永远结不掉、全公司就永远结不了。
  反结必须级联——只解汇总锁的话，项目明细还锁着，反结之后依然补录不了，等于白反。

**实测**

```
公告  草稿直接发布 → 409/40914；提审 → 待审核；发布 → 已发布且已读归零
附件  列表份数与合同一致、不带 url；下载 → 带 sign 的临时链接 + EL 导出日志；不存在 → 404
范围  R-SEC 本部门 → 全部项目：202 待审，审批通过后才变；收紧 200 立即；改 scope 422
超时  待审批单带 ageHours/overdue；vf=overdue 只回超时；页面显示「3 条超时（>24h）」+「已挂 Nh」
月结  全公司结账先被 422 拦住并点名「翡翠城」；项目级 P01 → 201（单号 YJ-202610-P01-01）
      全公司反结 → 项目级记录同步转「已反结」，两边都恢复可结
```

### 二十五、组织维护入口 + 补一个「能看档案、不能看工资」的角色

**① 组织维护为什么做成抽屉，而不是新页面**

契约第 38 批就有 `POST /orgs` / `PATCH /orgs/{orgId}`，但原型一直没有入口。做成独立页面看着"更正规"，
实际上有两个坑：

- 新路径要走权限守卫，而守卫是靠 `permissions.json` 的 `route` 字段反查权限码的（`permCodeOfPath`）。
  新页面没有对应权限码 → 反查结果为空 → **按公共页放行**，等于把组织增删改暴露给所有人。
  要补就得新增权限位 + 改两份 mock + 改契约 fixture + 改种子，为一个"维护入口"扩一圈权限表，不划算。
- 组织维护天然依附于"看组织"这件事，抽屉里改完立刻能看见左树变化，比跳页再回来更顺。

所以做成 `/e/org` 工具栏上的「组织维护」抽屉：**复用 `e.org.view` 看、`e.org.edit` 改**，零新增权限位。
只读角色（如只读观察员）能打开抽屉看结构，但「新增下级 / 编辑」全是灰的。

**② 三个交互取舍**

| 取舍 | 原因 |
|---|---|
| 树表用 `el-table` 的 `tree-props`，行内「新增下级」 | 上级由所在行决定，省掉"先选上级"这一步——那是最容易选错的一步 |
| 类型默认值随上级推断（项目下→班组、部门下→部门） | 选错类型会直接产生一个语义不对的组织，而改类型是禁止的（只能删了重建） |
| 改名后重算员工行上的 `orgName` / `orgPath` | 不重算的结果是「组织已经叫客服一组，成员列表还写着客服二组」 |

三条不让改与契约一致：**类型**（班组改部门，下面的人从"走排班"变"走职能"）、**集团改上级**、
**挂到自己的下级下面**（成环后整棵子树从组织树上消失，但人还在列表里）。`orgId` 服务端生成——
前端生成的话两人同时新增会撞号，而 `orgId` 是员工、账套、报表的引用键。

### 二十六、导出清单：给「数据外流」单独一个页签

**① 为什么另开一个页签，而不是并到访问留痕里**

访问留痕回答的是「谁看了谁的身份证」，导出清单回答的是「谁把多少行数据导到机器外面去了」——
两个问题，两种粒度（一次一个字段 vs 一个文件几万行）。并在一张表里的直接后果是：
48 条揭示把 6 条导出淹掉，而**导出才是数据外流的主通道**，被拦下的那几次最该被看见。

所以 `/e/access-log` 加了两个页签（仍复用 `e.accessLog.view`，没有新增权限位）：

| 页签 | 内容 | 筛选 |
|---|---|---|
| 访问留痕 | 每次揭示一条（对象 · 字段 · 来源页） | 动作 / 结果 / 操作人 / 时间 / 关键字 |
| 导出清单 | 文件级（文件名 · 格式 · 行数 · 结果） | 结果 / 操作人 / 时间 / 关键字 |

**② 页面顺便把契约补齐了**

页面要传 `days` 与 `kw`，而 `/export-logs` 原先只有 `result` / `operator` ——http 模式下这两个条件会被
服务端丢掉，用户以为筛了。所以给契约补了 `days` / `kw`，并在实现里做了个刻意的选择：

> `days` **只在显式传了才过滤**。给默认值 7 会把「查全部」的老调用悄悄截断，
> 排查时只看到 6 条而不是 12 条，还找不到原因。默认值放在**页面**上（默认近 7 天），
> 不放在接口语义里。

**③ 一个交互细节**

换页签会重置筛选：导出清单没有「动作」这个维度，把上一条留在查询条件里，会让人以为筛了两次。
KPI 两个页签共用——它统计的是"审计口径"的整体（揭示 / 导出 / 脱敏 / 拦截），不随表格切换而变。

**实测**（浏览器，零 console 错误）

```
页签    访问留痕 48 条（含查看明文）｜导出清单 6 条，表头是 文件名/格式/行数/结果
筛选    结果=拦截 → 只剩 1 条且整行高亮（被拦的最值得看）
切回    动作筛选回来、筛选被重置，不会把「拦截」带过去
契约    112/112，新增断言：result 筛选全命中、kw 是子集、days 越小结果不变多
```
