## 四、三条最容易踩的坑

1. **`tokens.css` 的引入顺序**。Element Plus 的样式是运行时注入的 CSS 变量，`tokens.css` 必须在其后引入才能真正覆盖 `--el-color-primary` 等变量。顺序反了会表现为「改了没生效」。
2. **EP 把组件变量定义在组件作用域**。`--el-table-*`、`--el-pagination-*`、`--el-checkbox-input-*`、`--el-datepicker-*` 写在 `:root` 无效，必须写成 `.el-table {}` / `.el-pagination {}` 这样的组件选择器（见 `tokens.css` §16）。这是「变量改了没反应」的第二大原因。
3. **`bills.json` 有 2.4MB**。原型阶段按需 import 即可，正式开发一律改接口分页，不要把全量账单塞进前端。

**两条工程纪律（踩过坑，务必保持）**：

1. **写操作必须同步派生行**。`api.js` 里 `OWNER_ROWS / HOUSE_ROWS / WO_ROWS / NOTICE_ROWS / PLAN_ROWS / EMP_ROWS / ROLE_ROWS`
   是模块级派生数组，只改原数组会出现「保存成功、列表不变」。写操作统一走 `_syncXxxRow(row, { insert })`。
2. **内联编辑的值由组件自持**。`InlineField` 保存成功后自己显示新值，不等父组件回填
   （详情抽屉里父级数据常被整体替换，回填不一定触发该字段重渲染）。
3. **权限矩阵要读「生效权限」而不是原始字典**。`permissionMatrix()` 走 `rbac.permCodesOfRole()`，
   保存后再 `syncRolePermsRow()` 回写 `ROLE_ROWS`；否则会出现「菜单已收紧、抽屉仍显示 50/50」。
4. **数据范围只在数据层收一次**。列表与汇总统一走 `scopeFilter()`，页面不各写一套；
   新增列表查询时记得挂上，否则会出现「菜单看着对、列表越权」。
5. **表格数据列用 `min-width`，只有「选择 / 操作 / 固定列」用 `width`**。Element Plus 的列宽算法
   （`table-layout.mjs`）只在存在 `min-width` 弹性列时才分摊剩余宽度；全写死 `width` 会在宽屏右侧留白
   （实测 1920 下最多 554px），且「操作」列的 `fixed="right"` 因无横向溢出而不生效。
6. **KPI 汇总也要跟着写操作刷新**。转工单、改状态后若 KPI 是 setup 时算好的普通对象，数字就不动。
   汇总统一做成 `ref(...)`，写成功后 `summary.value = xxxSummary()`；左树计数同理。
7. **写操作前先分清「原数组」与「派生数组」**。`api.js` 里 16 个 `*_ROWS` 都是 `{...}` 浅拷贝：
   列表 / 树 / 汇总读派生数组，`feeSummary` / `debtPoolRows` / `houseRow.debt` 读**原数组**——
   只改一边就出现同会话数字不一致（如「账单列表已缴、催缴台仍显示欠费」）。
   第 9 批逐一对账后补齐 `_syncBillRow` / `_syncHouseRow` / `_syncPayRow`；新增写操作先确认两边都改。
8. **枚举值必须与字典一致，且不要硬编码 ID**。第 9 批抓到两处：`deductPrepay` 写「部分缴费」
   （全站口径「部分缴」）→ 部分缴费账单整笔从欠费统计消失（抵扣 500 元却错降 1,194.08 元）；
   `generateShareBills` 把科目 ID 硬编码成 `FI07`（车位管理服务费）→ 736 笔公摊账全算进车位费、
   FI03 公共能耗分摊为 0。状态与字典 ID 一律按名称反查或引用常量。

## 六·补、巡检体系职责划分（第 10 批 P0，2026-10-29）

原先的巡检模型把「一线作业」和「管理」混在一起：执行页挂在后台菜单、任何能看列表的人
都能代填结果、也没有「谁去核验下属」这一层。按业务口径重构为三级，**配置权与执行权分离**：

```
物业公司 · 运营管理部（原「品质管理部」，2026-11-03 更名，职能不变；品质督导 = 品质经理）
├── 维护【执行模板】→ 告诉一线员工「做什么、什么算合格」
├── 维护【监督模板】→ 告诉部门经理「查下属哪些方面、什么算不合格」
└── 下达【监督计划】→ 指派到具体部门经理
        ↓
各项目 · 各部门（组）· 部门经理 = 组长
└── 只做现场核验：抽查下属责任区实际达标情况 → 发现问题 → 指定责任员工
        ↓
一线员工：按执行模板作业、留证、提交（移动端）
        ↓
品质督导：按部门 × 周期聚合 → 加权达标率 → 生成品质检查记录
```

### 职责边界（后台 vs 移动端）

| 模块 | 后台（PC） | 移动端 |
|---|---|---|
| 任务类型 / 检查模板 | ✅ 品质督导配置，其余角色只读 | 只读（据此渲染表单） |
| 巡检计划 | ✅ 品质督导建计划并指派 | 只读（接收排班） |
| **任务执行** | ❌ **不做**（仅监管视图：完成率 / 异常 / 超时） | ✅ 接单 → 打卡 → 逐项判定 → 拍照 → 异常转单 |
| **监督核验** | 配置规则、查复核记录与统计 | ✅ **部门经理专属**：现场核验 → 标记问题 → 指定责任员工 |
| 品质评价 | ✅ 聚合执行数据 → 加权 → 出记录 | 只读 |
| 报表 | ✅ 全部 | ❌ |

## 六·补2、整改闭环与主管考核（P3，2026-10-29）

评价只解决「打多少分」，还差两件事：**分低之后谁去改、改没改完**，以及**主管到底查不查**。
P3 补的就是这两条，并让它们与评价结果咬合。

### 1. 整改闭环 `/f/rectify`

流程与状态机（四态 + 两个派生标记）：

```
开单 ──▶ 待整改 ──提交整改──▶ 待复核 ──复核通过──▶ 已闭环
              ▲                    │
              └────── 已退回 ◀──────┘（退回后整改项归零，需重做再提交）
派生：overdue（过期限未提交） / recheckOverdue（提交后 >3 天未复核）
```

- **开单来源**：现场抽查记录（76 条有扣分项的记录自动派生整改单，问题项沿用评分卡的问题库）、
  任务评价自动开单、手动开单；整改单是**独立台账**，不塞进品质记录里就地展开。
- **责任归属**：区域 → 责任班组（园区外围/车库→安保、设备房/机房→工程、大堂/公区/绿化→环境），
  责任人取该班组一线岗位，可「改派 / 延期」。
- **与评价联动（三处）**：① 评价不合格（<70 分）自动开单，问题项取该部门本期监督任务查出的问题
  （带责任员工）+ 抽查问题；② 整改项进度实时回写品质记录的 `rectifyCount / rectifyDone`，
  记录状态随「待整改 / 待复核 / 已闭环」变化；③ 删除评价时联动删除其整改单，不留悬空单号。
- **一处克制**：不允许「提交人自己复核」（提交人 = 复核人时直接报错），避免闭环自证。

### 2. 主管发现问题数 `/f/sup-finding`（独立考核报表）

| 指标 | 口径 |
|---|---|
| 统计对象 | 部门经理本人提交的**监督**任务（一线执行任务不计） |
| 发现问题数 | 监督任务 `issueCount` 合计，每项必须指定责任员工 |
| 次均问题 / 检出率 | 发现问题 ÷ 已完成监督任务 / 发现问题 ÷ 检查项总数 |
| 申报冲突 | 下属当日申报「零异常」却被组长查出问题的次数（自动比对，非人工填写） |
| 抽查未发现 | 评价记录录入的 `crossIssues`；未评价时按同项目同月「现场抽查」扣分项依区域折算 |
| 主动发现率 | 自查 ÷（自查 + 抽查未发现） |

- 展示维度：**按主管**（考核明细，可下钻到该主管本期每一条监督任务与问题项）与**按部门**（汇总）双视图，
  右侧配「发现问题排名」条形，报表中心同步注册 `sup-finding`（可导出）。
- 排除项：无监督任务的班组不进表；下钻抽屉只读，写操作仍归移动端作业台。

**实测（2026-10）**：11 名主管 / 监督任务 29-33 / 发现问题 27 项 / 次均 0.93 / 申报冲突 5 次 /
主动发现率 14%（10 月抽查未发现 166 项）——「主管自查覆盖率低」这个结论是数据算出来的，不是写死的。

### 3. 种子扩充（不消耗 PRNG）

监督计划 6 → 11（补齐三个项目的工程 / 客服组），监督任务 12 → 66（每名主管覆盖近 6 周，
问题数按主管做出梯度），任务总量 240 → 306；权限位 55 → 58（`f.rectify` view/edit、
`f.supFinding` view），角色按「品质督导配置+复核 / 部门经理提交+查看 / 项目经理双向」分配。

## 六·补3、租户口径修正（P4，2026-10-29）

### 定性（用户确认）

> 租户是**业主**出租产生的，不是物业出租；租户信息（含新增）**主要由业主在小程序维护**；
> 物业可**代为补充或修正，保存即生效**（不需要业主二次确认），且补充动作要能在
> **「租户到场代缴物业费」的收银台流程里完成**。物业不是出租方 ⇒ **租金不进后台**。

一句话：物业要的是「这套房现在住着谁」，用于门禁人脸、通知触达、上门服务；不是替业主管租约。

### 「租约管理」→「在住人管理」的具体改动

| 处理 | 内容 | 理由 |
|---|---|---|
| 删 | KPI「月租金合计 / 平均月租」、列表「月租」列、详情「年租金」 | 租金是业主与租户的商业条款，物业既不掌握也不该考核 |
| 删 | 主按钮「新增租约」→ 改「代业主登记」；「发起续租」→ 删除 | 物业无权签/续租，只能代录与提醒 |
| 删 | 左树（项目/楼栋/单元） | 租户有唯一检索键（姓名/电话/房号），树只是三次点击换 5 行结果；状态与范围本应可叠加，树让二者互斥 |
| 改 | 状态语义：生效中/即将到期/已到期 → **在住 / 已搬离**（届满只提醒，不自动改状态） | 合同状态 ≠ 在住状态，搬离必须人工确认 |
| 加 | `source`（业主自助 / 物业补录）、`verifyStatus`（待核验 / 已核验 / 信息不全）、`relation`、`residents` | 数据主权在业主，物业侧必须能看出"谁录的、核过没有" |
| 加 | 顶部快捷视图（全部在住 / 待核验 / 信息不全 / 未实名 / 未录人脸 / 90 天内届满 / 已搬离）+ 项目·楼栋·单元·核验·来源筛选 | 状态与范围**可叠加**（例如「翡翠城 + 待核验」26 条） |
| 加 | 信息完整度：8 项口径（姓名·手机·证件·实名·人脸·关系·居住人数·紧急联系人），其中 6 项基础信息是**核验门槛** | 补什么、能不能核验，要有一把尺子 |
| 加 | 操作闭环：补充信息 → 核验通过（=实名成立）→ 录入人脸（门禁授权）→ 标记搬离（停用门禁、释放房屋） | 物业该做的三件事：核验、补全、失效 |

收银台右栏新增「在住租户」卡片：显示该业主名下在住租户、房号、完整度与核验状态，点「补充」直接开同一个补充抽屉；
左栏检索**支持租户姓名/手机**（租户到场报名字即可定位到业主的房）。保存后卡片完整度即时变化，账单主体仍是业主。

- 业主维护、物业只读：承租房屋、租期、产权业主（`TENANT_OWNER_FIELDS`）

## 六·补5、数据安全：敏感字段与导出留痕（P6，2026-10-29）

### 需求

> 用户信息（业主 / 租户的姓名、手机、证件）比较敏感，需逐级管理并隔离权限。

P5 解决的是「**看不看得到这一行**」（责任范围），P6 解决的是「**看得到这一行，但是不是能看到明文**」——两层叠加：

| 层 | 手段 | 落点 |
|---|---|---|
| 行级 | 数据范围六档，责任范围默认拒绝 | `scopeFilter(..., { house })` |
| 字段级 | 敏感字段默认脱敏 + 揭示留痕 + 导出校验 | `maskSensitive` / `revealSensitive` / `prepareExport` |

### 敏感字段白名单

`phone / mobile / emergencyPhone / idCard / bankAccount` 五个 prop 登记在 `SENSITIVE_FIELDS`，
只有登记过的列才参与脱敏、留痕与导出校验（其他字段一律不动，避免误伤）。

- **展示**：`<SensitiveText>` 统一渲染 → 默认 `138****8001` / `5101**********1231`，点眼睛才出明文；
- **留痕**：每点一次写一条 `查看明文`（操作人 / 角色 / 组织 / 对象 / 字段 / 来源页面 / 时间）；
- **编辑**：`InlineField` 加 `sensitive` 属性 —— 未揭示时不允许直接编辑（否则会把掩码值存回去）；
- **逐级**：`a.sensitive.view` 决定能不能揭示，角色矩阵里取消该位即刻生效。

### 权限位（60 → 62）

| 权限码 | 名称 | 分配 |
|---|---|---|
| `a.sensitive.view` | 敏感字段明文 | 楼管 / 客服 / 收银员 / 项目经理 / 部门经理 / 财务 / 人事（**只读观察员不给**，按外部审计口径只看脱敏） |
| `e.accessLog.view` | 数据访问日志 | 总经理 / 项目经理 / 人事 / 只读观察员 |

`a.sensitive.view` 的 `route` 故意留空：它不是一个页面，而是「在页面上点开脱敏值」的能力，
绑路由会抢掉 `/a/owners` 的页面守卫（`permCodeOfPath` 按 route 精确匹配取第一个 view）。

### 导出校验（`prepareExport`，页面 → 下载中心唯一入口）

| 情形 | 处理 | 日志结果 |
|---|---|---|
| 含敏感列 + 有明文权限 | 明文导出 | 成功（说明里标「含敏感字段 X（明文）」） |
| 含敏感列 + 无明文权限 | **自动改脱敏值导出**（不拦截，避免业务停摆） | 脱敏 |
| 条数 > 200 | 照常导出 | 成功，说明标「大额导出」 |
| 条数 > 系统配置「导出单次上限」 | **直接拦截，不产生下载任务** | 拦截 |

### 页面

| 页面 | 改动 |
|---|---|
| `/e/access-log`（新页） | 4 KPI（查看明文 / 涉及对象 / 导出任务 / 脱敏·拦截）+ 动作·结果·操作人·时间·关键字筛选 + 明细表 + 导出；<b>只增不删，无删除入口</b> |

## 六·补6、列表骨架收敛：A 型保留 4 页，其余全部转 B 型（2026-10-29 夜）

### 决策依据

树承担四类职能：①定位 ②盘点 ③定范围 ④承载虚拟视图。判断公式：

> **目标本身是空间实体、且用户需要「发现未知」→ 树必需；用户带着唯一键来（单号/车牌/人名）→ 树的①③用不上，只剩②④，而②④不需要 248px。**

另加一条实测出来的硬伤：**⑤ 状态维度与空间维度能否叠加**。原实现里 `onPick` 先 `Object.assign(query, BLANK)` 再套节点，
而虚拟视图节点的 `patch` 又把 `communityId/buildingId/unitId` 置空 —— **点「已逾期」就清掉楼栋**，
「1 栋的已逾期账单」这种最常用组合根本筛不出来。

### 最终分档

| 档 | 页面 | 理由 |
|---|---|---|
| **A 型（保留树）** | 房屋台账、业主档案、车位与车辆、组织与权限 | 空间/组织本身是主键，需要「盘点未知」（哪些房空置、哪栋还有闲置车位） |
| **B 型（去树）** | 租户管理、账单查询、缴费流水、工单列表、品质检查记录、通行记录、合同管理、公告通知 | 主键是人/单号/车牌/时间；树只剩「定范围」，而范围用 3 个下拉更快，且能与状态叠加 |

### 新增两个公共组件（避免 8 页各写一遍）

| 组件 | 职责 |
|---|---|
| `QuickViews.vue` | 带计数的单选 chips（`items[{key,label,n}] + v-model`），替代原树的虚拟视图节点；支持 `#after` 插槽放附加开关 |
| `ScopeFilter.vue` | 项目 → 楼栋 → 单元级联（`levels` 可只保留项目），改上级自动清下级；发出 `patch` 事件而不是直接改 prop |

配套 CSS：`.ia.is-flat`（去掉 248px 左列）、`.scopebar__sum`（范围小计）、`.qvwrap`（chips 行与筛选栏的分隔线）。

### 逐页迁移要点

| 页面 | 树原来给什么 | 迁移后 |
|---|---|---|
| 账单查询 | 项目→楼栋→单元 + 4 个状态节点（带应收/欠费金额） | 5 chips + 3 级筛选；**新增「范围小计条」**（张数 / 应收 / 未收 / 有欠费张数）承接树节点金额 |
| 缴费流水 | 同上 + 「车位收费」分支 | 同上；车位收费 → **「只看车位收费」开关**（可与视图叠加）；小计给笔数/金额/现金/未开票 |
| 工单列表 | 项目→楼栋→单元 + 「公共/非入户」分支 | 5 chips + 3 级筛选；无房屋工单 → **开关**；「哪栋报修集中」改由**报表**回答 |
| 品质检查记录 | 项目 → 区域（保洁/安保/工程/客服） | 6 chips + 项目 + **区域下拉**；区域是业务条线不是空间层级 |
| 通行记录 | 项目 → 车库区域 | 5 chips + 项目 + **车库区域下拉**；道闸跨项目复用，只能做筛选 |
| 合同管理 | 类型 → 子类型 | 6 chips + **类型/子类型下拉（联动）** + 状态 + 项目 |
| 公告通知 | 类型 → 项目 | 6 chips + **类型下拉** + 状态 + 项目 |
| 租户管理（P4 已改） | — | 同一套骨架，本次统一到公共组件 |

### 新增报表：工单按楼栋分布 `/e/reports/wo-by-building`

去树后「哪栋报修集中」不能靠翻树，改由报表回答：`项目 / 楼栋 / 工单数 / 未闭环 / 已超时 / 紧急及以上 / 涉及户数 / 每百户工单 / 主要类型`，
按工单数倒序（实测 14 栋，最高翡翠城 6栋 4 单）。

## 六·补9、派生值怎么算：报表改为跑批快照（2026-10-30 拍板）

**决策**：欠费账龄 / 收缴率 / 部门达标率这类**派生值不做实时查询**，由夜间跑批算好落库，页面读统计批次快照。

三条理由（写在 `api.js` 的注释里，免得以后有人改回实时）：

1. 账龄 = 统计日 − 到期日，实时算会让同一张表每刷新一次变一个数；
2. 审计要能回答「上个月报表当时长什么样」，实时算答不了；
3. 部门达标率要扫全量巡检明细，实时算会把列表拖到秒级。

### 一、原型侧怎么落

| 能力 | 落点 | 口径 |
|---|---|---|
| 快照存储 | `api.js` 的 `REPORT_SNAPSHOTS` | 模块加载即「跑一次夜批」，算完**冻结**；之后改账单不影响已生成批次 |
| 统计批次 | 报表页页头下拉 | 2026-10-19 / 10-20 / 10-21 三批；一天一批，一批里 3 张表（`RPT-20261021-01/02/03`） |
| 批次元信息 | 页头一行 | 生成时间 / 数据截止 / 公式版本 / 行数 / 耗时；落后最新批次给「落后最新批次」标签 |
| 重算 | 「重算」按钮 | 异步任务 → 轮询 → 生成新批次并跳转；同参数运行中不重复建批次（幂等） |
| 范围 | 读取时裁行 | 批次**全局算**，越权在读取时按行过滤（与契约一致，不是两套口径） |
| 失败批次 | 保留 | `dept-target` 10-20 留了一条失败批次：能查失败原因，但不参与「最新成功批次」选取 |

### 二、报表中心变化

- 新增分组 **G 统计（跑批）**：`欠费账龄统计`（楼栋 × 账龄）、`收缴率统计`（账期 × 科目）。
- `部门达标率` 改为快照版（列里补「已完成」，去掉与口径无关的「申报冲突」）。
- 其余明细类报表（费用明细 / 欠费明细 / 未收费房屋 / 缴费明细 / 营业报表 / 押金 / 报修 / 巡检 / 主管发现数 / 工单按楼栋）仍是**实时查询**——
  明细按行查更合适，物化收益不大。卡片上带「跑批」标记，一眼能分清。

### 六、月报 / 年报：期次模型（2026-10-30 拍板）

拍了两条板：**月报＝月结后一次算，当月给试算值**；**年报拆两张表——余额（时点）与发生额（区间）**。

| 类型 | 报表 | 月报 | 年报 | 能否由日快照累加 |

### 九、月结落进契约 + 反结（2026-10-30 夜）

上一批的月结只在原型里跑通，接口没进契约——因为三条口径没定。这一批按行业惯例定了，并写进契约：

| 问题 | 答案 | 理由 |
|---|---|---|
| 谁有权结 | `b.monthClose.submit`（财务），**项目经理没有** | 封账是财务动作。让项目经理封自己项目的账，等于让他自己掩盖欠费 |
| 能不能反结 | 能，`b.monthClose.reopen`（更高一级）+ 必填 ≥10 字原因 | 不允许反结的结果是有人去数据库改数，那才是真正的失控 |
| 结完能改什么 | 该期流水 / 退款一律 409 / 40903 | 退款会改上月已封存的收款与欠费，必须「反结 → 改 → 重结」 |

**反结做四件事，一件都不能省**：记录置「已反结」（留 `reopenReason` / `reopenCount` / `reversalNo`）；
该期报表批次标 `voided`（保留可查，不删除）；期间恢复可写；报表实时回到 `provisional=true`。

两个在实现时才想明白的点：

1. **`provisional` 必须实时算**，不能用建批次时存下的值。反结后旧批次仍是那份冻结的数，但它已经不是定稿了——
   状态属于**期间**，不属于批次。这一条不改，反结后报表会一直显示「定稿」，比不显示更误导。
2. **反结不写进退款流水**。反结不是退款，混进去会让「退款金额」统计失真；它有自己的红冲凭证号。
   （契约里本来写的是"生成一条反结流水"，实现时发现这个坑，已把契约措辞改掉。）

### 十、批次保留与清理

日快照一天 3 张表，一年 1000+ 批次。设了保留策略：**日 90 天 / 月 24 期 / 年永久**，
且**已月结期间的批次一律受保护**——审计要能回答「那个月报表当时长什么样」，而月结正是"当时"被确认的时间点。

`POST /reports/purge` 带 `dryRun`（首次上线先看会删什么）、幂等（第二次 `removed=0`）。
**清理任务必须能无条件重试**，否则失败一次就没人敢再跑。

原型侧只在报表中心加了一句说明——内存态没有清理的意义，硬做会变成假动作。

### 十一、月结两级授权：会结账 ≠ 能反结（2026-10-30 夜）

上一批只做了接口语义约束，页面上人人可见按钮——权限做成了 UI 装饰。这一批补上：

| 权限码 | 守什么 | 谁有 |
|---|---|---|
| `b.monthClose.view` | 页面守卫（能不能进 `/b/month-close`） | 财务、财务主管、总经理、只读观察员 |
| `b.monthClose.edit` | 提交月结 | 财务、财务主管、总经理 |
| `e.monthReopen.edit` | 反结 | 财务主管、总经理（**财务专员没有**） |

**反结权限刻意放在 e 域而不是 b 域**：财务角色对 b 域是通配（`b.*` view/edit），反结是治理动作，
不该被"管收费"这一个事实自动授予——放 b 域的结果是每个财务都**静默**获得推翻封账的能力，
而页面上看不出区别（按钮就在那里）。`/e/audit` 新增两条不变量专门锁这个设计：

- 「会结账 ≠ 能反结」：可结账的角色里，只有显式授权的才能反结；
- 「反结是无路由的按钮级权限」：绑了路由会抢走页面守卫，两级授权塌成一级。

**权限码是服务端校验，不只是隐藏按钮**。`submitMonthClose` / `reopenMonthClose` 开头就
`assertPerm()`，无权限直接 403/40301——只在前端隐藏按钮而接口不校验，改个请求就绕过去了。

新增角色 **R-FINM 财务主管**（14 个角色 / 69 个权限位）：封账归财务专员，推翻封账归财务主管。

### 十三、权限变更留痕：记 diff，不记动作（2026-10-30 夜）

这套 RBAC 之前唯一缺的一环：**改完权限查不到是谁动的**。`/e/org` 能勾选，保存就生效，
没有任何记录——真出事时只有"现在这个样子"，没有"怎么变成这样"。

新页 `/e/perm-log`「权限变更日志」（E 域，`e.permLog.view`）：

| 纪律 | 做法 | 为什么 |
|---|---|---|
| **记 diff，不记动作** | 每条记 `added[]` / `removed[]` + 逐条明细 | 只记「保存了一次角色权限」等于没留痕：查不到动了哪一位 |
| **无变化不记** | `logPermChange` 返回 `null`，提示「权限未发生变化」 | 点开看一眼再保存不是治理事件，记了只是噪音，会把真事件淹掉 |
| **只增不删** | 页面无任何删除入口 | 同数据访问日志的口径 |
| **可解释** | 编辑态多一个「本次变更说明」（选填） | 收回权限时尤其该写：审计要问"为什么收" |

`/e/org` 保存后的提示直接带变更摘要与记录号：
`已保存「集团总经理」70 个权限位（+1，记录 PC001006）`。

**为什么不塞进 `operationLogs`**：那张表记的是"谁做了什么动作"（发布公告 / 提交品质检查），
粒度到"改了权限"就没了。审计真正要问的是——谁在什么时候、给哪个角色、加了哪一个权限。

`/e/audit` 加两条不变量锁这个设计（29 → 31）：

- 变更只记有差异的记录，且 `+N / -N` 与明细条数一致（防止以后改成只记动作）；
- 明细里的权限码都存在于权限表（写错码 = 留了一条**假痕**，比没记更糟）。

**实测**

```

### 十四、高敏权限审批：提权要批，降权即时（2026-10-30 夜）

上一批解决了"改完查不到是谁动的"，这一批解决"**能不能随便改**"。

不是所有权限都送审——普通权限（看报表、执行巡检）每天要调十几次，全要审批的结果是审批人闭眼点"通过"，
**审批变成橡皮章，真正该看的反而没人看**。所以只拦五类（`SENSITIVE_PERM_RULES`）：

| 权限 | 为什么算高敏 |
|---|---|
| `a.sensitive.view` | 能看业主 / 租户的证件号与银行账号明文 |
| `e.monthReopen.edit` | 能推翻已封账的月结结果 |
| `e.org.edit` | 能改角色权限本身——等于能给自己加任何权限 |
| `c.payroll.edit` | 能改工资表 |
| `a.stewards.edit` | 能改楼栋责任范围——等于能自己扩大可见范围 |

### 两条不显然但很关键的口径

**① 提权要审批，降权即时生效。**
判断只看 `added`，不看 `removed`。发现谁多给了权限，第一反应是**马上掐掉**——
卡在审批队列里等一天，等于让漏洞多开一天。收紧方向不需要拦，只需要留痕。
（这条是实测时发现的：第一次测的是"收回敏感权限"，结果被卡进审批，当场改了。）

**② 提交人不能审批自己提交的申请（双人原则）。**
审批权只给总经理与财务主管两个角色，于是形成闭环：

```
人事提交    → 总经理 / 财务主管 都能批
总经理提交  → 只能财务主管批（自己批不了自己）
财务主管提交 → 只能总经理批
```

单人演示时这条很碍事（"我为什么点不了通过"），但它是「不能给自己提权」的唯一技术保障。
页面上对"我提交的"那条直接显示「我提交的 · 撤回」，不给通过按钮——不是灰掉，是根本不给点。

审批通过时**先写权限、再记变更日志**：顺序反了，中途失败会留下一条"批准了但没生效"的假痕。

### 实测（切角色逐个验，零 console 错误）

```

R-HR 提权    勾「敏感字段明文·查看」→「本次新增 1 项高敏权限，已提交审批（REQ0004）」（warning）
             待审批 2 → 3 条，变更日志仍是 5 条（**未生效**，这就是审批的意义）
R-HR 降权    收回同一项 →「已保存 14 个权限位（-1，记录 PC001006）」（success，即时生效）
R-GM 审批    通过 REQ0002 →「已通过，收银员权限已更新（记录 PC001006）」→ 待审批 2 → 1
/e/audit     34 条全过，治理留痕 5 条（新增 3 条：已通过必有记录、不得自批、申请明细可解析）
```

`/e/audit` 新增的三条不变量本质是在防"断链"：**批准了不写权限**（等于没批）、
**写权限不留痕**（等于没批）、**自己批自己**（等于没设审批）。

### 两条状态机口径（这轮最值钱的部分）

**合同：变更是独立单据。** 改金额、改期限、提前终止都**不动合同**，先生成 `ContractChange`
（`before` / `after` 快照）进审批，通过才回写。直接改合同的话——谁在什么时候把 30 万改成 50 万，永远查不出来。

变更单在审批中时：合同金额**不变**，且 `changePending=true` 挡住第二次变更（**409 / 40906**，不是 422——
这不是参数错，是要先去处理那一单）。

**公告：单向状态机。** 草稿 → 待审核 → 已发布 → 已过期；已发布可撤回，撤回后重新提交审核。三条硬约束：

| 约束 | 回应 |
|---|---|
| 已发布不能改内容 | 409 / 40907——业主已经看过了，改了等于篡改留痕，要改先撤回 |
| 已发布/已过期不能再发布 | 409 / 40908——重复点，业主收两条一样的推送，然后打客服问"到底停不停水" |
| 撤回不清零已读 | 业主确实看过，撤个公告就抹数字就是伪造台账（重新发布才归零） |

最后一条顺手把原型里 `withdrawNotice` 的 `readCount = 0` 删了——原来那个写法是错的。

### 联调抓到三处"真接一下"才暴露的问题

### 十七、员工域进契约（人事口径，不含薪资）

| 口径 | 不这么做会怎样 |
|---|---|
| **薪资不进本域**（`baseSalary` / `monthlySalary` / `bankCard` 归工资域） | 能看到员工列表的人，就能看到全公司工资 |
| **角色不存员工表**（岗位反推 + override 覆盖，`roleSource` 标来源） | 改一次岗位要手工改一遍权限，两边长期不一致 |
| **离职即收权**（`roleId` 为空 / 不可指派 / 不能调角色 409/40910） | 人走了权限还在，这是最常见的一类越权 |

- **组织归属拆两个字段**：`homeOrgId`（档案上存的项目部）+ `orgId`（岗位反推的班组）。

  不清的结果是——人已经去工程组了，系统还让他批客服的假。
- **揭示要双权限**：`c.employees.view` + `a.sensitive.view`。只校验后者的话，楼管（为联系业主本来就有这个权限位）

  班组长排不了班——他没有翻人事档案的权限，但他每天都要选人。

**页面**：`/c/employee` 切到 `@/api`；薪酬块改为「受限 · 属工资域」提示（有 `c.payroll.view` 提示去工资表，
没有则说明仅能看人事档案）。适配层对这一域**统一剥掉薪资字段**——页面拿不到就不会去显示，
显示过一次就再也回不去了。

### 十八、工资域进契约：状态机比字段重要

`04-契约` 新增 `payroll` 域 10 个接口，规模到 **74 路径 / 82 接口 / 147 schema / 91 条测试（91 通过）**。

工资表原来是前端实时算 + `paid` 一个内存 Set，三个按钮（重新核算 / 导出 / 批量发放）里两个是提示框。
这次把它做实，核心不是字段而是**状态机**：

```
草稿 →（核算锁定）已核算 →（提交发放）待发放审批 →（审批通过）已发放 →（冲正）已冲正
                        └──（驳回）已核算
```

三条硬规矩：

| 规矩 | 不这么做会怎样 |
|---|---|
| **金额只由数据层算**（`grossPay` / `deductionTotal` / `netPay`） | 页面各加一遍 → 列表一个数、工资条一个数、汇总又一个数 |
| **已核算后金额不可变**（409/40913） | 发一次钱、记两本账 |
| **提交人不能审批自己的发放单**（409/40915） | 一个人既能核算又能批准，"谁批的"永远写的是同一个人 |

另外两处口径：

- **`dataScope=仅本人` 只回自己那一条**，不是下发全表让前端藏。样例里专门加了 `staff` 账号
  （EM0020 / 仅本人 / 只有 `c.payroll.view`）来守这条——这类账号最容易漏测，因为只有大规模上线后
  才会被发现"能看到别人的工资"。
- **已冲正的行不进 `netTotal`**，单列 `reversedCount` / `reversedAmount`。钱已经退回去了，
  还算在实发里就是账上凭空多一笔。

**页面改造**（`/c/payroll`）：按钮按状态出现/隐藏（草稿才有"重新核算 / 核算锁定"，已核算才有"提交发放"，
待审批才有"审批通过 / 驳回"），行内加「明细」抽屉——应发/代扣分解项与流转时间线**全部由服务端给**
（`calc` + `timeline`），页面不自己拼。

**实测**

```
契约        80 行 · 每行 netPay = grossPay − deductionTotal · 应发 836,324.18 → 实发 754,506.83
            行里没有 bankCard / phone / idCard（工资域不是员工档案的后门）
            草稿直接发放 409/40914 · 已核算重算 409/40913 · 自己审批 409/40915
            staff 列表 total=1 · 冲正后 reversedCount+1、netTotal 减掉该笔
页面        118 人：草稿 → 核算 → 提交 → 自己审批被拦 → 切财务主管审批通过 → 明细(4 条时间线) → 冲正
            零 console 错误
```

> **两个坑**：① 页面 mock 是内存态，**切角色必须在同一页面内切**（顶栏下拉）。新开页面 = 刷新 = 回种子，
> 第一版测试用 `page.goto` 换角色，看到的是"审批通过后又是草稿"。
> ② `el-drawer` 内部是滚动容器，`innerText` 只覆盖首屏——时间线 4 条只读到 1 条，
> 断言要直接取 `.el-timeline-item`。

**仍未做**：个税还是简化的 3% 速算（真接要换成年度累计预扣，税率表不能留代码里）；
批量冲正（现在逐条调）；代发文件导出（银企直连格式）；工资条 PDF；离职当月工资手工补录。

### 十九、组织与权限域进契约（提权要批、降权即时）

`04-契约` 新增 `access` 域 13 个接口，规模到 **86 路径 / 97 接口 / 172 schema / 106 条测试（106 通过）**。
这是最后一个还全在 mock 的业务域。

**权限只挂角色，人只挂角色**——契约里没有"给某人加一个权限码"这种接口。逐人授权的系统最后
没人说得清"谁到底能干什么"。

保存权限矩阵三条分支（**服务端自己算 diff**，前端只提交保存后的完整集合）：

| 情况 | 结果 |
|---|---|
| 与保存前完全一致 | 200 `noChange=true`，不写日志 |
| 新增命中高敏白名单 | **202，不生效**，生成待审批申请 |
| 纯降权 / 普通新增 | **200，立即生效**并记 diff |

高敏五类：看证件明文 / 推翻封账 / 改权限本身 / 改工资表 / 改楼栋责任范围——共同点是
「拿到就等于能自己扩权或掩盖问题」。**降权即时**：收回还要等审批，这段时间里他能做的事一点没少。

双人原则（409/40917）在这条链上是唯一的意义：自己提自己批，等于没有审批，
日志里还会留下一次"审批通过"的假象。

日志是**追加写 + 哈希链**：访问/导出日志每条带 `hash`/`prevHash`，任何一条被改，链上后面全对不上——
否则"谁在什么时候看了谁的证件号"这条记录本身就可以被删掉。

**实测**

```

降权       R-VIEW 去掉 a.vehicles.view → 200 立即生效 · diff 写清是哪个码
提权       R-CLN 加 a.sensitive.view → 202 未生效 · 重复提交 409/40916
原样保存    noChange=true · log=null · 日志条数不变
双人       gm 提交 → gm 审批 409/40917 → pm 审批通过 → 权限此时才生效 → 再批 409/40918
驳回/撤回   驳回要原因且权限不生效；撤回只有提交人能操作
访问日志    12 条逐条 prevHash === 上条 hash · 成功/脱敏/拦截三态齐全
六档        78（有角色）+ 2（离职无角色）= 80 人
```

> **反向发现**：14 个角色里有 **10 个**都持有 `a.sensitive.view`（含客服专员、收银员、楼栋管家）。
> 契约把提权路径收紧了，但**授权基线本身太宽**——真接后台要按最小权限重排一遍，
> 否则审批流拦的只是"从一个已经很宽的口子再加一点"。没改 seed，记录在案。

**未做**：`/e/org`（963 行）与两个日志页仍在用 `utils/api`，还没切到 `@/api`——
E 域的适配层与页面切换是下一步；组织的增删改（新增部门 / 班组）也还没进契约。

### 二十、E 域接适配层：两个日志页切到 `@/api`

### 二十二、组织 CRUD 进契约（原型只有读，没有写）

补 3 个接口，规模到 **88 路径 / 100 接口 / 174 schema / 109 条测试（109 通过）**：

| 接口 | 关键约束 |
|---|---|
| `GET /orgs` | 扁平列表 + `parentId` + `sort` + 人数。返回树的话，"按部门下所有班组筛人"还得先摊平一次 |
| `POST /orgs` | 只能建**部门 / 班组**（集团与项目要伴随立项一整套动作）；`orgId` 服务端生成；同级重名 409 |

- **为什么不做 DELETE**：删组织要么带着人一起删（等于离职），要么先把人挪走——两种都是组织调整单据，
  一个 `DELETE` 表达不了；硬做的结果是库里留下一批 `orgId` 指向不存在组织的员工。

  等于重挂一批人。这该是组织调整，不是一个字段。

防环的后果很具体：把「工程组」的上级设成它自己的下级，这棵子树在组织树上就点不到了，
但列表里人还在——最后没人解释得清"为什么这个人不在组织架构里"。

**实测**：列表 20+ 节点、`headcount ≥ selfHeadcount`、组织树根节点人数之和 = 员工总数；
新增班组 ID 形如 `O-P01-T5`、同级重名 409/40902、建"项目"422、上级不存在 404；
改名/负责人/排序生效、改 type 422、挂到自己下面 422、集团改上级 422。

**`/e/audit` 34 条自检没有接口化**，这是有意的：它检查的是**库里的数据**，不是一个业务资源。
做成 REST 接口后后台要维护 34 条 SQL 断言，收益低于成本；更合适的形态是运维健康检查端点
（`/health/checks`）或定时任务，不该进业务契约。

### 二十三、清掉五处遗留补口（收尾批）

契约到 **91 路径 / 104 接口 / 178 schema / 112 条测试（112 通过）**。这一批全是"接一个口子"的活：

| # | 补口 | 关键点 |
|---|---|---|
| 1 | 公告**提审 / 发布拆开** | 两个动作两个角色。草稿直接发布 → 409/40914；提审不清已读，发布才归零 |
| 2 | 合同**附件下载** | 列表只回元数据，下载**签发临时链接**（20 分钟）并写导出日志 |
| 3 | **`dataScope` 变更纳入审批** | 变宽 → 202；变窄 → 200 立即生效；同档换项目也算变宽 |
| 4 | **审批超时提醒** | 申请带 `ageHours` / `overdue`，`vf=overdue` 只挑挂满 24h 的 |
| 5 | **月结按项目分别结账** | 全公司结账要求"有业务的项目"先结；反结**级联**项目级 |

四处的判断值得记下来：

- **公告拆开**的理由不是"REST 更纯粹"，而是**提审与发布不是同一个人**。合成一个接口的结果是
  只要点了发布就自动跳过审核，"谁审的"那栏永远是空的。
- **附件不发下载地址**：给地址的接口一旦被复制，链接就永远有效。所以列表只回元数据，
  下载单独签发临时链接并留痕——合同是"谁拿走了扫描件"最该查得到的一类文件。
- **`dataScope` 也是扩权**：改「全部项目」扩的是"能看多少行"，不是"能点哪个按钮"。
  档位取 `仅本人 < 本部门 < 责任范围 < 本项目 < 指定项目 < 全部项目`；
  「指定项目」排在「本项目」之上是保守取法——指定 3 个项目的人通常比只看 1 个项目部的人看得多。
- **月结前置 + 级联反结**：全公司结账要求有业务的项目先结（汇总前明细没清，等于用总数掩盖问题）；
  但**当期一笔账都没有的项目不参与**，否则空项目永远结不掉、全公司就永远结不了。
  反结必须级联——只解汇总锁的话，项目明细还锁着，反结之后依然补录不了，等于白反。

### 二十五、组织维护入口 + 补一个「能看档案、不能看工资」的角色

**① 组织维护为什么做成抽屉，而不是新页面**

契约第 38 批就有 `POST /orgs` / `PATCH /orgs/{orgId}`，但原型一直没有入口。做成独立页面看着"更正规"，

- 新路径要走权限守卫，而守卫是靠 `permissions.json` 的 `route` 字段反查权限码的（`permCodeOfPath`）。
  新页面没有对应权限码 → 反查结果为空 → **按公共页放行**，等于把组织增删改暴露给所有人。
  要补就得新增权限位 + 改两份 mock + 改契约 fixture + 改种子，为一个"维护入口"扩一圈权限表，不划算。
- 组织维护天然依附于"看组织"这件事，抽屉里改完立刻能看见左树变化，比跳页再回来更顺。

所以做成 `/e/org` 工具栏上的「组织维护」抽屉：**复用 `e.org.view` 看、`e.org.edit` 改**，零新增权限位。

**② 三个交互取舍**

| 取舍 | 原因 |
|---|---|
| 树表用 `el-table` 的 `tree-props`，行内「新增下级」 | 上级由所在行决定，省掉"先选上级"这一步——那是最容易选错的一步 |

**挂到自己的下级下面**（成环后整棵子树从组织树上消失，但人还在列表里）。`orgId` 服务端生成——

### 二十六、导出清单：给「数据外流」单独一个页签

**① 为什么另开一个页签，而不是并到访问留痕里**

访问留痕回答的是「谁看了谁的身份证」，导出清单回答的是「谁把多少行数据导到机器外面去了」——
两个问题，两种粒度（一次一个字段 vs 一个文件几万行）。并在一张表里的直接后果是：
48 条揭示把 6 条导出淹掉，而**导出才是数据外流的主通道**，被拦下的那几次最该被看见。

所以 `/e/access-log` 加了两个页签（仍复用 `e.accessLog.view`，没有新增权限位）：

| 页签 | 内容 | 筛选 |
|---|---|---|
| 访问留痕 | 每次揭示一条（对象 · 字段 · 来源页） | 动作 / 结果 / 操作人 / 时间 / 关键字 |
| 导出清单 | 文件级（文件名 · 格式 · 行数 · 结果） | 结果 / 操作人 / 时间 / 关键字 |

**② 页面顺便把契约补齐了**

页面要传 `days` 与 `kw`，而 `/export-logs` 原先只有 `result` / `operator` ——http 模式下这两个条件会被
服务端丢掉，用户以为筛了。所以给契约补了 `days` / `kw`，并在实现里做了个刻意的选择：

> `days` **只在显式传了才过滤**。给默认值 7 会把「查全部」的老调用悄悄截断，
> 排查时只看到 6 条而不是 12 条，还找不到原因。默认值放在**页面**上（默认近 7 天），
> 不放在接口语义里。

**③ 一个交互细节**

换页签会重置筛选：导出清单没有「动作」这个维度，把上一条留在查询条件里，会让人以为筛了两次。
KPI 两个页签共用——它统计的是"审计口径"的整体（揭示 / 导出 / 脱敏 / 拦截），不随表格切换而变。

**实测**（浏览器，零 console 错误）

```
页签    访问留痕 48 条（含查看明文）｜导出清单 6 条，表头是 文件名/格式/行数/结果
筛选    结果=拦截 → 只剩 1 条且整行高亮（被拦的最值得看）
切回    动作筛选回来、筛选被重置，不会把「拦截」带过去
契约    112/112，新增断言：result 筛选全命中、kw 是子集、days 越小结果不变多
```

| 新增 · 业主级 12 项 | `ownerCategory` 分类、`economicLevel` 经济状况、`politicalStatus` 政治面貌、`weddingDate` 结婚纪念日、`employer`/`jobTitle`/`occupation`、`workAddress`、`hobbies`、`pets`、`positiveNotes`、`negativeNotes` |
| 新增 · 房屋级 3 项 | `deliverDate` 交房日期、`decorationViolation` 是否违规装修、`decorationResult` 处理结果 |
| 派生 / 不落库 | 序号（导出用）、家庭成员人数 |

**三条设计判断**

1. **违规装修挂房屋，不挂业主**。一个业主可能有多套房，违规是某套的事；
   挂到人身上，房子卖了标记还跟着人走，下一任业主莫名其妙背一条违规。
2. **经济状况 / 政治面貌 / 负面信息按敏感字段处理**：列表回 `***`，详情要 `a.sensitive.view`
   且揭示留痕。它们不进计费也不进考核，但整表下发就是"整栋楼谁家困难、谁被投诉过"的名单。
   枚举类字段的掩码不做"保留前后位"——对「一般」「群众」保留前后位等于把答案写脸上。
3. **婚姻/职业等字段允许为空**，不给假日期假单位。原来 `weddingDate` 若给 `2015-01-01` 这种默认值，
   两年后没人分得清哪些是真登记过的。

**数据层怎么做的（避免全库漂移）**

新增字段用**独立随机流 `SEED+77`**，主随机流一个数都没消耗——重跑种子后只有
`owners.json` / `houses.json` / `members.json` 三个文件变化，其余 46 个文件逐字不变。

**契约**

`Owner` 扩 12 项、`House` 扩 3 项；枚举与掩码用 `oneOf`（`enum` + `'***'`）而不是把掩码塞进枚举——
前者能同时校验"真实取值合法"和"掩码是唯一形态"，后者会让 `***` 看起来像一个合法选项。
`PATCH /owners/{id}` 白名单同步扩展，脏枚举当场 422。

**页面**

业主 360 新增「客户画像」页签：居住与分类 / 职业与经济 / 偏好 / 评价 四组，
敏感三项用 `SensitiveText`（默认打码，点眼睛才揭示并写访问日志），底部附「房屋级：交付与装修」小表。
「编辑画像」按字段逐条提交——一格失败只回滚那一格，不整单丢弃。

**实测**

```

      刷新回到种子值（内存态）
契约  114/114：列表三项掩码 · 详情回真枚举 · 违规装修四档合法 · 非「无」必有处理结果 ·
      内联编辑合法枚举 200 / 脏值 422 / 日期格式 422
种子  仅 owners / houses / members 变化，其余 46 张表逐字不变
```

### 二十八、业主标签：字典 + 打标签（需求 2）

**① 为什么存 tagId 不存名称**

原来 `owner.tags` 是字符串数组。改成 `tagIds` 只有一个理由，但足够：**词条会变**。
改名要刷 682 条业主、停用一个词条会让历史标签变成无主的字符串、两个词条叫重了根本分不清。
存键之后，改名只改字典一行，停用只改一个布尔位。

**② 为什么权限放在 e 域，不放在 a 域**

需求是「楼管打标签 + 后台维护可选标签」。这两件事的授权面完全不同：

| 动作 | 权限位 | 谁能做 |
|---|---|---|
| 读字典（选择弹层的选项来源） | `a.owners.view` | 所有能看业主档案的人 |
| 打 / 去标签 | `a.owners.edit` | 楼管（受责任范围约束） |
| 维护字典（新增 / 改名 / 停用） | `e.ownerTags.edit` | 人事专员、总经理；**楼管没有** |

**如果把字典维护放在 a 域**，项目经理的 `a.* view/edit` 通配会自动带上它 ——
每个项目经理都能改全公司的标签词条。而字典是全公司共用口径，改一个词条会影响所有人筛选与分组。
放 e 域之后，楼管拿到的是「能选不能改」，正好是需求要的效果。

**读字典刻意只要 `a.owners.view`**：要求 `e.ownerTags.view` 的话，楼管打开选择弹层会是一个空列表 ——
打标签的人读不到「有哪些标签可选」，这功能就等于没有。

**③ 停用 ≠ 删除**

停用（`enabled=false`）只拦「新打」，**已经打上去的保留**，而且**仍然可以摘掉**：

- 已打的不消失：历史事实不因为现在不统计而变假（「这户去年确实涉过诉」）
- 仍可摘掉：停用只拦新增，不拦撤销 —— 不然挂错了就永远摘不掉
- 停用前先看 `ownerCount`：页面会把「已有 N 位业主的标签会保留」写进确认提示，而不是悄悄停掉

内置词条可改名 / 停用，**不可删除**：删了历史标签就成孤儿。名称唯一性**包含已停用词条** ——
否则会出现一个启用一个停用的两个「重点关怀」，打标签的人分不清该选哪个。

**④ 种子：标签必须与账单、工单对得上**

原来那 133 人的标签是 `random.random() < 0.08` 随机挂的，后果是「不欠费的人也挂长期欠费」，
评审第一眼就会被指出来。现在改成**派生 + 独立随机流**：

| 标签 | 判据（都能从数据验） | 人数 |
|---|---|---|
| 独居老人 | 年龄 ≥65 且同住成员 0 人 | 51 |
| 重点关怀 | 独居老人 ∪ 70 岁以上 ∪ 欠费 ≥3000 | 57 |
| 家有婴幼儿 | 有「子女」成员且业主 ≤45 岁 | 18 |
| 投诉频繁 | 投诉建议类工单 ≥1 条 | 19 |
| 长期欠费 | 欠费 ≥500 且最长逾期 ≥30 天 | 34 |
| 违规装修 | 名下房屋 `decorationViolation=已认定` | 38 |
| 养宠家庭 | 画像 `pets ≠ 无` | 174 |
| 意见领袖 / 社区志愿者 | 独立随机流少量 | 29 / 13 |
| 法律纠纷 | **停用词条**，3 人（演示"停用后已打的不消失"） | 3 |

有一段旧代码**必须保留**：原来那个随机打标签的循环消耗了 4×682 个随机数，
直接删掉会让后面账单、工单、租户全部漂移。改成只消耗、不赋值，并在注释里写明原因。

**⑤ 页面**

| 页面 | 内容 |
|---|---|
| `/a/owner-tags`（新增） | 4 个 KPI（词条 / 已用 / 已打标签业主 / 未打）· 分类与状态筛选 · 使用人数可点跳业主列表 · 新增/编辑抽屉 · 停用确认 |

**⑥ 实测踩到的一个坑（值得记）**

从标签页点「57 人」跳到业主列表，结果列表还是全量 682 条。原因是业主列表的 `clearScope()`

### 二十九、房屋六态与租客类型（2026-11-02）

**① 房屋使用状态：五个混维度的旧值 → 六态一条线**

旧枚举是「自住 / 出租 / 空置 / 装修中 / 限制使用」——它把**居住关系**（自住/出租）和
**装修进度**（空置/装修中）塞进同一个字段，于是"出租 + 毛坯"这种组合在数据里并存：
实测有 **58 套出租房是毛坯**、**152 套自住房是毛坯**。房子租出去了却写着毛坯，
物业费照收、上门维修进不了门，评审一眼就能看出是假数据。

新六态按现场《房屋状态》看板统一，是"交付 → 装修 → 入住"一条线上的档位：

| 状态 | 配色 | 判据（种子里强制成立） |
|---|---|---|
| 已入住 | 绿 | 有业主自住，或有在住租户；**装修不能是毛坯** |
| 装修未入住 | 紫 | 已交付、装修完工、业主未搬入 |
| 正在装修 | 黄 | 施工中 |
| 已交房未装修 | 靛 | 已拿钥匙、还是毛坯 |
| 未交房 | 橙红 | 未到交付日；**不计物业费、不可出租** |
| 空置房 | 灰 | 可住但长期无人（旧「限制使用」并入此档） |

**居住关系没有丢**：改由 `tenantId` 派生 —— 有租客 = 出租，无租客但已入住 = 自住。
页面 KPI 也从"自住 / 出租 / 空置"改成"总数（含未交房）/ 已入住（含入住率）/ 空置房 / 在装修"。

**入住率的口径**：分母是**已交付**房屋，未交房不算 —— 房子还没交，谈入住率没有意义。
这条写进了 `houseLedgerSummary`，页面不再自己算。

**② 「未交房」是为了让枚举成立而补的真实数据**

原来 736 套全部已交付。为了让「未交房」这一档有实际数据、也能被验到，种子里补了
**锦绣家园 7 栋（2 单元 × 10 层 = 20 套，2027-03 交付）**：

- 挂在账单/缴费/工单生成**之后**追加 —— 未交付不计费，天然不会被算进收缴率
- 无业主、无租户、无交付日期、无违规装修（还没拿钥匙，谈违规没意义）
- 房屋总数 736 → **756**，社区/楼栋人头重算

**③ 用途新增「公寓」**

锦绣家园 6 栋整体转公寓（旧改公寓，**按住宅标准计费**）。只改 `usage` 与 `houseType`，
面积与已生成的账单一个数都不动 —— 账单是 `area × 单价` 算出来的，
改面积会让历史账单与房屋对不上。

**④ 租客类型：个人 / 公司两套字段，不是一张表塞两种东西**

| | 个人 | 公司 |
|---|---|---|
| 主体凭证 | 身份证 | **统一社会信用代码**（`idCard` 为空） |
| 核验看什么 | 实名 + 人脸 | **营业执照**（代码 + 法人 + 经办人） |
| 门禁人脸录谁 | 本人 | **经办人** |
| 完整度 8 项 | 姓名/手机/证件/实名/人脸/与业主关系/居住人数/紧急联系人 | 公司名/信用代码/法人/法人电话/经办人/经办人手机/经营类目/注册地址 |
| 核验门槛 5 项 | 姓名/手机/证件/关系/人数 | 公司名/信用代码/法人/经办人/经办人手机 |

**表单是整组替换，不是叠加**：切到「公司」后，「姓名 / 证件号码 / 与业主关系」直接消失，
「员工人数」替掉「居住人数」。叠加的后果是公司租户永远被"姓名必填"挡住，
而姓名对一家公司根本没有意义。

**⑤ 信用代码用真算法校验，不是查长度**

GB 32100-2015：31 位字符集（去掉 I O S V Z，它们和 1 0 5 视觉上分不清）+ 加权求和 + 校验位。
种子里 50 个公司租户的代码都是**算出来的**，能过同一个校验函数 —— 编 18 位数字的结果是
前端和契约两边的校验把自己拦住，最后只能把校验关掉，那校验就等于没有。

前端输入时实时提示：长度不对 / 含非法字符 / **校验位不对（并告诉应该是什么）**。

**⑥ 顺带修掉的口径分裂**

补充抽屉原来自己写了一套 8 项完整度，和 `utils/api` 里的那套阈值不同 ——
同一个租户可能出现「列表说 62%、抽屉说 75%」。现在两边都调 `computeTenantFill()`。

**实测**（34 条断言，零 console 错误）

```

### 三十、用途可改 · 营业执照影像件 · 换承租主体（2026-11-02 收尾）

**① 房屋「用途」补齐内联编辑**

数据层早就支持 `usage` 校验，但详情抽屉里它一直是纯文本 —— 于是"这套房其实是公寓"
只能退回编辑页改。现在点开即选（住宅 / 公寓 / 商业），保存后提示**计费口径随新用途**：
公寓按住宅标准计费，改用途不是改一个标签，下个月账单会变。

**② 交付状态 × 使用状态必须自洽（上一批的漏改点）**

六态上线时，房屋表单里还留着三处旧口径，任一处都能造出脏数据：

| 位置 | 旧值 | 后果 |
|---|---|---|
| `EMPTY.useStatus` | `自住` | 新建房屋保存时被自己的六态校验拦住，等于新增房屋直接不可用 |
| 交付状态下拉 | 已交付 / **未交付** / **待交付** | 数据与契约只有「已交付 / 未交房」，选「未交付」的房子被 `isDelivered` 判成已交付，**当天就能计费** |
| 使用状态 | 不随交付联动 | 能选出「未交房 + 已入住」这种连钥匙都没交却已入住的组合 |

现在：交付状态收敛成常量 `HOUSE_DELIVER_STATUS = ['已交付','未交房']`；选「未交房」时
使用状态自动锁成「未交房」并禁用；`saveHouse` 与 `updateHouseField` 两头都校验 ——
**页面能绕过，数据层不能**。内联改使用状态时同样拦（提示"先去编辑页改交付状态"）。

**③ 营业执照影像件：公司核验的「依据」，不是装饰**

公司核验核的是执照原件，所以影像件做成**核验前置**：没有影像件，`verify` 直接
422/42203 —— 没看过原件就盖「已核验」，核验等于没发生。

规则（前后端同一套 `TENANT_FILE_RULES`）：

| 项 | 口径 | 为什么 |
|---|---|---|
| 格式 | JPG / PNG / WEBP / PDF | 执照要能看清国徽与二维码，不放开随意格式 |
| 单张 | ≤ 5 MB | 手机直出照片约 2–4 MB，再大是没压缩的原图 |
| 张数 | ≤ 3 张 | 正本 / 副本 / 变更页，够了 |
| 重复 | 同名同大小 → 409/40922 | 同一张传三次不会让"有据可查"更成立 |

**为什么不塞进「完整度 8 项」**：完整度衡量"信息填全没有"，影像件决定"能不能核验"。
混进去会一次性改掉全部公司的完整度分母，列表人数与既有断言跟着漂，而业务上它们本就是两件事。
所以 `completeness` 里单列 `licenseRequired / licenseCount / licenseReady`。

原型没有对象存储：只登记元数据（名称 / 大小 / 类型 / 谁传的 / 什么时候），
预览用本地文件生成的 blob URL，**刷新即失效**；但校验、留痕、核验前置三件事都按真接口做。
新建公司租户时 `tenantId` 还不存在，组件以 `local` 模式把文件挂在表单上，保存时随主体一次写入。

**④ 换承租主体：从"不允许"改成"允许但说清代价"**

上一批写的是"类型不可互转，换主体请先搬离再登记"。这个口径有问题：换主体在现实里真会发生
（个体户注册成公司、公司注销后由经办人个人续租），重新登记会把**同一段租约、同一条核验记录劈成两条**，
往后追溯"这套房到底谁住过"对不上。

改成 `POST /tenants/{id}/change-type`，一次事务做完 5 件事：

1. **撤销人脸**（`faceRegistered=false`）——人脸属于自然人，公司主体没有脸
2. **复位核验**（`certified=false` / `verifyStatus=待核验`）——换主体等于换证件，核过的证不作数
3. **清空另一套字段**——个人租户里躺着公司名，列表与报表都会算错

### 三十一、工单模块改造：商业服务独立成线（2026-11-02）

**① 两根毛病的根：两套分类维度被挤进一个下拉**

原先工单有 6 个类型，其中「入户维修」既是类型、它的分类又和公共区域共用同一批「维修品类」：
水管漏水 / 下水道堵塞 / 空调不制冷 / 电路故障 / 门锁故障 / 门窗损坏 / 墙面开裂 / 瓷砖空鼓 /
照明不亮 / 电梯异常。于是下拉里出现「电梯异常」（**部位**）和「下水道堵塞」（**工种**）并列 ——
两者根本不是一个维度，选哪个都对，选哪个都别扭。

拆完之后两条维修线各有一套分类：

| | 公共区域维修（免费） | 商业服务（收费） |
|---|---|---|
| 分类维度 | **设施部位**（东西坏在哪） | **维修品类**（要动什么工种） |
| 取值 | 电梯 / 给排水 / 公区照明 / 配电 / 土建 / 门窗五金 / 公共设备 / 道闸门禁 / 环境其他 | 水管漏水 / 下水道堵塞 / 电路故障 / 照明不亮 / 门锁故障 / 门窗损坏 / 空调不制冷 / 瓷砖空鼓 / 墙面开裂 / 其他 |
| 可维护 | 内置 9 项（可停用排序，不开放新增） | **后台可维护**（分类 + 项目 + 服务价 + 成本价） |

**② 商业服务项目 = 激活了那份"孤儿价目表"**

`repairPrices.json` 原本被业主端小程序与员工端 APP 直接 import（三处金额一致的验收靠它），
但 PC 后台**没有维护页** —— 注释里写的「收费项目 → 维修服务价目」页面并不存在，只能手改 JSON。
这次把它升级成正式字典：

```
服务价格 = 材料费 + 人工费        对业主报价；人工费也是师傅提成的基数
成本价   = 材料成本 + 人工成本    材料按成本价过账（materialsChargedAtCost），人工 = 工时 × 48 元/时
```

- 两个合计**由服务端算**，页面只填四个分项 —— 允许直接填合计再反推，就是下一次「列表 125 / 详情 124.99」的来源；
- **材料成本 > 材料费**直接拦（42205）：材料按成本价过账，成本比售价高等于材料在亏本卖；
- **成本价 ≥ 服务价格**直接拦（42206）：这一项启用就亏本；
- **停用不删**：历史工单还引着它；有在途工单时不给停（40924），否则那几张单的价格来源就断了。

**③ 金额是"下单那一刻"的快照，改价不回溯**

工单上同时落下 `priceCode / serviceName / totalFee / serviceCost` 四个快照字段。
字典把人工费从 90 改成 110 之后：新单按 125 涨到 145，**已完工的旧单仍然是 125**，成本也还是 67。
不这么做的话，一次调价会把历史毛利全部改写，月度利润表每次看都不一样。

**④ 详情页原来是静态演示，现在是真数据**

`WorkOrderDetail` 之前写死 `getWorkOrder('WO000001')`：从列表点任何一行进来看到的都是第一张单，
而费用明细是另一套硬编码的 120 + 80，跟工单自己的 `totalFee` 都对不上。现在：

- 按 `?id=` 取数，单号 / 业主 / 房屋 / 时间线全部真实；
- 费用卡三分支：商业服务 → 服务费用表 + 内部成本毛利条 + 收款状态；公共区域 → 免费说明（不生成账单）；非维修类 → 整卡不显示；
- 时间线只渲染真实发生过的节点，没发生的写「等待派单 / 等待接单 / 等待完工」，不再假装已完成。

**⑤ 收益：商业服务进营业报表，毛利单列**

营业报表原本只有账单口径的 4 个科目（物业费 / 车位 / 水 / 电），工单的 36 单 5,005 元
**完全不入统计**。现在：

- 营业报表末行加「商业服务收入」，取数规则是**完工确认制**：只算已完工 / 已评价 / 已关闭的单，
  未完工不产生应收（账单是应收制，工单是完工确认制，两者不能混着算）；
- 报修汇总表加 **服务收入 / 服务成本 / 毛利** 三列，只有商业服务行有值，公共区域恒为 0（免费，成本走运营）；
- 年度收益取**毛利**：光看收入会把材料成本当成利润。

**⑥ 顺带修掉**

- 报表「报修汇总」的合计行原来复用 `payable/paid` 字段位装「已完工/超时量」，合计恒为 0 —— 换成独立字段；
- 告警转工单的分类写的是「设备故障」（不在任何字典里）→ 归到「公共设备」；
- 工单新建默认类型从「入户维修」改成「公共区域维修」：报修里最常见、且不需要房屋与业主配合，开单门槛最低。

### 三十二、收入结构：多种经营独立成一类（2026-11-02）

**① 三条需求其实是一条主线**

合同加公共收益、多种经营单列、工时积分，表面是三件事，落到数据上是一句话：

```
公司收入
├─ 主营业务收入 ── 物业费 / 车位 / 能耗（账单口径，应收制）
└─ 多种经营收入                        ← 新增大类
   ├─ 商业服务收入  ← 收费工单（完工确认制）
   └─ 商业合作收入  ← 经营性合同（年化，扣归业主的公共收益）
```

没有这一层，"商业服务收入"只是营业报表末尾一个孤零零的行，说不清占公司收入几成。

**② 合同必须加三值分类，不能只加公共收益金额**

需求是「合同金额 − 公共收益金额 = 商业合作收入」。直接套公式会算错 1074 万：

| 类型 | 份数 | 金额 | 实际性质 |
|---|---|---|---|
| 外包服务 | 30 | 647.9 万 | **支出** |
| 采购 | 20 | 290.6 万 | **支出** |
| 劳动 | 12 | 135.8 万 | **支出** |
| 租赁 | 16 | 152.1 万 | 收入（经营） |
| 物业服务 | 7 | 340.8 万 | **存疑** |

「物业服务」这 7 份的乙方全是「嘉合智联机电」「兴洁美服务」这类外包商，实际是支出；
但同类型的「前期物业服务合同」是收入。**同类型两向，按 type 推不出来**，只能逐份标：

| `incomeCategory` | 含义 | 份数 |
|---|---|---|
| `主营业务` | 物业费口径，**不进**多种经营 | 1 |
| `多种经营` | 进商业合作收入，扣公共收益 | 16 |
| `不计入` | 支出合同，只进成本 | 68 |

公共收益按「占用了多少共有部位」给比例：广告位 60–78%、车位 50–72%、商铺 38–55%、
房屋 0%（物业自有/代管）。合计 64.4 万归业主，物业实得 87.7 万（期间总额）。

**③ 合同金额是期间总额，必须年化 + 乘覆盖月数**

85 份合同期间是 6 / 12 / 24 / 36 个月。直接加总当收入，一份 36 个月的广告合同会让今年虚高 3 倍。

```
年化商业合作收入 = (合同金额 − 公共收益) ÷ 期间月数 × 12
计入当年          = 年化 × 当年覆盖月数 ÷ 12
```

「当年覆盖月数」是第二层保护：10 月才签的 12 个月合同，当年只计 3 个月，不会把整年的钱记进今年。

**④ 三个载体，各干一件事**

| 载体 | 内容 | 为什么放这儿 |
|---|---|---|
| 费用驾驶舱 | 一条摘要带（总额 + 两分项 + 占比 + 入口） | 驾驶舱是 B 组入口页，总经理第一眼要能看到；但它已有 6 KPI + 5 图，再加会散 |
| **多种经营收入页** `/b/multi-revenue` | 收入结构带 + 4 KPI + 占比 + 月趋势 + 项目排行 + 工单/合同双表 | 两个分项粒度差一个数量级（16 单 vs 8 份），展开放不下 |
| 营业报表 | 末段三行：小计 + 其中商业服务 + 其中商业合作（`rowLevel` 缩进） | 财务做月报时"收入合计"要能在同一张表里加出来 |

另加一张「多种经营收入表」（项目 × 分项铺平），因为分项的口径字段不同（商业服务有成本毛利、
商业合作有公共收益），合并成列会一半格子空着。

**⑤ 工时积分：只记录，但把绩效的接口形状先定下来**

公共区域维修免费、没有提成 —— 75 张单是典型的"干了没好处"，积分是这块活唯一的激励入口。
商业服务**不给积分**：它按人工费提成，已经直接给钱，再叠一层等于同一件事发两次奖，师傅会挑单。

```
积分 = 工时 × 10 分/时 × 部位权重
权重：电梯 1.5 / 公共设备 1.4 / 配电 1.3 / 给排水与道闸 1.2 / 土建 1.1 / 照明门窗 1.0 / 环境 0.8
```

权重体现"同样 1 小时，风险与技能要求不同"：电梯困人 30 分钟和绿化浇水 30 分钟不该同分。

本期**不做绩效折算**，但三样东西先摆好，否则以后接不上：

| 预留项 | 取值 | 不预留的后果 |
|---|---|---|
| `pointRuleVersion` | `POINT-2026-11-01` | 调权重会把历史积分一起重算，上个月的绩效下个月变 |
| `pointsPeriod` | `YYYY-MM`（按完工月） | 绩效按自然月核算，积分聚合不起来 |
| `pointsStatus` | 待结算 / 已结算 / 已作废 | 月末结完还能改数 |

绩效侧的读取口已经定成一个：`laborPointSummary({ empId, period })`，按 `empId + period` 聚合有效流水。
页面上直接写明"本期只做记录，绩效折算尚未开通"，折算系数与基准分待考核办法确定，不由接口层拍。

### 三十三、部门更名与合同审批可见性（2026-11-03）

**① 品质管理部 → 运营管理部：只改名，不动职能**

### 三十四、OA 审批底座（2026-11-03）

**① 之前的「审批」只做了一半**

系统里一直有审批单、待办聚合、同意/驳回/转办/加签，但**只处理别人交上来的单**：
没有发起入口，没有流程配置，四类审批（费用减免 / 报修验收 / 押金退还 / 公告发布）
全部**从业务单据派生**（挂 billId / woId / depositId / noticeId）。

补的就是缺的那半：**能自己发起一张单** + **能配流程**。

**② OA 单据不塞进业务单据表，复用 approvals 加个 formData**

| | 业务单据（合同/工单） | OA 单据（用车/报销） |
|---|---|---|
| 有没有实体 | 有（contracts / workOrders） | **没有**，内容就是表单 |
| bizId | 指向合同/工单 | **留空** |
| 内容存哪 | 业务表 | `formData`（表单快照） |

所以 OA 不新表：`approvals` 本来就是"审批实例"表，多带一个 `formData` 即可。
待办中心、超时计算、转办加签全部白得，一行不用重写。

**③ 字段是「描述」不是固定列**

六类单据的表单写在 `utils/oa.js`，每类是一组 `{key,label,type,required,min,max,options,role}`，
页面按它渲染控件。**加第七种单据只加一条定义，不改页面、不改表结构。**

`role` 是语义标记：
- `role: 'amount'` → 这个字段参与金额分支（决定走基础流程还是超额流程）
- `role: 'periodEnd'` → 这个字段要校验晚于 `after` 指定的字段（请假、加班的结束时间）

**④ 审批人按规则取，不写死人名**

五种来源：部门负责人 / 项目经理 / 直属上级 / 指定岗位 / 指定部门负责人。
写死"张经理"之后，人一调岗审批就断。

这里踩到一个数据坑：**不能用职级判断「主管及以上」** —— 环境主管是 P5、财务主管是 P7，
按 P 值一刀切会把环境主管漏掉。系统里现成的做法是按**岗位名**判（`/主管|经理|总监/`）。

顺带修了 seed：原来员工 `orgId` 完全随机，出现"总经理挂在翡翠城项目部"，
OA 审批就成了"总经理向项目经理报批"。现在把 5 个关键岗位归位（总经理→总部、财务主管→财务部、
项目经理→各项目），其余不动，避免部门人数分布整体漂移。

**⑤ 金额决定级数**

| 单据 | 阈值 | ≤ 阈值 | > 阈值 |
|---|---|---|---|
| 费用报销 | 5000 | 部门负责人 → 财务复核 | 再加项目经理 |
| 采购申请 | 10000 | 部门负责人 → 项目经理 | 再加财务预算复核 |
| 合同审批 | **300000** | 合同初审 → 部门负责人 | 再加**法务复核 + 总经理** |

合同审批这一行的阈值原来**硬编码在 api.js**（`amount >= 300000 ? 三级 : 两级`），
收进配置表后可以改 —— 这是 OA 底座对存量功能的正向改造，不只是给新单据用。

**⑥ 流程配置：改完只影响新单**

在途单的 `flow` 是发起时的**快照**，改配置回头改会让"批到一半换规则"，说不清谁批的算数。
页面上直接标出"当前 N 张在途单沿用旧流程"。

两条配置校验：节点不能清空（否则提交即通过）、配了超额流程但阈值是 0 直接拦
（那套节点永远走不到，配了等于没配）。

**⑦ 本期边界：批准即结束**

费用报销批了**不生成付款单**、请假批了**不进考勤**、采购批了**不建采购单**。
每个"落结果"都要动别的域的状态机（付款牵日结月结、请假牵考勤申诉），单独排批。
页面上三处都写明了这句话，避免被误读为已打通。

**⑧ 实测**（39 条断言，零 console 错误）

## 八、第 51 批 · 部门计划管理（2026-11-03）

需求口径由用户拍定三条：**一个部门一个月一份计划**（内含多任务、权重合计 100）、
**「主管及以上」按岗位清单判断**（不按职级 —— 环境主管 P5、财务主管 P7，拿职级切会漏一半人）、
**计划评分与品质评价完全独立**（不合并、不互相折算，本期只记录评分、不接入工资核算）。

### 8.1 开工前先修的地基：组织负责人

`orgs.leader` 原本是自由文本，有 **9 个组织的负责人写的是员工表里不存在的人名**
（周建国 / 谢文博 / 梁雅静 / 罗天佑 / 张振华 / 李春梅 / 陈瑞），另有一个班组负责人（万军）已离职。
计划管理要按「我负责哪几个部门」反查，按姓名扫会扫空 —— 而且员工表里有**两个「宋杰」**
（EM0017 客服主管 / EM0040 保安），按姓名反查还会串号。

处理：
- 补 `leaderEmpId` 作为**权威引用**，`leader` 姓名改为由员工表回填、降级为展示快照；
- 不改多值数组：一人多部门用「一人挂多个组织的负责人」表达，第 52 批做关系表时只换 `leadsOf()` 实现；
- 造两个多部门案例：EM0001 雷志强（集团 + 总部职能）、EM0017 宋杰（星光天地客服组 + 翡翠城客服组，缺编代管）。

### 8.2 两套关系，别混成一个

**任职**（belongs）必须唯一：工资、社保、考勤、工龄、工时积分、部门绩效系数全部依赖单一归属。
**负责**（leads）可以多值：管几个部门、代管几个月，是职责授权，天然多条且有有效期。
把 `employees.orgId` 改成数组会让所有按部门汇总的口径同时出问题 —— 所以主职不动，另建负责关系。

### 8.3 计划模型

- 状态机：`草稿 → 审批中 → 已批准 / 已驳回 → 执行中 → 已结案`，已驳回可重编重提；
- `(planMonth, orgId)` 唯一，已驳回的不占位；服务端**重新校验**提报人是不是该组织负责人（不信前端下拉）；
- **权重合计 100 卡在提交，不卡草稿** —— 逼着草稿一次填完的结果是权重全填 25 凑数；
- 完成率**按权重加权**，不是任务条数占比；计划总分 = Σ(任务得分 × 权重)/100，不是平均分；
- 提报身份落库（`submitterDuty` 正职 / 兼管）：半年后他可能已经不管这个部门了，历史单据要能解释当时凭什么提的。

### 8.4 审批接入与「自己审自己」

走统一 OA 引擎（`bizType='计划审批'`，`bizId=planId`，`noForm`），审批结果回写计划状态。
两个关键处理：

1. **审批链按提报部门解析，不按人事归属**。一人管两个部门时，两个部门的项目经理不是同一个人 ——
   宋杰提报翡翠城客服组，第一节点是徐悦；提报星光天地客服组，第一节点是杜若曦。
   `createOaRequest` 为此加了 `orgScopeId`。
2. **自审跳升**。项目经理给自己项目提计划，第一节点「项目经理审批」解析到的就是他本人，流程直接死锁。
   现在解析结果等于申请人时沿组织链向上找第一个不是自己的负责人（徐悦 → 雷志强），
   并在节点上写明「原审批人为本人，已跳升至…」。这条是通用能力，所有 OA 单据受益。

另外 `projectManager` 规则修了一处：班组节点会一路向上找所属项目，不再直接回落到集团总经理。

| `/f/plans` | 计划列表 | 月度 / 项目 / 状态筛选；4 张 KPI；统计三块（按项目部门 · 执行情况 · 评分分布）；身份条显示「我负责 N 个部门」 |

## 九、第 52 批 · 组织负责人关系表（2026-11-03）

第 51 批做计划管理时用的是轻实现：`orgs.leaderEmpId` 一个部门一个负责人。本批把它做实。

### 9.1 为什么必须单独一张表

`orgs.leader` 是自由文本，只能表达「一个部门一个负责人」。现实里三种情况表达不出来：

| 情况 | 单值字段的后果 |
|---|---|
| 一个部门多个负责人（正职 + 副职分工） | 只能填一个，另一个人的职责无处安放 |
| 正职离任、代理顶上 | 代理没有起止日期，到期不会自动失效，只能靠人记着改回来 |
| 一人管多个部门且职责不同 | A 部门正职、B 部门代理 —— 一个字段装不下两种身份 |

### 9.2 三条口径

1. **正职唯一**：一个部门只能有一个在期正职，多了不知道谁签字（409/40927）；
2. **代理必须填结束日期**：没有到期的代理等于第二个正职，迟早忘了收回（422/42213）；
3. **副职不参与审批**：副职是分工不是授权。审批只认正职，**正职空缺才落到在期代理**。

`orgs.leader` / `leaderEmpId` 保留为展示快照，由关系表回写 —— 二十多处展示代码和契约样例都引着它，
删掉是纯风险没有收益。但**判断谁是审批人必须读关系表**，不能读快照。

### 9.3 落到页面上的效果

组织维护表（`/e/org` → 组织维护）的负责人列现在能一屏看完一个部门的人事结构：

```
安保组  O-P01-T3   胡建国 正职（已结束）   龚淼然 代理 至 2026-12-31   4/4
```

编辑弹窗里是负责人子表：人员选择 + 职责 + 起止日期，可增删多行。保存时**先存负责人再改组织信息** ——
负责人校验最严（正职唯一 / 代理必有结束日），先过这关能避免"名字改了、负责人没改"的半截状态。

### 9.4 代理生效的演示数据

种子里 O-P01-T3 的正职 2026-10-15 离任、代理 10-16 起在期。这样：
- `orgLeaderOf('O-P01-T3')` 返回代理龚淼然 → 审批落到她；
- `orgs.leader` 快照同步成龚淼然 → 组织树、巡检被检班组显示同一个人；
- 原来的正职胡建国留在表里标「已结束」，谁都能查到"去年这个组谁负责"。

另有一条已过期的代理（O-P02-T4，8/1–9/30）演示「到期自动失效」：不用定时任务，
`state` 按当天现算，过期就自然不参与审批。

计划提报页的「你负责 2 个部门（客服组、客服组）」—— 两个同名班组看不出是哪个项目的。
改成显示组织路径末两段：「翡翠城项目部 / 客服组、星光天地项目部 / 客服组」。

## 十、第 53 批 · 审批会签（2026-11-03）

第 52 批把「一个部门多个负责人」做实之后，政策上就卡住了：副职有分工，但审批只有一个人签。
本批把节点的签署方式打开。

### 10.1 三档签署方式

节点加 `signMode`，只对「部门负责人」这一种来源生效：

| 值 | 名称 | 规则 |
|---|---|---|
| `single` | 单人（默认） | 一个负责人签完即过，与以前一致 |
| `all` | 会签 | 本部门**正职 + 副职 + 代理全部同意**才推进，任一人驳回即整单驳回 |
| `any` | 或签 | 任一负责人同意即通过（抢办），其余人标「已跳过」 |

其他来源（项目经理 / 指定岗位 / 直属上级）天然只有一个对象，配了会签也等价于单人 ——
流程配置页会把这类节点的下拉禁用，避免配出一个"永远不会生效"的设置。

### 10.2 会签名单怎么来

`_resolveAssignees` 解析的是**本部门所有在期负责人**，不是一个人：

1. 取 `leadersOf(orgId)` 里 `active` 的人（正职 / 副职 / 代理都算）；
2. **排除申请人本人** —— 自己不能给自己签；
3. 排除后一个不剩（部门只有申请人一个负责人），沿组织链向上找，而不是让单据停在"自己审自己"。

这和第 52 批的「副职不参与审批」不矛盾：**单签节点**轮不到副职（副职是分工不是授权），
**会签节点**副职必须参与（既然设了会签，就是要两方都确认）。

### 10.3 一次同意只签掉一个人

`approvalAction` 的会签分支：

- 找到"我这一份"→ 标记同意；名单里还有人待签 → 单据仍停在当前节点，
  `currentNode` 变成「部门负责人审批（会签 1/2）」；
- 全部签完 → 节点通过，推进下一级，节点意见写「会签：2 人全部同意」；
- 任一人驳回 → 整单驳回，其余人标 **`已跳过`**（不是直接删掉 —— 要能看见"谁没签上"）；
- 加签：往名单里加一个人（不是插一级新节点）；转办：把"我这一份"换人。

原型只有角色没有真实登录身份，角色反推出的人常常不在名单里 ——
这时按第一份待处理**代签**，并在意见里写「（代 XXX 处理）」。
既不让单据卡死，也不假装是本人签的。真实系统应该直接拒绝并提示"你不是本节点审批人"。

### 10.4 页面

- **审批详情**：会签节点带 `会签` 标签 + 「已签 1/2」，下面逐人列出姓名、职责、状态、时间、意见
  （合成一行的话看不出卡在谁那儿）；处理区提示「还需 贺丽华 同意。全部签完才会推进下一节点；其中任一人驳回，整单驳回。」
- **流程配置**：节点行加「签署方式」下拉，非部门负责人来源自动禁用。

### 10.5 演示数据

- 流程配置里**采购申请的部门负责人默认会签**（金额敏感，正副职都要确认）
- O-P01 项目部加副职（贺丽华，分管工程与采购）
- 一张 10/19 提交的采购单：正职徐悦已签、副职贺丽华待签，停在「会签 1/2」

### 10.6 顺带补上的契约空缺

契约里**一直只有「发起 / 撤回」，没有审批动作接口** —— 审批是在页面里点完就完了，后端拿不到规格。
会签必须有它才能落地，本批补上 `POST /oa/requests/{approvalId}/action`（同意 / 驳回）。

## 十一、第 54 批 · 计划模板（2026-11-03）

前面几轮讨论定下来的形态先做成了可交互 demo（五套模板、三段式、目标值联动、审核直改留痕），
确认之后再落代码。本批把**模板本身**落地。

### 11.1 为什么模板必须是数据

第 51 批的计划是「部门自己写任务」，模板只给个起步骨架。实际业务里考核项是公司统一规定的：
项目经理一套、四个班组各一套，条目、权重、评价标准都不该由填报人改。
写死在代码里的后果是**调一次权重就要发一次版**，而权重是每月都可能微调的。

所以做成独立数据表，配一个维护页 `/f/plan-templates`。

### 11.2 权重是强制的，而且是三层校验

| 层级 | 规则 | 不通过 |
|---|---|---|
| 两段之间 | 量化段 + 重点段 = 100% | 422/42214 |
| 段内 | 条目权重合计 = 该段权重 | 422/42214 |
| 监控段 | 权重必须全部为 0 | 422/42214 |

第二条最容易漏。配成 10/10/10/10/10（合计 50）而段权重 35%，用这套模板提报出来的
每一份计划总分基数都是错的，而且是**隐性**的 —— 页面不报错，只是分数偏了。
所以保存时整单拒绝，不做部分保存。

### 11.3 六套模板

| 模板 | 适用 | 量化 | 监控 | 重点 |
|---|---|---|---|---|
| 项目经理 | 项目部 | 5 条 35% | 5 条 | 5 条 65% |
| 客服组 | 班组 T1 | 3 条 25% | 5 条 | 8 条 75% |
| 工程组 | 班组 T2 | 2 条 20% | **6 条** | 8 条 80% |
| 秩序组 | 班组 T3 | 2 条 20% | 5 条 | 8 条 80% |
| 环境组 | 班组 T4 | 2 条 20% | 5 条 | 8 条 80% |
| 职能通用 | 总部部门（兜底） | 2 条 30% | 4 条 | 7 条 70% |

工程组多一条「年度维保计划完成率」是源表就这么写的，不是笔误。
职能兜底是后加的 —— 源表只有五套，但总部部门也要提计划，不给兜底就提不出来。

### 11.4 自动匹配 + 可改

`planTplForOrg(orgId)`：项目部 → 项目经理模板；班组按 `-T1~-T4` 对应；总部部门 → 职能兜底。
匹配不到返回 `null` 让页面提示去配，**不静默给一个空模板** —— 那会提报出一张没有考核项的计划。

运营管理部在提报页可以改选模板（自动匹配是默认值不是锁定值），这是用户确认的口径。

### 11.5 改模板不影响已提报的计划

提报时把模板条目**整份拷贝**到计划里做快照，之后模板怎么改都不回写。
否则 7 月调一次权重，3 月已经归档的分数会跟着变 —— 那种「历史数据会自己动」的系统没人敢用。

比「模板版本号 + 按版本引用」简单得多，效果一样，代价只是多存一份条目。

「绩效考核降一档」这种非数值规则怎么表达 —— 它根本不是扣分。

## 十二、第 55 批 · 计划接入模板（2026-11-03）

第 54 批把模板做出来了，但计划还在用「部门自己写任务」。本批把两边接上。

### 12.1 数据结构从「任务」变成「考核项」

一份计划 = 模板铺开的条目快照 + 填报数据。条目带 `section`（量化/监控/重点），
三段的填报方式完全不同：

| 段 | 填什么 | 自评怎么来 |
|---|---|---|
| 量化 | 目标值（提报）、实际值（执行） | 公式算，夹 1–5 |
| 监控 | 完成情况 + 扣分（执行） | 没有分，只有扣分 |
| 重点 | 计划内容 + 完成标准（提报）、实际完成 + 1–5 分（执行） | 人工填 |

字段名仍是 `tasks`（页面和契约都在用），但语义已经是考核项 —— 改名成本高、
收益低，先留着，文档里写清楚。

### 12.2 算分只有一处实现

`planTargetOf` / `planSelfScoreOf` / `planItemCalc` / `planTotalsOf` 四个函数，
页面只调不重算。两处实现的分数迟早对不上，而对不上时没人能判断哪边是对的。

- 否决 = 目标 × 95%、挑战 = 目标 × 105%，**逆向指标镜像**（成本类越低越好）；
- 自评 = 5 ×（实际 − 否决）/（挑战 − 否决），夹在 **1–5**；
- 夹下限是刻意的：公式在否决点算 0，而规则说"低于否决记 1 分"，
  不夹会出现「完成 96 元比 95 元得分更低」的反转；
- 加权 = 分 × 权重/100（权重合计 100，所以自评合计满分就是 5 分）；
- **月度总得分 = 自评合计 × 20% + 复评合计 × 80%**。

目标为 0 的指标（工程组"有偿维修收入 0 元"）公式失效，退回人工打分 ——
这类零容忍/零收入指标本来就不适用比例法。

### 12.3 状态机与「复评必须先提交」

`草稿 → 审批中 → 已批准 → 执行中 → 待复评 → 已结案`，新增 **待复评**。

复评不看权限够不够，先看状态：不是「待复评」就报错，提示"要等填报人提交完成情况之后"。
口头约定会被人情绕过，状态卡不住就是没卡。

### 12.4 提报表单

- 三段各自一张表，列按类型给（量化要目标值、监控要标准文字、重点要计划内容和完成标准）；
- **权重全部只读**，来自模板；条目不能增删 —— 能改条目等于把考核标准交给被考核的人；
- 换部门自动换模板（不同岗位的考核项完全不同，留着旧条目等于拿错尺子）；
- 目标值一改，否决值和挑战值旁边实时重算。

### 12.5 详情页

三段 + 三张合计卡（自评 / 复评 / 总分）。执行阶段可以直接在表里改实际值，
量化项的自评立刻跟着变；复评阶段逐项打 1–5 分，监控项填扣分。

复评弹层的默认值 = 自评分，运营管理部只需要改不同意的项 —— 逐项从零填是负担。

### 12.6 验证

  被改的格子黄底高亮；
- 目标值一改，旁边的否决值 / 挑战值立刻按新目标重算；
- 点「通过并下发」前会再校验一次权重闭合 —— 直改允许中间状态，下发不允许。

改动逐条记进 `reviseLog`（字段 / 改前 / 改后 / 操作人 / 时间），
同时写一条「审核修改」进操作轨迹。半年后有人问"这个月的目标为什么和申报的不一样"，
能翻到是谁在哪天改的。

### 13.7 补丁：量化段漏了「复评加权」（2026-11-04）

**发现的缺陷。** 用户对着已结案计划的截图指出：量化指标段只有「自评 / 加权 / 复评」，
缺「复评加权」。核对后确认 —— 三段表格里**只有量化段漏了这一列**：

| 段 | 原有列 | 问题 |
|---|---|---|
| 一、量化 | …自评 / 加权 / 复评 | **缺复评加权** |
| 二、监控 | …自评扣分 / 复评扣分 | 正常（扣分本身即加权，两列对称） |
| 三、重点 | …自评 / 加权 / 复评 / 复评加权 | 正常 |

**但计算一直是对的。** `planItemCalc`（`api.js:12761`）对所有非监控项都算
`reviewWeighted = review × weight / 100`，`planTotalsOf` 也累加了，
归档时 `closeDeptPlan` 给所有非监控项写 `reviewScore`。所以合计卡的数字没问题，
**只是明细里看不到这一项是怎么来的** —— 评审会上被问「复评合计 4.19 是怎么加的」，
只能拿计算器逐项加。

**根因是三段表格各自手写列定义。** 第 55 批重写详情页时，三段是三个独立的 `<el-table>`，
列各写各的。漏一列不会编译报错、不会 e2e 失败，只有人眼看得见。

**这一轮改了三件事：**

1. **补列**：量化段在「复评」后加「复评加权」，调用现成的 `reviewWeighted(row)`；
2. **统一列名**：两处裸的 `label="加权"` 改成「自评加权」。

   这条不只是好看。三段里都叫"加权"，但量化/重点是「分 × 权重」，监控段是「扣分本身」——
   三个"加权"摆在一起，人会以为算法一样。现在四列分别是
   **自评加权 / 复评加权 / 自评扣分 / 复评扣分**，望名知义。

3. **加静态自检**（`scripts/check.mjs` 第 ⑥ 条）：按三段标题切区间，
   断言量化与重点段都含「自评加权 + 复评加权」、监控段含「自评扣分 + 复评扣分」，
   且不允许出现裸的 `label="加权"`。

   自检**验证过能抓到**：把三处 `label="复评加权"` 临时改名后跑 check，报
   `量化段缺「复评加权」、重点段缺「复评加权」`；恢复后通过。一条永远绿的检查等于没加。

**顺带修掉一个同类问题：重点工作「有分没依据」。**

截图里第三段（重点工作）的「计划 / 完成标准」和「实际完成」两列全是 `—`，
但「自评」列有分数。原因是种子对 `section === 'k'` 只填了 `selfScore`，
`content` 和 `actual` 都留空 —— 一份**已结案**的计划，重点工作只显示名称和分数，
看不到做了什么。这和"量化段缺复评加权"是同一类：**分数在，依据不在**。

种子补了 `PLAN_K_PLAN` / `PLAN_K_DONE` 两个文案池（按项名生成，7 条轮换），
契约样例 `gen-dept-plans-fixture.py` 同步补上（审批中只填计划内容，执行后才填实际完成）。

## 十四、员工档案 · 紧急联系人（2026-11-04）

### 14.1 为什么加

员工档案原来只有本人手机。真出状况（工伤、送医、失联）时，HR 手上只有一个打不通的号码。
这一栏存在的唯一目的就是应急，所以设计上按"要么完整、要么明说没有"来做，不留半截数据。

### 14.2 三个字段，比业主多一个「关系」

业主档案里已有 `emergencyContact` / `emergencyPhone` 两个字段，员工这边沿用同名，
另加 `emergencyRelation`：

| 字段 | 说明 |
|---|---|
| `emergencyContact` | 姓名，≤12 字 |
| `emergencyRelation` | 与本人关系，**枚举**：配偶 / 父亲 / 母亲 / 子女 / 兄弟姐妹 / 其他 |
| `emergencyPhone` | 11 位手机号，**列表恒为掩码** |

多一个关系，是因为场景不同：社区服务只需要一个能接电话的人；
HR 需要知道**先找谁**——配偶和父亲在授权签字、陪护安排上不是一回事。

### 14.3 数据：独立随机流 + 顺手修了姓名性别矛盾

种子生成时**另开一个 `random.Random(SEED+91)`**。如果在主序列里多调几次 `person_name()`，
后面所有实体的随机数整体后移，几千行 mock 全部变掉（第 51 批补 `leaderEmpId` 时踩过）。
验证方式：重跑 seed 后 `diff -rq`，只应 `employees.json` 变化。

生成时按关系挑性别合适的名字（配偶取异性、父亲取男性名）。过程中发现**原有数据本身就有矛盾**：
`gender` 是独立随机抽的，于是出现「雷志强·女」「韩娟·男」。不修的话，新字段会把矛盾放大成
"女员工的父亲叫女性名"这种一眼可见的问题。所以按名字反推修正了 `gender` 一列（只改这一列，不碰随机流）。

### 14.4 成对校验：不完整的值不落库

`updateEmployeeProfile` 里加三条（422）：

| 情况 | 后果 |
|---|---|
| 有电话没姓名 | 打过去不知道该找谁 |
| 有姓名没电话 | 等于没留联系方式 |
| 有姓名或电话、关系为空 | 不知道先找谁 |

三项全空是**合法**的（新人还没录），页面上用一块明确的空态说明"未填 + 为什么该补"，而不是一个破折号。

### 14.5 权限与脱敏

- 编辑入口挂 `c.employees.edit`（人事专员 / 人事助理 / 总经理有；只读观察员按钮置灰）；
- `emergencyPhone` 进 `redactList`，与手机号同口径；揭示走 `revealSensitive` 并写访问日志
  （`SENSITIVE_TABLE` 早就含「员工」，所以回源链路是现成的）。

### 14.6 顺带修掉两个真缺陷

**① 编辑框带出的是掩码。**
打开编辑抽屉时 `cur.emergencyPhone` 是 `188****7048`（列表行已脱敏）。用户不动它直接保存，
就会把这串星号写进数据——紧急联系电话从此永久打不通。现在打开时先 `revealSensitive` 取明文
（这一次揭示顺手留痕，正是想要的），无明文权限则留空，由成对校验逼着重填。

**② `SensitiveText` 切换人员不重置揭示状态。**（`components/SensitiveText.vue`）
组件实例会被 diff 复用，`shown` 是内部 ref。点开 A 的明文再切到 B，B 的位置上仍显示明文，
而且显示的是 **A 的号码** —— 既是数据错位，又等于绕过了 B 那一次的揭示留痕。
现在 `watch` 了 `[value, entityId]`，换了就收起。这条影响所有用该组件的页面（业主 / 租户 / 员工）。

## 十五、办公资产（2026-11-04 · 第 58/59 批）

### 15.1 先说清楚它不是什么

系统里原来就有「设备台账」（D 域，80 台）。**这次做的不是它的扩展**：

| | 设备台账 | 办公资产（本批） |
|---|---|---|
| 管什么 | 门禁 / 摄像头 / 车闸 / 电梯（装在公共区域） | 电脑 / 桌椅 / 打印机 / 工具（可被个人领用） |
| 看什么 | 在不在线、告警、维保到期 | 值多少钱、在哪个部门 |
| 谁用 | 工程 + 物业 | 行政 / 人事 |
| 状态 | 在线 / 离线 / 告警 / 故障 | 闲置 / 在用 / 报废（**描述性**） |

唯一可能的交集是电梯（既是设备也是资产），靠 `devices.assetId` 单向关联，
**不合并两张表** —— 合并的话「在线状态」和「原值折旧」会互相稀释。

### 15.2 范围：只做「上架」

用户明确收窄过，这一批**不做**领用 / 归还 / 送修 / 报废审批、盘点、折旧与净值。

留下的流程只有一条：

```
建分类 → 新增资产 → 生成编号与 token → 打印标签 → 贴码上架（闲置）
```

这条减法带来一个必须写进页面的后果：**状态是描述性字段**。
没有单据推动它流转，就没人负责让它准确。所以列表和表单上都写了
「不能拿状态推断资产在哪，要看使用人」—— 不写的话，半年后一定有人拿它做统计。

### 15.3 分类：两级，改名不回写

- **最多两级**。三级分类在录入时选不出来，实际业务也用不到；
- **改名不回写资产**：资产上存 `catName` / `catPath` 快照，所以「电脑」改叫「笔记本电脑」后，
  历史资产仍显示当时的名字；
- **停用不删**：停用后不能新增，已有资产保留；
- **有子级或有资产不给删**（409/40927），并说清是几件。

### 15.4 编号与 token：两个都要，用途不同

| | 格式 | 能不能改 | 干什么用 |
|---|---|---|---|
| `assetNo` | `ZC20260001`（年 + 4 位流水） | **永不可改** | 印在标签上、报修时报号 |
| `assetCode` | `BG-PC-001`（可自定义） | 可改 | 内部约定的编码习惯 |
| `qrToken` | 16 位随机串 | 换码才变 | 扫码取数 |

`assetNo` 不可改的原因是物理的：标签已经贴在实物上，改号等于让日志、报修记录和纸标签全部对不上。
`qrToken` 与编号无关，因为编号能顺序推，token 不能 —— 否则改一个字符就能枚举出全公司的资产。

### 15.5 扫码页：免登录，靠字段白名单兜底

用户确认：**不需要登录**，做一个独立 H5 页面。

要求登录等于把功能做废（扫码的人可能是访客、供应商，手机上根本没装这个系统）。
所以边界不靠登录态，靠**公开视图只返回 7 个字段**：

| 返回 | 不返回 |
|---|---|
| 名称、编号、分类、状态、**使用部门**、存放位置、保修到期 | 使用人姓名、原值、供应商、发票、序列号、备注、变更记录 |

判断依据是「这个字段暴露出去会不会被利用」：序列号能被拿去伪造保修，原值泄露采购价，
供应商暴露商务关系。

**使用人姓名**这一条单独说：显示它能解决"捡到电脑扫码找失主"，但你确认了只给使用部门 ——
所以公开页看不到人，只能看到组。

报废资产的码**仍然可查**（顶部加灰条），不做 404：历史要能追溯。

### 15.6 踩到的一个真坑：viewport 写死了 1280

`index.html` 原来是 `<meta name="viewport" content="width=1280">` —— 那是给 PC 后台的
（手机打开后台时整体缩放，看着"完整"但其实没法操作）。

扫码页放在同一个工程里，就继承了这个设置：**手机上按 1280 布局渲染，字小到看不清**。

试过在页面里动态改 viewport meta，**无效**：改 meta 不会触发布局重算（`innerWidth` 仍是 1280）。
最后改成两件事：

1. `index.html` 的 viewport 改成 `width=device-width`（PC 后台靠自己的 `min-width: 1280` 撑住，不受影响）；
2. 扫码页挂载时把 `body.style.minWidth` 置 0，离开还原 —— `body` 上那条 1280 的最小宽会把整页撑开。

改完实测：手机 414 宽下 `innerWidth=414`、卡片 382（两侧各 16 padding）、无横向滚动；
PC 1680 宽下后台布局不变。

**这也是"扫码页应当独立部署"的技术理由**：一份 HTML 服务两种终端，总要有一处妥协。

## 十六、设备图片与权重下放（2026-11-05 · 第 60 批）

这一批三件事：**资产能传图**、**权重从模板搬到计划**、**权重合计必须正好 100% 且列表可见**。
前两件是需求，第三件是第二件的必然结果 —— 权重一旦由人填，就必须有一道校验和一眼可见的位置。

### 16.1 设备图片：作为附件存在资产上

图片**不单独开表**，存在资产的 `files` 里（`kind: 'image'`）。理由很直白：图片脱离资产没有意义，
单独建一张 `asset_photos` 只会多一个"孤儿图"的来源。

| | 口径 | 为什么 |
|---|---|---|
| 张数 | 最多 **6 张** | 详情页一屏能看完；再多就该走档案系统 |
| 单张 | ≤ **5MB** | 手机直出照片常 3–8MB，再大浏览器预览明显卡 |
| 类型 | jpeg / png / webp / gif | 附件区不承担"扫描件、合同 PDF"，那是合同模块的事 |

三条限制在**页面和数据层各拦一次**：页面拦是为了"选完立刻知道"，数据层拦是因为**接口不能只信前端**。
数字只写两处（`ASSET_FILE_MAX` / `ASSET_FILE_MAX_SIZE`），页面从 `@/api` 取，不各写一遍。

**图片不进扫码页。** 扫码页是免登录的，而照片是现场随手拍的 —— 背景里常有工位、白板、同事。
"设备长什么样"和"这间办公室长什么样"是两件事，前者不需要用后者来换。

变更记录里只写**张数 + 文件名**（`空 → 1 张：office.png`）：把 base64 写进日志，变更记录几秒钟就成一屏乱码。

比对用 `fileId + 名称 + url` 三者：只比 `fileId` 的话，"同一个 id 换了内容"会被判定为没改动——
契约测试就是拿这个漏洞抓到的（把 PNG 换成 PDF 竟然通过了）。

原型里存的是 data URL（没上传服务，刷新即还原），**真实实现要存对象存储的 URL**，
不要把 base64 塞进数据库行里 —— 契约里写明了。

### 16.2 权重下放：模板只定「考什么」

原来权重在模板里（两段 `wq/wk` + 段内条目权重），第 60 批整段搬到计划上：

| | 改前（54–59 批） | 改后（60 批） |
|---|---|---|
| 谁定权重 | 运营管理部改模板 | **提报人新建计划时逐项填** |
| 模板字段 | `wq` / `wk` / 条目 `weight` | 全部删除 |
| 约束 | 段内合计 = 段权重，且两段合计 100（两级） | **各项合计正好 100%（一级）** |
| 审核阶段 | 改名称 / 目标值 / 评价标准 | 以上 + **改权重** |

理由不是"简化"，是业务事实：**同一套考核项，不同项目当月的重点不一样**。
写死在模板里只有两条路：要么所有人按同一比例（等于没有重点），要么运营管理部每个月改一遍模板
（还会把历史版本的分数搅乱）。让提报人填，审核时再纠偏，才是实际发生的事。

代价是提报人要填十几个数字，所以做了两件降低摩擦的事：

1. **打开就预填好 100%**：按条目数平均分（`planEvenWeights`），
   人改的是"谁该多一点"，而不是"怎么凑够 100"；
2. **一个「平均分配」按钮**：改乱了从头分，比一项项凑快。

### 16.2.1 权重只能按 5% 调（用户补充的口径）

"平均分"和"5 的倍数"是两条会打架的规则：9 个条目平均分是 11.11%，而 11.11 本身就不合规。
所以平均分配改成**以 5% 为单位发份**：100/5 = 20 份，先给每项 `floor(20/n)` 份，余下的份数给前面几项。

| 计分项数 | 预填结果 | 说明 |
|---|---|---|
| 10（项目经理模板） | 10 × 10 | 20 份 ÷ 10，正好整除 |
| 9（职能兜底） | 15、15、10 × 7 | 每项 2 份，多出的 2 份给前两项 |
| 16（工程组） | 10 × 4、5 × 12 | 每项 1 份，多出的 4 份给前四项 |

不这么做的话，表单**一打开就是红的**（预填 11% 不合规），比不预填更让人困惑。

三处落点，缺一处就有死角：

| 落点 | 做法 | 漏了会怎样 |
|---|---|---|
| 常量 | `PLAN_WEIGHT_STEP = 5`，只有这一处 | 各处硬编码，改步长要翻全站 |
| 输入框 | `:step="WEIGHT_STEP" step-strictly` | 手输 12 能填进去，提交时被拦 —— 用户不知道为什么 |
| 校验 | `planWeightCheck` 逐项判 5 的倍数 | 接口直调能塞进 12%，算分基数就飘了 |

`step-strictly` 的实际效果实测过：输入 12 回车，值自动归到 **10**（就近取整），
合计随之变 95%，提示"还差 5%"。加减按钮也是一档 5。

还有一个连带的边界：每项至少 5%，所以**计分项最多 20 条**。超过时"平均分配"必然有人拿 0，
而 0 权重的考核项等于没考 —— 校验会直接说明"最多 20 条，先在模板里合并或删减"。
现有模板最多 16 条（工程组），够用；这条是给以后加条目的人留的。

模板里保留一句说明（`模板不设权重`），并删掉了权重列和权重输入框 ——
`check` 新增第 ⑦ 条静态规则盯着这件事：模板页再出现 `v-model="row.weight"`、或 T 域又长出
`weight` / `wq` / `wk`，直接报错。防的是"改回来一半"：页面照样能开、保存照样成功，但两套权重同时存在。

### 16.3 权重校验：两条规则，且要按顺序报

```
① 每一项必须是 5 的倍数        （只能按 5% 调）
② 各项权重合计 = 100%          （监控项恒 0，不占权重）
```

- 非 5 的倍数：`「物业费清欠」12% 不是 5 的倍数，权重只能按 5% 调`
- **小于**：`各项权重合计 90%，还差 10% 才到 100%`
- **大于**：`各项权重合计 110%，超出 10%（必须正好 100%）`

**步长要先于合计报**：52 + 43 + 5 = 100，合计完全正确，只有逐项看才发现 52 这种填法不该存在。
如果先报合计，人会去调数字；真正该做的是把 12 改成 10 或 15 —— 顺序反了要改两轮。

只说"必须是 100%"，填了十几项的人得自己一项项加。所以要给出**差多少、哪个方向**。

卡点分三层，缺一不可：

| 时点 | 卡不卡 | 原因 |
|---|---|---|
| 保存草稿 | **不卡** | 写到一半就存是正常动作 |
| 提交审核 | 卡 | 不闭合的计划没法算分 |
| 审核「通过并下发」 | 卡 | 运营管理部改完权重也得闭合才能进执行 |

第三层容易漏：审核阶段允许"改一半先存"（改权重往往要动好几项），但下发是终态，
带着 95% 进执行，月底算出来的分就是错的，而且没人会发现。

**列表上直接给一列**：`100% / 正好 100%`（绿）或 `95% / 还差 5%`（橙）。
一个部门一个月一份计划，20 份列表里挑出哪份没闭合，不该靠点进去看。

### 16.4 顺带修掉的两个真问题

**① 提报页换模板不生效。** `planTplBundle(orgId, planMonth)` 只按组织自动匹配，
运营管理部在下拉里换了模板，铺开的还是原模板的条目 —— 下拉框等于摆设。
加了第三个参数 `forceTplId`，换了就按换的铺。

**② 集团总经理提报总部计划，第一节点"待指派"。** 计划审批第一节点是「项目经理审批」，
总部部门沿组织树往上找不到项目，回落到集团负责人 —— 恰好就是提报人自己。
`_skipSelf` 跳不动（上游没人了），返回空串，节点挂成"待指派"，**这张单永远没人能签**。

改法：走到顶都没找到别人时打上 `selfTop`，`createOaRequest` 把这一级记为
「自动通过 · 申请人即最高审批人」，`currentNode` 落到下一个真正待办的节点。
现在提报后提示的是「运营管理部复核（史秀英）」，而不是「项目经理审批（待指派）」。

## 十七、开票设置（2026-11-06 · 第 61 批）

一个页面三件事：**抬头档案**、**费用项目**、**票据模板**。它们的共同点是"开票时要反复填、
但又跟具体某一张票无关"——收到一个地方，才不用每次手打。

### 17.1 为什么不是「开票时顺手填」

开一次票要填抬头、税号、开户行、地址、项目名称。前台一天开十几张，
其中八成是重复的；剩下两成是不重复的（外来摊贩、场地租用）。

所以拆成两层：**常用的存成档案，不常用的当场手填**。
两层都要有，只做档案会让"临时收个摊位费"卡住，只做手填会让前台每天重打十遍税号。

| | 档案（开票信息） | 临时手填 |
|---|---|---|
| 场景 | 业主、企业租户、月结单位 | 一次性缴费、临时摊位 |
| 是否落库 | 是 | 否（开完就没了） |
| 入口 | 开票设置 → 新增 | 开票弹窗里直接改 |

### 17.2 开票信息：带入 ≠ 建档

这是本批最容易做错的一处。**"从业主带入"只预填表单，不自动建档**。

理由不是省事，是数据质量：682 个业主如果都自动建档，档案列表立刻被淹没，
真正常用的那十几条要翻好几页。带入的价值是"少打一遍字"，不是"替你决定存不存"。

| 来源 | 带什么 | 不带什么 |
|---|---|---|
| 业主 | 姓名、手机 | 税号（个人开票凭姓名即可，身份证号不当税号用） |
| 个人租户 | 姓名、手机 | 税号 |
| **企业租户** | 名称、**统一社会信用代码**、注册地址、代理人 | — |

企业租户那行是重点：这些字段租户档案里**本来就有**（承租时录过），
让人再抄一遍是企业信息复用里最没道理的重复劳动。

**档案存的是抬头快照。** 业主后来改名，不回写已存的档案 ——
票据一旦开出，抬头就不能变（税务要求）；改了档案，三个月后查"这张票当时开给谁"就说不清了。
要跟着改，页面上点「重新带入」，显式覆盖并留痕（会记下改前的抬头）。

默认抬头**全库唯一**：收银台「默认开给房主」要的是确定的一条，不能并列。
停用一条原本是默认的档案时，默认位会被清空 —— 而不是留一条"停用的默认"。

### 17.3 费用项目：五项，但开票不受它限制

内置：摆摊费 6% / 场地租用 9% / 赔偿款 **0%** / 押金 **0%** / 其他 6%。

两个 0% 不是漏填，是两个真实的税务口径：

- **押金**是代收款项，退还时要冲回。按 6% 确认收入，等于对一笔最终要退的钱交了税。
- **赔偿款**（损坏赔偿、违约金）不属于增值税应税行为。

这两项开出来的多是**收据**而不是发票 —— 页面上专门写了一句提醒，
防的就是后来人"看着不整齐，把 0 改成 6%"。押金本身还在页面下方单独解释了
「代收不确认收入」。

**开票时项目名可以手打**（`allow-create`）。字典解决的是"常用的少打几遍"，
不是"只能选这些"——控制不了的临时收费不该被一张表卡住。
反过来，字典项停用不删除：历史票据上写的是名称，删了就说不清"当时这个项目还在不在"。

### 17.4 票据模板：1 套 + 参数可调

**只有一套。** 多套的代价是每张票都要先选版式，而现在只有一种纸（241×140 连续纸）。
真出现第二种纸（比如 A5 横向）再加，否则就是给自己找一步操作。

模板参数分四组：

| 组 | 参数 | 说明 |
|---|---|---|
| 纸张 | 宽 × 高（mm），含预设 | 241×140 三联 / 241×93 单联 / A5 横向 / A4 |
| 页边距 | 上下左右（mm） | 内容区不足会直接拦（左右至少留 40mm） |
| **套打偏移** | X / Y（mm，可负） | **比字号重要**：针打纸上已印好框线，歪 2mm 就压线 |
| 排版 | 字体（宋体/仿宋/黑体/楷体）、字号 6–16pt、行高 | 针打自带字库就这几套，给多了也打不出来 |

再加联数（1–4）、联次名、标题、落款、底部说明、二维码开关。

**单位一律 mm / pt，不用 px。** 针打按物理尺寸走纸，用 px 描述会随浏览器缩放跑偏。
预览的做法是：模板值直接写成 `mm`，容器用 `zoom` 缩小显示，打印时 `zoom` 归 1 ——
预览和打印共用一套数值，不会出现"预览好好的、打出来偏了"。

**打印方案的真实边界**：浏览器 `window.print()` + 动态注入 `@page { size: 241mm 140mm }`
能把版面和纸张尺寸做对，但**做不到 0.1mm 级的连续纸对位**。真正的套打要靠本地打印控件
（如 C-Lodop）或后端直接发 ESC/P 指令。原型做到了"版式可见、参数可调、能试打"，
控件选型留到实施阶段 —— 这一点写在页面提示里，不含糊过去。

### 17.5 接进开票页

`issueInvoice` 加了 `profileId` / `itemName` 两个可选参数：

- 单张开票时，按**这笔流水所属房屋**取抬头候选（`invoiceProfilesOfHouse`），房主在前、在住租户在后，默认选第一条 —— 这就是「默认开给房主，有租户时可切」；
- 批量开票时不给选（多房合并没法共用一条档案），按各自房主兜底；
- 项目名称从字典选，也可以直接打字；
- 票据上记 `buyerTitle` / `buyerTaxNo` / `itemName`，台账新增「购买方 / 项目」列；
- 税率按费用项目的默认值算，不再写死 6%；**收据一律 0**（收据不产生税额）。

## 十八、收银台真实收款 + 组合支付（2026-11-06 · 第 62 批）

这一批先修一个**真问题**，再加一个新能力。

### 18.1 修的是「假销账」

之前收银台的「确认收款」只做了一件事：把账单行的 `status` 改成已缴、`unpaid` 归零。
**一条 `payment` 都没写**。

后果不是"少了个字段"，是整条链路断了：

| 下游 | 之前 | 现在 |
|---|---|---|
| 收费日结 | 收的钱不进日结 | 按方式进日结，现金要实点 |
| 开票池 | 待开票里没有这笔 | 收款后立刻可开票 |
| 缴费流水 | 查不到 | 每条账单一条流水 + 批次号 |
| 预存抵扣 | 余额不动 | 按房扣减并记预存流水 |

**写流水 → 销账 → 回写账单**，三步必须一起做。少一步账就不平，而且是"界面上收款成功了、
账上什么都没发生"这种最难查的不平。

### 18.2 组合支付：三条规则

| 规则 | 为什么 |
|---|---|
| 最多 **3 种**方式 | 再多，对账时分不清是系统错还是人填错 |
| 同一种方式只能**一行** | 两行现金合成一行，否则日结会出现两条「现金」 |
| 合计**必须等于实收**，差一分不让提交 | 收银台宁可多问一句，也不能让账自己猜 |

**预存抵扣可以与其他方式组合**，固定排第一行：先抵余额，剩下的再刷微信/现金。
选中预存时自动填「余额与剩余额度里较小的那个」，同时把差额补回另一行 ——
不然用户还得自己算「总价减余额是多少」。

**挂账不进组合**：挂账是「没收到钱」，塞进金额行会让实收虚高。

交互上做了两处减摩擦：

- 默认**一行、金额自动等于实收** —— 八成收款是单方式全额，不该让人先填一遍；
- 点「再加一种方式」时，新行**从金额最大的一行分一半**过来，而不是给 0。
  加完立刻报红「金额必须大于 0」，是最容易让人放弃组合支付的地方。

### 18.3 一笔收款 = 多条流水（按账单拆）

`payment` 是「一条流水对一张账单」（开票、催缴、账单详情都按这个口径查），
所以一次收 8 张账单会写 **8 条流水**，共用 `batchNo`。

组合支付要按**各账单应收比例**把 splits 拆开：

```
3 张账单 100 / 200 / 300，实收 600，方式：现金 200 + 微信 400
→ 账单 1：现金 33.33 + 微信 66.67
→ 账单 2：现金 66.67 + 微信 133.33
→ 账单 3：现金 100   + 微信 200
```

每条流水的 splits 合计**必须等于它自己的金额**（舍入差补到最大那一笔上）。
不这么做，开票金额会飘，日结现金会少。

`method` 保留为**金额最大的一笔** —— 不是设计，是兼容：老报表、导出、月结都还在读它。
新增的 `splits` 才是真相，`_splitsOf()` 是**唯一判断分支**（老数据没有 splits 就用 method 兜底）。

### 18.4 日结与退款都按 splits 走

**日结**：`dailyCloseRows` 先把流水按方式展开再加总。一笔「现金 200 + 微信 122」
如果整笔记在金额最大的方式下，现金实点会少 200，而对账时又查不出差在哪。

**退款**：按原收款各方式的比例原路退。整笔按最大方式退，现金那部分会被记成微信退款，
日结的现金实点照样对不上。

### 18.5 一个边界：车位费没有房屋

预存账户挂在**房屋**上，而车位管理费的账单没有 `houseId`（挂在 `parkId` 上）。
所以「只有车位费的业主」选预存抵扣时余额是 0。

这不是 bug，但**必须给提示**：不给的话，用户看到「选了预存抵扣但金额填不进去」，
只会觉得坏了。现在的提示是「这些账单没有可用的预存账户（车位费不挂房屋，用不了房屋预存）」。

### 18.6 踩到的两个坑（都跟"看不见"有关）

**① 流水页查不到刚收的钱，不一定是坏了。**
流水页按角色数据范围过滤（收银员 = 本项目），而收银台可以收任意项目的业主。
本次这笔落在范围外，页面就是看不到 —— 这是设计如此。
判断"流水有没有落库"要看**日结**（不按范围过滤），而不是流水列表。

**② e2e 不能用整页刷新换页。**
`page.goto('?t=xxx#/b/payments')` 会重新加载应用，**内存态全部还原**，
刚收的钱自然"消失"。同文档改 hash 才能看到本会话的写操作 —— 这一条踩了四轮才定位。

- 收银台 **42 条**：默认单方式金额=实收 / 加行自动分半 / 还差与超出提示 / 确认收款置灰 /
  同方式禁用 / 三行后按钮置灰 / 删除后金额复位 / 收款成功条（批次号 + 明细）/
  账单从待收移除 / 日结现金 +50、微信 +8 笔 / 预存抵扣 646 元参与组合 / 四条校验边界
- 相邻回归：开票设置 48 · 资产 60 · 会签 35
- 契约 **170/170**（新增 3 条：组合支付拆流水与销账、四条拦截规则、减免按比例分摊）

## 十九、临时收费（2026-11-06 · 第 63 批）

摆摊费、场地租用、赔偿款 —— 这类钱**跟业务没有关系**：没有应收、不挂房屋、不进账单。
用户的原话是「和业务没关联的费用收取」，所以它不是"另一种账单"，是**另一种东西**。

### 19.1 为什么不能塞进账单表

账单表的三根柱子是 `houseId + ownerId + period`。硬塞进去会有两个后果，都是隐性的：

| 后果 | 说明 |
|---|---|
| **收缴率被污染** | 收缴率 = 应收 vs 实收。临时收费**没有应收**这一步，进了分母只会让收缴率凭空下降，而且没人能解释为什么这个月掉了 2 个点 |
| **账单页长出怪行** | 没有房屋、没有业主的行会让催缴、账龄分桶、欠费排行全部要加豁免，豁免写漏一处就是线上事故 |

所以**独立成表**。跟账单的关系是零：没有 `billId`、不改 `bills`、不生成应收。

独立之后有个新问题：钱是实实在在进来的，**收入报表不能看不见它**。这就是本批的两条口径：

```
进收入：✅ 按 itemName 汇总进营业收入（companyRevenue + 营业报表单独一行）
进收缴率：❌ 有实收无应收，进制分母是错的
```

数据层把这个决定写成了字段：`countsInCollectionRate: false`、`countsInIncome: true`。
营业报表里那一行的 `rate` 给的是 `null` 而不是 `0` —— 没有应收就没有收缴率，给 0 或 100 都是错的。

### 19.2 付款方三选一

| 类型 | 要填什么 | 能带出什么 |
|---|---|---|
| 业主 | 选人 | 房屋 → 项目，手机号 |
| 租户 | 选人 | 房屋 → 项目，企业名、手机 |
| **外部** | 单位/个人名称 + 手机（选填） | 项目要手选 |

外面摆摊的摊贩**没有档案**，硬要建档会把业主表撑成"业主 + 摊贩 + 一次性的赔偿对象"，
以后所有按业主统计的口径都要加豁免。所以给了「外部」这个口子：一个名字一个电话就够。

**项目是必填的**，外部类型也不能省。理由很实际：收入要按项目统计，
没有项目的收入只能进「集团」，月底对账时查不出来源。业主/租户选了房屋会自动带出，外部手选。

### 19.3 建单 ≠ 收款

建单只登记，不动钱；要收钱在台账里点「收款」，**那时才写缴费流水**。

这个分法是刻意的：收了钱就有 `payment`，而 `payment` 会被日结、开票池、月结三处读到。
如果建单就写流水，「待收款」的单会在日结里凭空多出一笔钱。

收银台的入口是另一条路 —— 摆摊的人就站在窗口，不能让人"建完单再去台账点一次收款"。
所以 `TempChargeDialog` 把「建单 + 收款」做成一步：填完点「确认收款」，两件事在一个事务里完成。

**只有「待收款」能改、能作废。** 收了钱再改金额，等于让流水与单据对不上，
而流水已经进了日结 —— 要改只能作废重开。作废**必须写原因**，台账事后要能解释这张单为什么没收钱。

### 19.4 预存抵扣用不了

预存账户挂在**房屋**上（`prepayAccounts.houseId`），而临时收费的对象可以是外部摊贩 —— 没有房屋。

所以收银台的临时收费弹窗里，收款方式下拉**直接把「预存抵扣」去掉了**。
不给选比"选了之后金额填不进去"好：后者看着像坏了。

### 19.5 顺带修掉的一个全局问题

`tokens.css` 里 `.el-button--primary { background: 主色 }` 没有排除 `.is-plain`，
而 plain 变体的**文字色也是主色** —— 结果是蓝底蓝字，整颗按钮变成一块什么都没有的色块。

这个问题在 5 处按钮上存在（错误页「去配置权限」、巡检执行「提交」、派单「派单」、
权限日志「通过」、本批的「新建收费单」），一直没被发现是因为**它们都是次要按钮**，
页面不崩、流程能走，只是那颗按钮看起来"就是个蓝色的块"。

修法是给实心按钮加 `:not(.is-plain)`，再单独给 plain 定义浅底 + 主色字 + 浅描边。

## 二十、收款后同页开票 + 收据打印（2026-11-06 · 第 64 批）

原来的流程是：收款 → 记下流水号 → 切到「发票与收据」→ 搜索这笔 → 开票。
收银台前面还排着人，这四步里三步是在做无意义的跳转。

本批把它压成一步：**收款成功后在右栏就地展开「开具票据」**。

### 20.1 收据与发票是两个状态，不是一个

这是本批最重要的一个决定。

| | 收据 | 发票 |
|---|---|---|
| 字段 | `receiptStatus` / `receiptNo` | `invoiceStatus` / `invoiceNo` |
| 税 | 0（不是扣税凭证） | 按项目税率 |
| 谁要 | 现场缴费的人，当场拿走 | 需要入账抵扣的（企业租户、月结单位） |

**为什么不能合成一个 `invoiceStatus`**：只开收据的笔数不少（个人业主现场缴费大多只要一张收据），
合成一个状态之后，「待开票池」就查不出"哪些还差一张发票"——而补开发票正是财务月结前要做的事。

所以待开票池的口径是 `invoiceStatus !== '已开票'`：**只开了收据的流水仍然留在池子里**。
页面上也给了提示："已开收据"和"未开票"是两个独立的事。

一次点击可以两种都开：`issueInvoice(ids, ['收据', '电子发票'])`。分两次调用会出现
"收据开成功、发票失败"的半截状态，而用户只看到一句"开票失败"。

### 20.2 购买方三档，按这个顺序回落

```
手填抬头  >  抬头档案  >  房主姓名
```

- **默认开给房主**，有在住租户时下拉可切（`invoiceProfilesOfHouse` 返回的顺序就是优先级）；
- **多房合并不能共用一条档案**：一次收 8 笔跨 3 套房，用同一条抬头会开错票。所以多房时禁用选择，
  按各自房主开（收据本来就按房拆）；
- **外来缴费人没有档案也没有房主**（临时收费），这时只能手填 —— 这一档如果不做，
  摆摊费永远开不出票，而摆摊费恰恰是最常要收据的。

### 20.3 项目名取实际科目

原来写死 `itemName: '物业服务费'`。现在：

```
opts.itemName  ||  账单科目  ||  流水上的临时收费科目  ||  '物业服务费'
```

不这么改的话，两张票都是错的：临时收费开出来写"物业服务费"，
水费开票也写"物业服务费"。票据台账的「购买方 / 项目」列能直接看出这一笔是什么。

### 20.4 收据打印：套打是物理问题，不是 CSS 问题

收据必须能**针打套打**：纸上已经印好框线，机器只负责把字打进去。

三件事做对了才有意义：

| 项 | 做法 | 为什么 |
|---|---|---|
| 尺寸 | 一律 **mm / pt**，不用 px | 针打按物理尺寸走纸，px 会随浏览器缩放跑偏 |
| 预览 | `zoom: 0.72` 缩小显示，打印时归 1 | 预览与打印共用一套数值，不会"预览好好的、打出来偏了" |
| 纸张 | 打印前动态注入 `@page { size: 241mm 140mm }` | 常驻会污染整个应用的打印行为；多联时高度乘联数 |

收据上有**金额大写**（「合计人民币（大写）：叁佰伍拾叁元壹角叁分」）——
手写凭证的行业习惯，打印也一样，少了这一栏财务可以直接打回。

打印用的 portal 挂在 `body` 下，`@media print` 里 `#app` 整个隐藏只留它 ——
不用和 Element Plus 的 dialog / overlay 层级纠缠。

**边界要说清**：浏览器 `window.print()` 能把版面和纸张尺寸做对，但**做不到 0.1mm 级的连续纸对位**。
真正投产要用本地打印控件（如 C-Lodop）或后端直发 ESC/P 指令。这句话写在预览弹窗顶部，
不是"以后再说"，是让人当场就知道该找谁。

### 20.5 顺带修掉的全局按钮问题（第二次）

上一批修了 `.el-button--primary` 没排除 `.is-plain`；这批发现 **`.is-link` 和 `.is-text` 也没排除** ——
「查看流水」「打印收据」「票据台账」全是蓝底蓝字的纯色块。

同一个 bug 踩两次，说明修法不彻底：只排一个变体，下次加个新变体又中招。
现在的规则是 `:not(.is-plain):not(.is-link):not(.is-text)` —— 只有真正的实心按钮才上底色。

- `check` 通过 · `build` 通过 · 冒烟 **66/66**

  （241×140mm、三联、联次名、大写、收款方式、票号）/ 只开收据后仍在待开票池 /
  补开发票后移出 / 临时收费手填抬头且项目名是「摆摊费」/ 都开后 SJ 与 0264 都在 /
  大写金额六组

## 二十一、通讯录（2026-11-06 · 第 66 批）

「后台少了通讯录，希望可以看到所有同事的联系方式」—— 这个需求听起来像"员工档案加个页面"，
但**它和员工档案是两件事**，混在一起会出问题。

### 21.1 为什么不复用员工档案

| | 员工档案 | 通讯录 |
|---|---|---|
| 回答什么 | 这个人的薪资、证件、合同、紧急联系人 | 这个人在哪个部门、怎么联系 |
| 谁用 | HR | 所有人 |
| 权限 | `c.employees.view` | `c.contacts.view`（**全角色默认给**） |
| 手机号 | 脱敏，揭示要留痕 | **明文** |

如果复用档案的权限，让全员看档案就等于把 120 人的薪资表发出去；
而按岗位逐个开通讯录，结果是"想找个人还得先问 HR"。所以是**两个权限位、两套字段**。

**手机号的处理正好相反**，这点值得单独说：在档案里看手机是"查个人信息"（所以脱敏 + 留痕），
在通讯录里看手机**就是它的用途本身**（所以明文）。同一个字段，两种场景，两种规则。

### 21.2 三条硬口径

**① 只取在职，含试用，排除离职。**
给离职同事打电话是这类工具最常见的错误。现在 120 人里有 2 位离职（万军、邹坤），
列表里 118 人 = 105 在职 + 13 试用。

**② 字段白名单，数据层不给。**
不是"页面不显示"，是 `queryContacts()` 返回的行里**只有 6 个字段**
（`empId / name / position / orgId / orgName / phone / gender`）。
薪资、身份证、银行卡、紧急联系人根本不在返回里 —— 页面想显示也显示不出来。

**③ 不带座机 / 分机 / 邮箱。**
数据模型里也没有，不为了"看起来全"造字段。要加这些得先改员工表，那是另一件事。

### 21.3 部门树只列有人的节点

组织树有 21 个节点（集团 → 总部/项目 → 部门 → 班组），但员工实际只挂在 6 个组织上。
如果原样铺出来，会看到十几个「0 人」的班组，找一个部门要点开三层还全是空的。

所以 `contactTree()` 做了 prune：**`totalCount === 0` 的节点不返回**。
现在树上是 7 个节点（集团 / 总部职能中心 / 财务管理部 / 翡翠城项目部 / 客服组 /
锦绣家园项目部 / 星光天地项目部），点两下就到人。

统计卡写「在岗部门 6 个」而不是「部门 6 个」—— 一个组织架构里 21 个部门、
通讯录里只有 6 个，不写清会让人以为数据丢了。

### 21.4 交互上做的三件小事

- **搜手机后 4 位**：前台记不住完整号码，但记得尾巴。`kw.length >= 4` 时按 `endsWith` 匹配；
- **复制**：`navigator.clipboard` 失败时（http 非安全上下文）退回提示"手动选中 + 号码"，
  而不是弹一句"复制失败"就完事；
- **拨打**：`<a href="tel:...">`，在支持拨号的设备上直接呼出。PC 上多数浏览器没配处理器，
  所以它只是个语义正确的链接，不假装能打通。

头像底色按姓名散列（5 种），同一个人每次进页面颜色一样 —— 不然像换了个系统。

## 二十二、契约收口（2026-11-06 · 第 67 批）

63 / 64 / 66 三批的功能都落到了 `04-契约`：**214 路径 / 247 接口 / 269 schema / 179 条测试**。

这一章只记"为什么这么定"，细节在契约的 `description` 里。

### 22.1 临时收费的三条口径都写进了契约

| 口径 | 契约里怎么表达 |
|---|---|
| 不进收缴率 | `TempCharge.countsInCollectionRate` 恒为 `false` —— **显式字段，不是靠文档说** |
| 计入收入 | `GET /temp-charges/income` 是唯一取数口，返回里同样带 `countsInCollectionRate: false` |
| 建单 ≠ 收款 | `POST /temp-charges` 只落单据；`POST /temp-charges/{id}/pay` 才写流水 |

**为什么把"不进收缴率"做成字段而不是注释**：注释会被忽略，字段会被序列化。
前端拿到 `countsInCollectionRate: false` 就没法"顺手"把它加进分母 —— 除非显式改代码。

另外契约里没有 `/temp-charges/{id}/refund`：**已收款的单据不能作废，退款本期不做**。
这一点在 `void` 的 `responses.409` 里写明了，而不是让后端自己猜。

### 22.2 收据状态加在 `Payment` 上，不新开一张表

`receiptStatus` / `receiptNo` 直接挂在 `Payment` 上，与 `invoiceStatus` 并列。

不新开表是因为：收据与流水是**一对零或一**，开表会让每次查流水都要 join 一次，
而这两个字段只在两个地方用（待开票池、收据打印）。等以后要管"收据作废/重开"时再拆表。

`POST /payments/{payId}/tickets` 用 `types: []` 数组而不是单个 `type`：
**分两次调用会出现"收据开成功、发票失败"的半截状态**，而用户只看到一句"开票失败"。

### 22.3 通讯录的"字段白名单"在服务端

契约的 `Contact` schema 里只有 7 个属性，测试里专门盯了两件事：

```
eq(keys.join(','), 'empId,gender,name,orgId,orgName,phone,position')   // 只有这些
for (const bad of ['baseSalary','idCard','bankCard','emergencyPhone'])
  eq(bad in rows[0], false)                                            // 这些一个都没有
```

**测的是返回体本身，不是页面**。因为"页面不显示"是可以被绕过的（改个前端就能看到），
而"接口不给"绕不过去。

## 二十三、邻里运营（2026-11-06 · 第 68 批 · 后台）

> 业主端「邻里」入口的后台一侧。本批只做后台，业主端改版另开（见 `交接单-业主端小程序.md` 第十二节）。

### 23.1 先划监管边界，再谈功能

同一句「邻里」，四种能力的监管待遇完全不同：

| 能力 | 微信类目 | 资质 | 判断 |
|---|---|---|---|
| 公告 | 房地产服务-住宅物业 / 生活服务-缴费 | 营业执照 | 低 |
| 意见征询投票 | 同上 | 无 | 低 |
| 活动（公益 / 收费） | 生活服务-缴费 + 微信支付商户号 | 商户号 | 中 |
| 闲置 | 生活服务-二手交易 | 该类目资质要求为空 | 中 |
| 话题 + 跟帖 | **社交-社区/论坛** | ICP 备案或增值电信业务许可证 | 高 |

关键判断：社区/论坛类目**门槛没想象的高**（ICP 备案即可，而小程序本来就要备案），
真正贵的是**常态化内容审核** —— 邻里纠纷、指名骂物业、涉政涉黄、造谣，
每条都要有人 24 小时内处理并留证。物业没有这个编制。所以不是"做不了"，是"不划算"。

**结论**：砍掉话题广场与跟帖；闲置做成「信息条目 + 私信」，不做公开评论墙 —— 这是它能留在
「生活服务-二手交易」类目的关键。砍完之后闲置成为全站唯一 UGC 源，一个队列就够了。

### 23.2 六页范围

| 页面 | 路由 | 关键点 |
|---|---|---|
| 邻里运营（工作台） | `/n/workbench` | 四件待办（待审闲置 / 待处理举报 / 待成行活动 / 进行中投票）+ 四个率 |
| 投票管理 | `/n/votes` | 意见征询 · 参与率 · 结果分布（**不给「是否通过」**） |
| 活动管理 | `/n/activities` | 公益 / 收费 · 成团下限 · 退款分档 · 确认流团 |
| 报名名单 | `/n/activities/:id/enrolls` | 出行人 · 代报名 · 退款 · 签到 · 导出 |
| 闲置审核 | `/n/items` | 左队列右预览 · 通过 / 驳回 · 已上架下架 |
| 举报处理 | `/n/reports` | 四动作 · 处理说明必填 |

公告**不新建页面**：复用 C 域「公告通知」，只加一列「邻里同步」（已发布即同步）。
否则运营要在两处发同一条通知，阅读数还对不上。

### 23.3 投票：为什么只做意见征询

《民法典》278 条的业主共同决定要 **人数 + 专有部分面积双过半**、要公示期、要能出纸质表决票。
小程序替代不了票箱，做了反而给人"已经表决过"的错觉 —— 而那句话一旦写进结果页，就要承担法律效力。

所以：

- 结果页只有**参与率 / 票数分布 / 可信度**，`voteResult()` 不返回 `passed` / `approved`；
- 参与率按**户**算，租户不计（征询的是产权人意见）；
- **发布后题目与选项不可改**：已投出的票会指向不存在的选项，改完合计还对不上。

`scripts/check.mjs` 第九条规则静态钉住这一点：N 域不得出现 `passed` / `approved` 字段，
结果抽屉里不得出现「通过」字样。

### 23.4 活动：三种状态缺一不可

```
报名中 --截止--> 待成行 --达下限--> 已成行 --活动日--> 已结束
                     └--未达下限--> 已流团（全额原路退）
```

「待成行」是独立状态，既不是"报名中"也不是"已结束"。少了它，钱收了团没成、活动当天
业主自己发现没车来接 —— 然后在群里炸。它是唯一能触发批量退款的入口（`confirmFlow`）。

收费活动三条硬约束：**成团下限**（否则退款没依据）、**退款分档**（否则取消时凭人情拍脑袋）、
**投保开关**（`needInsurance` 为真才收集证件号，且只写"用于购买当日意外险"）。

另有一条合规提醒：以「旅游」名义收费需要《旅行社业务经营许可证》，
所以口径写成**成本分摊**（车费 / 门票 / 餐费），不写"旅游产品"。

### 23.5 闲置：为什么不做评论墙

发布资格挂 A 域认证（业主或租户都能发），链路是「提交 → 内容安全预检 → 人工队列 → 通过 / 驳回」。
四条产品约束：

1. **先审后发**，驳回必带理由 —— 业主会拿着通知来问为什么；
2. 展示只到**楼栋**，不显示门牌；
3. 手机号默认不公开，走站内私信；
4. **没有公开评论墙**，只有「想要 / 私信」。

第 4 条不是产品偏好，是类目红线：一旦有业主对业主的公开回帖，审核就会把它往
【社交-社区/论坛】靠，那是另一套资质与人力。

### 23.6 两个被截图揪出来的数字错误

**① 投票参与率 164%。** 种子里的票数是独立随机生成的，出现「310 票 / 189 户」。
分母兜不住分子，这页的数字立刻没人信。修法：初始化时按户数上限归一（超过 55% 的按比例压回，
余数补给票数最高的选项），本来就低于 55% 的不动 —— 不能把"参与率低"这个真实信号抹平。

**② 活动报名 210%。** 种子报名数超过名额（42/20）。修法：进度条封顶 100%，
超额单独给「已超员 N 人」，不把 210% 画进进度条。

两条都是"页面能开、build 能过、e2e 默认也能过"的错误，只有人眼看截图才发现 ——
所以本批每页都截了图逐张看，而不是只看断言全绿。

### 23.7 代报名单独一个权限码

「帮业主报名」和「建活动、改价格、确认流团」拆成两个码（`n.activities.enroll` / `n.activities.edit`）。
合成一个的结果只有两种：要么一线客服报不了名，要么把发布权一起放给客服。
移动端上线后这条更明显 —— 手机上只做代报名，PC 才做发布。
客服（R-CS）拿到 `enroll` 但没有 `edit`：能替业主报名、能按分档退款，不能建活动。

## 二十四、租售信息（2026-11-06 · 第 69 批 · PC 后台）

> 方案全文见 `租售信息模块.md`。本节只记「为什么这么定」和「实现时踩到的」。

### 24.1 为什么放物业 A 域，不进商业系统

判断依据不是"习惯放哪"，而是数据结构：一套租售信息其实是三层东西。

| 层 | 归属 |
|---|---|
| 房源主数据（房屋、产权、租约、住户） | 物业 A 域，唯一主键 |
| 挂牌（价格、图片、描述） | 跟着业主走 → 仍属物业 |
| 成交、佣金、结算 | 商业侧 |

一期**只做信息发布**，第三层不存在，所以不进商业系统。
分水岭是"是否参与撮合与成交"，不是"收不收钱"——将来收信息发布费，接 B 域收入科目即可。

### 24.2 四个关键设计

**① 面积 / 户型 / 朝向 / 楼层从 `houseId` 派生，不落库。**
存副本的后果很具体：房本面积一改，挂牌页就是错的，而且没人知道哪个准。
顺带好处是"虚标面积"从设计上就不可能——审核项直接少一项。

**② 审核人是该房的责任楼管，不是"审核员"。**
按 `house.stewardEmpId` 分派。他门儿清这套房多大、装修什么样，照片是不是这套房（甚至是不是网图）
一眼能看出来；客服隔着屏幕只能看热闹。超 24 小时升直属上级，按 `orgLeaders` 解析，**不写死角色名**。

**③ 不外露楼管手机号。**
访客留自己的电话，楼管回拨——方向反过来，要保护的人也跟着变：从员工变成访客。
所以 `listing_viewing` 有四条义务：用途告知、不做营销、90 天清理、可按要求删除。

**④ 后台没有「新建」。**
挂牌只能由业主在业主端发起。留了编辑入口，最后一定会变成"客服帮业主改价格"，责任就绕回来了。

## 二十五、车位换绑留痕 + 人脸核验（2026-11-10 · H1 / H2 / H4 / H5）

> 业主端批次 79–81 交付后，后台要配合的四项。需求见 `交接单-后台-车位换绑与人脸核验.md`。

### 25.1 H1：阈值必须可配，不能写死在前端

`park.plateChangeLimit`（默认 1 次/月）与 `park.plateChangeWindow`（自然月）进系统参数，
分组「车位」。`e/Config.vue` 直接读 `PARAMS`，页面一行没改。

写死的代价很具体：业主端 `PLATE_LIMIT = 1` 是常量，运营想把上限调到 2，得发一次版。
接口化（批次 82）后从 `/mp/parkings` 读，后台配的值才真正生效。

### 25.2 H2：换绑记录从「现算」改「真表」

以前 `parkingBindLogs(parking, vehicle)` 是按车位当前状态**现算**的，
提交换绑只往 `detailData.bindLogs` push 一条 —— **刷新即丢**。
业主端已经能自助换绑，后台看不见记录 = 出纠纷时无法举证。

现在：`PARK_CHANGE_LOGS` 真表 + `addParkingChangeLog` / `parkingLogsOf` / `parkMonthChangeCount` / `resetParkMonthChanges`。
字段 `logId / parkId / parkNo / fromPlate / toPlate / source(业主自助|物业代操作|物业重置) / operatorName / vendorStatus / at / reason`。

三个细节：

- **写表时同步 `vehicles`**，否则详情页读完还是老车牌 —— 真源只能有一个；
- **本月次数以「最后一次重置」为界**，重置之前的记录不计入，否则重置完数字不变；
- 重置**必须写原因**并留一条「物业重置」记录，客服兜底但不能无声改数。

页面上：记录区顶部「本月已换 N / 上限 M 次」+「重置本月次数」，每条记录带**来源**与**厂商状态**标签。

### 25.3 H4：把「已录人脸」的开关撤掉

原来业主表单里是一个 `el-switch`，勾一下就生效 —— 等于物业替业主担保，
出了事说不清是谁录的。业主端采集提交上来之后**没有任何受理入口**，永远停在「待核验」。

现在状态机：`未采集 → 待核验 → 已生效 / 已驳回`（驳回必填原因，业主端原样展示）。
新增 `/a/faces` 工作台；业主表单改为只读状态 + 「去核验」入口。

### 25.4 H5：租客并进同一个工作台

租客的人脸以前散在租户编辑里（点一下直接 `faceRegistered = true`）。
现在两段并列：`业主与家庭成员` / `租客`，同一套通过/驳回落同一张表。

关键一处：**审核通过时回写主体**——业主本人写 `owners.faceRegistered`、家庭成员写 `members`、
租客写 `tenants`。所以「租户列表里的人脸标记跟着变」是数据层写的，不是页面自己算的。

顺带把 `TenantList` 的「录入人脸」从**直接置为已授权**改成**提交一条核验**：
前台自己录、自己审看着多余，但它留下了"谁录的、录的是谁"这条轨迹。
