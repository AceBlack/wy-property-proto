## 一、任务目标（一句话）

做一套**业主端小程序高保真原型**（H5 优先、可编译到微信小程序），把「业主自助」这条链路补齐，
让「报修 → 派单/抢单 → 上门 → 增项确认 → 支付 → 评价」在演示里真正闭环。

**三个"不是"**：

1. **不是把员工端缩小**。业主关心的是"我要交多少钱、我报的单到哪一步了、这单为什么多收了 80"，
   不是工单状态机。
2. **不是纯静态稿**。关键动作（绑定、下单、支付、增项确认、评价）必须能点通并写回数据。
3. **不接真后端、不接真支付**。支付只做到"生成待支付订单 + 模拟支付成功"（已确认口径）。

## 三、三条硬口径（写死在代码里，别自己发明）

### 3.1 绑定房产：实名校验一致才成功

```
微信授权 → 拿到手机号 → 实名（姓名 + 证件号）
        → 用「手机号 + 姓名 + 证件后四位」去匹配后台已导入的业主档案
        → 命中且房屋归属一致 → 绑定成功（可多套，逐套绑）
        → 不一致 → 失败，给出"哪一项对不上、去哪里核验"
```

**为什么要三态而不是直接进首页**：业主端最常见的真实问题是"我买了房但绑不上"，
这一态如果藏起来，一线管家会被电话打爆。

### 3.2 支付：只到"待支付订单 + 模拟成功"

- 业主点"缴费/支付"→ 生成 `待支付订单`（含金额、单号、有效期）
- 点"模拟支付成功"→ 订单转已支付、账单销账 / 工单 `payStatus=已支付`
- 契约里留**假回调** `POST /mp/payments/{payId}/simulate`，并在注释里写明：
  真接入时替换为渠道回调 + 签名校验 + 幂等，业务侧只认"已支付"这个结果

### 3.3 增项确认：业主确认后合并到同一订单

师傅现场加项后，业主会在首页看到"有 1 项待确认"。确认后：

- 增项金额**合并进本单总额**（不是新开一单）
- 员工端那边才允许完工（员工端已有拦截）
- 业主端要能看到"原价 / 增项 / 合计"三段，避免"怎么就多了 80"

## 五、跨端依赖：三件必须先想清楚的事

### 5.1 两端演示**不共享内存态**（最容易白干的一件事）

员工端与业主端是两个工程、两个端口、两个窗口。所有写操作都是内存态 + 各自 localStorage，
**不要试图做"员工端点完工 → 业主端立刻看到"的实时联动**——做不到，也不该做。

正确做法：两端各自完整跑自己的链路（员工端自己模拟收款、业主端自己模拟支付），
**跨端一致性体现在契约上**（同一个接口、同一套状态机），不体现在运行时。

### 5.2 增项数据必须落到 `workOrders[].addons`

现在员工端把增项存在**它自己的 store**（`app.addOns`），mock 里 `workOrders[].addons` 是空数组。
业主端要读"待我确认的增项"，就必须让增项写回 `workOrders[].addons`（内存态即可），
否则业主端只能读到自己造的假数据。

**约定**：增项以 `workOrders[].addons[]` 为唯一形状（`{ code, name, qty, material, labor, total, at, by, confirmed, confirmedAt }`），
员工端 store 退化为"本地缓存 + 写回 mock"。

### 5.3 数据不许手改

`03-原型/src/mock` 是 `02-原型设计/seed_dataset.py` 的产物（任务 A 已完成回灌）。
需要新字段（如 `orders`、`bindings`）时：

```bash
# 改 02-原型设计/seed_dataset.py → 重生成 → 同步
python3 02-原型设计/seed_dataset.py
bash tools/sync-mock.sh          # 02/mock + repairPrices.json → 03/src/mock
bash tools/sync-mock.sh --check  # 只比对，不一致退出码 1
```

改完必须跑两端自检：`cd 03-原型 && npm run check && npm run e2e`、`cd 05-员工端APP && npm run check:data && npm run smoke`。

## 九、已知风险与坑（从员工端趟过来的，别重踩一遍）

| 坑 | 说明 |
|---|---|
| `@pc` 只读引用抢不过 uni 的 `@/` | uni 自己注册 `@/` → 本项目 src，且 alias 先于用户插件执行；必须用 transform 改写 + `noDiscovery` |
| uni 的 `tap` 是原生事件名 | 组件 `$emit('tap')` + 父级 `@tap` 会拿到事件对象，参数丢失；改用 `pick` 一类的自定义名 |
| 同一路由换 query 不重新挂载（H5） | `house?A` → `?B` 内容还是 A；用 `hashchange` 同步参数（员工端 `building/house.vue` 有实现） |
| `padding` 里混 `constant()` | Chrome 不认，整条声明失效（底栏内边距变 0） |
| 图片上传 | H5 无相机时 `uni.chooseImage` 失败要落"占位 + 缺证说明"，别报错 |
| `certified` 全是 true | 数据里没有"未实名"样本；演示第二态请用"信息不匹配"，不要去改 682 条业主数据 |
| 租金口径与员工端相反 | 楼管**不能看**租金；业主是出租方，**能看**自己房的租约金额 |
| 断言别写死金额 | 抢到/选中哪一单会变；断言"汇总 = 明细"这类不变量 |

### 11.1 与本文不一致、需要你知道的三处

1. **接口数是 16 个，不是 15 个**：§六 正文写「共 15 个接口」，但表格实际列了 16 行（含 `/mp/orders/{woId}/evaluate`）。
   按表格实现，契约里 `mp` 共 16 个接口。契约总数：路径 113 → 129，接口 126 → 142，schema 185 → 207。
2. **账单取数多了一条规则（本文没写，但不加就错）**：`bills.json` 里有 1,344 张 `houseId` 为空的账单
   （车位管理服务费，车位是独立资产、不挂房）。只按 `workOrders/bills.houseId ∈ 已绑房产` 过滤，
   李秀兰的欠费会从 ¥3,390.55 变成 ¥3,028.03，**少看 ¥362.52** —— 业主会以为自己只欠这些。
   现在口径是「已绑房产 + 本人名下不挂房的车位费」，`check:data` 有一条守卫钉住这个差额。
3. **增项确认后要产生一笔"差额支付"**：只把 `totalFee` 从 125 改成 205、`payStatus` 仍是「已支付」的话，
   那 80 块永远收不上来，账面却显示收了 205。现补了 `paidAmount`（已预付），
   `dueFee = totalFee - paidAmount` 才是该付的钱；补付页会写明"本单已预付 ¥125，本次只付差额 ¥80"。

### 11.4 v0.2 重构（2026-11-01 晚 · 4 tab + 按需认证）
