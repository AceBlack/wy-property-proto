## 一、任务目标（一句话）

做一套**业主端小程序高保真原型**（H5 优先、可编译到微信小程序），把「业主自助」这条链路补齐，
让「报修 → 派单/抢单 → 上门 → 增项确认 → 支付 → 评价」在演示里真正闭环。

**三个"不是"**：

1. **不是把员工端缩小**。业主关心的是"我要交多少钱、我报的单到哪一步了、这单为什么多收了 80"，
   不是工单状态机。
2. **不是纯静态稿**。关键动作（绑定、下单、支付、增项确认、评价）必须能点通并写回数据。
3. **不接真后端、不接真支付**。支付只做到"生成待支付订单 + 模拟支付成功"（已确认口径）。

## 三、三条硬口径（写死在代码里，别自己发明）

### 3.1 绑定房产：实名校验一致才成功

```
微信授权 → 拿到手机号 → 实名（姓名 + 证件号）
        → 用「手机号 + 姓名 + 证件后四位」去匹配后台已导入的业主档案
        → 命中且房屋归属一致 → 绑定成功（可多套，逐套绑）
        → 不一致 → 失败，给出"哪一项对不上、去哪里核验"
```

**为什么要三态而不是直接进首页**：业主端最常见的真实问题是"我买了房但绑不上"，
这一态如果藏起来，一线管家会被电话打爆。

### 3.2 支付：只到"待支付订单 + 模拟成功"

- 业主点"缴费/支付"→ 生成 `待支付订单`（含金额、单号、有效期）
- 点"模拟支付成功"→ 订单转已支付、账单销账 / 工单 `payStatus=已支付`
- 契约里留**假回调** `POST /mp/payments/{payId}/simulate`，并在注释里写明：
  真接入时替换为渠道回调 + 签名校验 + 幂等，业务侧只认"已支付"这个结果

### 3.3 增项确认：业主确认后合并到同一订单

师傅现场加项后，业主会在首页看到"有 1 项待确认"。确认后：

- 增项金额**合并进本单总额**（不是新开一单）
- 员工端那边才允许完工（员工端已有拦截）
- 业主端要能看到"原价 / 增项 / 合计"三段，避免"怎么就多了 80"

## 五、跨端依赖：三件必须先想清楚的事

### 5.1 两端演示**不共享内存态**（最容易白干的一件事）

员工端与业主端是两个工程、两个端口、两个窗口。所有写操作都是内存态 + 各自 localStorage，
**不要试图做"员工端点完工 → 业主端立刻看到"的实时联动**——做不到，也不该做。

正确做法：两端各自完整跑自己的链路（员工端自己模拟收款、业主端自己模拟支付），
**跨端一致性体现在契约上**（同一个接口、同一套状态机），不体现在运行时。

### 5.2 增项数据必须落到 `workOrders[].addons`

现在员工端把增项存在**它自己的 store**（`app.addOns`），mock 里 `workOrders[].addons` 是空数组。
业主端要读"待我确认的增项"，就必须让增项写回 `workOrders[].addons`（内存态即可），
否则业主端只能读到自己造的假数据。

**约定**：增项以 `workOrders[].addons[]` 为唯一形状（`{ code, name, qty, material, labor, total, at, by, confirmed, confirmedAt }`），
员工端 store 退化为"本地缓存 + 写回 mock"。

### 5.3 数据不许手改

`03-原型/src/mock` 是 `02-原型设计/seed_dataset.py` 的产物（任务 A 已完成回灌）。
需要新字段（如 `orders`、`bindings`）时：

```bash
# 改 02-原型设计/seed_dataset.py → 重生成 → 同步
python3 02-原型设计/seed_dataset.py
bash tools/sync-mock.sh          # 02/mock + repairPrices.json → 03/src/mock
bash tools/sync-mock.sh --check  # 只比对，不一致退出码 1
```

改完必须跑两端自检：`cd 03-原型 && npm run check && npm run e2e`、`cd 05-员工端APP && npm run check:data && npm run smoke`。

## 九、已知风险与坑（从员工端趟过来的，别重踩一遍）

| 坑 | 说明 |
|---|---|
| `@pc` 只读引用抢不过 uni 的 `@/` | uni 自己注册 `@/` → 本项目 src，且 alias 先于用户插件执行；必须用 transform 改写 + `noDiscovery` |
| uni 的 `tap` 是原生事件名 | 组件 `$emit('tap')` + 父级 `@tap` 会拿到事件对象，参数丢失；改用 `pick` 一类的自定义名 |
| 同一路由换 query 不重新挂载（H5） | `house?A` → `?B` 内容还是 A；用 `hashchange` 同步参数（员工端 `building/house.vue` 有实现） |
| `padding` 里混 `constant()` | Chrome 不认，整条声明失效（底栏内边距变 0） |
| 图片上传 | H5 无相机时 `uni.chooseImage` 失败要落"占位 + 缺证说明"，别报错 |
| `certified` 全是 true | 数据里没有"未实名"样本；演示第二态请用"信息不匹配"，不要去改 682 条业主数据 |
| 租金口径与员工端相反 | 楼管**不能看**租金；业主是出租方，**能看**自己房的租约金额 |
| 断言别写死金额 | 抢到/选中哪一单会变；断言"汇总 = 明细"这类不变量 |

### 12.3 五条口径（写死在代码里，别自己发明）

1. **公告 = 同一张表**。后台公告「已发布」即同步到邻里；草稿 / 待审核 / 已撤回都不同步。
   业主端不要再做一套阅读数，直接读公告自带的 `readCount / targetHouses`。
2. **投票只做意见征询**。结果页**不能出现「通过 / 未通过」**——它不产生《民法典》278 条的效力。
   参与率按**户**算（租户不计，征询的是产权人意见）。
3. **收费活动三条硬约束**：成团下限、退款分档、投保开关。
   出行人证件号**只在开启投保时收集**，且只写"用于购买当日意外险"；活动结束 30 天脱敏。
4. **闲置先审后发**，驳回必带理由（业主看得到那句理由）。
   展示只到**楼栋**，不显示门牌；手机号默认不公开，走站内私信。
5. **不做话题广场、不做跟帖、不做公开评论墙**。这一条是类目红线，不是产品取舍。

退款分档的计算口径在后台是一个纯函数 `refundRatioOf(activityId, atDay)`：

业主端申请退款时要先**展示**这个比例与金额，再提交——不要直接调用退款。

同一批数据、三个端，别各做一套：

| 端 | 角色 | 做什么 |
|---|---|---|
| 业主端（本工程） | 业主 / 租户 | **产生内容**（发闲置、报名、投票）+ 看结果 |
| 员工端（`05-员工端APP`） | 客服 / 楼管 / 项目经理 | **处置内容**（审闲置、处理举报）+ **代客报名** |

对业主端有四处直接影响：

1. **「审核中」就是员工端还没审。** 业主端闲置列表要能显示"审核中"这一态并给出预计时长，

2. **驳回理由要原样展示。** 员工端驳回时必须写理由（接口层强制），业主端在「我发布的」里

3. **代报名的报名记录标「前台代报」。** 业主在「我的活动」里会看到别人帮他报的名 ——

## 十六、活动字段拆分：`type` → `category` + `feeType`（2026-11-07 · 第 71 批）

> 起因：§15.4 第 1 条。补契约时发现列表上会同时出现「亲子 · 免费」和「收费 · 收费」——
> 一个字段装了两套含义。这一批拆开，**五个工程一起改，不留半套**。

### 16.1 最终字段

| 字段 | 值域 | 落库 | 说明 |
|---|---|---|---|
| `category` | 敬老 / 亲子 / 文体 / 出游 / 公益 | 是 | 创建时必选，决定页面分组与筛选 |
| `feeType` | **免费 / 收费** | 否 | 由 `fee > 0` 派生 |
| `fee` | ≥0 | 是 | 0 = 免费；> 0 = 收费，需配 `minCapacity` + `refundPolicy` |

`type` 从活动域**彻底移除**。注意别和投票的 `type`（满意度调查/意见征询）搞混 —— 那是另一个域。

### 16.2 为什么 `feeType` 用「免费 / 收费」而不是「公益 / 收费」

类别里已经有一个「公益」。两个维度同词，前端一定会出现"公益 · 公益"，运营也不知道该填哪个。
换成「免费 / 收费」之后两者正交：

- 公益义诊 → 公益 · 免费
- 公益义卖 → 公益 · 收费
- 敬老茶话会 → 敬老 · 免费
- 敬老一日游 → 敬老 · 收费

### 16.3 校验规则的变化

原来靠 `type === '收费'` 判断要不要收三项（单价 / 成团下限 / 退款档位），现在靠 `fee > 0`：

- `fee = 0` → 免费场次，`minCapacity` 与 `refundPolicy` 不校验（存 0 / 空）；
- `fee > 0` → 必须有 `minCapacity ≥ 1`、`refundPolicy` 非空，且比例随提前天数递减。

**副作用**：想办收费活动却忘填单价，会静默变成免费活动。所以前端在提交前拦一道
（`feeMode === '收费'` 但 `fee` 为空 → 提示，不发请求）。后端只按金额判，不猜意图。

1. **只换"我的状态"，不换公共列表。** 公告/投票/闲置的**列表**由客户端本地渲染，

2. **写完重拉 `/mine`**，不在本地猜差量。8 个写操作都有这一步，多一个请求换"不会算错"。
3. **另开 `/mp/neighbor/*` 前缀**，不复用 `/neighbor/*`：后者是运营侧（`n.*` 权限码 + 数据范围），
   混用等于把"客服能看的内容"开放给业主。

1. **「我投的」读的是本地**：`pages/neighbor/my.vue` 直接 `Object.keys(app.votes)`，

## 三十、2026-11-13：费用体系配套（水电改账单缴费 · 取消预存账户）

> 一句话：**预存账户全线下线**，水电从"先存钱、后扣费"改成**抄表推单 → 待缴账单 → 缴费**；
> 端上 2 个页面删除、3 个页面改造、1 个入口拿掉。
> 后台侧（批 1~3）已完成，本文是端上要跟着改的部分。
> 自检：后台 `check` 通过 · `build` 通过 · 冒烟 77/77 · `meter-billing.mjs` **31/31**

### 30.1 为什么改（先说结论，再动手）

客户的原话是「预存的钱算公司收入不合理」。这句话背后是三笔账混在一起：

| 混在一起的三笔 | 实际是什么 | 现在怎么记 |
|---|---|---|
| 业主交的钱先进"预存余额" | **预收款 = 负债**，不是收入 | 取消。交多少记多少，钱和账期一一对应 |
| 水费电费按"充值买量"收 | 计量收费：**用量 × 单价 = 应收** | 抄表出账 → 账单 → 缴费 |
| 余额抵扣物业费 | 一笔钱抵两笔应收，账龄就乱了 | 取消。物业费按账期收，水电按账单收 |

所以端上要做的不是"换个文案"，而是**把"余额"这个概念从业主视野里删掉**。

### 30.2 三类项目模式，端上要分开显示（最容易做错的一条）

后台每个项目的水电是独立配置的（`communityUtility`），端上不能统一按"待缴"处理：

| 模式 | 含义 | 端上应该显示什么 | 能点支付吗 |
|---|---|---|---|
| `meter` 抄表出账 | 物业抄表 → 出账单 → 业主缴 | 本期用量、单价、应缴金额、抄表日、账单号 | **能** |
| `card` 插卡买量 | 先到物业买量，再插表；系统不记余额 | 「插卡表 · 到物业服务中心买量」，**不显示余额、不显示待缴** | 不能 |
| `none` 业主自缴 | 国网 / 水司直接收 | 「由国家电网/自来水公司直接收取」，只留用量参考 | 不能 |

现有三个项目的配置（**别写死，从接口取**）：

- P01 翡翠城：电 `meter` / 水 `meter`
- P02 锦绣家园：电 `none` / 水 `card`
- P03 星光天地：电 `card` / 水 `meter`

把 `card` 当成"待缴"，业主会找不到缴费入口；给 `none` 加支付按钮，等于代收国网的钱。
