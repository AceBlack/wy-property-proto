# 方案 · 移动抄表（员工端）

> 一句话：**让师傅拿手机在楼道里把读数录进去**，而不是回办公室对着 PC 抄。
> 端上只做到「抄完落库、异常标出来」，推单出账与复核准在后台 —— 别把财务动作搬到手机上。

- 提出：2026-11-14（接 §30.7 的 backlog）
- 状态：**规划，未开工**
- 前置结论：**契约完全没有抄表**（无权限位、无 schema、无读接口），这是 P0 阻塞项

## 一、现状盘点

### 1.1 后台已经有了（不用重做）

| 能力 | 位置 | 说明 |
|---|---|---|
| 抄表录入 | `/b/meters` → 抄表录入 | 1218 条记录，状态：待录入 165 / 待复核 102 / 已计费 951 |
| 抄表推单 | `/b/meters` → 抄表推单 | 按读数生成账单，写应收矩阵 |
| 校验规则 | `saveReading()` | 见 §1.3，**必须复用** |
| 公摊分摊 | 同页 | 端上不涉及 |

数据形状（`meterReadings`，1218 条）：

```
readingId, meterId, meterNo, type(水表/电表), unit, period, communityId,
houseId, houseName, ownerName, lastReading, currentReading, usage,
readDate, reader, status(待录入/待复核/已计费), abnormal, billId
```

### 1.2 端上和契约都没有

| | 状态 |
|---|---|
| 05 员工端 | `pages.json` 34 个页面里**没有抄表**，tabBar 已满 5 个（工作台/任务/工单/消息/我的） |
| 04 契约 | 只有 `/meter-bills`（推单）与 `/meter-bills/preview`，**没有 meter-readings**；权限码表里 **0 个 meter 相关** |
| 06 业主端 | 不涉及（业主只看自己的用量） |

### 1.3 后台的三条校验（照抄，不要另写）

```js
if (cur < lastReading)  throw '本期读数不得小于上期读数（' + lastReading + '）'
if (cur > METER_CAP[type]) throw '本期读数超出' + type + '量程（上限 ' + cap + '），请核对'
usage = cur - lastReading
abnormal = usage > (type === '电表' ? 330 : 24)
```

- **上期读数**是硬约束，不是提示；
- **量程**按表类型（`METER_CAP`）；
- **异常**只标记不拦截（异常单进"待复核"，由后台判断）。

> 这三条写在 `03/src/utils/api.js` 的 `saveReading()` 里。端上**一条都不重写** ——
> 重写的后果是"手机说能过、PC 拒了"，或者反过来。

## 二、范围

### 做

1. **待抄清单**：按楼栋分组，显示房号 / 表号 / 表类型 / 上期读数 / 是否已抄
2. **逐户录入**：点行弹出录入面板，实时算用量、超阈值即时提示
3. **提交**：走接口落库，状态转"待复核"
4. **进度感**：本月还剩多少户没抄（工作台卡片）
5. **离线可用**：楼道里没信号是常态，复用巡检已有的本地队列

### 不做（明确留在后台）

| 不做 | 为什么 |
|---|---|
| 抄表推单 / 生成账单 | 财务动作，牵动应收矩阵与账期；后台一次批量处理更稳 |
| 读数复核 | 复核的价值在于"换一个人看"，自己抄自己核等于没核 |
| 修改已计费的读数 | 要反结/退款，属于后台的作废重开流程 |
| 公摊分摊 | 纯后台计算 |
| 批量粘贴录入 | 读数必须逐个确认（见 §5 决策 3） |

## 三、入口与页面

### 3.1 入口：任务页 + 工作台卡片（不加第 6 个 tab）

tabBar 已经 5 个，再加就是"每个都不好用"。抄表在业务上属于**周期性例行工作**，
和巡检同类，放「任务」页最自然。

| 位置 | 形态 |
|---|---|
| 任务页 | 顶部加一个「抄表」分段（与巡检 / 保养 / 整改并列），带"待抄 N 户" |
| 工作台 | 一张卡片：`本月待抄 165 户 · 已抄 0``，点进清单 |

工作台那张卡是**压力源**：不点进去也知道还剩多少。

### 3.2 页面：清单 + 弹层，不开新页

```
pages/meter/list          待抄清单（按楼栋分组）
  └─ 点行 → Sheet 录入面板（不跳页）
```

**为什么用弹层而不是独立页面**：现场是"走到门口、低头录一个、抬头去下一户"。
独立页每次都要进出导航；弹层录完即收，配合"下一户"按钮可以连着走。

### 3.3 清单长什么样

```
1 栋                                    已抄 3 / 待抄 12
  0101  水表 S90405   上期 910     [录入]
  0101  电表 E90406   上期 3210    [录入]
  0102  水表 S90407   上期 875     已抄 882（用量 7）
  ...
```

- **一行一块表**（不是一行一户）：一户两个表，混在一起会漏抄；
- **上期读数放最右且加粗**：现场最容易犯的错是"把上期当本期填"；
- 已抄的行灰掉但保留（师傅需要回头核对）。

### 3.4 录入面板

```
┌─────────────────────────────┐
│ 1栋 0101 · 水表 S90405       │
│ 上期读数  910                │
│                             │
│ 本期读数  [ 输入 ]  ← 大号数字键盘
│ 用量      7 吨（自动算）      │
│                             │
│ ⚠ 用量 35 吨，超过 24 吨阈值  │
│   请确认读数无误              │
│                             │
│ [ 确认 ]  [ 下一户 → ]       │
└─────────────────────────────┘
```

- 输入框 `type="digit"`（调数字键盘，不弹全键盘）；
- 用量**实时算**，不用等提交；
- 异常**黄条提示但不拦提交** —— 拦了师傅会改数字凑合规，那更糟；
- "下一户"自动跳到清单里的下一条待抄。

## 四、要补的契约（P0）

### 4.1 权限位（新增 2 条）

| 码 | 名称 | 给谁 |
|---|---|---|
| `b.meters.view` | 查看抄表任务 | 楼栋管家、工程维修、项目经理 |
| `b.meters.read` | 录入抄表读数 | 楼栋管家、工程维修 |

理由：抄表是**现场动作**，售后/客服/财务都不该有。

### 4.2 接口（新增 3 条）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/mobile/meters` | 待抄清单，`?status=待录入&period=2026-11&buildingId=`，按登录人的责任楼栋收敛 |
| `POST` | `/mobile/meters/{readingId}/reading` | 录入 `{ currentReading }`，返回 `{ usage, abnormal, status }` |
| `GET` | `/mobile/meters/summary` | `{ pending, done, abnormal, period }`，工作台卡片用 |

**为什么挂在 `/mobile/*` 而不是复用 PC 的路径**：PC 那边抄表是"全项目随便抄"（后台管理员），
端上必须按责任楼栋收敛 —— 两套数据范围，两个入口更清楚。

### 4.3 种子数据

直接复用 `03/src/mock/meterReadings.json`（1218 条），增量脚本投影到契约，
**不重跑 `gen-fixtures.mjs`**（见 §31.2 的警告）。

注意：`待录入 165` 分布在各项目，要确认 P01 有足够样例（否则演示时清单是空的）。

## 五、五个设计决策

### 决策 1：校验在服务端，端上只做"预提示"

端上可以实时算用量、提前警告"超阈值"，但**是否放行由服务端决定**。
理由：规则会变（量程、阈值），改一次就要发版不现实；而且端上代码可被绕过。

### 决策 2：异常不拦提交

用量异常（电 > 330 / 水 > 24）只标记 + 提示，允许提交。
理由：真实异常是存在的（漏水、抄错、换表）。**拦住提交的后果是师傅改数字凑合规** ——
数字好看了，问题被埋了。让它进"待复核"，由后台判断，这是现有设计。

### 决策 3：不做批量录入

不做"粘贴一串读数一次提交"。
理由：读数错行的代价是**账单错了要退款**，比手动多点几下贵得多。
效率问题用"下一户"连录解决，不用批量。

### 决策 4：和三期分开 —— 先解决"能录"，再解决"好录"

P1 只要求"抄完能落库"。P2 才做工作台卡片、分组、连续录入、离线。
理由：抄表最痛的是**根本没做过**（现在师傅只能回办公室），不是"少一个进度条"。

### 决策 5：离线复用巡检的队列

巡检已经有完整的"断网 → 本地暂存 → 回网自动同步"（smoke 的第 11 节验过）。
抄表直接复用那套，不要另写一个。
理由：楼道信号差是共性问题，同一套队列才能保证"同步顺序、失败重试、状态提示"一致。

## 六、三期计划

### P1 · 最小可用（能抄完）

| 项 | 内容 |
|---|---|
| 契约 | 2 个权限位 + 3 条接口 + meterReadings 种子 |
| 05 | `pages/meter/list` 清单 + 录入弹层 + `api/meter.js` |
| 入口 | 任务页加「抄表」分段（工作台卡片放 P2） |
| 验收 | 莫瑞登录 → 待抄清单有数据 → 录一户 → 清单变"已抄" → PC 抄表页能看到这条读数且状态是「待复核」 |

**P1 的验收必须是"PC 能看到"**，不是"手机上说成功了" —— 这是之前几轮反复踩的坑。

### P2 · 好用（抄得快）

| 项 | 内容 |
|---|---|
| 工作台卡片 | 本月待抄 / 已抄 / 异常 |
| 分组 | 按楼栋 → 单元折叠，默认展开"当前楼栋" |
| 连续录入 | 「下一户」跳下一条待抄 |
| 离线 | 复用巡检队列 |
| 校验提示 | 上期读数高亮、用量实时算、超阈值黄条 |

### P3 · 闭环（抄完能出账）

| 项 | 内容 |
|---|---|
| 复核回写 | PC 复核后状态从「待复核」→「已复核」，端上清单同步 |
| 推单联动 | 推单后该户读数变「已计费」，清单里隐藏 |
| 照片存证 | 表盘拍照（可选，涉及文件存储） |

P3 依赖后台的复核与推单接口暴露到契约，属于跨端协商，单独排。

## 七、风险

| 风险 | 影响 | 对策 |
|---|---|---|
| **契约零基础** | P1 无法开工 | 先做 §4 的三条接口，这是唯一的前置 |
| 165 户 × 2 表 ≈ 330 次录入 | 师傅嫌慢，宁可用纸 | P2 的「下一户」+ 分组折叠必须有；P1 先证明能落库 |
| 上期读数填错 | 用量算错 → 账单错 | 上期读数加粗置顶；录入面板不允许改上期 |
| 楼道无信号 | 提交失败、白抄 | 离线队列（复用巡检）要在 P2 到位，P1 可先只支持在线 |
| 与财务时序冲突 | 抄完但没推单，业主来问用量 | 端上只显示"已抄/待复核"，**不显示金额** —— 金额是账单出来才有的事 |
